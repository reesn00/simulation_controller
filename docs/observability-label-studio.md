# Label Studio 集成（用户视角）

> 你好，这份文档面向**用这套系统的人**，不面向维护代码的人。
> 技术细节见 [`设计方案/label-studio-integration.md`](设计方案/label-studio-integration.md)
> 与 [`contracts/C4-scorecard.md`](contracts/C4-scorecard.md)。
>
> **要改标注页配置的人看 [`label-studio-playbook.md`](label-studio-playbook.md)** ——
> 尤其注意：服务端 `validate/` 报绿**不代表页面能渲染**，只有打开标注页才知道。

## 1. 这是什么

你写的模拟任务跑完之后，除了产出训练用的 4 视图数据，还会把**同一条轨迹
连同一张"评分卡"一起推到本机的 Label Studio**（LS）。

LS 是这条链的**终点**：你在那里逐条核对、给出最终判定。**判定结果不回流到
本项目** —— 本项目不会因为你的标注而改变任何行为，也不维护"哪些已经标过了"
的状态。要查标注结果，去 LS 里查。

## 2. 为什么要推评分卡

自动检查能算出很多东西，但它**不告诉你这个数字有多可信**。

举个真实例子：一条轨迹的"训练价值分"是 0.58，拆开是七个分量的加权和。
其中权重最大的一项（占四分之一）的计算代码里自己写着注释：

> health 来自 router.health_scores，runner 没把它落盘。这里按 message 数和
> 总 toolcall 数做粗估

也就是说，0.58 里有四分之一是**猜的**。如果只把 0.58 推给你，你会以为那是
实测值。评分卡把这一层摊开：

- 每个维度标 `source`：`measured`（实测）/ `partly_estimated`（部分估算）/
  `estimated`（整体推断）/ `missing`（数据缺失，**不可评分**）
- 估算过的分量列出来，并写清为什么是估算的
- **数据缺失时给"不可用"，绝不给 0** —— 0 是一个很具体的数，"没测过"不是 0

## 3. 怎么用

### 3.1 一条命令（推荐）

```powershell
scripts\label_studio.bat            # init-project → status → upload 全跑
scripts\label_studio.bat dry-run    # 同上，但只打印计划不真推
scripts\label_studio.bat status     # 只做连通性 + 配置自检
scripts\label_studio.bat upload --task-id T007   # 过滤条件原样透传
```

脚本自己处理 key、Python 启动方式和控制台编码（`chcp 65001`，否则中文报错
全是 `????`），不用记 uv 命令。完整用法跑 `scripts\label_studio.bat help`。

key 两种给法（脚本按 env → 文件顺序取，都支持）：

```powershell
$env:LABEL_STUDIO_API_KEY = "<你的 key>"     # 换窗口就失效
# 或写进 config\label_studio_api_key.txt    # 已 gitignored, 一次配好长期有效
```

**不要**把 key 当命令行参数传 —— 会留在 shell 历史和进程列表里。

### 3.2 准备

1. 本机跑起 Label Studio（默认 `http://127.0.0.1:8099`）
2. 在 `config/config.yaml` 里确认 `label_studio:` 段的 `base_url` 是 8099
3. 按 3.1 配好 key

> **端口不是 8088。** 8088 上跑的是 QwenPaw 执行后端。指错不报"连不上"，
> 而报**认证失败** —— 会把人引去反复检查一个完全正确的 key。

### 3.3 底层三条命令

```powershell
# 1. 建项目（幂等，重复跑不会建出第二个）
uv run python -m label_studio init-project

# 2. 自检：LS 通不通、配置全不全、凭据在不在（不打印凭据内容）
uv run python -m label_studio status

# 3. 先看看会推什么，不真推
uv run python -m label_studio upload --dry-run

# 4. 真推
uv run python -m label_studio upload
```

`upload` 的常用参数：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只打印计划（含每条的评分卡摘要），不推 |
| `--task-id T007` | 只推某一个 task（调试） |
| `--complexity-tier hard` | 只推某个难度档 |
| `--min-score 0.5` | 只推训练价值分 ≥ 0.5 的 |
| `--no-scorecard` | 只推轨迹不带评分卡（排障用） |
| `--force` | 样本数超过 `dry_run_skip_threshold` 时强制推 |

### 3.4 标注界面

一个 task 的界面是**平铺的分区**，从上到下依次是（`<Tabs>` 在本机 LS 1.23 没注册，
所以用分隔标题而不是页签）：

| 分区 | 内容 | 可否修改 |
|---|---|---|
| **低分标记** | 被 gdr 拒收过的样本，在这里写明理由 | 可改 |
| **评分卡** | 自动评分与依据。**结论先行**：第一行是建议判定与置信度，下面按 L0–L5 逐维度展开，每条依据单列一行。`estimated` / `missing` 的维度有标记 | 可改 |
| **风险提示** | 机器已经查过什么（预标注，会自动填一条） | 可改 |
| **指令核对** | 逐条列出每条指令的自动判定（PASS/FAIL + 原因），每条一行。**整体认不认同**必选；选了「有哪几条不认同」要在下面点名 | 必答 |
| **轨迹** | 结构化的消息与工具调用（C3 messages 视图） | 可改 |
| **ChatML** | 渲染成 Qwen3 格式的纯文本，训练框架实际吃的就是这个 | 可改 |
| **元数据** | 审计用的全量 metadata（C3 meta.json） | 可改 |

最下面四个控件：

- **展示内容核对**：`原样未改` / `已修正` / `内容不可用` —— 必选。告诉下游该用
  机器原文还是你改过的版本
- **最终判定**：`通过` / `需修改` / `拒绝` —— 留空提交不了
- **失败模式**：多选（`推理错误` / `工具调用错误` / `格式错误` / `幻觉` / `违规` /
  `回复不完整` / `其他`）
- **修订意见**：选填（**最终判定选了「需修改」时必填**）

> **页面上看到的是中文，存进标注的是英文键。** 每个选项的 `value`（机器键，如
> `accept` / `some_disagree`）走 `html=` 单独指定了显示文本，两者是分开的——
> 2026-09-30 改的，之前页面上直接显示 `accept[2]` 这种机器键加角标。
> 写脚本读导出时按**英文键**匹配，见
> [`label-studio-annotation-export.md`](label-studio-annotation-export.md) §4。
>
> ⚠️ 反过来，**别用 `alias=` 改显示**——实测它会把 LS 认的选项标识从 `value`
> 换成 `alias`，提交上去的就是中文，等于静默改掉契约键。

**`最终判定` 没有预填值，这是故意的。** 系统不会替你判"这条该收还是该扔"。

**「指令核对」是整体判定，不是逐条打勾——这是被逼的，不是偷懒。** 原设计是让
每条指令旁边各有一组「认同 / 不认同」单选，这样下游能直接知道哪几条判错了。
**实测在 Label Studio 1.23 上做不到**：不管写 `perItem` 还是 `perRegion`，都只出
一组单选，提交进去也没有逐条结果，只有一句无归属的 `agree`。查出来的根因是
`perRegion` 的语义其实是"当前选中的那个条目适用此控件"——前提是那 6 条能各自被
选中，而它们只是一段文本。（`<Chat>` 的导入消息不可选，`<List>` 在本机不渲染，
三轮探针的完整记录见 [todolist.md](todolist.md) 已完成的 P0 第 2 项。）

所以现在是：

- **清单照旧逐条列出**，每条一行，读起来跟以前一样清楚
- **判定收成三选一**：`每一条都认同` / `有哪几条不认同` / `自动判定整体不可信`
- 选了第二条，就在下面的框里点名，格式：`criterion_id: 理由`，例如
  `media.playable: 实际给了可播放链接`

代价要说清楚：**点名是自由文本，机器没法按 criterion_id 自动聚合。** 所以
"哪些判据写错了"这个问题，得人工读这些备注汇总，而不是跑个脚本。

**评分卡是给人读的，不是 JSON 转储。** 它曾经被压成 `json.dumps(indent=2)`
直接塞进文本框——实测 5679 个字符，打开时滚动位置停在 evidence 数组中段，
第一眼看到的是半行 `should_revise_task": false,`，而最该先看的建议判定在
几百行之上。现在渲染成「结论先行 + 维度分行 + 依据逐条」。

看评分卡时记三条：

- **`—` 不是 0 分，是"没测过"。** `source=missing` 的维度会写明不可用原因。
  看到 `—` 别当成"这项没扣分"。
- **布尔值印成「是 / 否」。** 红线维的 `否` 是"**没有**违规"（好），与覆盖率维的
  `0`（全灭）含义相反。
- **超长字段截断成 `…`。** 完整结构化内容在 LS 端的 `scorecard` 结构化字段里，
  展示块只是它的可读投影，不复述全文。

> 导出标注给下游用时怎么读这些字段，见
> [`label-studio-annotation-export.md`](label-studio-annotation-export.md)。

### 3.5 展示块可以改，改了会存进标注

上面标「可改」的几块**不是只读的**——它们是审查工作区，核对到错处直接改，
提交后你这份**修正稿**会存进标注结果。

这件事有两个后果，都要知道：

**一、标注里的数据是你的修正稿，不是训练稿。** 从 LS 导出的 `messages_view` /
`qf_text_view` / `metadata_view` 是**你改过之后的内容**。要拿训练制品，永远读
`output/refine_data/` 下的 C3 文件，不要拿标注里的副本顶替——那是你改的版本。
这跟本文件 §6 讲的是同一件事的两个方向：那里是我们不改你的样本让你来判断，
这里是标注结果不假装是原始数据。

好消息是导出时**两者是分开的两列**：`*_text` 列是机器原值，`*_view` 列是你提交
的值。所以下游不必只信「展示内容核对」那个开关，两列直接比对也是独立证据。
（这只在 `JSON_MIN` 导出下成立；`JSON` 导出里两者混在同一个 `result` 列表中。）

**二、写错了可以直接改，不用再点一次 Add。** 2026-09-30 起这几块都写成
`editable="true"`（此前是 `false`），提交之后**还能就地编辑**。以前没有第二个
入口，想修一个错字只能再点一次 Add，于是多存一条一模一样的 submission
（2026-09-29 实测「风险提示」因此存了两条）。

> `editable` 只管"加完之后能不能再改"，**不管能不能提交**。能不能提交取决于
> **Add 按钮**，而 Add 按钮在 `rows > 1` 时默认可见——这几块 rows 全部大于 1。
> 所以 `editable="false"` 时期它们同样可提交、修改同样会进标注，**改这个属性
> 从来没让它们变安全**。`rows > 1` 现在是被刻意保留的约束，别为省版面调成 1。

**机器判断和人工作出判断是分开的两件事。** 对机器的评分、风险提示、低分标记有
异议时，走「指令核对」的**不认同**和「修订意见」，**不要直接改写那几个块**——
改掉了就再也读不出"机器当初判的是什么"。（能改 ≠ 该改。）

> 顺带说一句：这些块**结构上也可以做成只读**，办法是换成 `<Text>` 标签（非控件，
> LS 挂不上 submission），配 `<Style>.htx-text { white-space: pre-wrap; }</Style>`
> 保住缩进——2026-09-30 在探针上实测过，两半都成立。**目前不做**：展示块可改是
> 设计决定，不是被工具能力卡住的。唯一的例外是「风险提示」换不了，它是预标注的
> 唯一落点。

## 4. 为什么"最终判定"不自动填

设计文档里原来有过一条规则：训练价值分 ≥ 0.7 就自动 accept，< 0.4 就自动 reject。
后来删掉了，因为 0.40 正好是"难度 = hard"的阈值 —— 也就是说，**自动 reject
掉的恰恰是最需要人看的样本**。而 easy 样本（0.7 以上）反被人自动放过，最不需要
人看。规则和自己的目标正好反了。

所以现在系统只做一件事：**提示风险**。下面按生成顺序列出全部提示（`label_studio/scorecard.py::build_risk_hints`）：

| 触发条件 | 提示原文 |
|---|---|
| 样本被 gdr 拒收（低分样本） | 「低分样本（精修质量评分未达标, gdr 已拒收）｜…」——**永远排第一条**，见 §5.2 |
| 有指令项判为 fail | 「指令未完全达成，请核对: c2, c4」（列的是 criterion_id） |
| 有指令项判为 inconclusive / error | 「指令判定待定，请核对: c3」——同样是"没过"，单独提示避免语义待定项在界面上隐身 |
| 整体验证未通过 | 「该样本验证未通过（已记 0 分）｜归因 xxx：…」 |
| 触发红线 | 「红线违规 2 项，必须复核」 |
| 有高权重的估算分量 | 「该分量为估算值，非实测: health（合计权重 0.25）」 |
| 什么都没命中 | 「自动检查未见异常，仍需人工确认」 |

> 注意第 2 行的原文是 `请核对: c2, c4` 这样**列 criterion_id**，不是固定某个
> 编号。老版本文档在这里写的是「请核对 C4」，那是笔误，已改。

## 5. 自动推送

`orchestration` 跑完一个 task、etl 写完 C3 之后，会**自动**推一条到 LS。

三条保证：

1. **推不推得动都不影响 task 的结果**。task 的终态照常落库，LS 挂了只是日志里一句告警
2. **不会拖慢流水线**。推送有独立超时（默认 **30 秒**），LS 卡死就放弃
3. **默认关闭**。要开得在配置里显式写 `label_studio.hook.enabled: true`

自动推送用 `hook.enabled` 这个开关，命令行 `upload` 用 `upload.enabled`，
两个互不串。配了其中一个不会让另一个跟着开。

### 5.1 超时 / 进程被杀不会丢样本

一次推送要串完 PAT 刷新 → 建连 → 查项目 → 同步标注配置 → 建 task → 写预标注，
所以超时给的是 30 秒而不是 5 秒。

万一还是超时了、或者批次结束时进程被回收，**那条样本不会丢**：`push_single_c3`
是**先拿到 LS task id 再写台账**，所以「台账里没有」严格等价于「LS 上没建成」。
批次跑完之后补一次全量对账，缺的那些会被补上：

```powershell
.\scripts\label_studio.bat upload      # init-project → status → upload
```

这是幂等的 —— 已经推过的 session 靠台账跳过。**别删台账文件**，删了等于每次
upload 都推一份重复样本（LS 1.23 没有任何原生去重）。

### 5.2 低分样本也会推上来（2026-09-29）

gdr 判 `judge_discard`（质量评分没过的 session）**同样会推**。这类样本结构
合格、只是评分低，按项目的「数据保留原则」属于有用素材，不是废数据。

标注界面最上方有一个**「低分标记」**区块，写明它为什么被拒收。**看到这个
标记时请重点复核「精修质量」维度** —— 判别是"gdr 拒得对"还是"gdr 判错了"。
其余维度分数低不代表样本本身不可用。

没有这个标记只有两种可能：样本本来就没被拒收，或者它来自 `scoring_reject`
（那一支 gdr 刻意不写 C2，所以走不到推送）。

## 6. 有一类样本会被**拒绝推送**

Agent 的工具调用参数是**模型自己写的自由文本**，理论上可能把用户传进去的
凭据（`Bearer xxx`、`sk-xxx`、私钥块等）原样写进轨迹。协议上我们不主动存
Cookie / Authorization，但**挡不住 Agent 自己往里写**。

所以推送前会扫一遍，命中就**整条拒推**，并在输出里告诉你哪条、哪个视图、
第几个模式命中。

**为什么不自动脱敏后照推？** 因为那样你在 LS 里看到的样本就与训练时用的样本
不一致了 —— 你标的是"改过的东西"，评出来的结论没法用。宁可少一条，让你决定
怎么处理。

如果 `upload` 的输出里有 `rejected` 字段，去看一眼对应的 C3 是怎么生成的。

## 7. 常见问题

**Q：`status` 说"未找到凭据"**
设 `LABEL_STUDIO_API_KEY` 环境变量，或在配置里写 `label_studio.api_key_path`
指向一个存了 key 的文件。两者都配时 `api_key_path` 优先。

**Q：`upload` 说"未找到 LS 项目"**
先跑一次 `init-project`。

**Q：同一条轨迹推了两次，LS 里出现两条？**
本项目会跳过。判重靠本地台账 `output/label_studio/push_index__<project_id>.jsonl`
（`session_id → LS task id` 映射）。

> 早先的方案写的是"靠 LS 原生 `inner_id` 去重"，**这是错的** —— 2026-09-29 对
> LS 1.23.0 实测：`Task.inner_id` 是整数字段（发字符串直接 400），批量 import
> **静默丢弃**，整数 inner_id 重复导入照样每次新建一条（42 推三次 → id 7/8/9）。
> 所以台账不是"多一份状态"，是唯一挡板。

台账丢了或想重推：`scripts\label_studio.bat purge --confirm`（**会连标注一起
删**）后重新 `upload`，或者直接删掉那个 jsonl —— 删掉只会导致重推重复。

**Q：`upload` 报 `data['messages']=...` 400 / `data['qf_text']=...` 400**
多半是 LS 项目里的 `label_config` 与本地 XML 不一致。LS 端存的是**建项目那一刻**
的 XML，而校验接口查的是你递过去的文本，两者不同步时"`init-project` 报绿、
upload 却 400"。

这类 400 的根因是 LS 的文本标签只吃字符串，喂 dict / list 会被拒；所以
`task_exporter` 给每个展示块都准备了字符串孪生字段（`messages_text` /
`qf_text` / `metadata_text` / `criteria_text` / `scorecard_text`）。
**如果你看到报的是 `data['criteria']=...`**，那是老版本的事了——`criteria` 原来
是列表，2026-09-30 已改成换行分隔的 `criteria_text` 字符串。

正常路径下 `init-project` 和 `upload` 都会把本地 XML 同步进项目
（`PATCH /api/projects/{id}`），所以直接重跑 `scripts\label_studio.bat` 即可。
若项目在 LS 界面里被人手改过导致同步失败（脚本会打 warning），删掉项目重建：
`purge --confirm` 然后 `init`。

**Q：某条轨迹的评分卡大部分是"不可用"？**
说明这条数据缺前置产物（比如 simulate 端没跑验证，或验证结果没注入 C3）。
系统不会拿 0 糊弄你 —— 但也别把这条当"没问题"看，它就是没测过。

**Q：能把标注结果导回本项目吗？**
