### 先建闸门而不是 writer

三查里**实体核查是「100% 覆盖」的那部分，且不调 LLM**，能完全离线验证；
writer 每步都要调 LLM，在闸门缺席时生成的 rationale **没人能判**。
先有判据再有生成——顺序反了的话，第一步产出的就是无法评估的批次。

### 两处设计决定（都可能判反，所以各有测试钉住）

1. **不用中文分词。** 中文没有词边界，切词工具换一版就换一套结果，
   而闸门要跨批次可比（同 `renderer.VERBAL_TAILS` 的契约）。实体只抽
   **URL 与成对引号**两类高置信形态；单字实体不抽（「有」「的」几乎不可能
   出现在观察里，判它「不在观察里」是纯假阳性）。
2. **任务给的实体是豁免域。** rationale 提到片名「功夫」而观察里没有它，
   **不是幻觉**——片名来自任务，不是模型看来的。把任务给的词当
   「模型引入的实体」去核，会把**每一条**提到片名的 rationale 都判成幻觉。

### 最重要的一条：观察不充分时**不判幻觉**

rubric D-9 边界规则：「观察被截断时，落在截断外的实体**不得判成幻觉**——
判『不可判定』」。这是 §5.5 那条最贵教训的落点（iqiyi 播放页
`video=1` 被判「否」，模型把**采集失败**讲成了通顺的错结论）。

三处守这条：

- 本步及前置步**都不完整** → 不判幻觉，全部记不可判定；
- **一份完整即可定案**——被裁的那份不能把结论拖成不可判定；
- 后续步的**不完整**观察里出现过该实体 → 它当时**可能**就在而只是没采到
  （懒加载/渲染时序），不判幻觉。

### ⚠️ 第四次「变异测试翻车」，且这次是**假变异**

去掉「任务给的片名是豁免域」那条守卫后，测试**全绿**。查下来是两层：

1. **fixture 自己含片名**：默认夹具的 `page_title` 就是「功夫 - 腾讯视频」，

改成按行号精确变异后才看出真相：那条测试确实需要先把片名从夹具里拿掉。

## 2026-10-10 增量四：`writer.py` 落地 + 共享解析层修一个真 bug

**门禁 1133 → 1183 passed。** 35 条新测试 + 6 条变异测试（全部被抓住）。

### 那个 403 是**大小写**，而 403 与 503 是两种不同的失败

```
deepseek-V4.1-Flash   →  http:403   ← 名字未注册（大小写不符）
DeepSeek-V4.1-Flash   →  http:503   ← 已注册，但服务过载
deepseek-v4.1-flash   →  OK
```

上一版把两者混成「后端有问题」，于是得出了「writer 暂不建」。
**403 = 精确匹配失败，503 = 匹配成功但过载**，处置完全不同：
前者改一个字就好，后者只能等。清单里同时躺着
`DeepSeek-V4.1-Flash` 与 `deepseek-v4.1-flash` 两个大小写不同的条目，
而报错 403 的那个**一个字符都没匹配上**。

当前环境是 `MiniMax-M3.1-Flash-Preview`（实测可用）。**不猜模型名**
这条纪律没变——变的是「配置有问题」不等于「不许动代码」。

### ⚠️ 真 bug：字符串值里写**未转义的 ASCII 双引号**（第三种漂移）

`deepseek-v4.1-flash` 在同一提示词下**时好时坏**（4 次坏 2 次），
坏的时候返的是：

```json
{"thinking": "标题只是笼统的"腾讯视频"，正文只有导航。", "conclusion": "无法确认"}
```

大括号是**配平的**——`_balanced` 取出来那一段**看起来完全正常**，
只有 `json.loads` 知道它坏了（`Expecting ',' delimiter: line 1 column 103`）。

**为什么这条很凶**：坏掉的症状是「解析失败」，而
`llm_perceptor._ask_json` 走的是**同一条路**——于是感知层把
**解析故障**记成「模型判不出来」，整道题 fail-closed 成 `None`。
这正是 §5.5 那条教训在**解析层**的复刻。

**修法**：报错位置驱动的转义修复（`extract_json_reporting`）。
`json.loads` 精确指出错误在第几个字符，把**那一个**引号转义后重试。

⚠️ **不用「引号后面跟的是不是逗号」那种局部规则**——那个规则在实测那条上
就是错的：`只是笼统的"腾讯视频"，正文` 里**两个**引号后面都不是 ASCII 逗号
（一个是中文逗号，一个是真正的结束引号），局部规则会把结束引号也转义掉，
于是永远解析不出来；而每轮又「成功」修掉一个，症状变成另一种失败。

**修可以，账要记**：修复记录随结果返回，writer 写进 `degraded_from`。
不记的话「被修过」与「原样解析出来」形状一样、可信度不同。

### ⚠️ 第五次变异测试翻车：加的那道守卫是**死的**

第一版给修复加了一道「只修 `Expecting ',' delimiter` 这一类错误」的白名单，
看着在限定范围。**变异测试把它删掉，13 条测试照样全绿。**

进一步枚举才下结论：17 种畸形输入 + 把一条真含坏引号的合法 JSON
**从每个位置截断**（58 个截断点），**没有一种**是靠它救回来的——
真正在拦的是那句「解析器报错的位置恰好是一个双引号」。

**死守卫比没守卫更坏**：它看起来在限定修复范围，于是没人再去验证真正
起作用的那道。已删，并把「不要加第二道门」写进 docstring。
替代它的是一条**性质断言**（任意位置截断都不得被修成假对象），
比样例断言强——样例只覆盖已想到的形态。

### writer 的七条口径（三条是实测出来的，不是设计出来的）

| # | 口径 | 依据 |
|---|---|---|
| 2 | `<think>` 剥完是空串 → 判**不可用**，不是「模型没说话」 | 未闭合 `<think>` 被剥净后是空串，与下游「模型这轮没说话」同形 |
| 3 | **采集降级写进提示词**，闸门只是第二道防线 | §5.5：模型是**当场**编故事的，闸门是事后才发现 |
| 6 | 残留思维链标记 → **拒写** | raw CoT 不落盘，而 writer 是 thinking 变成落盘数据的第一站 |
| 7 | 解析失败判不可用，不静默只留散文 | 悄悄少一个字段，下游看到的是「结论为空」而非「这一条没写成」 |

**口径 2 那条预判只对了一半**：`<think>` 内联**不是普遍行为**。
同一端点、同一提示词实测：

| 模型 | 内联 `<think>` | 正文长度 |
|---|---|---|
| `MiniMax-M3` / `MiniMax-M2.7` | ✅ **有** | 2286 / 2320 |
| `MiniMax-M3.1-Flash-Preview`（当前配置） | ❌ 无 | 209 |

### 一条死守卫：残留标记表曾经和 `strip_think` 重叠

第一版把 `<think>` / `<thinking>` / `<reasoning>` 也列进 writer 的

## 2026-10-10 增量六：模块 4 接线（writer → P1 → 闸门 → P2/P3）

**门禁 1201 → 1241 passed。变异测试 15 → 21 条，全部变红。**
`writer.py` 此前**零调用方**，`GateMark` 恒 `not_run` 且理由写着
「rationale 模块未落地」——那句话是错的。现在整条链通了。

### 落点与一条设计决定

| 环节 | 位置 |
|---|---|
| 生成（执行期） | `orchestrator._write_rationales()` → CLI 注入的 `rationale_writer` |
| 落盘 | `actions.ActionStep.rationale` → P1 的 `steps[i].rationale` |
| 核查（组装期） | `schema.gate_of()` 逐条跑 `gates.gate()` |
| 渲染 | `views._rationale_text()` 逐步对齐 |

**生成放在 orchestrator 而不是 `visit_site` 里**：动作流是**记录**、
rationale 是**补记**，两者在一次访问结束时才都完整。放进 `visit_site`
会让执行层直接依赖 LLM 模块（依赖方向 executor → perception）。
CLI 注入可调用对象，`visit.py` 因此完全不知道 rationale 的存在。

**D2「边写边生成」的实质是「生成时能看到那一步的动作与观察」**，
而不是「必须在线程内即时生成」——两者在同一份数据上等价，
而事后补记换来的是：writer 挂掉只少一段 rationale，不影响采集。

### 契约变更：第 ⑥ 件从「一条」变成「与动作对齐的一条」

执行期是**逐步**生成的，P2 却只有单个 `rationale: Rationale | None`——
两者对不上。改为 `rationales: tuple[Rationale, ...]`，按 `step_index`
与 `ActionView` 一一对齐：

- 训练态的思考与动作逐步对应，模型学到的是「这一步为什么这么做」；
- 闸门能逐条核（时序核查本来就需要 `step_index`）；
- **缺一条不补空串、不挪位**：按出现顺序猜会在中间缺一条时整体错位，
  而错位的 rationale 会被时序核查当成凭空引入的实体——**凭空造出负样本**。

`Sample` 的 `rationales` / `gate` / `outcome` 三项带默认值，
让「没接模块 4」成为可显式表达的状态，而不是逼每个调用方传两个
与它无关的参数（评分器就因此少改了三处）。

### 闸门真的跑了（不是恒 `not_run`）

`cli build` 于 38 份存档切出 221 条样本：

| 闸门 | 条数 |
|---|---|
| `not_run` | 216（老存档没有 rationale 字段） |
| **`passed`** | **5**（本轮 7 条 rationale 分布在 5 个样本里） |
| `failed` | 0 |

`rationale_missing` 与闸门状态同分布（216 True / 5 False）。
**「没跑」没有被渲染成「通过」**——这正是三值闸门的意义。

### 真实后端跑通：7/7 全部 `written`

T001《功夫》5 个站点 7 步全部生成，**内容如实反映「无法确认」而非编故事**：

> 但正文和交互元素被截断，无法确认播放器是否已加载及视频能否正常播放。

### 接线上撞出的两个缺陷（都是「照读一遍」才暴露的）

1. **`write_one()` 没有 `error` 参数**——动作失败时 orchestrator 传不进去，
   于是模型会拿着空观察解释「我看到了什么」，而真相是这一步压根没拿到观察。
   现已补：`error` 进提示词（`this_action_failed`）+ 系统提示词第 4 条

### 还没做的

代理切出的那两档**在事实层面无法合并**：要判它们是不是同一批，

新增测试盯的是一个契约测试盯不到的洞：`Test字段集一致` 只核 `to_json`
的**键集合**里有这个键，**值取错、写空、或者压根没写，它照样全绿**。
所以另加了 `TestSchemaVersion落盘`（落盘值 == `SCHEMA_VERSION` 且非空）
与 `TestSchemaVersion`（缺键给**空串**而不是默认版本号）。

后者的理由值得单说：给个默认值 `"1"` 看着无害，实际后果是**所有历史存档
被静默归进「v1」那一档**——而它们并不是 v1，是「不知道」。这两种在
报表上差很远。

改 `SCHEMA_VERSION` 等于宣告一批存档与另一批不可比，所以**只在破坏性

「模型给了地址但都错了」。于是读证据的人（包括写这条记录的人）
跑去查 URL 格式、查重定向、查 `www.`，而真正的问题是「它为什么一个都不给」。

**诊断被措辞带偏，代价不是措辞。** 空返回与地址对不上要分开记，
现在两句话已经分开（`TestNoConclusionVsUnmatched` 守着）。

> 这条也是「逐条打开存档读 evidence」的直接收益：evidence 读起来永远通顺，
> 通顺到把读的人骗过去——**通顺不等于指向真的那个问题**。

### 一、`FIND_PLAY_CONTROL`：ref 不给就由代码取回

**旧行为**：模型没回 ref + 词表在本页有非预告控件 → fail-closed `None`
→ 控制流不点击 → `player_obs` 全无 → 判断点 ④ 无从判起
→ **D-2 全批 undetermined**。因果链完整，见增量十。

**新行为**：`play_control_candidates(obs)` 取第一个非预告控件的 ref 直接用，
evidence 写明「模型未回传 ref；代码按词表从本页 N 个非预告播放控件中取
ref=e5」——**人读存档时要能分清 ref 是模型给的还是代码补的**，两者证据强度不同。

判据沿用本项目已有的立场（`trailer_only` 早就是「词表说了算」）：
**确定性事实归代码，模型只是传感器**。模型给不给 ref 是它的读数，
页面上有没有播放控件是事实。

三条不做的事，都有测试封着：

| 不做 | 为什么 | 守卫 |
|---|---|---|
| 不因此判 `False` | 「模型没回字段」与「这站看不了」毫无证据关系，而负样本不可逆 | `test_词表为空时仍然判否` |
| 不放开 ref 白名单 | 模型**给了**而不存在的 ref 仍是编造，点错不可逆 | `test_编造ref仍被白名单拦住` + 1 条变异 |
| 不取回预告控件 | 点了预告片，采到的是预告资源 | `test_预告控件不会被当成可点的ref` |

**顺带修掉一条 W1/W3 不一致**：页面上只有预告控件时，W1 落
`trailer_only`、W3 落 `no_play_control`——同一批素材两个结论，且都看着像对的。
新函数 `trailer_only_candidates` 让两边同源（两者互补，并起来就是
`is_play_control` 筛出的全部候选）。

### 二、判断点 ①：回编号而不是回 URL

**为什么**：回长 URL 是**记忆**任务，回编号是**复制**任务。模型会顺手改写
scheme、吞掉 `www.`、丢掉 query 尾巴，于是「选的 URL 压根不在观察里」整批作废。
改成回 `i` 之后 href 由代码从窗口里取，**模型碰不到字符串**。

三处必须看同一批链接且顺序一致，抽成 `_link_window(obs, question, title)`：

```text
预检（_title_link_sufficiency）  ┐
渲染（_render）                    ├─→ 同一份 obs.links → 排序 → 截 LLM_LINKS
回指（_select_play_sites）        ┘
```

这三处曾各拼一遍 `_ordered_links(...)[:LLM_LINKS]`，**预检与渲染已经错位过一次**
（增量五那次 5 个候选全落 `not_play_site` 假负样本：预检数到 3 条命中就放行，
模型收到的前 20 条全是导航栏）。同源之后它们是同一条判据的三个说法。

`i` 是**主路径但不是唯一路径**：回不到编号就退回 URL 匹配，好让按旧契约回
`url` 的后端不至于整批作废。编号读不出来（越界 / 越界到窗口外）也退回——
**退回而不是当命中**，否则 `i=999` 会指向窗口外的东西而控制流会去访问它。

提示词同时显式禁掉「两个数组都留空」：`selected` 与 `rejected` 至少一条，
一个都选不出来也要把最像的几个放进 `rejected` 并说明为什么。

⚠️ **这只降低失败概率，不保证模型就肯作答。** 若下一批仍全空，
说明提示词约束无效，该查后端能力而不是继续改提示词。

### 三、站点首页核（环节 ①.6）

`hao123.com` 走完访问链后记了 `no_play_control`——**结论方向碰巧对了，
理由全错**。那是导航站，问题是「压根不是搜索结果该返回的东西」，
不是「去了发现看不了」。两类混成一条，负样本池就再也答不出「为什么看不了」。

判据是**纯确定性的**：URL 的 path 为空或 `/` 就是首页，首页结构上不可能是
某部作品的播放页。这正是「代码管事实层」的用法——它不是语义判断。

**为什么不加进 `EXCLUDED_HOST_ROOTS`**：那样它压根不成为候选，
`not_play_site` 永远 0 条，而「每条分支都必须有对应样本入库」是硬要求。
这条分支的样本只能从这里来。

**为什么落在判断点 ① 之后**：① 的 True / False / None 三条路径都要过这道核，
而 `_apply_selection` 只在 True 时被调——挂在它里面就只能覆盖三分之一，
而实测那批走的正是 `None` 那条路。

### 四、核对时撞见的红线破口：raw CoT 正在落盘

不在原计划里。是核对上面三项时读代码读出来的，而且它比三项都严重——
**CLAUDE.md 红线「不保存 raw CoT」有一条真实破口**。

[`llm_perceptor._why_unparsable`] 直接 `raw[:120]`，**没调 `strip_think`**。
而 `evidence` 是 `SiteOutcome` 的持久字段，直接落 P1。实测形态：

```text
<think>模型内部推理：链接里有 5 条像结果…</think>根据页面观察，我无法确定。
└────────────── 前 120 字全是这个 ──────────────┘
```

不是罕见分支：**解析失败本身在真实批次里是常态**（散文、格式漂移、
markdown fence、预算耗尽），而推理模型人人带 think，两件事撞上就漏。

落盘点只有这一个——`RunRecord.to_json()` 里**没有 `payload`**，
模型原文进 P1 的路径就这一条。另一侧 [`rationale/writer.py`] 早就
`strip_think` 了，**只有感知层这一处漏**。

**为什么漏了很久而门禁全绿**——根因不在生产代码，在 **fake**：

```python
if self.prose:
    return _prose_for(qid)          # ← 提前 return
raw = json.dumps(payload)
if self.think:
    raw = f"<think>…</think>\n{raw}"  # ← 套不上
```

`think=True, prose=True` **组合不出「带思考且正文不是 JSON」这个形态**，
于是没有任何测试造得出它。修的时候才发现：连我自己第一次验证都踩了同一个坑
（用 `FakeLLM(think=True, prose=True)` 去复现，跑出来干干净净，
差点得出「没有漏洞」的结论）。fake 已改成 think 包装统一在 prose 之后套。

> **fake 造不出的形态 = 不存在的守卫。** 加 bad-output 形态前先问一句
> 「这两个开关能同时打开吗」——这是本项目第二笔「fixture 与规则一起错」的账，
> 第一笔是 D-2 的 fixture 全带 click 动作。

修完顺带得到一个更好的诊断：剥完为空时（只吐思考、没有正文）单独说一句，
因为它与客户端报的「预算被思考吃光」**症状同源而成因不同**——
后者压根没返回正文。写成一句话会让人以为该去调预算。

见[避坑指南 §8.6](02-避坑指南.md)。

### 元教训：变异打空与守卫无效，结论恰好相反

改 `_render` 时把一处 `for` 循环重写成了先算 `window` 再列表推导，
结果 `mutation_check` 里那条锚在旧代码上的变异**找不到锚点**，静默报
「ALIVE（守卫无效）」。

框架本身有 `[SKIP]` 提示并把它计入失败（所以这次没被骗过去），
但形态值得记：**「守卫无效」与「这条变异根本没打出去」在报表上长得很像**，
而两者的处置相反——前者要去补测试，后者要去更新锚点。改生产代码后
`mutation_check` 突然多出 ALIVE，先确认是 `[SKIP]` 还是 `[ALIVE]`。

### 本次没修、但看见了

- **LLM 版没有 0 元素的采集预检**。规则版有（`rule_perceptor.py` 的
  「采到 0 个交互元素 → `None` 而非 `False`」），LLM 版没有——
  页面没渲染完时它会照着模型的话判 `False`，把采集故障写成业务负样本。
  同款坑，W3 上一份。首页核只挡住了「首页」这一种形态。
- **本批的 `steps[0].rationale` 恒 `null`**（增量十已记，仍未核实）。

## 增量十二：URL 播放黄金集 Q1–Q4 口径冻结（2026-10-12）

对齐方案（`设计方案/06-URL播放黄金集与轨迹黄金集标签对齐方案.md`）阶段 0 的落地：
把「URL 视频可播放性校验 · 黄金数据集」要用的四条判断口径，从方案裁决表升格为
本档案的正式条目。**纯口径，不动代码、不动门禁**（门禁维持 1392）。

> 这是本档案第一次对「还没进代码的规则」先冻口径。此前 Q1（付费）只以
> `review_queue.py` 的 `confirm_paywall` 注释形式留痕，Q2/Q3/Q4 连代码留痕都没有；
> 若不先落条目，阶段 1 实现时四条口径容易各写各的。

| 口径 | 问题 | 裁定 | 依据 |
|---|---|---|---|
| Q1 | 付费算不算不可播放 | **算不可播放** | 2026-10-10 已实施：有播放页但需订阅/付费 → `subscription_wall` |
| Q2 | 登录后免费算不算通过 | **不通过** | agent 任务不含登录态；`login_required` 负类，与 `IS_REACHABLE` 语义一致 |
| Q3 | 前贴广告/试看算不算正常播放 | 广告后能播 = success + `ads_present=true`；试看后付费 = `partial_free` 负类 | 业务裁定 2026-10-12 |
| Q4 | 地区/验证码/反爬如何归类 | **环境阻断** `blocked` | 与内容损坏 `broken` 分离：内容问题 vs 环境问题 |

### 一、Q1 付费：沿用 2026-10-10 口径，不重订

「有播放页但需订阅/付费不算成功」已于 2026-10-10 实施（`confirm_paywall` 裁定枚举
就是为它补的）。本期只把话固化：付费墙是**内容访问控制**，不是环境故障，
归 `subscription_wall`，不落 `blocked`。

### 二、Q2 登录：登录后免费 = 不通过

agent 任务不含登录态，站方要求登录才能看 = 该 URL 对 agent「当前不可播放」。
`login_required` 是负类；语义与 `IS_REACHABLE` 判断点一致（走到登录墙即判负，
不继续）。对应新体系 `login_required` 标签，阶段 1 从 `login_wall_or_blocked`
拆分。

### 三、Q3 广告：广告后能播算通过，试看后付费算不通过（新裁定）

业务裁定（2026-10-12）：

1. **广告后能播 = success + `ads_present=true`**。`ads_then_playable` 不单列，
   作为 `success` 的等价视图挂入；广告信息只进元数据，不进标签。
2. **试看后付费 = `partial_free` 负类**。试看 N 分钟/抢先看弹付费
   → `paywall_type=preview/trial` → 落 `partial_free`，不进 `success`。

采集时要区分两种形态：**纯前贴广告**（广告播完/可跳过自动进正片）
记 `ads_present=true`；**试看后付费**（免费部分有播放、完整内容要钱）
记 `paywall_type=preview/trial`。两者混在一起会同时污染正样本纯度
（把试看算成功）和负样本纯度（把纯广告站点算不通过）。

### 四、Q4 环境阻断：归 `blocked`，与内容损坏 `broken` 分离

地区限制 / 验证码 / 反爬 / robots 是**环境阻断**（`blocked`，payload
`access_control_type=region/captcha/anti_bot`）；404/媒体损坏是**内容损坏**
（`broken`）。两者都判负，但修的东西不同：前者是环境/网络策略，后者是
数据/内容问题，混在一支报表分不出该修什么（理由同 `NON_SAMPLE_BRANCHES`
的拆分逻辑）。

> 历史 `login_wall_or_blocked` 里的 404 **不回填**为 `broken`：旧存档
> evidence 大概率分不出是登录、地区还是 404，重标等于虚构（见对齐方案 §8
> 风险 3）。新数据才走 `broken` 通道。

阶段 0 产出条件「本方案评审通过 + Q3 裁定记录」已满足。

### 一、为什么不在分析阶段就把断链补上

变更是**契约层**：`_ask()` 拼接 system prompt 用 `CONTRACTS[spec.id]`，扩字段

prompt 漏，造成 LLM 输出格式漂移、契约测试不预期——`test_perception` 里
parametrize 跑 `answer_null / answer_missing / answer_garbage` 三档
会首先红。

所以本次先诊断拿到「**不补就跑不出分支**」的硬证据，再分两批落地。

### 五、P3 的诚实定位

> **P3 evidence fallback 是**「防 regression 的最后兜底」**，不是触发新形态的
> 工具**。

1. **真实收益**：在本次 7 URL 重跑里，**0 个样本触发** code fallback——LLM 这一轮
   表现稳定，access 字段全部自主给出（"地区码 70017001"、"页面错误"等关键词
   LLM 自己能识别）。P3 的设计哲学是"LLM-first → code-evidence-last"，
   LLM 不漏字段时 code 永远闲置。
2. **真实风险**：P3 v1 已实证：evidence 文本是 LLM 自述、不能直接当 raw keyword
   匹配——任何过于宽的关键词集合都会引入 regression。**所有真实回归**都要先
   收紧关键词再反复测试，不能上"覆盖率优先"姿势。
3. **真实缺口**：partial_free / login_required 在 7 URL 重跑里仍 0 触发——
   不是因为 evidence fallback 没生效（fallback 是"兜底"不是"主力"），
   而是因为 **LLM evidence 中没含明确的 paywall/auth 关键词**（B 站"大会员"
   与 fallback 关键词集合不重合）。

### 六、给后续阶段 4 / P4 的接口

本次改动留下的**结构性接口**：
- `_resolve_field()` 在 `llm_perceptor` 内，是 code → field 的**单一桥**；
  任何 code-derived fallback 都走它；
- `infer_access_from_evidence` / `infer_paywall_type_from_evidence` 是
  **纯函数 + 关键词表**，加新词条改的就是它们；
- evidence 末尾 `[code_fallback] <field>=<value>（reason）` 是给人工复核的
  单一信号——人工看 evidence 后缀即可识别 fallback；
- LLM payload 仍优先于 code fallback（defense in depth）。

**真正解决 LLM 给字段稳定度**的办法，落在后续 P4（阶段 4 配套）：
- L0 静态可达性探测：让 anti_bot / captcha 在采失败前就被识别为
  `access_control_type=anti_bot` 而**不**依赖 evidence 关键词；
- L2 `media_probe` + probe.md：让 `paywall_type=preview/trial` 在 PLAYER_OK
  阶段有结构化信号（媒体事件 / 视频时长截断）替代 evidence 字符串；
- LLM prompt 让模型**单独回传**"页面引用短语"字段（不是塞进 evidence）——
  P3 实证：evidence 是 LLM 自述而非 raw 文案，需要分离。

### 七、留下的一句教训

> "**LLM evidence 不能当 raw keyword 匹配**"——这是 P3 v1 → v2 的真教训。
> evidence 是「结论+证据」混合文本，**整体关键词匹配会把 LLM 推断语言误识为
> 页面引用**。任何 code 层用 LLM evidence 反推字段，必须假设 LLM 的措辞可能
> 与关键词集合重合且语义相反。**收紧 + 反复测试**比"扩词覆盖"更重要。

## 2026-10-12 增量十六：P4a · LLM 单独回传 page_quotes 字段（解决 P3 v1 根因）

承接增量十五——**LLM evidence 不能当 raw keyword 匹配**是 P3 v1 → v2 的
教训，但 P3 v2 的修复只是"收紧 not_found 关键词"，没解决根本结构问题：
LLM evidence 永远是「结论+证据」混合文本，任何关键词集合都可能在它
推断语言里被误触。本条增量**根除这个根因**：让 LLM 单独回传
``page_quotes`` 字段——只装页面原文短语，与 evidence 分离，code fallback
改用 page_quotes。

### 〇、设计动机

> **evidence 是 LLM 自述，page_quotes 是页面原文**。这两件事**不该**塞在
> 一个字段里。

P3 v1 实例：v.qq.com/70017001 的 evidence 是 LLM 写的"目标视频已不存在"
——这是 LLM 自述**结论**而非引用页面文案，但 code 不区分、用 "视频不存在"
字面匹配触发 `not_found` 误判。

**根因不是关键词过宽，是数据流设计**：evidence 字段就是"结论+证据"混合，
把任何关键词集合放在这字段上都会撞上 LLM 推断语言。

**修正姿势**：让 LLM 在 evidence **之外**单独给一个 ``page_quotes`` 字段，
严格按"逐字引用页面真实出现的字符"——code 层 fallback 看的就是这个字段。

### 二、契约变更总览

P4a 是**契约变更**：LLM 必须多回传一个 ``page_quotes`` 字段。
- field name: ``page_quotes``
- field type: ``array of str``
- 字段语义：**逐字**引用页面真实出现的字符（中文/英文皆可）。
- 不改写、不翻译、不补前缀（"用户须"、"页面含"等）、不写自己推断。
- 没看到明显短语就空数组 ``[]``。

**Lark test 持续 1539 passed**（之前 1532 + 7 新 = 1539）。

### 三、P4a 修复了什么、不修复什么

**修复**：
- LLM 自述（写进 evidence 的"看似页面引用其实是结论"）**不再能**触发 fallback；
- code fallback 的输入源只可能是**真正页面原文**——LLM 把它**逐字**引用才有效；
- P3 v1 的"目标视频已不存在 → broken 误判"**已被根除**（LLM 即使在 evidence
  里写这句话，code fallback 看的是 page_quotes，不命中）。

**不修复**：
- LLM 是否**真的**逐字引用（schema 不能强制）——只能靠 prompt 引导。
  若 LLM 自述混入 page_quotes，regression 会以另一种方式复现。
- `partial_free` / `login_required` 在已知样本上的**触发数**——P4a 是
  "不再误判" 的修复，不是"新增触发"的引擎。真正触发要靠 (a) LLM 在 page_quotes
  真的逐字引用试看/登录短语，或 (b) 阶段 4 L0/L2 工具加结构化信号。

**0 个样本触发 fallback**——但**没有回归**到 P3 v1 的 broken 误判（防住）。这是 P4a 的**第一次实跑成果**：

#### 重要观察：LLM 未按契约回 page_quotes 字段

**问题**：prompt 让 LLM 把页面原文放进 ``page_quotes`` 字段，
但**实际** LLM 把"页面原文"塞到 evidence 字段，用引号包裹（如 `"当前设备不支持播放"`）。

SiteOutcome 是 frozen dataclass，**不存 payload**——
``page_quotes`` 字段随 Decision payload 流转但不落 P1，
归因只能从 evidence 字符串看到。**第一轮实跑看到所有 evidence 都含"「...」"
包裹的页面引文**——LLM 在做"逐字引用"行为，但**没**放进 page_quotes。

**根本原因（推测）**：
- LLM 训练语料里 evidence 通常是"自然语言段"，page_quotes 字段是 P4a 新
  引入的概念，模型对此字段的指令遵循度尚低；
- 一两轮 prompt 调整不足以让 LLM **稳定按**新 schema 输出新字段。

**对策（待评估）**：

1. **强化 prompt**：明示"page_quotes 才是 P4a 的目标字段——evidence 含页面
   引文是反模式；同时调整 schema_hint 把 page_quotes 标到字段表首位。
2. **后处理解析**：从 evidence 里**抽取**引文括起来的段（如 `"..."` / `"..."`
   内容），作为 fallback 输入——这能让 LLM 即使不严格守契约也能让 fallback
   拿到证据。但这又让 evidence 与 fallback 输入混在一起，复现 P3 v1 的
   regression 风险**需要严格验证**。
3. **接受现状**：把 P4a 当作**长期** prompt engineering 的方向，短期不动；
   短期新分支触发仍靠：
   - 阶段 4 L0 静态可达性探测（auto_bot 用 403/状态码触发）
   - 阶段 4 L2 media_probe（partial_free 用试看秒数信号触发）
   - 真实黄金集构建（增量十四 §五：login_required 真实数据稀疏，主动构造）

#### 综合结论

| 维度 | 结论 |
|---|---|
| P3 v1 regression（v.qq.com blocked→broken 误判） | ✅ **已防住**，0 样本误判 |
| P4a 的"LLM 真的把页面引文放进 page_quotes" | ⚠️ **首次实跑 0/7**——需要 prompt 强化或后处理 |
| 真实新增分支触发（partial_free / login_required）| ⚠️ 0/7——LLM 没让 fallback 启用 |

P4a **真**价值：**根除 P3 v1 设计根因**（让 fallback 输入只来自"LLM 真看到的原文"），
且 P1 归档里 evidence 字符串已含页面引文（即使 LLM 没分隔），
**给未来后处理留好接口**——任何从 evidence 抽取引文的代码都可基于今天的标记/
字段体系扩展。
