## 一、怎么读这些数（三条口径边界）

1. **P1 主档 / 复核档不是两份数据**——`<task>__<run>.reviewed.json` 是同一条 run 的**人工复核版**，同名时取代主档。所以「唯一轨迹数」按 `task__run` 去重（**167 条**，不是 246 个文件）。
2. **交付面 ≠ 存量面**——按方案 23 R-5，`camofox-1` 是现行交付面，`obscura-1` / `camoufox-1` 是**只读存量**（不再产出，仍读得懂）。**混池即错**（台账 H-14 / M-21）。
   ⚠️ **2026-11-10 起追加一条口径**：旧面**默认不再重渲染**——`cli build` / `cli task-view`
   **只构交付面**，旧面要重建得显式 `--include-legacy`（按需）。详见[§七③](#七③-旧面派生产物已清--且不会自己长回来)。
   ⇒ **盘点脚本据此把「洞」拆成两类**：`p1_without_p2`（**真洞** = 交付面 P1 没有 P2）·
   `p1_legacy_without_p2`（**旧面源档**，按口径不渲染，**不是洞**）。脚本的「面」由
   **driver 折算**（`camofox→camofox-1` · `camoufox→camoufox-1` · `driver=None→obscura-1`），
   **不靠产物目录反推**——否则旧面一清，面就跟着「消失」了。
3. **P2 的 `outcome` 取末条结论**，站点级细节在 `site_outcomes[]`——**一条 = 一条轨迹 = 一个 Run**（per-Run 口径）。**两层分母不能混**：87 份 P2 对应 880 行站点明细。

## 七、盘点时发现的两处问题

### ① `mediabrowse/` 里 **2218 / 2271 个文件是 pytest 残留**（不是生产数据）—— ✅ **已清、已修、已立守卫**

- **现象**：`output/pipeline/mediabrowse/` 有 **2271** 个 JSON，其中 **2218 个**的 `requested_url` 是 `https://a.example.com/N`（pytest 的假域名），只剩 **53 个**是真实站点（全是 `v.qq.com`）。
- **根因**（**已复现**）：`tests/unit/test_cmd_mediabrowse.py` 有 **7 处**把 `out=None` 传给 `cmd_mediabrowse` ⇒ `P1Archive(root=None)` 落 `DEFAULT_ROOT`（= **生产产物目录**，不是 `tmp_path`）⇒ **每跑一次 pytest 就往生产目录写 4 个文件**。

  本次盘点期间实测：跑一次该测试文件 ⇒ `mediabrowse/` 从 **2271 → 2275**（已把这 4 个我自己跑出来的删掉，恢复原状）。

- ⚠️ **根因有两条，盘点时漏了一条**：`dispatch_l6` 的 `queue_path` **默认也落 `DEFAULT_ROOT`**——
  即使 `--out` 指到别处，**L6 派发队列仍写生产目录**（`review_auto/l6_dispatch.jsonl` 盘上 15 行
  **全是测试命名空间**）。这既是生产语义 bug，也是测试写生产目录的**第二条路**。

- **影响面**：**不污染训练数据**——P2/P3/T 的组装 glob 只扫 `output/pipeline/` 顶层与 `samples/` / `views/` / `task_views/`，`mediabrowse/` 是子目录、不被收走；`--mediabrowse-dir` 按 `(task_id, url)` 索引，假域名的 `task_id` 是 `P024-reuse` 这类**测试命名空间**，挂不到交付面样本上。

  ⇒ **是产物目录脏 + 磁盘占用（4 MB），不是数据正确性问题。**

- ✅ **已清（2026-11-10 owner 指令）**：`mediabrowse/` **2271 → 53**（删 2218 个 pytest 残留 +
  1 个 `127.0.0.1:18097` 残留；**保留 53 个 `v.qq.com` 真实探针数据**——判定按**内容**
  （`requested_url` 的 host）、不按文件名）；`review_auto/l6_dispatch.jsonl` 整份删（15 行全测试
  命名空间）。**9.9 MB → 957 KB。**

- ✅ **已修**：① 7 处 `out=None` → `out=str(tmp_path)`；② 新增 `cli.py::_archive_root(args)`
  （**`--out` 给了就用它，没给才用默认根**），三处 `P1Archive(...)` 构造与三处
  `_dispatch_l6_summary(...)` 派发改用它 ⇒ **测试不再写生产目录**。

- ✅ **已立守卫**（`tests/unit/test_output_isolation.py`，两条）：
  ① **静态**——AST 扫测试树，**不许出现 `out=None`**（它在 CLI 层的含义就是「落生产目录」）；
  ② **运行时**——`mediabrowse/` 与 `review_auto/` 里不许出现**保留测试域名**
  （RFC 2606 / RFC 6761）。守卫**自检**：喂它一段坏例子得报出来。

- ✅ **硬证据**：全量 ~5200 测试跑完，生产产物目录 **8118 → 8118 文件，0 新增 0 减少**
  （跑前跑后逐文件快照比对）。台账 **H-28**。

### ② `P2 → P3/T` 的零缺口**是这次盘点期间才达成的**

盘点开始时（16:06）`E001__1aaa1916` / `E005__d26df4b6` / `E006__4455d64b` 三条新档**有 P2、没有 P3 也没有 T**；随后一轮 `build` + `task-view` 在 **16:48–16:50** 跑完，缺口归零。

### ③ 旧面派生产物已清，**且不会自己长回来**（2026-11-10 owner 裁定）

- **清理**：`legacy/` 整棵删除——`obscura-1` **52** 份样本 + `camoufox-1` **14** 份样本，
  连同派生视图（**198**）与任务视图（**80**），合计 **344** 个文件 / **16 MB**。

- **保留**：**旧面 P1 源档（80 份）仍在盘上顶层** ⇒ **随时可重建**（`--include-legacy`）。
  「退役 ≠ 失忆」指的是**存量证据仍读得出来**，不是「旧面文件不许删」。
- ⚠️ **清理在旧口径下不持久**：`cli build` / `cli task-view` 会把旧面 P2 / P3 / T
  **重渲染回 `legacy/`** ⇒ 池自己长回来，而读的人只看到「又多了 66 份」，
  看不到为什么。⇒ **owner 裁定改 build 口径**：

- **落地**：`pool.py::should_render`（口径唯一真源）· `builder.build_all` ·
  `views.build_views_from_dir` · `task_view.build_all_task_views` · `cli build` / `cli task-view`
  的 `--include-legacy`。测试：`test_pool.py`（口径单元测试 + 三层默认/按需）·
  `test_cli_build.py` · `test_cli_task_view.py`。
- **实测**（生产目录，`cli build --stage p2` 不覆盖）：**`legacy/` 没被建出来**，
  印出「旧面 66 份**未重渲染**」，`pool_meta.json` 的 `samples.legacy_skipped_now = 66`。
  ⇒ 读数口径见[方案 23 R3-3 修订](../设计方案/23-训练轨迹语料整改方案.md)。
- **盘点脚本同步改了口径**（`research/probes/corpus_survey.py`）：① **面由 driver 折算**，
  不靠产物目录反推——旧面一清，面不会跟着「消失」（旧面源档 **80** 条仍报得出）；
  ② **「洞」拆成两类**：`p1_without_p2`（真洞）· `p1_legacy_without_p2`（旧面未渲染，**不是洞**）；
  ③ 新增 `p2.legacy_source_runs`（**可重建但默认不渲染**的 P1 源档数）。
