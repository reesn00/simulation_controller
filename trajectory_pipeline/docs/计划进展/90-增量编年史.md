## 增量五十 · LLM 多轮入口 chat_messages（A2a-1，INC50，2026-10-17）

方案 13 §3.5（A2a-1）落地：agent 循环要「按步喂对话历史 + 拿 token 账本」，
而 `llm/client.py` 的 `chat` 是**单轮两消息**形态（system+user 固定）、
且 `_content_of` 把 `usage` 整体丢弃。新增 `chat_messages` 多轮入口，
**`chat` 的外部契约一字不动**（十一道判断题 + FakeLLM + 全部感知层测试
零改动）。

### 一个请求循环，两个入口

`chat` 的请求段抽到私有 `_exchange(messages, max_tokens) -> (content, usage, error)`，
`chat` 与 `chat_messages` 共用它。抽的理由不是省几行，而是**重试与失败
分类必须只有一个副本**：分叉的后果是「某一类失败只在其中一条路径上被
正确处理」，那要等真实后端出状况才暴露，代价是一次批次。

`chat` 因此成了薄壳（组装两条消息 + 取 `content`），且保留原语义——
`last_error` **只在失败时写**，成功后不清除（diag 路径依赖「上一次失败的
原因」这个语义），并由测试 `test_成功后last_error不清空` 钉住。

### 三个刻意的设计

| 设计 | 理由 |
|---|---|
| `messages` **原样透传**（OpenAI 形态 `{role, content}`），客户端不合并 system、不裁剪历史 | 加工了就会让「模型实际看到什么」有**两份真相**；裁剪是 agent_loop 的事（步数预算的下游） |
| **不加 `tools` / `tool_choice`** | D-B1 拍板 JSON 动作指令走文本通道；加上去等于把半个原生 tool_calls 协议引进来，而 P3 视图是从 Action 渲染的，两套形状会打架 |
| `usage` **只认 `int`**（显式排除 `bool`），取不到返回 `None` 而**不补 0** | 账本上「0」与「后端没给」是两个事实——补零后「这批没记到 token」会看起来像「这批一个 token 没花」，成本对比先错在**分母**上且不报任何警 |

`total_tokens` 刻意不取（可由两者相加得到，记下来就多一份要同步的东西）。

`ChatResult` 是 frozen dataclass：`content` / `usage` / `latency_ms` / `error`，
`error` 与 `last_error` 同格式（`transport:` / `http:` / `shape:` / `budget:`），
**空串 = 成功**。⚠️ 契约要点写进 docstring：`content is None` 在 agent 循环里
不能被当成「模型说放弃」——「没作答」（要重试引导）与「答了放弃」（收口
unresolved）是两种事实。

### FakeLLM 侧

`chat` 的题号 dispatch + 坏行为开关抽到 `_respond(user) -> (原文, 错误码)`，
`chat_messages` 与 `chat` 共用——**开关表是 fake 的价值所在，它必须两个
入口都生效**（分叉的后果是「某个开关只在单轮形态下生效」）。
`chat_messages` 取**首条 system + 末条 user** 记账，`usage` 默认给固定值
（真后端会回 token 计数），`no_usage=True` 模拟「后端没给」。
（`FakeAgentLLM` 是 A2a-5 的活，A2a-1 只补同签名方法。）

## INC 51 · A2a-2 落地：agent_loop 循环体 + 分支收敛映射（2026-10-17）

**类型**：功能（方案 12 阶段 A2 / 方案 13 §3.2–§3.4、§3.9 前半）
**范围**：新建 `executor/agent_loop.py`（~950 行，含 docstring）；
`tests/fakes.py` 新增 `FakeAgentLLM`；新建 `tests/unit/test_agent_loop.py` 74 例

### 三条落地的硬设计

| 设计 | 为什么 | 落点 |
|---|---|---|
| **agent 永不直接产分支**——出口只有 `AgentOutcome` 三种形态，分支靠 `_FALLCLOSED_BRANCH` 查表 | 22 分支封闭集是 P2/P3 与 d5_scorer 的共同地基，让它随 LLM 输出浮动等于把评估口径交给不可复现的东西 | `_branch_of` 是折算的**唯一一处** |
| **I6 白名单取自「渲染进对话的那一份」而非 driver 采到的全部** | 挡得住 e999 只算挡住最笨的编造；真会污染存档的是「编一个在第 51 位、页面上确实存在但没给他看的 e51」 | `_visible_interactive`；用例 `test_白名单取自渲染进对话的那一份` |
| **模型原文从不进本模块**——进对话的是解析后**重新序列化**的规范 JSON，解析失败的原文根本不落 | raw CoT 因此没有路径流进 P1/P2，**不靠调用方记得先剥** | `_canonical`；用例 `test_模型原文不进对话` |

### 依赖方向：executor 不 import llm

`json_of`（text → dict）**由调用方注入**，与 `rationale_writer` 同款姿势
（`01-架构总览` L26-50：`common ← llm ← {taskgen, perception, rationale}`，
executor 只依赖 perception 的协议）。分工：

- **格式契约（schema）在 loop 侧**——字段在不在、ref 在不在白名单，执行器
  才知道哪些 ref 是真的；
- **文本解析在 llm 侧**——剥 `<think>`、抠 fence、宽容修复是共享资产，
  复制一份就有两份解析，而两份解析必然在某天分叉。

生产侧传 `lambda raw: extract_json(strip_think(raw))`，测试用同一个。
`LLMClient` / `ChatResult` 只在 `TYPE_CHECKING` 下 import（有 import 后的
断言性质用例守着）。

### 「没作答」与「答错了」分两条路（A2a-1 留下的契约提醒）

| 事实 | 处置 | 理由 |
|---|---|---|
| 后端没作答（`content is None`） | **直接收口，不重试、不升配** | 那是运维问题——client 内部已重试过；升配更是南辕北辙（更强的模型也连不上同一个挂掉的端点） |
| 模型答了但不合契约 | 注入契约原文 → **重试一次** | 这是**能教**的 |
| 说「找不到」 | `gave_up` → `unresolved` | 三支「没判出来」分立的纪律 |

第三轮重试的准入条件只有一个：**刚升配过**（`_MAX_ATTEMPTS=3`，
`_maybe_escalate` 返回 True 才 continue）。升配每个候选只发生一次
（`_escalated`），且 `escalate=None` 时只落事件——**升配是能力不是依赖**。

### 拦截的两条次序纪律

1. **拦截只在新观察到达时触发**，不在每轮循环开始时触发——同一份观察被拦
   两次会让「格式纠正重试」意外吃满 `_GUIDANCE_LIMIT`，模型还没来得及换路
   就被判成二次拦截收口；
2. **BLOCKED_CF / CAPTCHA 一次性收口，不给引导机会**——agent 没有登录态也
   没有指纹可换，引导只会烧一次 llm_call 然后得到一句「我换不了」。
   LOGIN_WALL / PAYWALL / DEAD_LOOP 才是「换路有机会」的那三类。

### 刻意不做的两件事

- **循环内不拦 goto URL**（纪律写进 prompt，A3-2 批次级溯源断言负责）——
  与 D-2 的样本级口径分开放，两个信号不混；
- **失败的两条路径都不消耗步数**（步数记的是「走到的页面数」）——给 agent
  换路的机会，但那机会由 llm_calls 预算兜底，不让「点了三次都点不动」吃光
  整个步数预算。

### FakeAgentLLM（方案 13 §3.9 前半，A2a-1 未做）

与 `FakeLLM` 分开：那边的 dispatch 是「题号 → 答案」，这边是「第几步 →
动作指令」，两种逻辑塞进一个类就会出现开关之间的隐式优先级。
`flaky=N` 取代原计划的 `wrong_then_recover` 布尔：**前 N 次吐散文、之后按
脚本走**——用整数是因为「连续错两步」是另一种真实现象（那是升配的触发
条件），布尔开关造不出第二种。

## INC 52 · A2a-3 落地：agent_visit 薄壳 + 两段共用 + executor_mode 埋点（2026-10-17）

**类型**：接线（方案 12 阶段 A2 / 方案 13 §3.7、§6.1 A2a 段）
**范围**：新建 `executor/steps/agent_visit.py` + `executor/mode.py`；
`visit.py` 抽两段共用；`orchestrator` / `cli` 接线；`RunRecord.executor_mode`；
新测试 48 例

### 两条链的形状：只换中间那一段

```
visit_site   ① ② ③ ③.5 ④ ⑤ ⑥ ⑦     七段固定序列
agent_visit  ① ② ─── [agent_loop] ─── ⑦   站内交给循环
             └ 共用 ┘                  └ 共用 ┘
```

共用的两段是 `enter_site`（① 导航 + ② 观察）与 `judge_player`（⑦ PLAYER_OK
+ 记账）。**抽函数共用，不复制**——理由不是省行数：

| 段 | 分叉的后果 |
|---|---|
| `enter_site` | 两条链对「进站失败算什么」给出不同答案，负样本池里就混进两种成因的 `unreachable_hard`——它们是同一支分支，混了看不出来 |
| `judge_player` | `component_unverified` 的前置事实守卫（「到了播放页」）长在这一段，两条链各写一份的话，闸只会在一条上生效；漏掉的那条产出的假负样本**理由通顺、看着专业**，人工也未必看得出 |

`visit_site` 本身**不删不改**——A3 的 fallback 与黄金基线都是它。

### 四个刻意的设计

1. **PLAYER_OK 判在「agent 看到的那一份观察」上**（`AgentOutcome.final_obs`）。
   循环外再取一次快照，判的就是另一份快照了——播放器会自转、广告会轮换，
   而 D-2/D-5 判的正是观察正文。**判据与决策依据分叉**是最难查的一类不一致。
   附带收益：省掉一次浏览器往返。
2. **落地即在播放页的保守降级**。深层链接候选中 agent 一步没走就报「到了」，
   于是 `pre_obs == player_obs`，守卫会把 PLAYER_OK=False 的记账从
   `component_unverified` 降级为 `unresolved`。这是**刻意的**——agent 说「到了」
   是自报，未经跨页证实；拿自报的前提贴负标签等于把「模型没找到」写成
   「这里看不了」。丢一个负样本，好过产一条假负样本。
3. **`executor_mode` 在构造期定下，分派只有一处**（`_visit_guarded`）。模式是
   批次级属性，逐候选判断会让「这条轨迹是谁产的」变成逐条才能回答的问题。
   有用例数着源码里 `self._mode ==` 的出现次数（=1）。
4. **要 agent 而没后端 → 当场报错，不静默退回 scripted**。退回的那一批在
   存档上写的是 `executor_mode="scripted"`，于是「agent 批失败了 40%」会被
   读成「scripted 跑得好好的」——**配置错误伪装成一次成功的灰度**：不报错、
   不空转，报表还挺好看。与 `--perceptor llm` 未配后端报错同款口径。

### 三条已知口径（留给 A3）

- **共用 `per_site_timeout_s`**：一个候选最多 12 次 llm_call，90s 默认值会被
  走得满的候选撞到。超时即 `unresolved`，与 scripted 同形；要单列改一处。
- **agent 模式不跑 `IS_REACHABLE`**：页面级「能不能看」由 gatekeeper 逐步
  拦截（LOGIN_WALL → `login_required` 等），比那道题更早也更硬。
- **A2a-3 不接 `llm_calls` 账本**（§3.6）：`RunRecord.llm_calls` 属 A2a-4，
  现在传 `None` = 丢弃。先接一半的账本会在报表上假装这批成本可查。

## INC53 · A2b 任务③④：B/C 中间页的 agent 形态（方案 13 §4）

**日期**：2026-10-17

### 一句话

同一个循环，换的是任务指令：`IS_AGGREGATOR` / `SELECT_SITE_ENTRIES` /
`SELECT_REFERRAL_LINKS` 三道判断题在 agent 模式下**一道都不跑**，语义进

### 三处对文档设计的原创细化

| 细化 | 理由 |
|---|---|
| **终局自报的 URL 走白名单强制**，goto 的 URL 不拦 | goto 编了会走到 404，agent 自己看得见、能换路（可自愈）；终局报出来的 URL 会直接过外链校验变成候选进 P2，而循环已经结束，**没有退路**。这个区分同时保住了 A3 的溯源断言有意义——那边统计的正是循环里没拦的那一类 |
| **新增第四种处置对象 `RejectedReport`** | 挡下来是**处置**，记账是**事实**，两件事都要有：循环内挡住了不等于没发生过，而事件是 A3 批次级幻觉计数的唯一数据源。否则那份计数恒为 0 |
| **`resolve_into_candidates` 加 `parent` 覆盖** | agent 在站内导航过，站外链接的 `same_host` 剔除要以「它当时站在哪」为基准。用落地页当基准会把自己所在站的链接也当成引荐放进来 |

### 一个连续第三次撞上的结构代价

**三支负分支在 agent 模式下没有产地**（`not_aggregator` /
`aggregator_no_entries` / `article_no_links`）：

- 它们的成立前提是「判断题判了 False」这个**真结论**；
- agent 模式下那三道题一道都不跑，agent 说「没找到」一律落 `unresolved`；
- 三支名字仍留在 22 分支封闭集里（scripted 独占产出），
  `test_agent_intermediate::Test分支收敛` 逐支钉住「不产」。

前两次：A2a-2 的任务②（自报放弃不进负样本池）、A2a-3 的
`site_search_no_results`（agent 模式没有站搜单元）。**连续三次说明它是
agent 化的结构代价**，不是某条链的疏漏——A3 的 A/B 报表要按它解读：

## INC54 · A2a-4：llm_calls[] 账本 + ESCALATE 升配后端（方案 13 §3.5 G2 / §3.6）

**日期**：2026-10-17
**范围**：`TRAJECTORY_LLM_ESCALATE_*` 三键落地 + `RunRecord.llm_calls` 字段
+ orchestrator 两处接线 + 候选收口统一盖 `ts`。
**依赖**：INC50（`chat_messages` 的 usage/latency 回传）、INC52（两处
`llm_calls=None` 预留接口）、INC53（中间页链接线点）。

### 一句话

A2a 的「最小账本」闭环：agent 循环每次问模型落一行进 P1
（`{ts, caller, candidate, model, latency_ms, prompt_tokens,
completion_tokens, error}`），升配后端从「文档里的三个环境变量」变成
真实可配的第二条 client。

### 三个落地决定（两处有文档依据，一处是新的）

| 决定 | 理由 |
|---|---|
| `ts` 盖在**候选访问收口时**（orchestrator `_stamp_llm_calls`），粒度候选级——同候选各条共享一戳 | 循环体不引入时间源是 INC51 已记的纪律；候选内次序由 list 顺序保证、单条耗时由 `latency_ms` 给出，ts 要回答的只是「这批成本是哪段时间烧的」。超时/异常收口的候选带没盖戳的残条落盘是**诚实残账**，不补假戳 |
| 升配**半配 = 报错**（有 BASE_URL 没 MODEL 或反之，光给 KEY 也算），全没配 = `None` | 主后端「缺件即报错，不猜」纪律的降档版：升配是能力不是依赖，全没配不 fail；但半配说明**想配没配齐**，静默当无升配处理，那一半配置就成了没人读的尸体——想升配的人看到「升配没生效」时不会去查「是不是只配了一半」 |
| 升配 config **继承主后端的 `timeout_s` / `max_tokens`** | 升配接的是同一类请求（agent 指令 + 推理模型的思考预算），主后端上校准过的输出预算原样带过去。继承的是「已校准值」而非类默认值——升配通常是远端大模型，预算被默认值悄悄放大/缩小的代价都是真金白银 |

## INC56 · A3-1：executor_mode 转正 RunConfig 字段 + --executor-mode 参数门（方案 13 §6.1）

**日期**：2026-10-17

### 一句话

### 三个落地决定

| 决定 | 理由 |
|---|---|
| **Orchestrator 删掉 `executor_mode` 关键字参数**（TypeError 用例钉死） | 构造器能绕开 config 传模式的那一天，「这批是谁跑的」就有了两个互相矛盾的答案来源。`agent_backend` 保留 kwarg——「agent 必须有后端」是 RunConfig 看不见注入侧、只有构造 Orchestrator 时才知道的事，产地不同不冲突 |

| argparse `choices=EXECUTOR_MODES` 直接用封闭集本身 | 「参数有哪些值」与「模式有哪些值」一个产地；parser 层面多一个值是改 mode.py 的事，不在两处各维护一份名单（parser 用例比对 tuple） |

## INC57 · A3-2：goto URL 溯源断言（批次级幻觉计数，方案 13 §6.2）

## INC58 · A3-3：D-2/5/6 守卫 + D-9 判据修订落地（INC58）

**日期**：2026-10-17
**范围**：agent 批 D-9 断链修复（think → P1 rationale 槽位）、D-2/D-5 守卫、

**依赖**：INC51-53（agent_loop / 真链 fixture）、INC57（守卫复用其端到端姿势）、

### 一句话

「D-9 纳入 A3 验收」从拍板变成可执行：复核发现 agent_loop 此前**不落任何
rationale**——think 只活在对话历史与 `AgentOutcome.transcript`（都不进 P1），
agent 样本切出来 `rationales=()` → 闸门 `not_run` → D-9 永不触发，拍板会
落空成永远缺分的维度。本刀把 think 装进 P1 `steps[i].rationale` 槽位，
全链（P1 → P2 → 闸门 → D-9 触发）用守卫钉死。

### 断链修复的三个落地决定

| 决定 | 理由 |
|---|---|
| 挂接点在 `_execute` 的 `act()` 后、**成败两条路都挂** | think 是动作前动机，与执行结果无关——「点了但点不动」那一步的动机恰是 D-9 最该看的原文；挂在执行成功路径上会丢掉失败步的判据 |
| 空 think 不挂（rationale 保持 `None`） | 「没说话」与「说了但没落」不混——`align_rationales` 的缺件语义就是稀疏序列 |
| payload `reason="native-think"` | writer 成功时 `reason=""`，两值不冲突；「这条 rationale 是原生 think 还是 writer 产物」在 P1 里有了机器可读标记——同分不同质核对的刻痕，也是 A/B 报表按来源分桶的数据源 |

### 判据层零改动的复核结论（守卫即证据）

- **gates 不需要动**：时序/实体/因果三查吃的是 P2 形状，A2a 的同形纪律让
  agent 形状天然兼容。实测：引用后续步才出现的实体的 think 被
  `temporal_leak` 抓出（hard → failed → D-9 强制走 LLM，judge prompt 里
  带 think 原文）；干净 think 走成本控制口径与 scripted 完全一致
  （passed + 无可判短板 → not_evaluated，不烧 LLM）。
- **首步早退不误伤**：agent 链首条 rationale 步的可见窗口里有进站观察
  （site 链 index 2 窗口=[site_obs, 缺件占位]；中间页链 index 1 窗口=
  [agg obs]——`probe_and_observe`/`enter_site` 都落 goto+观察步）。窗口
  真空的 step 0 早退照走（防御钉）。
- **`check_boilerplate` 的 ≤20 字规则对 think 不对称**（think 是设计出来的
  短句）：只产生 soft finding，不进 GateMark、不改状态，下游零影响——

## 增量五十三 · scout per-Run 聚合（2026-10-19）

### 背景

方案 14 v0.1 §9 实施分阶段 Phase 3——`evaluation/scout/aggregate.py` 落地
+ `trajectory_candidates.jsonl` 产物。

之前 scout 三件套是 per-unit(每条记录 `sample_id` 形式
`<task_id>__<run_id>__<unit>`),LS 上传时把同 `(task_id, run_id)` 的 N 条
上传为 N 个独立 task——per-unit 看不到任务级因果。D14.5 要求上传走
per-Run,所以 scout 输出**新增一条聚合步**:

### 决策

1. **聚合策略 = min**: 四维各自取**最差 unit**的 score,任一 unit 站错
   整条轨迹站错——这是最保守的策略(方案 14 §4.3);
2. **任一维 `score=None` 短路到 `undetermined`**: 不能拿 None 算 min
   (None 参与 min 会抛),而且语义上「这一维没判出来」就足以让整条
   trajectory 不能入正/负例池,走 quarantine;
3. **任一维 `is_veto=True` 短路到任务级 `is_veto=True`**: 任务级 status
   仍为 `scored`(score 全到齐),只是该维打 veto 标记——这与 `scored` 含义
   「四维 score 都到齐」一致;
4. **tags 并集(去重,保序)**: 任一 unit 的 tag 都计入;
5. **evidence_supplement 合并(键冲突取第一个非空)**: 决策记
   `aggregation_log`,给人工复查;
6. **缺 unit 留痕不补**: 缺 unit 是上游 scout 的事,per-run 聚合只能
   如实聚合已有数据;
7. **聚合逻辑独立模块** `aggregate_to_trajectory(units) -> TrajectoryRecord`:
   纯函数,单测独立盯分支;
8. **不 import executor / assembler / storage**: 聚合只动 scout 三件套的
   内存 dict(交接面是格式不是对象,与 T 视图层纪律同款)。
9. **默认不覆盖**已存在的 `trajectory_candidates.jsonl`(与
   `cli build` / `cli task-view` 同款纪律);
10. **三态计数落 `trajectory_stats.json`**: 报告侧直接读,不再二次解析。

   里,被平铺进 `arguments`)。声明与调用对不上,训出来的模型会发**空参数
   的点击**。`fill` 同理少两个参数。
2. **工具清单被手抄了两份**(`assembler/schema.TOOL_SPECS` 与
   `assembler/task_view._TASK_TOOL_SPECS`)。扩到 13 条时必漂。

## 增量六十五 · 动作面按 camoufox 形态落地(P2)(2026-10-20)

**域**:01 采集域 / 跨层
**状态**:实施完成。`camoufox_driver` 的三个动作原语 + 协议改名。
判据**一半达成、一半顺延**(见「验证」)。

### 起因:动作面现在有两个司机,而方向盘只有一个形状

P3-α 落地后 `interactive()` 已经产出 camoufox 的词表(`role+name`),
但**没有一个动作能吃下它**:`click`/`fill`/`press` 在 camoufox 实现里还是
`NotImplementedError`。同时 `PageDriver` 协议的方法名还是 obscura 时代的
`type_text`/`press_key`——**那个名字在撒谎**(暗示逐字追加,两个实现做的
都是设值),`agent_loop._apply` 里因此养着一张**翻译表**把 `fill` 译回
`type_text`。名字与语义对不上,翻译表就是那道疤。

### 改动

1. **`camoufox_driver.click` / `fill` / `press`**:
   `get_by_role(role, name=name, exact=True)` + **先 `count()` 再操作**。
   `exact=True` 钉死在唯一的定位器构造点(`_locate`),不是每个调用点各写一遍。
2. **三态映射**(方案 §4.2/§4.5.4):
   `count==0` → 静默 `not_found`(业务事实) · `count>1` → **不动作**记
   `ambiguous` · `count` 报错 → `DriverError` · 操作报错 → `DriverError`。
   **不解析 playwright 的异常消息**——「元素不存在」与「页面卡住」都是
   `TimeoutError`(F4),靠解析文案分三态是赌版本。
3. **跨面参数抛 `ValueError`,不抛 `DriverError`**:`ref`/`selector` 是
   obscura 面的词汇,拿它调 camoufox 是**接线错误**。而 `DriverError` 会被
   `steps/aggregator` 捕获成 `unreachable_hard`——于是一个接线 bug 变成一条
   **理由通顺的负样本**。对称地 `ObscuraDriver` 收到 `role`/`name` 也抛。
4. **协议改名**:`type_text`→`fill`、`press_key`→`press`,
   `obscura_driver` / `camoufox_driver` / `agent_loop._apply` /
   `steps/site_search` / 全部假 driver 同步,**翻译表删除**。
5. **账目**:`last_action = {op, role, name, outcome[, matches]}`。
   动作返回 `None`,成功与「元素不存在」同形——账目是唯一区分。

### 三条冒烟抓出来的第一手事实(都不是设计出来的,是跑出来的)

1. **`role+name` 是页面级定位:导航之后它不失效,而是可能静默点中新页的
   同名元素。** 对照 `ref`——那是会话句柄,导航后必然报错(F4)。
   第一次冒烟「fill+press 提交搜索 → 直接点上一页枚举的 `link "新闻"`」返回
   `not_found`,**那是运气**:新页恰好没有「新闻」,有的话就点下去了。
   → **任何导航之后必须重新枚举**。冒烟的「页面已变 → 重枚举」是示范实现。
2. **`click()` 返回时不保证导航已经开始。** 动作之后立刻读,可能读到
   **整个旧页**——而旧页在导航开始前**天然稳定**,于是「连续两次读数一致
   算读稳」这种判据**恒真**。加这条判据的当次就骗过了一次(报告停在 `/s?…`,
   0.5s 后才跳到首页);更早一版读到的是过渡态(`title == ''`)。
   → 判据只能是**「URL 相对动作前变了没有」**,且分两段:①等 URL 变化
   → ②等 `(url,title)` 连续两次一致**且 title 非空**(空标题本身也能连读两次
   一致——只要求一致仍会把过渡态交出去)。实现在 `cli._after_action_snapshot`。
   **对整条链的影响不止冒烟**:动作后立刻 `interactive()` 会枚举旧页,
   下一步就拿旧页的名字去动作——与第 1 条是同一个坑的两个入口
   (**一个在名字过期,一个在读得太早**),症状侧记在避坑指南 §8.8。
3. **`ACTION_TIMEOUT_MS = 5000` 让一半的点击直接失败,而根因是「我们在等一个
   没人需要的信号」。** 冒烟连跑三次两次报 `Locator.click: Timeout 5000ms
   exceeded`(日志停在 `performing click action`),现场取证逐项排除了页面因素:
   元素 `count=1`、`visible`、`enabled`、包围盒 12 次采样只变 1 次(首帧后恒定)、
   `elementFromPoint` 就是它本身。而 `click(no_wait_after=True)` **1.1s** 完成、
   跳转正常;`goto` 同一地址 **0.3s**。→ 动作本身快,9–13s 是 playwright 在等
   **它触发的那次导航「完成」**(比 `goto` 的 `load` 苛刻得多)。
   **处置**:`click`/`press` 关掉 `no_wait_after`,动作返回后 `_settle()` 等一次
   `domcontentloaded`(上限 2s),结果记 `last_action["settle"]`=`ok`/`timeout`
   ——**等不到不抛**(点击确实发出去了),但**必须说出来**。

## 增量六十六 · 采集面剩余五条补齐（P3-β）(2026-10-20)

**做了什么**：`CamoufoxDriver` 的 `links` / `extract` / `new_tab` / `close_tab` /
`observe` 全部落地，骨架期的 `_todo` 删除，**协议原语齐了**。
`CamoufoxSession` 从「一个 `_page` 字段」改成**页面栈**。

**三条口径是被实测改写的，不是设计出来的**（详见方案 04 §4.7）：

1. **标签页必须是栈**。`steps/link_check` 的形态是「开 tab → 观察 → 关 tab →
   **回中间页继续采**」；一个 `_page` 关完就无处可回。配套三条不能省：
   只剩一页时**先补一张空白页再关**（否则后续 `observe` 都在读已关闭句柄，
   症状是「页面读不到」，真相是「我们自己关空了」）；`close_tab(id)` 认不出
   就抛（关错页**不报错**）；开页导航失败**把新页收掉再抛**（留着它当前页
   停在 `about:blank`，一次外链失败会连带弄丢中间页的证据）。
   真浏览器冒烟四条语义全对（`pages` 1→2→1、回原页、关最后一页后仍能 `goto`、
   坏域名 `DriverError` 且 `pages` 仍是 1）。
2. **`links` 必须按 href 去重**。实测同一对搜索页：obscura 的 `browser_links`
   恒 `total == distinct`（**131/131、33/33**），而 camoufox 不去重是
   `168/133`、`48/35`——**`links_total` 高 28–37%**。这个数要进 D-2 口径
   （`Observation.elements_total` 的注释解释了为什么「采到的条数」必须落盘），
   两面不同义，并池比出来的分布就是假的。去重保留**第一次**出现的那条。
3. **`extract` 取文本必须 `innerText || textContent`**。实测 bing 结果页
   `li.b_algo h2 a` 的 **10 个锚 `innerText` 全是空串**，`textContent` 才是完整标题。
   只取 `innerText` 的症状是「抽到 10 个空标题」→ `result_titles` 判「长度不等或为空」
   → 判断点 ① 退回 fail-closed：**看着像选择器随改版失效，其实是取文本的路窄了**。

## 增量六十七 · P4 契约迁移：键名是方言的投影 (2026-10-20)

**做了什么**：元素字段从 `{tag, label}` 统一成**槽位** `{role, name}`，而**落盘的
键名按方言投影**——obscura 面仍写 `{tag, label}`（历史 361 份 P2 样本逐字节不变），
camoufox 面写 `{role, name}`。方言只有一条轴：`driver` → `surface_of_driver` →
`toolcatalog.DIALECTS` → 键名/词表。

**为什么不是直接改名**（详见方案 04 §4.8）：

1. obscura 面的 `tag` 装的是 HTML 标签名。改叫 `role` 之后
   `{"role": "a[role=pagedescription]"}` 会让读档人以为那是 ARIA role——
   **名字对了、意思是错的**，报告上看不出来；
2. 盘上 75 份 P1 + 361 份 P2 全是 `{tag, label}`。整批重写等于换一批数据
   （`required` 统计的分母跟着变）；投影才能在「老数据不动」的前提下引入新方言。

**四处结构改动**：

1. **`common/elements.py` 是新文件**（`ELEMENT_VOCAB_*` / `ELEMENT_KEYS` /
   `element_role` / `element_name` / `element_json` / `element_keys` /
   `vocabulary_of_archive_elements`）。放 `common` 而不是 `perception.base`：
   `rationale`、`assembler`、T 都有「不 import 上游」的硬规矩
   （`test_writer.py::TestNoUpstreamImport` 直接钉住），而**读一个存档键名是
   纯格式的事**。`perception.base` 只**用**它、**不转发**——两个导入路径
   迟早各自漂。
2. **`Observation.element_vocabulary`**（默认 `html_tag`）：词表由**驱动实现**
   写、回放按**存档键名**恢复。没有它，收窄后的 `SEARCH_BOX_WORDS` /
   `_SEARCHABLE_WORDS` 在 camoufox 面上恒 0 候选——而「0 个候选」在报告里
   读作「这页真没有搜索框」。
3. **词表逐面两套，认不出就抛**：`SEARCH_BOX_WORDS`（`input/textarea` vs
   `textbox/searchbox`）、`_SEARCHABLE_WORDS`（`button/input/a` vs
   `button/link`）。P3-α 的并集是过渡手段，P4 必须收窄——并集会让「换了执行层」
   与「这页真没有」在观察里同形。
4. **读档侧统一 `element_role`/`element_name`**：`views` / `task_view` /
   `observation_view` / `rationale.writer` / `rationale.lexicon` / `code_scorer` /
   `d3_scorer` / `review_queue` / `replay` / `probe_llm`。写死 `get("label")`
   的后果不是抛错，是**整批 camoufox 样本的元素读成空串**（D-2 全判「引用
   不存在」、实体核查全判「幻觉」）。

**被测试当场抓出来的一处旧错**：`orchestrator._obs_json` 原先由调用方传
`vocabulary`。契约测试第一条就把 camoufox 观察 + 默认 `html_tag` 的组合照出来了
（值对、键错）。改成**从观察自己取**之后，这类错在结构上不可能再发生。

**验证**：

## 增量六十八 · P5：切换机制与判据都就位，**判据没过所以没切** (2026-10-20)

**做了什么**：P5 的三块机制全落地——动作参数的**按面派发**、`run --driver` 入口、
§6.1 六条判据的**机械对账工具**。第一轮真双跑**判 fail**，于是 `DEFAULT_KIND`
保持 `obscura`：**这不是没做完，是证据说现在不能换**。

**为什么 P5 不能只改那一行默认值**：

1. **执行路径还是 obscura 的**：`steps/visit.py` / `steps/site_search.py` /
   `agent_loop._apply` 全都 `driver.click(ref=…)`。camoufox 面**不认 ref**，
   跨面调用被驱动显式拒绝（抛 `ValueError`，刻意的）——改默认值等于让生产链
   第一次点击就炸。
2. **没有判据**：§6.1 的六条此前**没有任何代码实现**。没有它，「换过去效果怎么样」
   只能靠体感——而体感在「理由通顺的假负样本」面前是最不可靠的东西。

**四处结构改动**：

1. **`executor/actions.py` 新增 `target_params(vocabulary, target, *, ref)`**——
   动作参数的**唯一派发点**：`html_tag` 面给 `{ref}`、`aria_role` 面给
   `{role, name}`。两个刻意的取舍：`aria_role` 面缺语义目标抛
   `UnaddressableTarget` **而不是退回 ref**，认不出的词汇表抛 `ValueError`
   **而不是回落成 ref**——两种「退回」都是发一个对面不认的参数，而**报错信息
   不会出现在存档里**。它收的是 `Observation.element_vocabulary`：方言由观察
   自带，与 P4 的 `_obs_json` 同一条纪律，**不许出现第二个来源**。
2. **三个执行点改走它**：`steps/visit.py`（点播放）、`steps/site_search.py`
   （填词 + 点搜索按钮）、`agent_loop._apply`（agent 的 click/fill）。agent 的
   wire format 仍是 `ref`（R3/R4 才迁移），但**驱动层收到的**是对面的参数——
   这条边界不混。
3. **`cli.py` 加 `--driver {obscura,camoufox}`**（默认取 `DEFAULT_KIND`，「切换」
   仍只有一处可改）+ `_driver_for_run`：obscura **整批一条连接复用**（P5 之前就是
   这样，行为一个字节不改）、camoufox **一个 Run 一次 launch**（身份/指纹/cookie
   随 Run 重建——跨 Run 复用会把上一部作品的会话状态带进下一条样本）。
4. **`executor/dual_run.py` + `cli compare-drivers`**：§6.1 的对账实现。分支占比的
   分母是**出过分支的站点数**（不是 run 数）、`body_text` 与 `elements_total` 取
   全观察中位数、拦截率只作读数、负样本原文逐条摊开。`verdict` 只有
   `pass` / `fail` / `incomplete` 三种，**不合成加权分**——「判不了」不许读成「判过」。

## 增量六十九 · 无人值守口径定为 headless（owner 拍板 + 三处代码改动）

**性质**：P5 切换前的一个**开放口径**收口。上一节（增量六十八）记的
「剩下的不是查根因，而是**选口径**」——本节就是那个选择的落地。

### 裁定

**无人值守批次跑 `headless=True`。**

这是对设计方案 04 §4.3「有意选 headful」的一次**口径反转**，
理由三条：

1. **headful 的前提在真无人值守场景里保证不了。** 「机器不锁屏 / 不息屏 /
   不最小化 / 不被完全遮挡」——这正是无人值守的定义（跑一夜、笔记本合盖、
   远程桌面断开都会触发）。B 案只适用于「人守着的桌面」。
2. **差的是两个数量级**，不是「慢一点」：无头实测 **34–71ms**，
   headful 窗口不可渲染时 **5–13s**（上限 13323ms，
   `research/probes/click_occluded.json`）。
3. **口径改动有地方装**：`headless` 是 `fingerprint` 的一个取值，
   批次元数据本来就记 fingerprint 实测值——**既有维度的新取值，不是新分叉轴**。

**A 的前置门**：headless 下的**反爬拦截率**（§6.1 写明「显著变高」是否决项，
而这是 headless 唯一没测过的维度）。**先量一次，再往下走。**

### 三处代码改动

| 改动 | 位置 | 内容 |
|---|---|---|
| 默认无头 | `executor/browser/camoufox_session.py` | `launch(headless: bool = True)`；`fingerprint` 加第九项 `headless` |
| `--headful` 开关 | `executor/cli.py` | `run` / `check` 两个子命令；**缺省无头** |
| 动作预算 5s → 15s | `executor/browser/camoufox_driver.py` | `ACTION_TIMEOUT_MS = 15000`，盖住实测上界 13323ms |

**顺带两件（与口径无关，A/B 都要做）**：

- **超时后不重试**——探针实测**超时那次点击的事件照样落地**
  （页内 `pointerdown` 计数上涨），重试 = 点两次。已在驱动层与
  `orchestrator`（单次 tool 失败不重跑）各有一道，加测试钉住；
- **`steps[]` 记单步耗时**（`duration_ms`）——超时的点击与「页面没有播放器」
  在证据上**同形**（都是一条 `error` 非空的步骤），没有耗时字段就分不出
  5s 与 13s。口径是**整步**（动作 + 随后的观察），失败路径上 ≈ 动作耗时；
  `None` ≠ 0（没走到收口 vs 真的瞬间完成）。
  ⚠️ 落地时撞到一个时钟问题，见下节「顺带第三件」。

### ★ 顺带第三件：`duration_ms` 的计时器在 Windows 上是**粗刻度**

`duration_ms` 落地后，它的守卫测试 `test_耗时_真的量到了_时间`
（睡 30ms → 断言 ≥30ms）**时红时绿**——第一次跑门禁就撞上了。

根因不在测试，在**计时器**：

| 时钟 | Windows 实现 | 分辨率 |
|---|---|---|
| `time.monotonic()` | `GetTickCount64()` | **15.625ms** |
| `time.perf_counter()` | `QueryPerformanceCounter()` | 1e-07 |

`time.monotonic()` 在 Windows 上**不是**高精度时钟——它的刻度是 15.6ms。
于是「睡 30ms」可能被量成 15ms，**耗时字段在 Windows 上是假的**。
已把 `StepLog` 换成 `time.perf_counter()`（两者都单调、只做同进程内相减，
换过去不引入语义变化），并在 `actions.py` 与测试模块文档里写明**为什么**。

**剩下四处没换**（`rule_perceptor` / `llm_perceptor` / `orchestrator` /
`mcp_client`）：它们的 `latency_ms` / `elapsed_ms` **只进账本、不进任何阈值**
（已核：无一处拿它做判定），所以误差是**遥测精度问题，不是判定错误**。
本轮不动它们——那是独立的一项，且不挡 P5。

### ★ 顺带挖出来的第二个问题：判据②③的差值**不可比**

第一轮双跑记的是「`elements_total` 中位数 105.5 → 31.5（−70%）」，
并记了「要查因果（判断点 ① 的输入短一半 → 分支怎么变）」。

**这次梳理发现：那件事现在查不通**——因为两面 `elements_total`
**根本不是同一个东西**（§4.7.4 早就记了「不同义」，但没接到这条后果上）：

- obscura 侧 = **DOM 全量元素数**；
- camoufox 侧 = **ARIA 枚举 kept 数**（词表外 role / 无可访问名 /
  真同名整组丢，§4.5.6 的三处已知偏离）。

**差值里有两层不可比**：枚举基础不同 + 过滤规则不同。
所以「−70%」不是一个可解释的量，**阈值调宽调窄都没意义**。

**要做的是「让两面可比」**：枚举基础对齐（obscura 面也出 ARIA 可访问名，
或 camoufox 面也报 DOM 总数）+ 过滤规则对齐（可见性 / 词表 / 无名三档）。
