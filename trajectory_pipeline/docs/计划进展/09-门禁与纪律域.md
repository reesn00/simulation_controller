**职责：** 测试门禁的计数口径、skip 陷阱、「绿灯 ≠ 验过」这条元纪律。

`test_media_probe::test_elapsed_ms_recorded` 在全量跑里红了，单跑 3/3 通过。

## 仓库根 `tmp_*` 研究产物迁移（2026-10-19 调研 · **2026-10-20 已执行**）

> **✅ 已执行（2026-10-20）**，实施结果见本节末「实施结果与偏差」。
> 下面保留的是**当时的调研原文**（目标布局与五件事仍然有效），数字以实施结果为准。

### 现象

仓库根的 `tmp_recollect_*`（4）、`tmp/`（29）、`.tmp_inc46_probe/`（1）以及
`_test_short.mp4`、`plan-ab.json` 共 **36 个文件 / 约 862 KB，全部已被 git 跟踪**，
工作区干净，且**没有一条 ignore 规则命中它们**。

它们**不是临时残留**，是被文档反复引用的可重现研究产物——但命名落在
`.gitignore` 的临时约定之外，看起来像没 ignore 干净的垃圾。

### 根因

`.gitignore` 的临时约定是**点前缀**，只有 `.tmp/` 与 `.pytest-tmp/` 两条。
无点前缀的 `tmp/` `tmp_*` 天然落在约定之外 → 被提交 → 误读。

冲突是**双向**的：既有产物被误读，且**将来新的真临时物照样会被提交**
（`/tmp/` 根本没被 ignore）。

## `cli.py` God 文件拆分（2026-10-19 · **已评审并纠正，未执行**）

### 一、诊断（成立，且是真洞察）

`cli.py` 2978 行 / 18 个子命令。**不均匀**——三块性质完全不同：

| 块 | 行区间 | 行数 | 性质 | 真实职责 |
|---|---|---|---|---|
| **A 组装 + 分发** | 151–725 | 575 | 真正的 CLI 职责 | `_make_rationale_writer` / `_make_agent_backend` / `cmd_run` / `_run_plan` |
| **B 取证探针流水线** | 727–1641 | **915** | **不是 CLI，是 L0–L6 探针编排** | `_probe_one` / `cmd_probe`…`_mediabrowse` / `FakePageDriver` / `_run_l4_review_async` |
| **C 归档维护命令** | 1643–2661 | 1019 | 薄壳，每个 `cmd_*` 都很薄 | `cmd_gen` / `cmd_review` / `cmd_build` / `cmd_report` 等 12 个 |
| `build_parser` | 2663–2943 | 281 | argparse 固有形状，**不要拆** | 18 × (`add_parser` + 参数 + `set_defaults`)，扁平同源数据 |
| `main` | 2945–2978 | 34 | 分发 | `inspect.iscoroutinefunction(args.func)` |

> 行号说明：1–150 是模块 docstring + import，A 块实际从 151 起。

**B 块是病灶的机制**：`executor/probe/` 包已存在（`ffprobe.py` 498 /
`media_probe.py` 435 / `static_probe.py` 306），但它只装**探针的原子实现**；
915 行的**编排层 + L4/L5/L6 + 浏览器驱动胶水**留在 `cli.py` 里。
包有能力长起来，旁边没人接，于是被 CLI 吸走——这就是 God 文件的成因。

**为什么不先拆更长的文件**：`orchestrator.py`（1558，`run` 349 行）是**流程长**，
`agent_loop.py`（1559）是**分支多**。两者拆分风险高于收益。`cli.py` 是
**职责混**——拆开有天然缝。

### 二、钉死的两条纪律

1. **`build_parser` 与 `set_defaults(func=...)` 必须同源**。
   `test_cli_dispatch.py::test_没有第二份命令名清单` 断言
   `inspect.getsource(cli.main)` 里不得出现 `"args.cmd in ("`。
   分发靠 `inspect.iscoroutinefunction(args.func)` 从函数本身推。
2. **`build_parser` 的 281 行是它该有的长度**——`argparse` 的固有形状。
   拆了反而把 18 个子命令定义分散到 18 处，同源性更难保证。

（同源纪律的正确出处是避坑指南 **§一**；§5.16 讲的是 `@property` 上的括号，无关。）

### 三、原审阅方案的六处错误（逐条带证据）

**① 最严重：把「有 AST 用例守着」当成活约束。**

```
tests/unit/test_executor_mode.py:348
FILES = ("executor/agent_loop.py", "executor/steps/agent_visit.py",
         "executor/steps/visit.py", "executor/orchestrator.py", "executor/mode.py")
```

这是 5 个文件的**显式白名单**，注释写明「本 INC 新增/改动的 executor 侧文件」，
**不扫树**。搬迁新建的 5 个 `executor/probe/*.py` 一个都不在里面 →
**门禁对被搬走的代码彻底失效，且一声不响**。
这就是 CLAUDE.md 那条 gdr/tests 教训的原样复现：
「门禁必须显式枚举每一棵在发展的树，**漏一棵 = 静默失效不可见**」。

**② 「唯一要动的测试是纯路径变更」——错，会静默失效。**

```
tests/unit/test_cmd_mediabrowse.py:44
monkeypatch.setattr(cli_mod, "FakePageDriver", lambda: driver)
```

搬迁后 `cmd_mediabrowse` 在新模块里读**自己的模块全局**，不再经过
`cli.FakePageDriver` → patch 静默脱钩，测试可能照样绿但已不测原本那条路径。
**不能跑绿就算**，必须证明 patch 还咬得住（故意破坏实现看是否变红）。

**③ 「B 块不碰 llm」的论证举错了函数。**
承重的是 `_run_l4_review_async`（`cli.py:1211`）调 `build_reviewer()`，
不是 `_vlm_error_sentinel`。**结论侥幸成立**但理由要换：
`executor/review/multim_vlm.py` 直接用 `httpx` 打 VLM，不 import
`trajectory_pipeline.llm`；`cli.py` 仅有的 llm import 在 209 / 275 / 276
行，**全在 A 块**。按原论证走的人会以为「不直接 import 就算干净」，
**间接链没人管**。

**④ 「组装工厂不能搬进 `executor/cli/` 子包，否则带进 llm 依赖」——不成立。**
`executor/cli.py` 本来就在 executor 里、早就运行时 import 了 llm，搬进子包
不改变这条边。真实理由很朴素：模块 `executor/cli.py` 与包 `executor/cli/`
**撞名**，且这两个工厂本就属于组装边界。

**⑤ `_classify_candidates`「纯判定、不碰状态，适合直接成模块」——不准。**
它是 `Orchestrator` 的**方法**（`orchestrator.py:1173`，128 行），签名
`def _classify_candidates(self, record, ledger)`，吃 `self` 和可变
`RunLedger`；而且它**本来就是从 `run` 里抽出来的方法**，再抽是重复劳动。

**⑥ 体积数字全线对不上（且原方案内部自相矛盾：说 C 块止于 2661，
却说全文件 2618 行——终点超过总长）。**

| 原方案 | 实际 |
|---|---|
| cli.py **2618** | **2978** |
| orchestrator.py 1446 | 1558 |
| ffprobe.py 411 / media_probe.py 384 / static_probe.py 254 | 498 / 435 / 306 |
| llm_perceptor.py 1530 | 未进前十（`agent_loop.py` 1559） |
| 2711 条门禁 | 文档记 **2368 passed / 1 failed** |

对得上的：`run` 349（说 347）、`_classify_candidates` 128（说 126）、
`build_parser` 281（说 279）、18 个子命令 ✅、B/C 块边界 ✅。
→ **块边界可用，体积数字全部重取**（或直接删掉，不影响任何结论）。

### 四、纠正后的三阶段方案

**门禁接线先行（阶段 0，新增，不可跳过）**

1. 把 `FILES` 从 5 文件白名单**改成扫 `executor/` 全树**，让搬迁不再依赖
   手工枚举；或退一步，阶段 1 新建的 5 个文件**先加进 `FILES`**。
   二选一，但**必须在搬代码之前做完**。

**阶段 1：抽 B 块（915 行 → `executor/probe/`，收益最大、风险最低）**

测试半径只有 **2 个文件**（见下表），是三阶段里最干净的切口。

| 新文件 | 承接（cli.py 行号） |
|---|---|
| `probe/orchestrator.py` | `_probe_one`(727) / `cmd_probe`(772) / `cmd_proberun`(803) |
| `probe/static_probe_cmd.py` | `cmd_staticprobe`(900) |
| `probe/mediaprobe_cmd.py` | `cmd_mediaprobe`(991) |
| `probe/mediabrowse.py` | `cmd_mediabrowse`(1107) / `_collect_l4_text`(1171) / `_run_l4_review_async`(1211) / `_vlm_error_sentinel`(1263) / `_mediabrowse_with_driver`(1279) / `FakePageDriver`(1508) / `_dispatch_l6_summary`(1604) |
| `probe/l6.py` | `_dispatch_l6_summary`(1604) / `_urls_of`(1622) |

**别忘了带走 B 块的三条模块常量**：`_BODY_INNER_TEXT_JS`(1166)、
`_BODY_EXCERPT_MAX_CHARS`(1167)、`_SNAPSHOT_EXCERPT_MAX_CHARS`(1168)。
（`_SITATION_MARKS`(723) 在 A/B 边界上，属 A 块，别动。）

`build_parser` 里 `set_defaults(func=cmd_proberun)` 改为从 `probe/` import
后绑定，**`add_parser` 与 `set_defaults` 仍同处 `build_parser` 一个函数体内**。

**阶段 2：C 块 → `executor/commands/`，每个命令自带 parser 片段**

```python
# executor/commands/review.py
def register(sub) -> None:
    p = sub.add_parser("review", help="…")
    p.add_argument(...)
    p.set_defaults(func=cmd_review)   # ← func 与 subparser 同文件、同函数
```

`build_parser` 变成 18 行注册循环 `for mod in COMMANDS: mod.register(sub)`。
纪律 1 仍满足。`COMMANDS` 是**模块清单**，不是「命令名 → handler」表。

**别忘了带走 C 块的模块常量**：`BACKUP_DIRNAME`(2256，被测试 import)、
`_ZERO_SUCCESS_MIN_VISITS`(2554)。

**阶段 3：只做「内聚不改行」**

`orchestrator.run`（349 行）**不拆大**——它长是因为采集流程本身长，
抽出后仍是同一函数串起来，可读性收益有限。可按现有注释分节抽私有函数，
**签名与返回不变**。`_classify_candidates` **不动**（见错误 ⑤）。
