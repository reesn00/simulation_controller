### ✅ 第二批实测结论：判断点 ① 真正根因 = 「窗口与候选集合错位」，不是「空回传」

**2026-10-11 增量十二，第二批（`T013`/`T011`《功夫》，llm 感知，`plan_batch2`）现场数据**
把根因钉死了——**模型根本没「空回传」，它答了 `selected` 非空（answer=True）**。
证据链：

1. 存档 `candidate_source=perceptor`、warning「选出 0/5 个候选，0 个记
   not_play_site，5 个模型未点名」——只有 `_apply_selection`（answer=True 分支）
   会产出；若空回传（answer=None）会走 heuristic 分支，`candidate_source`
   会是 `heuristic`。**模型给了选中项。**
2. 5 个候选全部 `unresolved`（kept=0）——`_apply_selection` 遍历候选时，
   模型选中的 URL **一个都没命中**候选的 `source_href`/`url`。
3. **错位机制**：`extract_candidates` 从全量 111 条 links 过滤出 5 个候选
   （`candidate_filter: engine_self=89, excluded_host:baidu.com=17`，111-106=5），
   而送给模型的窗口 `_link_window = _ordered_links[:20]` **只看排序后的前 20 条**——
   百度把导航（登录/新闻/地图/视频/贴吧/学术/设置…）排在结果之前，
   「含片名」的命中项提前后，窗口 20 条里**只有 hao123 一个候选**，
   爱奇艺/西瓜/搜狐/优酷四个真实候选排在 index≥50，**模型根本看不见**。
4. 模型在窗口里能选的，是「《功夫》完整版免费」这类**站内搜索链接**
   （`baidu.com/s?wd=…`）——它把这些当成「可看的站」选上，但它们是
   `baidu.com` 域，全被候选过滤剔除 → 模型的答案与候选集合零交集。
   **模型不是偷懒，是候选在它的视野之外。**
5. 顺带证实：T2 加的「空回传原文摘录」分支（`raw_selected`/`raw_rejected`
   全空）没有触发——因为根本没有空回传发生。存档里搜不到「模型原文摘录」
   正是这个原因，与改动本身正确与否无关。

**修复方向（下一批）**：候选提取（代码层事实）与 LLM 视野（`_link_window`）
**必须同源**——要么让窗口先包含全部候选（把候选链接钉进窗口），要么
`_apply_selection` 之前先问 LLM「这 20 条里哪些是可看站」再把答案与候选
求交。当前「窗口 ≠ 候选集合」的错位会让任何模型都答不出正确结果。

防空回传的提示词两手（保留，与上节根因无关——那是「候选不可见」，
这是「模型答不答」的另一条防线）：

- 提示词显式禁掉「两个数组都留空」，并要求回 `i`；
- `_render` 给每条链接编号，回指交给代码。

**空回传时把模型原文片段记进 evidence——已做（2026-10-11，增量十二），
第二批未触发（因本批根本没有空回传，见上节「第二批实测结论」）。**
这个改动仍然保留：万一将来真出现 selected/rejected 全空（比如换引擎、
输入退化），`_select_play_sites` 空回传分支会把模型原文**先 `strip_think`
再截前 120 字**记进 evidence（`_excerpt`，与 `_why_unparsable` 同一条红线；
测试 `TestNoConclusionVsUnmatched` 守着「剥 think 后的原文能看见、思考本身
不落入」）。

这一步**曾经被一条红线破口挡住**（解析失败路径会把 raw CoT 写进 evidence），
该破口 2026-10-11 已修（增量十一第四项）——所以现在可以安全地做了。

**⚠️ 本批结论修正了「下一步」的指向**：之前以为「拿到原文片段就能分三类」，
实测发现空回传分支根本没走到——**当前 ① 的瓶颈不在模型答不答，而在候选
根本进不了模型视野**。所以下一批的验证目标不是「等原文片段」，而是先修
「窗口 ≠ 候选集合」的错位（见上节修复方向），否则再跑多少批都是同一个
「模型选了、答案对不上候选」。

## 解码损坏的采集侧防护（2026-10-11 落地）

清空前有一批存档的观察正文含 U+FFFD（`mojibake` ×30，涉 9 份），
成因当时**没查清**就删了数据——那批数据原文不可恢复（字节丢了），
但成因已查清并落地防护。

**实测成因**：`tv.sohu.com` 响应头**不带 charset**，编码只由 HTML 里唯一的
`<meta charset=GBK">` 声明，而实际字节确实是 GBK——**声明与实际一致**。
损坏发生在**页面内容经 MCP 传出时被按 UTF-8 处理**：按 GBK 严格解码 0 个替换符，
按 UTF-8 解则同一段产出数千个。

⚠️ **损坏是局部的**：同一段里中文与 ASCII 都好，只有中间夹着一小片烂掉。
「整页换个编码写错了」这个直觉判断在这里**是错的**，
而它正是让第一次排查绕远路的原因。

**防护落点**（三个变异已封：阈值函数 + 采集侧两个接线点）：

| 环节 | 位置 |
|---|---|
| 检测 | [`dom.is_mojibake`](../executor/dom.py) ——阈值 `MOJIBAKE_MIN_COUNT = 3`，**不是「出现即降级」** |
| 记降级 | [`obscura_driver`](../executor/browser/obscura_driver.py#L171-L184) → `body_mojibake` / `title_mojibake` |
| 契约 | [`schema`](../assembler/schema.py#L486) 区分「键缺失」与「键在但内容是烂的」 |
| 门禁信号 | [`integrity`](../executor/integrity.py#L99-L110) 的 `mojibake` / `evidence_mojibake` |

**为什么拦在采集侧而不是闸门里**：坏正文一旦进感知层，rationale 闸门的
实体核查会把「模型引用了页面上真实存在、但已损坏的实体」判成**幻觉**
——**凭空造出一条理由通顺、格式正确、不报任何错的负样本**。
而 [`gates.observation_shortfall`](../rationale/gates.py) 见到 `degraded`
非空就拒绝判幻觉（rubric D-9 边界规则），所以只要采集侧记一次降级，
闸门侧就自动获得保护——**不需要在闸门里再加第二道门**。

这与「观察被截断 → 不判幻觉」是同一条纪律：**判断建立在残缺事实上时，
正确做法是记不可判定，而不是拿残缺事实去指控。**

⚠️ **阈值定在 3 的理由**：单个 U+FFFD 可能来自页面真实内容（页面上就印着一个 �），
正文里偶发一两个不该让整份观察降级成不可判定——那会把「观察不充分」这条
降级路径变得过于宽松，最后人人都忽略它。实测坏站一个正文里有**数十个**，
好站是 0，两侧都离得很远。

**尚未验证**：防护只在离线测试里成立，**没被真实站点触发过**。
第一批（2026-10-11）3 个站的正文全是 0 个 U+FFFD，**一次都没触发**——
「已修」目前仍只是离线成立。要证伪需要跑一个已知会坏编码的站
（`tv.sohu.com` 是已知案例）。
