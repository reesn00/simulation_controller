## 二、计数与记账

> **计数说谎比不计数更坏。** 不计数让人知道这里有损失；
> 说谎的计数让人**基于错的数字下结论**，而且毫无察觉。

### 2.1 字段名与字段值不同语义

**症状**：`gen` 打印「排除 98 个」，而 `--all-modes` 下**一个都没排除**。

**根因**：`excluded_by_skeleton_mode` 填的是**全库 mode 分布**。
字段名说 excluded，值里却含「未排除」的项（81 个 single_title 是被用上的）。

**后果**：`--all-modes` 时报「98 次因骨架模式排除」；读的人会以为真排掉了 98 个，
进而以为「剩下 81 个都被用上了」，而实际用的是 98 个里的任意若干。

**纪律**：
- `excluded_by_skeleton_mode` 只记**真被排除**的（判据取 `runnable_in_w1` 属性本身，
  不硬编码模式名——属性才是真值源）
- `mode_distribution` 记全库分布，无条件
- 加**自洽性测试**：排除数 + 可跑数 == 全库
→ `taskgen/sampler.py`

### 2.2 静默剔除让损失不可见

**症状**：存档写着 11 个候选，没人知道引擎原本给了 50 个链接、其中多少被规则扔掉。

**纪律**：剔除**必须带原因计数**。`extract_candidates(..., stats=...)`
是可选出参，填 `{"excluded_host:baidu.com": 16, "duplicate_host": 1}`。
`engine_self` 与 `excluded_host:<root>` 分开记——读的人处置不同。
→ `executor/steps/search.py`

### 2.2b 报表统计了「算过但没落盘」的条目 ⇒ 报出来的成功数比盘上多

**症状**（2026-11-13，真实批次实测）：精炼批次跑完，终端报
「成功 55 条 / 规则层够用 17 条 / 失败 5 条」（合计 **77** 条），
而盘上 5 份旁挂里的条目加起来只有 **62** 条（47 / 13 / 2）。
**差 15 条**——那 15 条在批次预算用尽时算过，但那份档案**整份没落盘**。

**根因**：计数的 `+= 1` 写在**每条**处理之后，而「这份档案要不要落盘」
是**处理到一半**才判的（预算用尽 ⇒ `continue` 掉整份）。于是
「算过的」与「写下去的」被**同一个计数器**记成了一件事。

**为什么难查**：报表上的数**比真实产出大**，而不是小——
「多算了」看着像好事，而真相是有一批工作白做了（钱花了、词没进语料）。
而且这批工作**在旁挂里查不到**（没落盘）⇒ 从产物反推报表也对不上。

**纪律**：
- **落盘统计与「算过」分开记**。落盘的才进最终统计；没落盘的**单算一个
  数字**并**印出来**（「另有 N 条已算但没落盘」）。
- **批次级丢弃必须逐份报**（哪一份、因为什么、丢了几条），不能只报总数——
  总数对不上时，得能立刻定位到是哪一份。

**同族第二例（2026-11-13 同一条命令）**：**计划数**比真发请求多 **45%**
（说「约 35 次」，真发 24 次）。根因同上：真跑时**同一份正文只发一次**
（正文一样 ⇒ 精炼结果一样），而计划阶段**逐条算**——可它打印的字明明写着
「正文键去重后逐份算的」。**字与代码不符**，而这个数是运营方用来估
`--max-calls` 的（估大了 ⇒ 预算不够 ⇒ 一半档案被丢弃）。

⇒ **凡是印给人做决策的数，必须与真正执行的那条路径同口径**；
「去重」这类优化**两边都要做**，不能只做一边。

→ `executor/cli.py::cmd_refine`（`tally` / `discarded` / `would_call`）

### 2.3 缺字段 ≠ 空值

**症状**（三次，同一款病）：

1. persona 切片全落到 `(无 provenance)`——分不清「不是 taskgen 跑的」与「taskgen 没生效」
2. `report` 把存量存档（字段引入前跑的）算成「可跑」——
   而那批**恰恰最不该算**（被验证码页拦下的）
3. **D-6 把 20 条老存档判成「播放页 URL 缺失」**——
   而那 20 条的 `play_page_url` **键压根不存在**（字段 2026-10-10 才补），
   结论本身完全正确

**根因**（三个各不相同，但都是「把两件事折叠成一个值」）：

1. `provenance.get("persona_id")` 与 `data.get("search_blocked") or ""`
   把「字段不存在」与「字段为空」折叠成同一个值。
2. 同上。
3. ⚠️ **而这条最隐蔽**：缺字段信息在 **`to_json` 之后已经丢了**——
   `OutcomeRef` 无条件输出 `site_url`/`play_page_url`，
   老存档的「键不存在」渲染成 `""`，与「键在但值为空」**完全同形**。
   于是评分器里的 `_has_key(outcome, "play_page_url")` **恒为 True**，
   守卫写了、看着在、实际从不生效。

**纪律**：
- 空 `dict` 的含义**固定为「不是 taskgen 跑的」**，绝不兼表「没生效」
- 存量存档缺字段时，用**同一个判定函数**从存档里确定性重算，
  并在输出里**标注「存量存档重算」**
- **经过序列化之后，缺字段信息必须单独记一条**
  （`OutcomeRef.p1_missing_fields` 逐条记「P1 里没有这个键」）。
  靠序列化后的形状推断「键在不在」是**恒过的假检查**。
- **判缺失之前先问一句：这个键在源头真的存在吗**——
  拿一个本就不该存在的字段去核，得到的是**采集器缺件**，不是**轨迹不合格**。

→ `executor/plan.py`、`executor/cli.py::cmd_report`、`assembler/schema.py`、
`evaluation/scorers/d6_scorer.py`

### 2.4 中位数混了不同尺度的观察：整体读数会**翻号**

**症状**（2026-10-21 第二轮双跑）：`compare-drivers` 的判据②③ 报
「B 面正文更长」，按族拆开却是**三个族里有两个 B 更短**；
判据③' 的共享口径另报「播放页族 A 60 / B 35（B 更少）」——
**两个判据指向相反方向**，而报表上只有一行数。

**根因**：「一个观察」不是同一个尺度的东西。`search` / `step` /
`visit_step` / `site_obs` / `player_obs` 五族，正文长度与元素数
**差一个量级**。把它们塞进**同一个中位数**，得到的数**由各族占比决定**——
某族多一条，整体就翻向。

**纪律**：
- 跨族比大小**一律分族**：报告按观察槽族分列，**族内比，族间不比**
- **不出「总计行」**：各族**不投票、不合成**——合成就是把不可比的数加起来
  （与「禁止投票/集成」同一条纪律）
- 「归因表」里各档的**中位数不可相减**：各中位数来自**不同的观察**
  （实测 candidates 52 − hidden 3 ≠ visible 31）。要逐观察看落差，
  跑 `research/probes/inc72_ladder_identity.py`
→ `executor/dual_run.py`、`executor/browser/element_basis.py`

### 2.5 「没测出来」不是「测出来是好的」——**缺基线的项不许进分母**

**症状**（2026-10-21 增量七十四）：判据⑥ 的动作重放读数里，
3 条旧批次存档的条目**没有可比基线**（既没标题也没正文长度）。
若把「页面没漂」写成 `False`（= 没漂），报表上就长成
「3 条**验过**，页面没漂，定位到了」——而真相是**这 3 条从来没比过**。

**根因**：「没读到」与「读到的是这个」在布尔值里**同形**：
`False` 既可以是「读到了，确实没漂」，也可以是「没读，漂不漂不知道」。
把两种情况塞进同一个 `False`，**失败就消失了**。

**纪律**：
- **缺基线 ⇒ 记 `null`（未知），不许记 `False`**；分母只取「**真的量到了**」的条目
- 归因要**三列并排**：读数 × 当时在不在采集面阶梯里 × 页面漂没漂——
  少一列就会把「站点改版」误记成「动作不可移植」
- 同一族的坑：**拦截率不分桶**（§3.7）、**中位数不分族**（§2.4）、
  **降级表不可相减**（§2.4）——都是「把不同口径的数字摆到一张表上」

→ `research/probes/inc73_action_replay.py`

### 2.6 分母写 191 而实际只有 188：**行数 ≠ 站点级行**

**症状**（2026-10-23，方案 16 C-03/C-04）：计划文档、冻结 manifest、
`cli agreement` 三处报的头条分母**互不相同**——
文档写 191、`manifest` 写 131、agreement 打 `n=188`（v7 是 128）。
**谁都没算错**，但按任何一个数字去和旧基线比较都会偏。
同一批数据还会同时打出两个百分数（旧口径 `216/289 = 74.7%`、
头条 `139/188 = 73.9%`），**更让人以为有一边算错了**。

**根因**：golden 里有两种行——**站点级行**与 **trajectory 行**
（`source_kind == "p2_sample"`）。两者都在 `golden_id` 里、都进池，
但 D-10 判的是「**对站点的结论**」，trajectory 行没有可判的站点结论 ⇒
**不进 D-10 分母**。v6 的 191 行里有 3 条 trajectory ⇒ 站点级 188；
holdout 103 行里同样有 2 条 ⇒ 101。289 = 188 + 101 只数站点级。
**两个百分数之差不是误差，是分母不同**（289 = 三档站点级合计，
188 = 只算调参池），两个数都留着、都标口径才有用。

**纪律**：
- **报分母必须带单位**：「191 **行**（188 站点级）」——只写一个数就会被下一个人当成另一种
- **分母只有一处真源**：`agreement` 的 `d10_denominator.n` / `site_rows_by_split`。
  往文档里抄数之前**先跑一遍命令**，别从上一版文档转抄
- **新旧口径同时输出、各自标名**（`d10_denominator` vs `legacy_denominator`），
  不许只留一个——历史基线（216/289）要能继续对得上
- 同一族的坑：**缺基线的项进分母**（§2.5）——都是「分母装了什么」的问题

→ `evaluation/golden/builder.py`（`cmd_agreement`）· `evaluation/golden/splits.py`
