### 8.29 写给上游的表达式**求不出值**：整批 0 候选，**且零报错**

**症状**（2026-10-27，camofox 面第一批 10 条）：每一条都是

```
环节① 取回候选 0 个（links=99，过滤记账 {'degraded': 1}）
搜索页未提取到候选，run 提前结束
```

**零报错、零异常退出码**，链接数 `links=99` 说明页面**读得到**（网络没问题、
浏览器没问题），只是**候选一个都没留下**。10 条任务全在第一步夭折。

**根因**：表达式写成**没被调用的函数字面量**（`() => …`）。
上游把它交给 Playwright 的 `page.evaluate(expression)`（上游 `server.js` 的
evaluate 路由），而 **Playwright 收到字符串时按「表达式」求值**——
`() => …` 求出来是**函数对象**，序列化后是 `undefined`
⇒ 响应里**没有 `result` 键** ⇒ 本层读到的是 `None`
⇒ 文档代号恒为空串 ⇒ **每次观察都被判成「读到一半」**
⇒ `degraded=['nav_unsettled']` ⇒ 环节① **返回 0 候选**。

⚠️ **为什么整批 10 条一起死、且看不出异常**：
「读到一半」是**代码层的 fail-closed**（跨了文档就不判）——它**保护**了判断，
但把**能力问题**误报成**时序问题**。两种在 P1 存档里**同形**
（都只写 `nav_unsettled`）⇒ **存档里没有的东西，就去现场拿**
（本轮是新增探针 `research/probes/camofox_nav_probe.py` 重演 `observe()`
的读序，逐段打**文档代号**）。

**纪律**：

1. **送上游的每一段 JS 都必须「求得出值」**——写成**立即调用的 IIFE**
   （`(function(){return …;})()`），**不是**裸函数字面量。
   本仓其余 JS 片段（`_PAGE_TEXT_JS` / `_LINKS_JS` / `SHARED_DOM_JS`）
   **本来就是 IIFE** ⇒ **新写的片段照着它们的形态写**，别凭直觉写箭头函数。
2. **判据要能机械挡住这一类**：契约测试 `test_发给上游的表达式都不是函数字面量`
   盯住**每一段** JS（含**生成**出来的 JS），假会话按上游语义求值
   （函数字面量 ⇒ 返回 `None`）。
   ⚠️ 这条测试**复刻的是上游的语义规则**，**不是**一个 JS 引擎——
   它只判「是不是函数字面量」这个**形状**。
3. **「读不到」与「读到空」必须分得开**：上游 `result` 键**不存在** = 没测到；
   `result` 存在且为 `null` = 页面里就是 null。**两者混成一个 ⇒ 判据恒假**。
4. **失败模式先分「时序」与「能力」**：症状同形时，用**现场读数**分——
   「文档代号一直在变」= 时序；「文档代号恒为空串」= **能力**（读不到）。
   **等**解决前者，**改代码**解决后者。

→ `executor/browser/camofox_driver.py`（`DOC_STAMP_EXPR` 写成 IIFE）·
`tests/unit/test_camofox_driver.py`（`test_文档代号表达式求得出值` /
`test_发给上游的表达式都不是函数字面量`）·
`research/probes/camofox_nav_probe.py`（现场取证）·

### 8.30 指纹在**导航之后**才有，存档记录在**导航之前**就构造好了：指纹恒空

**症状**（2026-10-27，camofox 面第一批 10 条）：跑完逐条打开存档，
每一条的 `fingerprint` 都是 `{}`——**不是缺字段**（键在），
是**记好的空对象**。

**零报错、零异常退出码**：整个批次看起来**完全正常**
（候选、访问、分支、动作流一应俱全），只是**批次元数据**是空的。

**根因**：**读指纹的时机早于它被测出来的时机**。

| 时刻 | 发生了什么 | 读到的指纹 |
|---|---|---|
| `RunRecord(...)` 构造 | `fingerprint=dict(getattr(self._driver, "fingerprint", {}) or {})` | `{}` |
| `await self._driver.goto(url)` | camofox 面**第一次建页**时才测身份（`CamofoxDriver.goto` → `session.measure_fingerprint()`） | 这之后才有读数 |

⚠️ **为什么旧执行层上看不出来**：camoufox 面在 **launch 那一刻**
就把 9 项指纹填好了 ⇒ 构造记录时读到的**已经是读数**。
camofox 面的浏览器由**上游服务**持有，本仓**第一次拿到页**才能测身份
⇒ 构造记录那一刻**必然读不到**。
⇒ **换执行层时，「什么时候才有」这个前提要重新核一遍**——
旧执行层对，不代表新执行层也对。

⚠️ **为什么「空 dict」最坏**：它与「驱动根本没有指纹」（obscura 是远端 MCP，
本地看不见）**长得一样** ⇒ 读档人会把「**没记到**」读成「指纹为空」。
而指纹**事后补不回来**（只在 launch 那一刻确定）⇒ 这一批的执行层几何
**永远丢了**，而报告上**看不出任何异常**。

**纪律**：

1. **补读要「紧跟第一次导航」**：那时指纹已落进驱动缓存，且此后不再变
   （`measure_fingerprint` 命中缓存就返回）。
2. **「有没有指纹」与「什么时候才有」是两个问题**——
   前者写在协议里，后者**只能实测**：钉它的测试要**复刻懒测的形状**
   （测之前是空、测之后才有值），不是钉一个恒有值的假驱动。
3. **存档里恒空 ⇒ 当成没记**：`fingerprint` 空 dict 与 `driver` 空串
   **都不是「未知」**，是「没记」⇒ 跨批次对读时**不可判定**，
   不要拿它说「这批指纹没漂」。
4. **换执行层时，把「批次元数据」的读法重新核一遍**——
   凡是「旧实现里恰好对」的前提，都要单独测。
5. **两个构造点都要补**：`RunRecord(...)` 全仓只有两处构造——
   批次的（`executor/orchestrator.py`）与诊断命令 `proberun` 的
   （`executor/cli.py`）⇒ **补读也要两处都做**。
   只修生产链、把诊断工具漏掉 ⇒ `proberun` 落出来的存档照样是空指纹，
   而它恰恰是**人工看现场的那一份**。

→ `executor/orchestrator.py`（第一次导航之后补读 `driver.fingerprint`）·
`executor/cli.py`（`proberun` 的补读点，在 try/except **之外**——
炸了也要补，因为炸在 goto 之后时指纹已经测到了）·
`tests/unit/test_visit.py`（`Test指纹补读`：懒测驱动 ⇒ 存档里必须有读数）·
`tests/unit/test_camofox_driver.py`（`Test指纹时机`：测一次就够）·
[03-数据契约 P1 §](../03-数据契约.md)

### 8.31 页级状态**不跨页**：上一页的降级标记挂到了这一页的观察上

**症状**（2026-10-27，camofox 面第一批 10 条）：一次**做不到的按键**
（按 `F5`）之后，**之后每一次导航**之后的观察都挂上了
`degraded: ["press_unsupported"]`——**那一页什么也没缺**。

**量到的比例**：T004 一条里 **39 个观察有 7 个带这个假降级**（**18%**）。

**根因**：驱动的 ``last_action`` 记着「**上一页**上那一次动作的结果」，
而 ``observe()`` 拿它判「这一页有没有降级」——但 ``last_action`` **不随导航作废**
（导航只清了 ref 表那几个）。

⇒ **拿上一页的账记这一页的头**——与 ``observe()`` 里对 ``last_enumeration``
早就防过的那一族错误**一模一样**，只是漏了 ``last_action`` 这一样。

⚠️ **为什么这不只是「存档里多个标记」**：``degraded`` **直接进 agent 的输入**
（`agent_loop._render_observation` 把它投影给模型）⇒ agent 以为
「这一页没读全」；而且闸门侧 ``gates.observation_shortfall``
**见到 ``degraded`` 非空即拒绝判幻觉** ⇒ **那一步的实体核查被静默关掉**。
⇒ **假降级 = 假证据 + 静默降级的闸门**，两者都落在下游。

**纪律**：

1. **页级状态只能活一页**：ref 表 / 上游句柄表 / 目标索引 / 剔掉清单 /
   填值缓存 / **动作结果**——**一起清**，漏一样就是「上一页的账记到这一页头上」。
   ⇒ **清它们的地方要收在一个函数里**（本仓：`CamofoxDriver._reset_page_state`），
   别在三个方法里各抄一遍（抄三遍就一定会漏一样——这次就漏了）。
2. **「换页」清状态的范围要含「动作结果」**：动作结果不是元素，
   容易觉得它「跟页面无关」——**它恰恰是页级的**（它是「这一页上那一次动作」）。
3. **守卫要复刻真实形状**：钉「降级只出现在降级的那一步之后」，
   而不是钉「观察里没有降级项」——后者在降级真发生时会误报。

→ `executor/browser/camofox_driver.py`（`_reset_page_state`：六个页级状态一起清）·
`tests/unit/test_camofox_driver.py`（`Test降级不跨页`：换页 / 开新页两条）

### 8.32 池行的 `golden_id` 里嵌了**行号**：池一增删，**人核标签就静默掉线**

**症状**：重建 `candidates.jsonl` 之后，**6 条人核标注不见了**——
D10 分母从 **289 掉到 283**，而报表上**看不出原因**（只是「条数少了」）。

**根因**：`evaluation/golden/builder.py::_scan_negative_pool` 造池行 id 时用

```
{task_id}__{run_id}__{url_hash}__neg{i:02d}
```

那个 `i` 是 `enumerate(rows)` 的下标 ⇒ **它在 `negative.jsonl` 里的行号**
⇒ **id 里嵌的是「计数」不是「身份」**。

⇒ **池里任何一次增删**（并池 / purge / **重跑**）都会让它**后面所有行**的 id
前移或后移 ⇒ **人工标注是按 `golden_id` 挂的** ⇒ **挂不上 ⇒ 标签掉线**。

⚠️ **为什么难发现**：标签**没被删**，只是**挂不上**了
⇒ 报表上表现为「分母小了几条」，**没有任何一条报「标签掉了」**。

**实测**（2026-10-27，本轮两次 purge 之后）：池里这 6 行是
`neg151/152/153/156/157/160`，`annotations.jsonl` 里记的是
`neg152/153/154/157/158/161` ⇒ **整体差 1**。
**证据一条没少**（task / run / URL 全没变，**只有序号变了**）。

⚠️ **后缀不能删**：同 `(task_id, run_id, url)` 可以挂**不同分支**的两行
（实测池里有 **2 组**）⇒ 需要一个区分符。
⇒ **区分符要用「身份」，不能用「位置」**：分支本身就在池的去重键里
（`(task_id, url, branch)`）⇒ 同 `(task, run, url)` 内**分支唯一**
⇒ `__neg_{branch}` 天然去重，且**池增删不影响它**。

**纪律**：

1. **id 里不许嵌计数**（行号 / 序号 / 全局计数器）——**嵌了就一定会漂**；
   要唯一性就用**身份**（分支 / `run_id` / hash）。
2. **改 id 方案 = 改人核数据的键** ⇒ 那是**动人的东西** ⇒ **要人签**；
   而且**迁移与改代码必须同批做**（只改代码不迁移 ⇒ 标签当场全掉）。
3. **重建候选集前先试算**：拿新旧两套 `golden_id` 求差集，
   **差集里有人核行 ⇒ 停**——这比事后看「分母少了几条」便宜得多。

→ `evaluation/golden/builder.py::_scan_negative_pool`（`__neg{i:02d}`）·
台账 §M-42 详解 / §Q-22（**代码与标注都还没动**，等 owner 拍板）

### 8.33 上游销毁了那一页 ⇒ 一串「站点打不开」的假负样本

**症状**（2026-10-27，camofox 面那批 10 条）：**一个候选连炸 9 次**，
9 次的失败原因**一字不差**是

```
导航失败（传输层）: camofox 导航失败: camofox tool camofox_navigate
返回错误: camofox error: 404: {"error":"Tab not found"}
```

这 9 条全被记成 `unreachable_hard`（「站点打不开」）
⇒ **9 条理由通顺的假负样本进了池**，而那个站点**一次都没被试过**。

**零报错**：整个批次**没有一条异常**、退出码正常、每个候选都有分支都有理由
⇒ 门禁全绿、报表上只有「这个站点打不开」。

**根因**（读上游 `server.js` 得到的，**上游不许改**）：上游在
**操作超时 / 连续超时 / 页崩溃 / 锁队列超时 / 建页失败**时**销毁那一页**
（`destroyTab` / `destroyTimedOutTab`），而**销毁不通知客户端**
⇒ 客户端手里的 `tabId` 成了**死引用** ⇒ 再导航就是 404，**每一次都 404**。

三层叠加才成为级联：

1. **上游**：销毁页**不通知**客户端——上游行为，改不了 ⇒ 只能容忍。
2. **适配层**：把上游的结构化错误**拍扁成一段文本**
   （`camofox error: {status}: {body}`）⇒ **机器可读的字段全丢了**。
3. **驱动层**：错误文本**只留前 400 字** ⇒ 结构彻底没了
   ⇒ 驱动**分不出「这一页没了」与「站点打不开」** ⇒ 只能猜。

**而级联之所以是级联**：一次访问的顺序是 `goto` → `new_tab` → 动作
⇒ **`goto` 失败就走不到 `new_tab`** ⇒ 页栈顶**永远压着那一张死页**
⇒ 后面每一次 `goto` 都撞同一张死页
⇒ **一个候选炸 9 次，9 次一模一样**。

⚠️ **为什么难发现**：失败原因**完全一致** ⇒ 看着像「这个站点真的打不开」
（**理由通顺**）；`unreachable_hard` 是**合法的既有分支**
⇒ 不触发任何异常、不触发门禁；而**「这个站点根本没被试过」这件事
不写在任何地方**——存档里只有一句「导航失败」。

⚠️ **为什么这不是「站点打不开」**：坏掉的是**我们手里那一页**，
不是**目标站点** ⇒ 它是**执行层会话失效** ⇒ 采集失败**不是站点结论**
⇒ 记 `unreachable_hard` 就是**把我们的故障写成了站点的事实**。

**上游其实已经写好了处置**：错误体里有 `code` / `retryable` / `recovery`，
其中 `recovery: "create_new_tab"` 的意思就是「这一页没了，换一张」
⇒ **不用猜，读它**。（但见上：适配层把结构拍扁了、驱动还截断了 ⇒ 到不了眼前。）

**纪律**：

1. **执行层故障不许记成站点结论**——失败分三档：
   传输层失败（**站点事实** ⇒ `unreachable_hard`）/
   **执行层会话失效（**我们的故障** ⇒ `unresolved`，不进池）**/
   语义判断（感知层的事）。**档位要在异常类型上分开**，
   别都塞进一个 `DriverError` 里再靠消息文本判。
2. **不要靠错误文本判断**：上游的结构化字段**先解析出来**，文本只留给人看；
   **截断先想清楚截的是头还是尾**（原因常在末尾）。
3. **页没了要能自愈，而且自愈要留痕**：丢弃死页 → 开新页 → **同一个 URL 重来**；
   自愈次数**进存档的运行级 warning**——**不许静默**（静默自愈 = 又一次
   「看起来正常」）。
4. **只有导航能自愈**：动作目标是**页级 ref**，换页之后重放会点到**别的元素**
   ⇒ **动作失败不自愈**（记会话失效）。
5. **自愈不是万能**：换页也失败 ⇒ 记会话失效 ⇒ `unresolved`（**不进池**），
   **不是** `unreachable_hard`。
6. **上游不许改**：处置一律做在**本仓**（适配层解析 + 驱动自愈 + 语义分档）。

**实测**（真上游探针，2026-10-27）：在**上游那一侧**把当前页关掉
（本地栈照旧攥着它——这正是上游销毁页之后的真实状态），再导航同一个 URL
⇒ **换了一张新页、同一个 URL 重来、页面真的加载出来了**（title=百度一下，你就知道）
⇒ 修好之前，这一步就是一条 `unreachable_hard` 假负样本。

⚠️ **契约测试拦住了「动态分支」的写法**：`branches.py` 的 22 类是**封闭集**，
而**无题记账点的分支必须静态可定** ⇒ 那一行要写成**两个字面量**
（`unresolved` 与 `unreachable_hard` 各一次 `ledger.record`），
不能拼一个变量——**可判定的分支比好看的代码重要**。

### 8.34 上游把「建页」与「导航」塞进**同一个路由** ⇒ 那个路由失败**证明不了站点打不开**

> ⚠️⚠️ **本节有两处口径已被 M-44 覆盖（2026-10-27 同日），以 §8.35 为准**：
> ① 下面表格里「导航路由 ⇒ 站点事实（DNS/**超时**/证书）」⇒ **超时与证书错
> **证明不了**站点不可达**（§8.35 纪律 2：机器码才算证据，
> `NS_ERROR_NET_TIMEOUT` / `kind: TimedOut` **两侧都不算**）；
> ② 「换页成功、导航失败 ⇒ 仍然是站点事实 ⇒ 记 `unreachable_hard`」⇒
> **只有机器码证明的那部分**（DNS 解析失败 / 连接被拒）才算站点事实，
> 其余（超时 / 打断 / 空响应 / 建页失败 / 会话失效）⇒ **`unresolved`
> （不进池）**。
> ⇒ 本节**仍然成立**的是它治的那件事：**建页路由的失败 ⇒ 执行层的故障
> ⇒ 不能当站点事实**（那条判据与 M-44 同向，不冲突）。

**症状**（2026-10-27，camofox 面那批 10 条，第 4 轮）：`T048` 的一条候选
被记成 `unreachable_hard`（「站点打不开」），evidence 是

```

返回错误: camofox error: 500: {"error":"tab create timed out after 30000ms","retryable":false}
```

⚠️ **而同一批的 `T038` 进到了同一个 iqiyi 站的正片页**
（`https://` 变体：「已进入《功夫》正片页并触发播放」；同一个 `http://` 变体
落的是「站点遍历超时（>180.0s）」⇒ `unresolved`，**没进池**）
⇒ **站点是通的** ⇒ 那条 `unreachable_hard` 是**假负样本**，
且**已经进了负样本池**（`negative.jsonl` 第 300 行）。
⚠️ **更硬的反证在老批**：`T054__93f110b6`（camoufox 面）**真打开过同一个 URL**

**根因（读上游 `server.js` 得到的，⚠️ **上游不许改**，owner 裁定 A2）**：
上游的 `POST /tabs`（`camofox_create_tab`）把**建页**与**导航**
塞进**同一个 30 秒预算**（`withTimeout(..., tabCreateRequestTimeoutMs(),
'tab create')`）⇒ **那个路由失败证明不了站点打不开**——
也可能是**建页本身**卡住了（浏览器起不来、并发排队）。

⚠️ **两种失败在错误体里同形**（实测，2026-10-27）：

| 失败 | HTTP | 体 |
|---|---|---|
| 导航到 DNS 不存在的域名 | 500 | `{"error":"page.goto: NS_ERROR_UNKNOWN_HOST…","retryable":false}` |
| 建页（带 URL）打同一个域名 | 500 | **字面同上** |

**都没有** `code` / `recovery` ⇒ **光看错误体分不开**
⇒ 「按错误文本判归属」这条路**走不通**（§8.33 的纪律在这里**不够用**）。

⇒ **唯一能分开的是「走哪个路由」**。而上游**支持**分开：
建页路由在 `url` 为空时**只建页不导航**（`server.js` 的 `if (url)`），
导航路由（`camofox_navigate`）**只做导航** ⇒ **拆成两次调用**之后：

| 失败落在 | 归属 | 分支 |
|---|---|---|
| **建页**路由（页面里根本没有站点 URL） | **执行层** | `unresolved`（**不进池**） |
| **导航**路由 | **站点事实**（**DNS 解析失败 / 连接被拒**；⚠️ **超时 / 证书错不算**，§8.35） | `unreachable_hard`（真负样本）；其余 ⇒ `unresolved`（**不进池**） |

⇒ **修法**（`CamofoxDriver._open_blank_and_navigate`）：建**空白页** +
再导航 ⇒ 失败落在哪个路由就是归属判据。**多一次往返（实测 ~1.4 s）**，
换的是「这个站点到底打不打得开」这个事实**站得住**。

⚠️ **顺带认领了第二个潜伏缺陷**：上游的 `recovery="retry"` 一族
（`session_expired` / `concurrency_timeout` / `browser_launch_timeout`）
说的是「**我们这边坏了，重来即可」**——上游**明说**的
⇒ 漏判的后果与 §8.33 一模一样（会话过期被记成「站点打不开」）。
实测当时池里 **0 条**命中 ⇒ **潜伏未爆**；现在由
`CamofoxToolError.execution_fault` 认领。

⚠️ **「换页也失败」与「换页成功、导航失败」不是一回事**（方案 21 §R5）：

- **换页本身失败** ⇒ 采集侧的故障 ⇒ 记 `unresolved`（**不进池**）；
- **换页成功、导航失败** ⇒ 在**一张干净的新页上**得到的传输层事实
  ⇒ **只有机器码证明的那部分**（DNS 解析失败 / 连接被拒）**才是站点事实**
  ⇒ 记 `unreachable_hard`；**超时 / 打断 / 空响应 / 证书错** ⇒ 证明不了
  ⇒ 记 `unresolved`（§8.35）。

⚠️ **不许把「站点事实」降级成「没判出来」来图省事**——那是**丢真负样本**，
方向与本条相反（本条治的是**假负样本**）。
⚠️ **但「站点事实」按 M-44 的口径是窄的那一种**（DNS 解析失败 / 连接被拒）
⇒ 「不许降级」说的是**那一种**不许降；「这次没打开」那几种**本来就该**
降成 `unresolved`（§8.35）。

**纪律**：

1. **判据要落在结构上**：上游的**路由划分**与**错误体里的
   `code`/`recovery`** 才是判据，**错误文本不是**。
2. **跨进程边界的「路由」是契约的一部分**：上游把哪几件事塞进哪个路由，
   直接决定**哪类失败能证明什么**——换执行层时**要重新核一遍**
   （旧实现里恰好对的前提，换层后可能反过来）。
3. **先量失败形状再定处置**：两种失败**同形**时，**先找能分开它们的那个维度**
   （这里是路由），**别急着按文本猜**。
4. **不许靠「把失败都记成没判出来」来止损**：那会让**真负样本**一起消失，
   而**池的分母**变化在报表上**看不出原因**。

**实测**（真上游，2026-10-27）：`research/probes/camofox_route_split_probe.py`
测出四种失败形状（空白页建页 / 导航 DNS 失败 / 建页 DNS 失败 / 两侧的挂住超时）
⇒ **建页与导航的失败在错误体里字面相同**；
`camofox_split_nav_probe.py` 测出**拆开之后导航照常工作**

⚠️ **「建页失败 ⇒ 执行层」这一条现场触发不到**（建空白页几乎不会失败）

### 8.35 分支的**名字**说了「站点不可达」，于是**采集侧的故障**被装进了这一支

**症状**（2026-10-27，M-44）：负样本池里出现「这个站打不开」，
可那条的 evidence 写的是

```
导航失败（传输层）: … 导航超时 30000ms
导航失败（传输层）: page.goto: Navigation to "…" is interrupted by another navigation to "…"
导航失败（传输层）: camofox tool camofox_create_tab 返回错误: … tab create timed out after 30000ms
```

⇒ **三条都证明不了「这个站打不开」**：一条是**慢**、一条是**跳转链中途断了**、
一条是**建页都没建成**（§8.34）⇒ 而分支名 `unreachable_hard`
与标签「站点不可达（网络/DNS/超时）」**说的却是站点性质**
⇒ 池里那一行的断言成了「**这里真的看不了**」⇒ **训练信号被污染**
（教模型「这个站看不了」，其实只是**这一次**没打开）。

**零报错**：它是**合法的既有分支**、理由**通顺**、门禁不报、退出码 0。

**根因**：`unreachable_hard` 这一支同时装着**三种成因**，
而它的**名字与标签只承认一种**（站点性质）⇒ **名字在说谎**。

**M-44 裁定（owner，2026-10-27）**：把「**这次没打开**」（超时 / 打断 / 建页失败 /
会话失效 / 快照失败）降成 **`unresolved`**（**不进池**），
只留「**真·站点不可达**」——**机器码**证明：**DNS 解析不出来 / 连接被拒**。

⚠️ **这一条修的过程里踩了三个坑，都不报错**：

1. **判据必须在截断之前判**——obscura 面的 `dns error` 机器码落在
   第 **~200 字**，而驱动把错误文本**截断到 200 字**
   ⇒ 截断后再判**认不出来** ⇒ 存量 **17** 条 `client error (Connect)` 行
   **就是这么丢的证据**（不是「本来就判不出」，是**判的时机不对**）。
2. **同一件事有多条记分链 ⇒ 口径要抽成一处**——`visit.py` 分了
   「会话失效 vs 导航失败」，`aggregator.py` 却**无条件**记 `unreachable_hard`
   ⇒ 同一个问题在两条链上答案不同 ⇒ **报告上看不出异常**
   （两条链都产存档、都不报错）。
3. **跨面词表不同，但**语义**要对齐**——camofox 面给
   `NS_ERROR_UNKNOWN_HOST` / `NS_ERROR_CONNECTION_REFUSED`，
   obscura 面给 `ConnectError("dns error")` / `kind: ConnectionRefused`
   ⇒ 判据得建在**语义**上（DNS 失败 / 连接被拒）而不是**码**上
   ⇒ **跨面可比**；而 `NS_ERROR_NET_TIMEOUT` / `kind: TimedOut`
   **两侧都不算**「真·站点不可达」。

**纪律**：

1. **分支的名字与标签要说得清「这是谁的事实」**——「站点不可达」只能装
   **站点性质**；**采集侧的故障**（慢 / 打断 / 建页失败 / 会话失效）不是。
2. **机器码才算证据，错误文本不算**——除非文本里**带着**机器码。
3. **判据要早于任何截断与清洗**（顺序错了，判据等于没有）。
4. **多条记分链 ⇒ 判据单点**（`nav_failure.py::site_unreachable()` 一处，
   两个面共用）。
5. **改判只影响新行**——「并池是写入时的动作、不回填历史存档」
   ⇒ 存量那条另走路（**Q-23**），**别拿改判当出池手段**。
6. **分支标签的文案不是契约**——契约冻的是分支**名**
   （`evaluation/golden/builder.py::LABEL_UNIVERSES`）⇒ 改文案不破契约；
   **存量金标行保留旧字面量不回填**（v13 三档共 **43** 行）⇒ 分代边界由
   `branch_eras.py` 的 **e6** 记。

**症状**（2026-10-28，Q-23 处置时撞到，**已修**）：把一批存档的分支降级
（`unreachable_hard` → `unresolved`）并从负样本池撤掉对应的行之后，
重跑 `check-archives` 却报

```
DEGRADED  negative_not_pooled ×3 — 真负样本没并池
    真负样本没并池：component_unverified https://www.bilibili.com/list/ml1179903751?oid=1143858172420
```

⇒ 降级**明明做了**（命令退出码 0，还打印了命中条数），
门禁却说「有真负样本没并池」。

**根因**：一份 run 有**两层**存档，而**读的那层不是改的那层**：

| 层 | 文件 | 谁读它 |
|---|---|---|
| **原档** | `<task>__<run_id>.json` | 人工复核、`review` 命令的输入 |

⚠️ **零报错**：降级命令**成功**（退出码 0），报错的是**下一道**门禁
⇒ 两件事看起来毫不相干 ⇒ 很容易去查「门禁是不是算错了」。

**纪律**：

1. **改判要两层都落**——原档 + 复核档。`cli downgrade` 已这么做了
   （2026-10-28 改）；**手写脚本改存档**时最容易只改一层。
2. **先确认「我改的那份是不是被读的那份」**——看 `select_archives` 的优先级，

3. **复核档与原档的口径代不同**（`assembler/schema.py::rationale_era_of`：

4. **改完存档要重跑门禁**——存档的 `evidence` 是**样本的一部分**（T 视图带它）

### 8.37b 轨迹行**没有** `__split__` 这个键：硬读顶层档位拿到空串

**症状**（2026-11-01，per-Run 改造后）：拿 `row.get("__split__")` 读一条**轨迹行**，
读到的是**空串 `""`**——不是 `calibration`，也不是报错。而「这一行属于哪一档」的
判据若是 `has_split = any(r.get("__split__") for r in rows)`，它在轨迹行上**恒假**
⇒ 分档那一栏退化成「没切过档」，而报表把「没切档」与「切档了但这一行不在调参池」
**印成同一个 0**。

**根因**：**分档是站点级的，轨迹没有单一档位**（实测 50 条轨迹里 **28 条**三档全跨）。
`__split__` 是**站点级行**的运行时注解（`cmd_agreement` 读冻结档时按档打上的），
轨迹级的档位在两个地方：顶层 `splits`（各档计数）与 `site_outcomes[].split`
（逐站点）。轨迹行压根**没有** `__split__` 这个键。

**档位面**的（28 条轨迹三档全跨 ⇒ 定不下单一档位）。⚠️ **两个集合不是同一批**：
实测**交集 24 条、各差 4 条**（复算 `research/probes/per_run_golden_shape.py`
末段「两个『28』的关系（防混）」）⇒ **同一个数、两个含义**，读错就等于把

**纪律**：

1. **任何问「这一行属于哪一档」的代码都必须先过 `rows.headline_split(row)`**
   （**头部站点口径** · owner 2026-11-01 裁的 ②），不许拿顶层 `__split__` 硬读；
2. 要「各档几条」用 `rows.row_splits(row)`；要「整条都在不在本次范围内」用

3. **判「这是不是轨迹行」看结构，不看 `source_kind`**：`rows.is_trajectory_row(row)`
   = `"site_outcomes" in row`（结构判据对手写/迁移过来的行同样成立）；
4. ⚠️ **取严（`strict_split`）不是唯一的口径，owner 2026-11-01 裁了「按头部站点」**

   ⚠️⚠️ **两个数不是「宽严关系」**：**交集只有 2 条** ⇒ ② 是**换了一批数据**；

### 8.38 `source_kind` 的值换了：轨迹级行是 `"trajectory"`，不是 `"p2_sample"`

**症状**（2026-11-01）：写「`source_kind == "p2_sample"` 就是 P2 样本」的判据，
在 per-Run 的数据上**一条都匹配不上**（条件恒假）⇒ 本该被排除的行**一条都没排除掉**；
反过来「`source_kind != "p2_sample"` 就算站点级」这条判据，在**轨迹行上恒真**
⇒ 轨迹级行被当站点级行算进分母，**分母整个变样，报表上看不出异常**。
另一处看得见的症状：把轨迹行喂给**站点级**的读现场函数
（`evaluation/calibration/evidence.py::locate_sample`）⇒ 返回
`source_kind='trajectory' 不认识（不猜）`、`sample: None`
⇒ **现场读不到**（而它其实读得到——轨迹级的读法是 `locate_trajectory`，
**不按 url 切片**，摆的是整条轨迹）。

**根因**：per-Run 之后「轨迹级候选行」是**有站点明细的轨迹**，
它的 `source_kind` 是 **`"trajectory"`**（`rows.SOURCE_TRAJECTORY`）；
旧的 `"p2_sample"` 行是「per-unit 轨迹占位」（没有 url、没有现场、label 恒为
`unresolved`），per-Run 之后**那种行不再产出**。⇒ 继续叫 `p2_sample` 会让
「D-10 只算 `source_kind != "p2_sample"`」这条判据把**带金标的轨迹级行一起排除掉**。

**纪律**：

1. **判「是不是轨迹行」用结构判据**：`rows.is_trajectory_row(row)`
   （`"site_outcomes" in row`）——它对手写/迁移过来的行同样成立，
   而 `source_kind` **可能被人改过**；
2. **`source_kind` 只是元数据**，不是行形状的判据；拿它当判据的地方要一并改成
   结构判据；
3. 站点级冻结档（v1–v16）里那些 `source_kind != "p2_sample"` 的判据
   （`snapshot.py::iter_site_rows` / `builder.py::cmd_agreement` 的 `site = [...]`）
   **对站点级行仍然成立**（冻结档本来就是站点级行）——**但它们不再能挡住轨迹级行**，
   所以凡是从**候选集 / `trajectories.jsonl`** 取分母的地方，必须先摊平成站点视图
   （`rows.expand_site_rows`）；
4. ⚠️ **`snapshot.py::iter_site_rows` 的 docstring 仍写着「轨迹级样本
   （`source_kind == "p2_sample"`）」**——那句话现在是**历史口径**，
   照着它读代码会把轨迹级行算进站点级分母。

→ `evaluation/golden/rows.py::SOURCE_TRAJECTORY`（含「为什么不能继续叫 p2_sample」）·
`is_trajectory_row` · `evaluation/calibration/evidence.py::locate_sample` /

### 8.39 两种标注粒度 = **两个** Label Studio 项目：混在一个项目里，回流的数据无法区分

**症状**（2026-11-01）：`golden_ls init-project --version 14` 打出的标题是 `golden-v14`，
而轨迹级那一路的标题应该是 `golden-v14-traj`；两个标题相同 ⇒ **两个粒度共用一个
LS 项目** ⇒ 标注页上**一半 task 是站点、一半 task 是整条轨迹**，
标注员分不清自己在判什么 ⇒ 回流上来的数据**无法区分是哪个粒度的裁定**
（而报告上看不出异常）。

另一处症状：`upload --version 14` 对 v1–v16 的站点级冻结档报
`错误:v14 没有轨迹级数据集（trajectories.jsonl 不存在或为空）——
v1–v16 是**站点级**冻结档……`——因为 `golden_ls` 的子命令**默认粒度是
`trajectory`**（裁定④），要按历史口径走必须显式 `--scope site`。

**根因**：**一个标注单元 = 一条轨迹**（裁定④）⇒ 站点级那一路是**历史口径**
（v1–v16 推上去的那些），两路的**标注单元不是一回事**，混在一页就分不清。
⇒ **两种粒度两个项目**，标题由 `projects.project_title(version, scope)` 唯一给出；
**台账按 `(version, scope)` 建键**——只按版本查会把轨迹级的任务推进站点级的
项目里（`GoldenProjectIndex.get(version)` 在 `scope=None` 时**站点级优先**）。

**纪律**：

1. **两种粒度两个项目**（`golden-v{N}` / `golden-v{N}-traj`），标题是**确定性**的
   ⇒ 幂等靠标题精确匹配，不靠「我记得是哪个」；
2. **台账按 `(version, scope)` 查**，`scope` 不许省（省了就是「站点级优先」）；
3. **凡是调 `golden_ls` 的子命令都要想清楚粒度**：默认是 `trajectory`，
   碰历史冻结档要显式 `--scope site`；
4. ⚠️ **粒度字面量只有一处**（`golden_ls/scope.py`）：`site` / `trajectory`
   两处各写一份，迟早有一处写成 `traj` 而另一处仍认 `trajectory`
   ⇒ **粒度认不出来**，两种粒度的行混进同一个项目。

→ `evaluation/golden_ls/scope.py`（`SCOPE_SITE` / `SCOPE_TRAJECTORY`）·
`evaluation/golden_ls/projects.py::project_title` / `GoldenProjectIndex.get` ·
`evaluation/golden_ls/cli.py::_scope_of` / `_cmd_init_project` / `_push` ·

### 8.40 两种粒度的产物**文件名**必须分开：同名 ⇒ 一个粒度的产物把另一个盖掉

**症状**（2026-11-01）：`v14/` 目录下同时躺着 `ls_annotations.jsonl` 与
`reflow_worksheet.jsonl`（站点级）与 `ls_annotations.traj.jsonl` /
`reflow_worksheet.traj.jsonl`（轨迹级）。若两个粒度**同名**，则后写的那次
**把前一次覆盖掉** ⇒ 回流读到的是**另一个粒度的内容**——**文件在、内容合法、
退出码 0，报告上看不出异常**。留底那一侧也一样：`label_config.xml` 被覆盖 ⇒
事后拿留底复算 sha **对不上的是哪一份就说不清了**（而 sha 对不上正是
「配置漂了」的唯一证据）。

**根因**：三个产物名各服务一个粒度，**粒度不同 ⇒ 文件名不同**。
留底文件与 sha 是**一对**（台账里记的 `label_config_sha` 对着留底算），
同名 ⇒ 这一对关系被拆散。

**纪律**：

1. **三个文件名都按粒度分开**（`golden_ls/cli.py`）：
   `label_config.xml` / `label_config.traj.xml` ·
   `ls_annotations.jsonl` / `ls_annotations.traj.jsonl` ·
   `reflow_worksheet.jsonl` / `reflow_worksheet.traj.jsonl`；
   **新增一个粒度就要新增三个名字**，不许复用；
2. ⚠️ **写产物一律按字节写**（`_write_text_bytes`）：Windows 上文本模式会把 `\n`
   翻成 `\r\n` ⇒ 留底与台账里记的 sha **对不上**，而「对不上」正是「配置漂了」
   的唯一证据 ⇒ **不能用 `Path.write_text`**；
3. **工作表同名更贵**：人在工作表里填的三栏（观测面 / 观测时刻 / 署名）
   **填到另一个粒度的行上**——而两栏一空一填都**不报错**（只有 apply 阶段才退 2）
   ⇒ 白填一轮。

→ `evaluation/golden_ls/cli.py::_label_config_name` / `_annotations_export_name` /
`_worksheet_name` / `_write_text_bytes` ·
[设计方案 23 §5.2](../设计方案/23-每任务一轨迹.md)
