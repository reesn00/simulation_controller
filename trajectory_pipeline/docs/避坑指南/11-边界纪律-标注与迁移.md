## 八、边界纪律（续二）

### 8.41 上传是「**整条推**」：「有交集就行」会把沾着封存内容的轨迹整个推上去

**症状**（2026-11-01）：`upload --version N` 打出一行
`⚠ 37 条轨迹**没有推**（跨档 ⇒ 整条不在本次范围内；或者被 --golden-ids / --limit 收窄）`
——「没推」的那批不是漏了，是**整条跨着本次范围之外的档**。
反过来若按「有交集就行」筛，那批**跨着 holdout 的轨迹会被整个推上去**
⇒ **封存面（holdout）上出现了人看过的内容** ⇒ 封存作废，而**报告上看不出异常**。

**根因**：LS 的页面摆的是**整条轨迹** ⇒ **没法只推一半** ⇒ 一条轨迹的**所有**档位
都得在本次范围内才推（`rows.splits_within`）。而**一条轨迹没有单一档位**
（实测 50 条里 **28 条**三档全跨）⇒ 「这条算哪一档」本身就得先过档位口径。

**纪律**：

1. **上传筛选一律用 `rows.splits_within(row, selected)`**（**全部档位都在范围内**），
   不许写「有交集就行」；
2. **点名推某几条 id 时，判据也是整条**（`_select_by_ids`）：
   id 不在本次范围内 ⇒ **退 2**（`这些 golden_id 不在本次要传的档 [...] 里`），
   与「点错的 id ⇒ 退 2」是同一道闸——**试点要覆盖到哪条就得是确的那条**；
3. **「没推」的行要在读数里说清**（`⚠ N 条轨迹**没有推**`），
   否则「推上去 13 条」会被读成「这版就这么多条」。

→ `evaluation/golden/rows.py::splits_within` ·
`evaluation/golden_ls/cli.py::_cmd_upload_trajectory` / `_select_by_ids` ·
[设计方案 23 §4.3](../设计方案/23-每任务一轨迹.md)

### 8.42 档闸按**头部站点**定档（owner 2026-11-01 裁的 ②）：封存面 / 回归集的头部站点**不进金标**（回流工作表里被跳过，不是漏了）

**症状**（2026-11-01）：`reflow worksheet` 打出一行
`跳过 37 条（逐条原因见 …skipped 明细）`，逐条是
`skipped: T001__67a05faa — holdout_not_reflowed`
（回归集则是 `regression_not_reflowed`）。
⇒ 那些行**在工作表里根本没有** ⇒ 人以为自己漏判了，重跑一遍还是那些行，
**而金标一条没多**。

**根因**：档位决定的是「**能不能进金标**」——holdout 的裁定**只上传、只被人看，
但不回流**（裁定③：它要保持「没被人看过」的封存状态）；回归集里的行
**不得改动**（C-17）。轨迹跨档 ⇒ 按 **owner 2026-11-01 裁的 ②（头部站点口径）**
取**头部站点那一档**（`rows.headline_split`）⇒ **头部站点落在封存面 / 回归集
就是不许回流**。
⚠️ **取严（`strict_split`）不再是档闸**——owner 裁的是 ② ⇒ 保留它作**对照口径**
（够格进金标 **13/50 vs 7/50**）。
⚠️ **头部站点认不出 ⇒ 退 2，不许放行**（`SKIP_NO_SPLIT`）——「定不出档」当成
「没有限制」恰恰是**最不该放**的那种情况（解不出来的那条往往**沾着封存面**）。
⭐⭐ **还有第二道闸**（owner 2026-11-01「泄露做兜底」）：**整条**沾着封存面 /
回归面 ⇒ **不放行**（`rows.non_reflow_splits`）——**头部站点在调参池也不够**：
其余站点里的封存事实会跟着轨迹级标签一起进调参池 ⇒ 封存面作废。

**纪律**：

1. **一律显式记原因，不静默丢弃**（`SKIP_HOLDOUT` / `SKIP_REGRESSION` /
   `SKIP_NO_SPLIT`）：被跳过的行要能回答「为什么它没进金标」；
2. **工作表里的「跳过」不是「漏了」**——它与「没复核」（`not_reviewed`）、
   「判不了」（`unverifiable`）、「没有原标注」（`no_annotation_row`）
   是**四种不同的原因**，处置动作各不相同；
3. **apply 侧同一道闸再拦一次**（`reflow.validate`）：
   holdout ⇒ `holdout 的裁定不进金标（裁定③只上传，不回流）`；
   regression ⇒ `回归集里的行不得改动（C-17）——要改就先把这一行挪出回归集`；
   **定不出档** ⇒ `定不出档（头部站点认不出）——不许回流`；
   **兜底** ⇒ `轨迹里沾着 holdout 站点的裁定——封存面不进金标` /
   `轨迹里沾着回归集的站点——回归集不得改动（C-17）`
   ⇒ **不靠工作表那一道**；
4. ⚠️⚠️ **② 的代价照实记**：② 放行的 **13 条里有 11 条含 holdout 站点**
   ⇒ **封存面泄漏面 11/13**（且**与取严的交集只有 2 条** ⇒ ② 是**换了一批数据**，
   不是「放宽」）⇒ **已加兜底**（owner 2026-11-01）⇒ **放行数 13 ⇒ 2**
   （被挡 11 条：2 条只沾 holdout · 9 条两样都沾）⇒ ⚠️ **「2」比取严的「7」
   还少**——差的 5 条是**「头部站点认不出」的残缺轨迹**（被 fail-closed 挡，
   **不是被兜底挡**）⇒ **补齐那 5 条 ⇒ 2 → 7**。
   ⇒ **要改口径就改档闸那两处**（`evaluation/golden_ls/reflow.py`），**别散着改**；
5. ⚠️ **跳过明细目前只打前 20 条**（`skipped_detail[:20]`），且提示里的
   `…skipped` **那个文件并没有落盘** ⇒ 条数多的时候剩下的原因**没地方查**
   ⇒ 超过 20 条时要把整份 `skipped_detail` 抄进台账，别只留那 20 行。

→ `evaluation/golden_ls/reflow.py::build_worksheet`（`SKIP_HOLDOUT` /
`SKIP_REGRESSION` / `SKIP_NO_SPLIT`）· `validate` ·
`evaluation/golden/rows.py::headline_split`（`strict_split` = 对照口径）·
`non_reflow_splits`（兜底）·
`evaluation/golden_ls/cli.py::_cmd_reflow_worksheet`（`skipped_detail`）·

### 8.43 回流工作表里的「**新建**」行必须有人署名：署不上就退 2

**症状**（2026-11-01）：`reflow apply` 退 2，打印
`工作表有 N 处不合格（**不写**）:`，逐条是
`<golden_id>：新建的轨迹级标注要署金标侧的名字（reviewed_by 不能空）`
或
`<golden_id>：reviewed_by='xxx' 不在人的署名集合里（['manual-review', 'reesn']）——
否则这条会从「人核」静默退化成「机器写的」`。

**根因**：轨迹级标注**大部分还不存在**（人核的单元刚从站点级换成轨迹级）
⇒ 人判的**第一条**没有原标注可改 ⇒ 这一行是**新建**（`creates_gold: true`）。
「谁定了这个标签」是**人的事实**，机器推不出来 ⇒ **署名必须由人填**。
⚠️ **署不上名的后果是静默的**：那条会从「人核」退化成「机器写的」，
而分类器把**空署名**算 `unknown`、**不在人名集合里**的署名算 `automated`
⇒ 它不会进「需要人看一眼」的那批 ⇒ **没人会发现它没被人看过**。

**纪律**：

1. **`creates_gold` 的行必须有人署名**（`reflow.validate`），
   签名集合是 `golden/signatures.py::HUMAN_SIGNATURES`（`manual-review` / `reesn`），
   **不许拿工具名 / agent 名顶替**；
2. **署名集合是封闭集**：新冒出来的署名先算「自动化」（fail-closed 的方向），
   别为了让它过关就把名字加进集合；
3. ⚠️ **「已复核」与「已署名」是两件事**：`submit: false` 的行**不校验**
   （它的三栏还没齐），下轮接着办——**别把「没提交」读成「没署名所以有问题」**。

→ `evaluation/golden_ls/reflow.py::build_worksheet`（`creates_gold`）·
`validate` · `evaluation/golden/signatures.py::HUMAN_SIGNATURES` ·
[设计方案 23 §5.3](../设计方案/23-每任务一轨迹.md)

### 8.44 改人核数据的**键**要先拿到 owner 的签字：迁移把站点明细挪进 `site_outcomes[]`

**症状**（2026-11-01）：跑 `builder migrate-trajectory` 打印了一屏迁移计划
（哪条旧 id 落到哪条新 id），最后一行是 `[dry-run] 加 --apply 才写盘`
——**盘上什么都没变**。不读那行 dry-run 提示，就会以为「迁移已经做完了」，
而人核标注**仍旧挂在旧 id 上** ⇒ 重建候选集时**一条都挂不上** ⇒
`重建候选集会让 N 条人核标注挂不上（**不重建**）`（`candidates` 的孤儿门禁当场拒绝）。

**根因**：per-Run 之后轨迹级 id = `{task}__{run}`，而旧人核标注挂在
`{task}__{run}__{search|site-N}`（per-unit id）上 ⇒ **键变了 ⇒ 整批掉线**，
而**报表上只是少了几条**，没有任何报错。⇒ 迁移走 **`id_alias_trajectory.json`**
这座桥，**默认 dry-run**，`--apply` 才写盘。

⚠️⚠️ **迁移表与 `id_alias.json` 不是同一张表**（2026-11-01 实测踩过，见
§8.46）：`id_alias.json` 是 **1:1** 的**行键**迁移表（代码拿它给冻结行换键），
迁移表是**多对一**的**合并**表（几个旧 id 合成一条新 id）⇒ **合成一张 ⇒ 撞 id**。

**纪律**：

1. **动的是人核数据的键 ⇒ 需 owner 签字**（同 `cmd_rekey` 的规矩）；
   **默认 dry-run**，`--apply` 才写盘；
2. **落点按「判决有没有内容」分**：`label == unresolved`（判不出来）⇒ 落**轨迹级**
   `{task}__{run}`；实打实的分支 ⇒ 落**站点级** `{task}__{run}__{url_hash}`
   （这个判决说的是**那个站点**，不许冒充整条轨迹的结论）；
3. **三条硬规矩**：① **禁止投票**——同一个 `(新 id, round)` 上出现两个不同的 label
   ⇒ 直接报错退出，把分歧摆给人看；② **人话不许丢**——被合并的每一行进
   `merged_notes`；③ **只改键不改内容**——label / note / 署名 / 时刻 / 软维度分
   **一个字不动**；
4. **配不出来就报错退出**：单元→站点的配对判不出来 ⇒ 人工核对后再迁，
   **不许把判决挂到猜出来的站点上**；
5. ⚠️ **round 2 是 retest（D9 的一致性复测），不是金标** ⇒ 迁移只动 round=1；
6. ⚠️ **迁移与改代码必须同批做**：只改代码不迁移 ⇒ 标签当场全掉（§8.32 同一族）。

→ `evaluation/golden/builder.py::cmd_migrate_trajectory`（`_LEGACY_UNIT_ID` /
`_unit_site_golden_id`）· `cmd_candidates` 的孤儿门禁 · `cmd_rekey` ·
[设计方案 23 §2.5 / §6 / §8 O-2](../设计方案/23-每任务一轨迹.md)

### 8.45 旧的 per-unit `sample_id` **照样读得懂**：老数据不报错，但口径是历史口径

**症状**（2026-11-01）：per-Run 的代码读一批**改造前**的 P2 样本（文件名
`samples/T001__67a05faa__site-1.json`）**不报错**：轨迹 id 取 sample_id 的
**前两段** ⇒ `T001__67a05faa` ⇒ 一个 Run 的几个单元**归并成同一条轨迹**。
于是「一条轨迹 = 一次执行」这个单位，在旧批次上其实是**几个旧单元拼出来的**，
而**报表上分不出来**。

**根因**：`builder.py::_scan_p2_samples` 的口径是「`task_id` / `run_id` 从 sample_id
**前两段**取」⇒ 老数据里 per-unit 的多个样例**归并到同一条轨迹**
（这正是 per-Run 要的效果）。但**归并的规则不是「一条 = 一条」**：
行上的 `sample_id` 会被**逐个覆盖**，**只留最后一个单元的 id**。

**纪律**——**怎么分辨「读到的是旧口径」**（三条判据，任一条命中就是旧口径）：

| 判据 | 旧口径 | 新口径 |
|---|---|---|
| 轨迹行的 `sample_id` 字段 | **三段**（`<task>__<run>__<unit>`，第三段形如 `search` / `site-N`） | **两段**（`<task>__<run>`，`assembler/schema.py::sample_id`） |
| 盘上的 P2 样本文件名 | `samples/<task>__<run>__<unit>.json` | `samples/<task>__<run>.json` |
| `builder migrate-trajectory` 的报告 | 「旧 per-unit 标注：N 条」**N ≠ 0** | 「标注里没有旧的 per-unit id ⇒ 无需迁移」 |

1. ⚠️ **判「是不是旧单元 id」看第三段的形状，不看段数**：
   站点级键 `<task>__<run>__<url_hash>` 也是**三段**
   （`builder.py::_LEGACY_UNIT_ID` 的注释明写这一条）⇒ 按段数判会把站点级键
   误当成单元级键；
2. **行形状判据永远是结构**：`rows.is_trajectory_row(row)`（有没有 `site_outcomes`），
   **不看 `source_kind`**——老数据被迁移过之后 `source_kind` 可能已经改过；
3. ⚠️ **「能读懂」不等于「口径一样」**：旧批次的**人核标注**仍挂在 per-unit id 上
   ⇒ 那些标注**不在**轨迹级行上 ⇒ 轨迹级标签**不存在** ⇒ 轨迹级那一路要**另判**
   （§8.43 的「新建」），**不许从站点级标签推导**（那是投票，CLAUDE.md 明令禁止）。

→ `evaluation/golden/builder.py::_scan_p2_samples` · `_LEGACY_UNIT_ID` ·
`cmd_migrate_trajectory` · `assembler/schema.py::sample_id` ·
`evaluation/golden/rows.py::is_trajectory_row` ·
[设计方案 23 §2.5 / §3.1](../设计方案/23-每任务一轨迹.md)

### 8.46 两张 id 迁移表合成一张 ⇒ **同一个 `golden_id` 出现两次**（报表上**看不出异常**）

**症状**（2026-11-01 实测）：跑完 `migrate-trajectory --apply` → `candidates --force`
→ `freeze --from-version 16`，**一切正常**（退出码 0，没有警告），
但打开**修之前**的那一版冻结档数一下就发现：

- `v17/holdout.jsonl` **103 行、只有 102 个 `golden_id`** ⇒ `E001__57bbf995` 出现 **2 次**；
- 同一个 `golden_id` `E001__57bbf995__6a28d60d` **同时落在 calibration 与 holdout 两档**
  ⇒ **一行进两个分母**。

⚠️ **修之后重冻的 v17 是干净的**（294 行 / 294 个不同 id，零重复）⇒
**这个坑是「迁移表合并了」才会犯**，不是新冻结档的常态。

**没有报错** ⇒ 只看命令输出与报表**看不出任何异常**——报表只是「少了几条」。

**根因**：`id_alias.json` 与迁移表**语义不同**，合成一张就出事：

| 表 | 映射 | 用途 |
|---|---|---|
| `id_alias.json` | **1:1** | **给冻结行换键**（`builder._rekey_rows`） |
| `id_alias_trajectory.json` | **多对一**（合并） | **给标注换键**（几个旧 per-unit id → 一条新轨迹 id） |

⇒ **合并语义用在 1:1 的换键上 ⇒ 几行换到同一个 id** ⇒
按 id 建索引时**后出现的赢**（前面那行**静默消失**），跨档时**一行进两个分母**。

**纪律**：

1. ⚠️ **判据：这张表的映射是 1:1 还是多对一** ⇒ 决定它能不能给**行**换键；
   **多对一的表只许给标注用**；
2. ⚠️ **主键门禁**（`builder._assert_unique_golden_ids`）：冻结前核
   「一个 `golden_id` 在整个冻结档里只出现一次」⇒ 撞了**不冻结**
   （报出撞在一起的 id 与它们各自的档），而不是冻出一份坏档；
3. ⚠️ **旧 per-unit 行在新的冻结档里保留自己的旧 id**（`E001__57bbf995__site-1`）
   ⇒ 它们在 per-Run 的世界里**没有后继**（不是站点、也不是轨迹）
   ⇒ **不许替它们编一个新 id**（编出来的 id 会指向别人的行）；
4. ⚠️ **别把「id 撞了」读成「数据坏了」**：撞 id 的那几行**内容一个字都没动**
   （金标 / code / 分数原样）⇒ 修的是**键**，不是数据。

→ `evaluation/golden/builder.py::ID_ALIAS_FILE` / `ID_ALIAS_TRAJECTORY_FILE` ·
`_rekey_rows` · `_assert_unique_golden_ids` · `cmd_migrate_trajectory` ·
[设计方案 23 §6](../设计方案/23-每任务一轨迹.md)

### 8.47 argparse 的 help 串里写 `%` ⇒ **整个 CLI 起不来**（连 `--help` 都进不去）

**症状**（2026-11-01 实测）：

```
ValueError: badly formed help string
```

⇒ **一个子命令都进不去**，**`--help` 也进不去** ⇒ 看起来像「这个 CLI 整个坏了」。

**根因**：argparse 拿 help 串**做 `%` 格式化** ⇒ help 串里有一个**光秃秃的 `%`**
（例：`"…可得率静默变成 0%"`）就抛上面那个错 ⇒ **炸在建 parser 的那一步**
⇒ **跟哪个子命令无关**：所有子命令共用一个 parser ⇒ **一个字符废掉整个 CLI**。

**纪律**：

1. ⚠️ **help 串里有 `%` 就写 `%%`**（argparse 的硬规矩，不是笔误）；
2. ⚠️ **这类错只在「跑起来」时炸** ⇒ **改完 CLI 一定要跑一次 `--help`**，
   单测里**建 parser** 的那条测试（`test_golden_ls_cli.py`）就是它；
3. ⚠️ **症状是「整个 CLI 坏了」，不是「某个参数坏了」** ⇒ 排查时先怀疑
   **建 parser 那一步**（`_build_parser()`），别一头扎进子命令里。

→ `evaluation/golden_ls/cli.py::_build_parser`（`--task-views-root` 的 help 串）

### 8.48 P3 的 `site_outcomes[].index` 与候选集站点行里那个**同义**字段**不能互相顶替**（名字差一个词，语义差一个「孤儿」）

**症状**（2026-11-01，per-Run 改造后）：在 P2 / P3 契约里看到
`site_outcomes[].index`，去**候选集站点行**里找对应的键 ⇒ **没有 `index`**，
只有另一个名字 ⇒ 以为「P3 写错了」⇒ **顺手改成那个名字** ⇒
契约测试当场炸：

```
AssertionError: P2 契约文档提到 'visit_index'，但 assembler 源码里找不到它
——文档写了实现没有的东西
```

（**炸得对**：契约测试的方向二就是「文档提到的字段必须在**本层**源码里真的存在」
⇒ 契约文档**只许写自己那层真有的字段名**。）

**根因**：两个字段在**不同的层**，指的是**同一个访问序号**，各带各的语义——

| 字段 | 层 | 键名 | 语义 |
|---|---|---|---|
| `site_outcomes[].index` | **P2 / P3**（`assembler/schema.py::SiteOutcomeView.to_json`） | `index` | 访问序号，**从 1 起**；列表本身按访问点枚举 ⇒ **恒 ≥ 1，没有 0** |
| 候选集站点行的同义键 | **评估侧**（`outcomerules.SiteEntry.visit_index` → `evaluation/golden/builder.py::cmd_candidates` 落盘） | `visit_index` | 同一个访问序号，**但 `0` = 孤儿记账**（这条 outcome 没被任何访问点配到，压根没有访问序号） |

⇒ **互相顶替的两种坏法**：改 P3 那个 ⇒ 把「孤儿」语义引进一个**不可能取 0**
的字段；改候选集那个 ⇒ 把 `0` 读成「第 0 次访问」（真实含义是「没有访问点」）。

**纪律**：

1. ⚠️ **跨层的字段对照写进避坑指南，不写进契约**——契约测试只认本层源码，
   写了就是「文档写了实现没有的东西」（方向二）；
2. ⚠️ **别「顺手统一」两个键名**：先问「这个字段**能不能取 0**」——
   能取 0 的那个带「孤儿」语义，不能取 0 的那个不带；
3. 判「是不是同一层的东西」看**落点**：`site_outcomes[]` 归 P2；
   候选集行的键归 `evaluation/golden`（`candidates.jsonl` 与冻结档那一层）。

→ `assembler/schema.py::SiteOutcomeView.to_json`（键是 `index`）·
`outcomerules/__init__.py::SiteConclusion.index`（从 1 起）·
`outcomerules/__init__.py::SiteEntry.visit_index`（`0` = 孤儿）·
`evaluation/golden/builder.py::cmd_candidates`（落盘 `"visit_index": entry.visit_index`）·

### 8.49 per-Run 之后「`degraded_from` 含 `steps`」**不再等于**「这条样本没有模型动作」——拿它当代理的测试会失效（而且**只在主树才红**）

**症状**（2026-11-01，per-Run 合回 main 之后）：一条**在分支上一直是绿的**
真存档测试，回主树跑就红：

```
FAILED trajectory_pipeline/tests/unit/test_code_scorer.py::TestOnRealArchives::
       test_老存档没有动作流时不可判定而非满分
AssertionError: assert False
 +  where False = all(<generator ...>)
```

**根因**：那条测试拿 `degraded_from` 里有没有 `steps` 当「这条样本**没有模型
动作**」的**代理**——而这个等价关系是 **per-unit 时代的副产物**：

| | `steps` 标记答的是 | 动作流是什么 | 二者 |
|---|---|---|---|
| **per-unit**（改造前） | 「**这个单元**缺动作流」 | 该单元自己的动作 | **等价** |
| **per-Run**（现在） | 「轨迹里**某一段**缺动作流」（降级**传染到整条**，与 `executor.integrity` 的 `steps_missing` 逐条同码） | 各段**摊平**后的**并集** | **不等价** |

⇒ 老存档里「访问点有动作、顶层 `steps` 缺」的那批：**整条轨迹有动作**，
却**仍然带 `steps` 标记** ⇒ 代理失效。
**实测**（145 份真存档 → 131 条轨迹）：带 `steps` 标记的 **38 条里 31 条有
模型动作**。

**为什么在分支上没发现**：⚠️ **工作树里 `output/` 是空的** ⇒ 真存档那几类
测试**整条 skip** ⇒ 分支上「全绿」是**假绿** ⇒ **回主树才红**。

**纪律**：

1. ⚠️ **判「这条样本有没有模型动作」⇒ 看事实**（模型可见的 click 动作流），
   **别看标记**；
2. ⚠️ **反向那条也要写上**（「判了分 ⇒ 确有可核的 click 动作」）⇒ 两头堵死
   「凭空白发通行证」；只写正向那条的话，改判据容易把护栏写成空断言；
3. ⚠️ **别为了保住旧代理去改标记的语义**——标记与 `integrity` 的**逐条同码**
   关系是另一条契约（`TestDegradedMarkersMatchSplit` 双向盯着）⇒ 改标记会
   把那条契约一起改掉；
4. ⚠️ **在真存档上跑的测试，必须回主树跑才算数**（工作树里它是 skip）。

→ `assembler/schema.py::split_archive`（动作流摊平 · `degraded` 的缺件集合）·
`executor/integrity.py::degraded_marker_map`（`steps_missing` → `steps`）·

### 8.50 实体核查的检索袋只收**完整**观察 ⇒ 「明明采到了」被判成幻觉

**症状**：仓库自带的真存档测试在旧实现上是**红**的——

```
FAILED trajectory_pipeline/tests/unit/test_rationale_gates.py::
       TestOnRealObservations::test_真实观察能跑且抽得出实体
AssertionError: E006__2729220b：观察里真实存在的「全面」被判成幻觉
```

**根因**：`rationale/gates.py::check_entities` 的**存在性检索袋**只收
`observation_shortfall(obs) == ""` 的观察 ⇒ 被排除在袋外的是**截断 / 裁剪 /
降级**的观察——而它们**采到的那部分是真的**。

rubric D-9 保护的是「**落在截断外**的实体」；落在截断**内**（采到了）的实体
本来就有据。旧实现把「这份记录不完整」当成了「这份记录里的东西不算数」
⇒ **拿记录的残缺去否认已经采到的证据**——与 §5.5「判断建立在残缺事实上时，
正确做法是记不可判定，而不是拿残缺事实去指控」正相反。

| | 检索袋收什么 | 后果 |
|---|---|---|
| 修复前 | 只有**完整**观察 | 采到了的实体**查不到** ⇒ 判幻觉 |
| 修复后 | 可见窗口的**全部**观察 | 采到了就是有据 |

⚠️ **同一个文件里两种口径**：`check_temporal_at` 判「当时就看得见」用的是
**全部**可见观察（`_bag(visible)`），`check_entities` 却只用完整的 ⇒ 同一份
数据，时序核查说不算后见之明、实体核查说不存在于观察里——**两个相反结论**。

**这不是 per-Run 引入的**（「最近才变红」≠「最近才有」）：旧 per-unit 产物
（`_backup_pre_m58/samples/`，1510 份）里本来就有 **18 条
`unsupported_entity`**、31 条 failed ⇒ 缺陷一直在。per-Run 把它**放大**了：
可见窗口从「一个单元的十几份观察」变成「一条轨迹的几十份」，而 **P1 原始
观察里约 1/3 带缺件**（DOM 截断 / 元素裁剪 / 采集降级）⇒ 被排除出检索袋的
文本比例跟着涨 ⇒ 命中变多、变显眼。

**纪律**：

1. ⚠️ **「存在」与「不存在」是两种结论，兜底条件不同**：「查不到」是**否定
   结论**，要由**完整**观察兜底；「采到了」是**肯定事实**，一份不完整观察里
   采到的部分**就是**有据。⇒ 检索袋收全部，否定结论另设门槛。
2. ⚠️ **同一个文件里同一个问题只能有一种口径**（这里：实体核查与时序核查的
   「当时看得见」）。
3. ⚠️ **测试输入要与生产输入同形**：那条真存档测试读的是 P2 落盘的
   `six.observations`——**`observation_view` 裁剪过的展示形**（≈每份观察都带
   `truncated.view=True`）⇒ 旧检索袋几乎为空 ⇒ 假阳性比生产路径多；生产走
   **P1 原始**观察（≈1/3 带缺件）⇒ 同一处缺陷，假阳性少一些。
   ⇒ **别拿测试的严重度当生产的严重度**，也别拿生产的读数说「测试太严」。
4. ⚠️ **要重算闸门就读 P1 存档，或直接重跑构建**——**闸门跑的是 P1 原始
   观察**，`six.observations` 是裁剪后的**副本** ⇒ 拿落盘副本重跑得到的结论
   **与构建期不是同一份数据**（据此得出过一组错的翻转读数）。
5. ⚠️ **后见之明与幻觉是两个锚点**（rubric D-9）：实体只在**后续步的完整
   观察**里出现 ⇒ 它**确实存在** ⇒ 那是后见之明（`temporal_leak`），不重复
   记一次幻觉候选——顺带把那条例子里「**更不在后续步的任何观察里**」的
   **假陈述**从负样本池的理由里去掉。
6. ⚠️ **抑制一条发现前先确认另一条会接手它**（这里用 `check_temporal_at`
   **同一套**匹配规则）⇒ **不丢结论**，只是换到对的桶里。
7. ⚠️ **闸门在热路径上**（L-21）：检索袋变大 ⇒ 每步扫的文本更多 ⇒ 这条修复
   **带性能代价**，别顺手再往袋里塞东西。

### 8.51 判重是 **skip-only** ⇒ 「重推」用 `ls_bridge upload` **一条都推不动**

**症状**：改完口径要把 LS 上那几行换成新内容，跑 `ls_bridge upload` ⇒
终端报 `tasks_pushed=0` / `skipped_duplicate=8`，**零报错、零异常**——
像「推成功了」，其实**什么都没变**。

**根因**：`evaluation/ls_bridge/exporter.py::push_batch` 的判重是
**skip-only**：`push_index`（`ls_bridge/push_index__<project_id>.jsonl`，
按 `sample_id`）里有这个 `sample_id` ⇒ **直接跳过**。
⇒ 那是**防重复推**的闸，**不是**「更新已有行」的闸。

⚠️ **绕它的那条路更糟**：LS 1.23 **不按 `inner_id` 去重** ⇒ 删掉索引再推
⇒ 得到 **N 条重复行**（旧的行还赖在项目里，标注员看到两条一样的）
⇒ 而且 `inner_id` 必须是**整数**（字符串 ⇒ 400）。

**正解**（本次就是这么做的）：**PATCH 就地替换**
（`PATCH /api/tasks/{id}` + `PATCH /api/predictions/{id}`）⇒
**LS task id 不变** ⇒ 判重台账不用动、标注员看到的还是同一行。

⚠️ **三件容易漏的**：

1. **预标注（ML 预填的 `risk_hints`）也要一起换**——旧的是旧口径算的，
   留在新内容上就是**过期预标注**，而标注员**先看到的正是它**。
2. **替换前留回滚快照**（那几行的 `data` + predictions 全文）。
3. **先干跑对账再写**：逐字段比 sha256，列出「哪几个字段变了」，
   再看**有没有人工标注**（有人标过 ⇒ **不覆盖**，**不替人投票**）。

⚠️ **写 LS 是外部写**：owner 授权是**必要**条件，但**权限门**可能还是拦
（分类器看不见对话里的授权）⇒ 被拦就把命令与理由报给 owner，**别绕**。

⚠️ **判重台账可能只活在一个根里**（实测踩到）：LS 的去重**只靠本地那一份
JSONL**（LS 自己不去重）⇒ 如果推送是在 **worktree** 里做的，而 worktree
被删 / 索引文件丢了，**主树的台账里就没有这些行** ⇒ 下次在主树跑 `upload`
⇒ **整批重复行**灌进人核项目。⇒ **推完就把台账并回主树**
（逐字合并，append-only，不改写；先确认主树已有行在工作树那份里**逐字相同**
且**无 `ls_task_id` 冲突** ⇒ 无损）。⚠️ 这类台账**不入库**
（`output/` 不在 git 里）⇒ **备份也得单独留**。

### 8.52 候选链接是**搜索结果的跳转链接** ⇒ 站点标签取它的 host 等于「怪搜索引擎」

**症状**：收尾答复写「已排除的站点：`www.baidu.com`（内容损坏，排除）」——
可用户明明是在看某个影视站打不开，**百度只是跳转中转**。

**根因**：`assembler/closing.py::_site_label` 取的是 `site_url`
（**候选链接**）的 host，而候选常常是 `http://www.baidu.com/link?url=…`
这种**搜索引擎的跳转链接** ⇒ 取它的 host = 把**搜索引擎**写成
「被排除的站点」。实测 A13 那 8 份存档里，per-Run 的失败清单
**大半是 `www.baidu.com`** ⇒ 训练语料在教模型「怪百度」。

**正解**：**优先取落地页 `url`**，取不到才退回 `site_url`，两个都没有就说
「该站点」——**不编**。**只取 host（不带协议）这条不变** ⇒ R2-1 的
「失败答复不含 URL」验收不受影响。

**纪律**：⚠️ **同一条结论里有两个 URL 时，「哪个是站点」要先定死**
（落地页 = `url`，候选 = `site_url`）——不然同一个词在两条路径上各取一个，
**报告上看不出异常**（只是文案变了）。
