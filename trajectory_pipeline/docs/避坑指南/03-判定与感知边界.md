## 三、判定与感知边界

> 铁律：**代码层做护栏，LLM层做探索。**
> 判据必须是 URL / 标题 / 标签计数这类**客观字符串**，
> 一旦需要「理解这句话的意思」，就该问 Perceptor。

### 3.1 绝不 fail-open

**症状（正确行为，别改）**：搜狐页面 200 个交互元素无一命中词表，
但页面已有 `<video>`×1 → 判 `unresolved`，**不判 `no_play_control`**。

**证据文本**（落进存档的原文）：
> 「200 个交互元素无一命中词表，但页面已有 `<video>`×1——「没有播放控件」与观察自相矛盾，不判负」

**纪律**：观察与判定**自相矛盾**时，一律 `unresolved`（fail-closed）。
矛盾点要写进 `evidence`——那是复核时唯一能看出问题的地方。
→ `perception/rule_perceptor.py`

### 3.2 媒体计数与 iframe 数量都不作判据

**症状（要避免的回归）**：导航站满屏 iframe，早期版本据「有 15 个 iframe」
把 hao123 判成播放页。

**纪律**：**两者都不进判据**——`<video>` / `<audio>` 计数与 iframe 数量都只写进
`evidence` 作排查线索。
⚠️ **2026-10-23 · M-26**：连「标签存在性」也**不再是判据**——媒体计数只是
**必要条件**，不许据此产出「成功」（**护栏可以否，不能许**）。规则版 ④ 一律
`None`；LLM 版 ④ 一律问模型。实测：优酷「试看6分钟｜开通会员看完整视频」页
`video=1` 曾被读成「能看正片」⇒ **5 份存档 5 条假成功**。
⇒ 现役口径见 [02 感知与判定域 §M-26](../计划进展/02-感知与判定域.md)。

### 3.3 正文有歧义时不要拿它当判据

**症状**：百度验证码页正文是「网络不给力，请稍后重试」。

**风险**：拿它当反爬判据 → **真网络故障会被误判成反爬，正好与目的相反**
（网络故障 → 重试；反爬 → 换引擎/加间隔）。

**纪律**：反爬判定**只看 URL 路径与页面标题**（`/captcha`、`wappass`、「安全验证」），
正文只认「访问过于频繁」这类**明确限流措辞**，且与网络故障措辞不重叠。
→ `executor/dom.py::detect_block`

### 3.4 反爬是运行级状态，不是失败分支

**纪律**：`search_blocked` **不进** 8 条 outcome 分支体系。
那套分支每一支都对应「这个站点看完之后的结论」，而拦截发生在**取候选之前**，
根本没有 outcome。塞进去会让负样本池混入**连站点都没访问到的条目**。

### 3.5 被拦的必须排除出切片

**症状**：persona 切片里出现 `half-悬疑 0/1`，读作「这个 persona 组合表现差」，
真相是「这条压根没跑」。

**纪律**：切片只含**实际跑过**的 task，且行数变化时**明说排除了几个**。
切片表的说服力会被这种行毁掉。

### 3.6 结构上不可能 ≠ 页面上没有

**症状**：bing 结果里混进 `help.bing.microsoft.com`、`beian.miit.gov.cn`（ICP 备案查询），
全判 `no_play_control` **直接进负样本池**。

**纪律**：
- 域名剔除按**注册域族**（带点边界：`host == root or host.endswith("." + root)`），
  不用裸 `endswith`——后者让 `help.bing.microsoft.com` 逃过 `www.bing.com` 的判定，
  且会误杀 `notbing.com`
- 只放**结构性不可能**的域（`gov.cn`），**不加 `edu.cn`**：
  部分高校图书馆确有影视资料页，误杀虽代价更低但**可避免**；
  `gov.cn` 不可能有影视资源，无误杀可能
- 「页面上没有播放控件」仍归感知层，**不在代码层判**
→ `executor/steps/search.py`

### 3.7 把登录墙算进「反爬拦截率」：同一批数据，两个相反的结论

**症状**（2026-10-21 第二轮双跑）：合并口径报
「A 19.15% / B 34.09%」⇒ 读作「camoufox 被拦得更凶」；
只留**真·反爬**读作「A 14.89% / B 9.09%」⇒ 读作「camoufox 被拦得更少」。
**同一批存档，两个相反的结论**，而前者是顺手就会用的那个。

**根因**：合并口径把**登录墙**（`login_required` / `login_wall_or_blocked`）
与**真·反爬**（`blocked`）算成一类。登录墙是**内容侧的访问控制**，
反爬是**采集侧的拦截**——两者处置完全不同（前者可能是负样本，
后者是**运行级状态**、压根不进分支体系，见 §3.4）。
混在一起算出来的「拦截率」**没有处置含义**。

**纪律**：
- 报拦截率**必须分桶**：`blocked`（真·反爬）单列，登录墙单列，**不合并**
- 报之前先问「**这个数是用来决定什么的**」：反爬率高 ⇒ 换执行层没意义；
  登录墙高 ⇒ 那是内容问题，与执行层无关
- ⚠️ 合并口径**看起来更严**，所以更容易被顺手采用——
  而它**恰好在这批数据上把结论读反**
→ `executor/dual_run.py`（`ANTI_BOT_BRANCHES` / `ACCESS_WALL_BRANCHES`）

**同一条纪律的第二处**（2026-10-26，方案 20 §R3）：`agreement` 报表的
「反爬拦截率（采集侧账）」块**排在 D10 头条与下钻口径 D 之前**，且按
`gatekeeper_events` 的 `verdict` 分桶（`blocked_cf` / `captcha` / `login_wall` /
`paywall` 各占一行）。拦截笔数**单列、不进 D10 分母**——它说的是「我们这张
采集面被拦」，处置是换面重采，不是改判据。⚠️ **「拦截笔数 0」有两种来源**：
真没被拦 / 这一版**判不出跨面**（旧行没记面），报表里靠 `comparable` 三态分开。
→ `evaluation/golden/builder.py::_report_collection_accounts` ·
`evaluation/calibration/disagreement.py`（`collection_accounts.jsonl`）
