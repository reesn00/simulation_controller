# 避坑指南 · 环境与外部依赖

> 本册是《避坑指南》按主题拆分的分册；条目编号沿用原 02-避坑指南.md 的编号，便于全仓「§X.Y」引用继续命中。

## 六、环境与外部依赖

### 6.1 搜索引擎会限流

**症状**：同批连跑，第 1 条正常，后 2 条被重定向到
`wappass.baidu.com/static/captcha/tuxing_v2.html`（标题「百度安全验证」）。

**处置**：加请求间隔，或 `--engine bing`（实测 11 候选 vs 5 候选，
分支覆盖 4 种 vs 2 种）。**直接重跑同一引擎大概率仍是验证码页。**

**纪律**：这类拦截**必须在 `report` 里排在分支分布之前**并单列统计——
它是运行级的，一次拦截会让后面所有分支分布都偏小，先看分支会被带着往下读。

### 6.3 Windows GBK 控制台

**症状**：探针上的 ✅/⚠️ 把整条链带崩；`pytest` 输出中文全是乱码。

**纪律**：脚本内加 `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`；
Bash 里跑 Python 用 `PYTHONIOENCODING=utf-8`。

`cli._reconfigure_stdio()` 分两种情况：
`tty` 时只放宽 `errors` **不改 `encoding`**（PowerShell 下当前编码本就正常，
不该替用户改掉）；**非 tty 时强制 `encoding='utf-8'`**——
重定向或走管道时 Python 按 locale 输出，也就是 cp936，
实测 `cli check-archives > out.txt` 写出的首字节是 `0xB4 0xE6`（GBK 的「存」），
按 UTF-8 读直接报错。**CI 日志、重定向文件、任何读档的下游脚本全是坏的**，
而那恰恰是没有控制台代码页、消费方是程序的场合。

### 6.4 终端乱码 ≠ 存档内容坏了

**症状**：读存档看到 `evidence` 是一串 `U+00FD` 加一串 U+FFFD 加 `video/audio=0`，
第一反应是「P1 里中文全烂了，落盘编码写错了，去改 `archive.py`」。

**实测反过来**：2026-10-09 拿现存 12 份真实存档逐条查，
**37 条 outcome 的 `evidence` 无一损坏**——那串乱码是 Windows 控制台
把 UTF-8 渲染成 cp936 造成的，`sys.stdout.reconfigure` 一下就正常。
落盘路径一直是干净的（`archive.py` 显式 `encoding="utf-8"`）。

**真正坏掉的是别的东西，而且范围小得多**：4 份 T001 存档的 `visits[3]`
（tv.sohu.com）`body_preview` 中间 109..225 那段，以及同页一个 `<a>` 的 label。
同一段里 `导航` / `倍速` 这些中文与 ASCII 都是好的，只有中间夹着
U+01F3 / U+0439（Latin 扩展与西里尔字母）的一小片烂成 U+FFFD——
**整档换编码写错会把正常中文一起烂掉，实测它们是好的**，所以触发条件是
站点声明的 charset 与实际内容不一致。同一批 11 个站没事、同一个站 4 次全坏，
**重跑同一批不会变好**。

### 6.5 成因已查实（2026-10-10）：**声明与实际是一致的**（⚠️ 2026-10-25 补充：**字节本身混合损坏**，见本节末）

上一节最后那句「触发条件是站点声明的 charset 与实际内容不一致」——
**2026-10-10 实测证明它是错的**，且错在方向上。

**损坏发生在**浏览器**按页面声明的 GBK 解码那批字节的时候**——
**不是传输层引入的**。现场复核（2026-10-25，commit `d01ee0d`，探针
[`research/probes/probe_obscura_gbk2.py`](../../research/probes/probe_obscura_gbk2.py)）：
在浏览器**内部**用 `charCodeAt` 逐字符看 `document.body.innerText`
——「简介」是**正确 Unicode**，紧接着就是 U+FFFD + 残留字节
⇒ **U+FFFD 在 DOM 里就已经存在** ⇒ **HTML 字节本身混合损坏**
（声明 GBK、夹着无效字节），浏览器按 GBK 解码即产出 U+FFFD。

⚠️ **换浏览器/执行层解决不了它**：任何执行层面对的都是**同一批坏字节**
（换浏览器也是按 GBK 解同一批字节 ⇒ 同样产出 U+FFFD）⇒ 换层无解。

**本仓库做的是采集侧防护**（`executor/dom.py::is_mojibake` +
`obscura_driver.snapshot`）：正文与标题**分开**检测，命中即记进
`Observation.degraded`。闸门侧 `gates.observation_shortfall` 见到
`degraded` 非空就拒绝判幻觉——**不在闸门里加第二道门**。

为什么这条防护不是锦上添花：坏正文进感知层后，rationale 闸门会把
「模型引用了页面上真实存在、但已损坏的实体」判成**幻觉**，
**凭空造出一条理由通顺、不报错的负样本**。这与「观察被截断 → 不判幻觉」
是同一条纪律：判断建立在残缺事实上时，记不可判定，不指控模型。

阈值 `MOJIBAKE_MIN_COUNT = 3` 而非「出现即降级」——单个 U+FFFD 可能来自
页面真实内容（页脚符号、图标字体损坏），一见到就降级会让「观察不充分」
这条路径过于宽松，最后人人都忽略它。实测坏站一个正文里数十个、好站 0 个，
两侧都离阈值很远。

### 6.6 纪律：判断「文件里是不是真有 U+FFFD」必须**落盘后重新解码**

且用 `strict`——在终端里 `print` 出来的样子不作数（§6.4 的整个教训）。
`cli check-archives` 的 `mojibake` / `evidence_mojibake` 干的就是这件事，
两种结果分两档严重度（坏在观察里只降级那条，坏在 `outcomes[*].evidence`
才让那条结论作废）：混成一档的话，「1 个站的正文烂了」会把整批 20 个
访问点一起判死，而门禁一旦老报 FATAL，人就会开始整体忽略它。

⚠️ **门禁信号与 P2 的 `degraded_from` 是两套东西，不要合并。**
`integrity.degraded_marker_map` 刻意**不收** `mojibake`，而
`schema._obs_missing` 答的是「P1 里没有哪个键」——乱码是「键在、内容坏了」。
混进去会让「正文被截短」与「正文是烂的」在 `degraded_from` 里长得一样，
而后者更糟：截短只影响落在截断外的实体，乱码让**整段正文都不可信**。
那张表是平铺的，扛不住这个轻重之分。
（`test_integrity.py::TestDegradedMarkersMatchSplit::test_损坏不进degraded_from词表`
钉住这条，改那张表时会红。）

### 6.7 worktree 里 `output/` 是空的：读数会**静默变成 0%**

**症状**：在 git worktree 里跑读数类命令，**可得率变成 0%**，而同样的命令在主树
跑出来是正常的：

```
现场可得率(本次导出 294 条): 0/294 = 0.0% ｜ T 视图可得率: 0/294 = 0.0%
```

**病根**：`trajectory_pipeline/output/` 是**产物目录、不入库**（纪律 5）⇒
worktree 里它是**空的**⇒ `--p2-root` / `--task-views-root` 的缺省值指向
**空目录**⇒ 「现场读不到」「T 视图读不到」。

⚠️ **它不报错，是 fail-closed 的读数**：「读不到」被报告成「**没有**」⇒
两者的区别在**统计与门禁里会消失**。更糟的是**推出去收不回**：
`golden_ls upload` 会把**空块**的 task 建进 LS，评审在标注页上看到的是
**没有现场、没有轨迹**的任务。

**判据**：**0% 的可得率不是「没有现场」，是「读不到根」**。⇒ 拿它跟
**已知基线**对一眼（现场 **216/294 = 73.5%** · T 视图 **288/294 = 98.0%**，
方案 22 §1）——**对不上先怀疑根，再怀疑数据**。

**修法**（显式指根，别依赖缺省）：

```
--p2-root <主树>/trajectory_pipeline/output/pipeline --task-views-root <主树>/trajectory_pipeline/output/pipeline
```

⚠️ **推之前必跑 `--dry-run`**（**推送计划留底**里带读数）⇒ 一眼看出
「现场 0%」就别推。**推出去那一步是唯一能拦住它的地方**——LS 的 task 建好之后
**空块不会自己补上**：判重台账按 `golden_id` 跳过 ⇒ 重跑**推不上去**，
要改得**删 LS task + 清判重台账**再重推。

⚠️ **同症状的第二个病因**（2026-10-29 踩到）：`--task-views-root` 给的是
**产物根**，实现**自己接 `task_views/`** ⇒ 多给一层就变成
`task_views/task_views/*.json` ⇒ **照样 0%**（现场是 73.5%，只有 T 视图是 0%
⇒ 更像「这一列单独坏了」）。⇒ **两个根都指 `.../output/pipeline`**，
**不要指 `.../output/pipeline/task_views`**。⚠️ CLI 的 `--help` 原话写
「T 视图根」，会误导——已改成「**产物根**（其下会自动接 `task_views/`）」。
