# 新树工程避坑指南

这份文档记的是**会踩什么坑、怎么一眼认出它**，不是设计决策的记录
（那些在 [`设计方案/00-总体方案.md`](设计方案/00-总体方案.md)）。

**每条的「症状」都写成你在终端、报告或测试输出里真正会看到的东西**，
这样可以直接全文搜索命中。方案文档回答「为什么这么做」，
这份回答「看到这句就该想起什么」。

条目按**复发频率**排序，不按发现时间。同一个坑踩两次比第一次更难查——
因为第一次的痕迹还在，第二次已经被误读成别的东西了。

---

## 一、同源纪律（本项目最高频的坑）

> **同源 = 同一个事实的推导侧与检查侧必须取自同一处数据。**
> 不同源的后果不是报错，是**两边安静地互相打架**，且没有任何告警。

### 1.1 渲染源 ≠ 约束推导源

**症状**：归一接受率 4%，12 条采样里 9 条退回骨架原文，persona 特征全部失效，
但所有测试全绿，表象只是「通过率偏低」。

**根因**：改写按 `intent.goal` 渲染，约束却按 `initial_request` 推导。
T001 的 `goal` 比 `initial_request` 少一个「全集」→ 探针必然判失败。

**纪律**：`renderer` 统一用 `skeleton.initial_request`（它才是首轮消息的来源），
`goal` 只作元数据。改写与判分要求检查必须读同一份文本。
→ `taskgen/persona/renderer.py`

> 通用形态：**症状与病因隔着三层时，调症状那一侧必然把纪律静默拆掉。**

### 1.2 检测词 ≠ 探针词

**症状**：最典型的 T001 反而不含 `has_episode_range`，约束检查形同虚设。

**根因**：检测词写死 `("集数", "季数", …)`，探针词多一个「全集」。
带空格或省略的写法处处漏。

**纪律**：检测与检查**共用 `CONSTRAINT_PROBES` 一份词表**。
两套词不同源 = 推导与检查互相打架且无任何报错。
→ `taskgen/skeleton.py::_derive_constraints`

### 1.3 判定逻辑 ≠ 使用点

**症状**：`FakeDriver` 构造的观察识别不出反爬拦截，真实路径却能——
测试与生产行为不一致。

**根因**：早一个版本把 `detect_block` 放进 `obscura_driver.observe()` 并落成
`Observation.blocked_reason` 字段，采集层于是要懂「什么页面是反爬页」这种业务语义。

**纪律**：**判定逻辑必须在使用点**（`orchestrator.run` 里直接调
`detect_block(obs.url, obs.page_title, obs.body_text)`）。
让任何 `Observation`——不论谁构造的——走同一条判定路径。
→ `executor/orchestrator.py` 环节 0.5

### 1.4 写含正则/转义的源码禁用 Bash heredoc

**症状**：源码里 `\xNN` 变成真控制字符，`re.compile` 在运行期才炸。

**纪律**：用 Write / Edit 工具写源码，**不要** `python << EOF`。
→ 见 memory `bash-tool-escapes-backslash-x`

## 二、计数与记账

> **计数说谎比不计数更坏。** 不计数让人知道这里有损失；
> 说谎的计数让人**基于错的数字下结论**，而且毫无察觉。

### 2.1 字段名与字段值不同语义

**症状**：`gen` 打印「排除 98 个」，而 `--all-modes` 下**一个都没排除**。

**根因**：`excluded_by_skeleton_mode` 填的是**全库 mode 分布**。
字段名说 excluded，值里却含「未排除」的项（81 个 single_title 是被用上的）。

**后果**：`--all-modes` 时报「98 次因骨架模式排除」；读的人会以为真排掉了 98 个，
进而以为「剩下 81 个都被用上了」，而实际用的是 98 个里的任意若干。

**纪律**：
- `excluded_by_skeleton_mode` 只记**真被排除**的（判据取 `runnable_in_w1` 属性本身，
  不硬编码模式名——属性才是真值源）
- `mode_distribution` 记全库分布，无条件
- 加**自洽性测试**：排除数 + 可跑数 == 全库
→ `taskgen/sampler.py`

### 2.2 静默剔除让损失不可见

**症状**：存档写着 11 个候选，没人知道引擎原本给了 50 个链接、其中多少被规则扔掉。

**纪律**：剔除**必须带原因计数**。`extract_candidates(..., stats=...)`
是可选出参，填 `{"excluded_host:baidu.com": 16, "duplicate_host": 1}`。
`engine_self` 与 `excluded_host:<root>` 分开记——读的人处置不同。
→ `executor/steps/search.py`

### 2.3 缺字段 ≠ 空值

**症状**（两次，同一款病）：

1. persona 切片全落到 `(无 provenance)`——分不清「不是 taskgen 跑的」与「taskgen 没生效」
2. `report` 把存量存档（字段引入前跑的）算成「可跑」——
   而那批**恰恰最不该算**（被验证码页拦下的）

**根因**：`provenance.get("persona_id")` 与 `data.get("search_blocked") or ""`
把「字段不存在」与「字段为空」折叠成同一个值。

**纪律**：
- 空 `dict` 的含义**固定为「不是 taskgen 跑的」**，绝不兼表「没生效」
- 存量存档缺字段时，用**同一个判定函数**从存档里确定性重算，
  并在输出里**标注「存量存档重算」**
→ `executor/plan.py`、`executor/cli.py::cmd_report`

## 三、判定与感知边界

> 铁律：**代码管事实层，LLM 管语言层。**
> 判据必须是 URL / 标题 / 标签计数这类**客观字符串**，
> 一旦需要「理解这句话的意思」，就该问 Perceptor。

### 3.1 绝不 fail-open

**症状（正确行为，别改）**：搜狐页面 200 个交互元素无一命中词表，
但页面已有 `<video>`×1 → 判 `unresolved`，**不判 `no_play_control`**。

**证据文本**（落进存档的原文）：
> 「200 个交互元素无一命中词表，但页面已有 `<video>`×1——「没有播放控件」与观察自相矛盾，不判负」

**纪律**：观察与判定**自相矛盾**时，一律 `unresolved`（fail-closed）。
矛盾点要写进 `evidence`——那是复核时唯一能看出问题的地方。
→ `perception/rule_perceptor.py`

### 3.2 iframe 数量不作判据

**症状（要避免的回归）**：导航站满屏 iframe，早期版本据「有 15 个 iframe」
把 hao123 判成播放页。

**纪律**：`PLAYER_OK` 只认 `<video>` / `<audio>` **标签存在性**；
iframe 数量只写进 `evidence` 作排查线索，不进判据。

### 3.3 正文有歧义时不要拿它当判据

**症状**：百度验证码页正文是「网络不给力，请稍后重试」。

**风险**：拿它当反爬判据 → **真网络故障会被误判成反爬，正好与目的相反**
（网络故障 → 重试；反爬 → 换引擎/加间隔）。

**纪律**：反爬判定**只看 URL 路径与页面标题**（`/captcha`、`wappass`、「安全验证」），
正文只认「访问过于频繁」这类**明确限流措辞**，且与网络故障措辞不重叠。
→ `executor/dom.py::detect_block`

### 3.4 反爬是运行级状态，不是失败分支

**纪律**：`search_blocked` **不进** 8 条 outcome 分支体系。
那套分支每一支都对应「这个站点看完之后的结论」，而拦截发生在**取候选之前**，
根本没有 outcome。塞进去会让负样本池混入**连站点都没访问到的条目**。

### 3.5 被拦的必须排除出切片

**症状**：persona 切片里出现 `half-悬疑 0/1`，读作「这个 persona 组合表现差」，
真相是「这条压根没跑」。

**纪律**：切片只含**实际跑过**的 task，且行数变化时**明说排除了几个**。
切片表的说服力会被这种行毁掉。

### 3.6 结构上不可能 ≠ 页面上没有

**症状**：bing 结果里混进 `help.bing.microsoft.com`、`beian.miit.gov.cn`（ICP 备案查询），
全判 `no_play_control` **直接进负样本池**。

**纪律**：
- 域名剔除按**注册域族**（带点边界：`host == root or host.endswith("." + root)`），
  不用裸 `endswith`——后者让 `help.bing.microsoft.com` 逃过 `www.bing.com` 的判定，
  且会误杀 `notbing.com`
- 只放**结构性不可能**的域（`gov.cn`），**不加 `edu.cn`**：
  部分高校图书馆确有影视资料页，误杀虽代价更低但**可避免**；
  `gov.cn` 不可能有影视资源，无误杀可能
- 「页面上没有播放控件」仍归感知层，**不在代码层判**
→ `executor/steps/search.py`

## 四、判分保真 ≠ 表达质量

> **探针全绿 ≠ 话是人话。**
> `CONSTRAINT_PROBES` 只覆盖**判分要求**，
> 句法通顺、措辞自洽、语义不打架**全都不在判分要求里**，探针一条都抓不到。

### 4.1 双句边界

**症状**：`…两天给我就行。啊。`——closer 以「。」收尾、tail 自带句号，**两个句子边界**。

**纪律**：拼 tail 前剥掉 closer 的尾部标点，让语气词落在**句内**。
→ `taskgen/persona/renderer.py::_join_tail`

### 4.2 片段粘连

**症状**：`…做版本对比慢慢找也没关系`、`对比表格这周内给我就行`。
存量 `initial_request` **大多不以标点结尾**（16 条抽样里 14 条如此）。

**纪律**：closer 前无标点则补「，」。
→ `renderer.py::_join_closer`

### 4.3 tail 接不上 closer

**症状**：`今晚要看求求了真的`——原 tail「求求了真的。」本是独立句子。

**纪律**：`VERBAL_TAILS` 每条**必须以语气词起头**（啊/呀/呢/吧/嘛/哦/噢）。
这条判据**不用中文分词**（太脆），旧词表一条都过不了。

### 4.4 措辞内部自相矛盾

**症状**：`不急，这两天给我就行`——一句里既说不急又给紧期限。

**纪律**：同档 `CLOSERS` 内部不得同时出现「不急」与紧期限词；
不得跨维度借用别档信号（「求求了」属"急"，出现在「闲时」档就是冲突）。

### 4.5 persona 只能改「怎么说」，改不了「要什么」

**症状**：产出「确认电影**类似《功夫》那样的动作片**的**版权方**」——
骨架要版权方，与动作片无关。persona 的品类偏好被冒充成用户需求。

**纪律**：`genre` 落到**检索侧**，不进表述；`OPENERS` / `SPECIFICITY_RENDER`
都不注入 `{genre}`。persona 未生效的维度**显式记进 provenance**
（`genre_in_prompt: "no:检索侧维度，不改用户表述"`），好让人区分
「有意不做」与「忘了做」。

### 4.6 opener 不带主语

**症状**：`有点想看，我想找电影…`——opener 与 goal 主语重复，拼出病句。

**纪律**：`OPENERS` 模板只留语气前缀（`嗯，` / `说起来，`），不带主语。

## 五、fail-closed 的边界

### 5.1 `unresolved` 不是负样本

**纪律**：`unresolved`（没判出来）与 `trailer_suspect`（词表判不准）
**不进负样本池**。混进去会让「负样本纯度」这个指标失去意义，
而**指标失效是察觉不到的**。

### 5.2 人工复核不得覆盖真负样本

**风险**：verdicts 文件可能混入真负样本的 url（手填 / 跨批次粘贴 /
对着旧队列编辑新存档）。无差别回填时**一次误填就把 `no_play_control` 改成成功**，
而负样本池的全部价值就是「这里真的看不了」，破坏是**静默**的
（分支分布只显示「成功 +1、负样本 −1」，看不出那条从哪来）。

**纪律**：`apply_verdicts` 只对 `REVIEW_BRANCHES` 内的分支生效，
其余计入 `ignored` 原样保留，CLI 显式告警。

### 5.3 保留原判才能测分歧率

**纪律**：回填保留 `branch_before_review` 与 `source=human`。
覆盖掉就永远测不出「人工与代码的分歧率」。

### 5.4 能力边界要诚实说出来

**症状（全 0 时）**：`共 20 个 task，成功 0`——读的人会当成「这批素材没价值」。

**纪律**：0 成功时**明说** W1 的三处能力边界
（`IS_REACHABLE` 恒为 None / `PLAYER_OK` 只认标签 / 存在性判定带 fallback_used），
让人能区分「素材质量差」与「这版规则判不了」。**不猜是哪一条原因**——
分支分布已经印在上面了，让读的人对着数字自己对。

### 5.5 LLM 不会替你 fail-closed（**W3 实测，最贵的一条**）

**症状**：iqiyi 播放页明明 `video_tag_count=1`，LLM 版 `PLAYER_OK` 判**否**，
evidence 是一段通顺的分析：「`body_text` 为空、`interactive_elements` 为空，
说明页面未渲染或采集失败，应判为不是播放器页」。

**根因**：模型**看不到采集层发生了什么**。它只看到「空的」，于是按常识推理
「空的 = 页面没内容」，然后给出一个**自信的错答案**。规则版早就防住这条
（`test_零个交互元素不判无播放控件`：哨兵返回分不清「没渲染完」与「确实为空」），
但那层保护在 `RulePerceptor` 里，**换成 LLM 就没了**——而它是最需要那层保护的地方。

**纪律**：**采集充分性在代码层预检，且发生在问模型之前**
（`llm_perceptor._sufficiency`）。可断言的硬证据是「预检失败时
`fake.calls == []`」——守卫的意义在于不把采集故障送去让模型编结论。
通用形态：**LLM 只会推理「我看到的东西」，不会推理「我没看到东西意味着什么」。**
→ `perception/llm_perceptor.py`、`tests/unit/test_llm_perceptor.py::TestSufficiencyGuard`

### 5.6 推理模型的思考与正文共用 `max_tokens` 一个预算

**症状**：`判断点 ① 未取得结论（LLM 不可用（shape:ValueError））`，
每道题都这样，报表上像「LLM 判不了」。

**根因**：`_ask` 里写死 `max_tokens=600`。本机后端是推理模型，
**思考与正文共用这个预算**，600 全花在思考上，正文一个字没吐：

```text
max_tokens= 600  finish_reason=length  content=null     （599 tok 全在思考上）
max_tokens=2048  finish_reason=length  content 截断
max_tokens=8192  finish_reason=stop    content 干净（2096 tok）
```

客户端按红线**故意不读** `reasoning_content`（那是 raw CoT），于是正文为空
这件事最终只表现为一句 `shape:ValueError`——看不出是「预算不够」还是
「后端坏了」，两者要采取的动作完全不同。

**为什么没人会去改那个数字**：症状摆在那里的是「模型答不出来」，
顺着这条线索想到「提示词不对」「模型不行」，想不到「预算被思考吃了」。

**纪律**：预算归 `LLMConfig`（`TRAJECTORY_LLM_MAX_TOKENS`，默认 8192），
**调用点一律不传**——签名默认值给 `None` 而不是数字，给了数字调用点就会
各写各的。预算用尽报 `budget:` 而不是 `shape:`，因为处置动作不同
（调参数 vs 查后端）。

**副产物**：预算调大后响应变慢，默认 30s 超时成了新瓶颈，
实测判断点 ① 在 3/5 个 task 上 `transport:ReadTimeout`。
调一个参数会撞出下一个——**改完必须重跑，不能凭推理宣布修好了**。

### 5.7 同一份输出契约不能认两题

**症状**：`FIND_PLAY_CONTROL` 静默返回 `None`，而 fake 明明回了一个 `ref`——
fake 把这次请求当成了 `IS_REACHABLE` 回答。

**根因**：fake 靠 system prompt 里的契约串反查题目，而 `IS_REACHABLE` 与
`PLAYER_OK` 的契约**字面完全相同**（同为 `bool + evidence`），先匹配到的
永远是前者。判定的 `ref` 字段就无声地丢了，答案从 `True` 掉成 `None`。

**纪律**：`question` **写进请求正文**，不靠任何文本比对推断。
通用形态：**当两个标识符可能取到相同值时，"认出来"就是猜。**
→ `llm_perceptor._ask`、`tests/fakes.py::_request`

### 5.8 嵌套 JSON 从后往前找会静默返回内层

**症状**：`{"selected":[...],"rejected":[]}` 解析成内层那个对象，
外层键全丢。判断点 ① 于是返回 `None`，且**没有任何报错**。

**根因**：为了「避开 JSON 后面的解释文字」而从后往前找 `{`——内层对象的 `{`
位置更靠后，于是被优先选中，而它恰好是合法 JSON，于是「解析成功」。

**纪律**：**从前往后**逐个 `{` 试平衡括号，第一个能 parse 的就是最外层。
通用形态：**一个能跑的解析器 ≠ 对所有形态都对。** 这条当时测试全绿——
只有判断点 ① 的 payload 是嵌套的，其余三题扁平单层，从后往前照样能取对。
→ `llm/schema_parse.py::extract_json`、`tests/unit/test_llm.py::TestExtractJson`

### 5.9 别把 fail-closed 的 `None` 当成一个判断

**症状**：两份实现对比时把「一版答了 True、另一版答 None」算成「一致」
（或反过来算成「分歧」），于是报表上「W1 判这站不行」——
而真实情况是 **W1 根本没判**，它 fail-closed 了。

**实测（2026-10-09，`cli replay` 在 12 份真实存档上回放 49 道判断题）**：
规则版只答得出 **9 道（18.4%）**，其中判断点 ② `IS_REACHABLE` 是 **0/20**、
① `SELECT_PLAY_SITES` 是 **0/4**。把这两类混在一起看，会得出
「规则版判断力很差」；分开看才知道它是**诚实**的——判不出来就说判不出来。

**纪律**：三态分开数——`AGREE` / `DIVERGE`（都答了且不同）/
`ONE_SILENT`（一方 fail-closed）/ `BOTH_SILENT`。
**渲染时 `None` 必须显式印出来**，省略成空白正是这个误读的来源。
→ `perception/replay.py::Comparison.verdict`

### 5.10 基线本身是错的时，任何准确率都是假数字

**症状**：算出「LLM 版准确率 95%、规则版 40%，所以 LLM 版更好」。

**根因**：拿 rule 的答案当真值。而实测 12 份真实存档里 rule 判成功的 3 条
**有 2 条是假阳性**（纯导航站 hao123 首页 iframe=15、youku iframe=1——
早于「iframe 不作判据」的修正）。**拿一个 1/3 正确的基线去算另一个实现
有多准，结论没有意义。**

**纪律**：对比工具**只输出分歧发生在哪里、两版各自说了什么**，
判断交人；准确率要等人工标注集——那也是 `CONFIDENCE_JUDGED` 校准的
前置条件，两件事一起做。
→ `perception/replay.py` 模块 docstring

### 5.11 模型的 fail-closed 也会产出**错的负样本**（W3 实测，判断点 ①）

**症状**：判断点 ① 接线后报表首次出现 `not_play_site`，看着分支终于活了。
翻 `negative.jsonl` 才发现 9 条里有 1 条与同一批的**成功记录直接矛盾**：

```text
negative.jsonl  not_play_site  v-wb.youku.com/…id_XNDE0NjYzODAzNg==…
    理由：现有检索摘要未显示作品标题，无法确认对应《功夫》
T011__d6badc6f  成功            同一条 URL
    理由：LLM 判 True：页面为《功夫》优酷视频播放页
```

**根因不是模型，是输入**。取 obscura 的 `browser_links` 原始 NDJSON 才发现，
bing 结果的 `text` 字段只有面包屑：

```text
{"text":"qq.com https://v.qq.com › cover","href":"https://v.qq.com/x/cover/…"}
```

片名在 `body_text` 里（同一份观察含「功夫」16 次，
`功夫 (普通话版)_电影_高清完整版视频在线观看_腾讯视频`），但**与 URL 无对应关系**。
模型被问「哪些链接是该片的播放站」，输入里没有任何一条链接写着片名——
它答「检索摘要未显示作品标题，无法确认」是**对输入的准确描述**，
随后按契约 fail-closed 成 `False`，而 `not_play_site` 是负样本分支。

**为什么这条特别危险**：fail-closed 的 `None` 不入负样本池（安全），
而**输入不足导致的 `False` 会入池**。同一个 `False`，一个安全一个污染，
区别不在模型，在**有没有能力判**——而 fail-closed 的定义正是
「没能力判就返回 `None`」。缺这层预检，W3 的守卫就只守了后端故障，
没守输入不足。

**纪律**：每道题问模型之前先问「**这个输入支持这道题吗**」。
④ 已有 `_sufficiency`（正文与元素皆空时不问模型），① 缺同款——
`links[].text` 全都不含目标片名时，① 就没有判别力，此时必须 `None`。
真要修输入（`browser_extract` 的 `field[]` 并行数组能一次取到
`li.b_algo h2 a` 的 title 与 href），那是让 ① 真能用的正路，
但**在修好之前 ① 必须先 fail-closed**，不能拿坏输入换分支覆盖率。

**通用形态**：接线一个新判断点时，「它有产出」不等于「它有用」。
负分支一接上就会往池子里写东西，**输入不足的题产出的是假负样本**，
比不产出更糟——不产出只是没覆盖，产出是往训练数据里掺错。

### 5.12 `browser_extract` 的入参叫 `schema`，返回的键不带 `[]`（一个坑，两处症状）

**症状**：判断点 ① 修完输入重跑，`result_titles` 恒为 0，
报表上 ① 仍是全 `unresolved`。看起来像**选择器失效**——
而选择器是好的。

**第一处**：`extract()` 传的是 `{"fields": {...}}`，
上游实参键叫 **`schema`**，回 `Error: Missing schema object`；
而 `extract` 的 `on_error="empty"` 把它吞成空字典。

**第二处（更阴）**：键名改对之后仍然抽不到。obscura 的 `[]` 是**入参**
约定（`titles[]` 表示取全部匹配、值为数组），**返回的 JSON 键不带 `[]`**：

```text
入参 {"titles[]": "li.b_algo h2 a", "urls[]": "li.b_algo h2 a@href"}
返回 {"titles": [...9项...], "urls": [...9项...]}      ← 键名没有 []
```

按 `titles[]` 读永远读到 `None` → `result_titles` 恒返回空字典 →
① 恒 fail-closed。**同一个症状，两层不同的错。**

**为什么两个坑叠在一起特别难查**：obscura 的 `tools/list`
**不返回 `inputSchema`**（实测四个采集 tool 全是 `null`，
它把 schema 放在自定义的 `input_schema` 键里），所以键名只能靠
`probe_returns.py` 取证；而 `[]` 的不对称只在真实响应里才看得见，
fixture 天然会照着入参写，于是**离线测试全绿**。

**纪律**：接一个没验过的 tool，**先跑探针拿原始返回**，再写解析。
参数名与返回形状是两回事，且都不能靠类型标注或文档推断。

**修复后的实测**（`probe_result_titles.py`，2026-10-09）：

```text
bing  : 9 对，标题含片名 9 条   面包屑含片名 0/32   ← 对照组
baidu : 9 对，标题含片名 9 条   面包屑含片名 26/99
```

**注意 baidu 那一行**：默认引擎的 `browser_links` 本来就带片名，
而 bing 不带。也就是说判断点 ① 的输入缺陷**只在 bing 上出现**——
这正是 §5.11 里「实测 bing 面包屑」那条的补充：**别把一个引擎的
观测推广成全体**。

### 5.13 缺 `--title` 拿 `task_id` 顶替：整批作废且**零报错**（W1 实测）

**症状**：`run --engine bing --perceptor llm`（忘了 `--title`）跑完，
报表一切正常：候选 7 个、站点 6 个、分支齐整、警告只有一行
「判断点 ① 选出 0/6」。逐条读 evidence，**每条都很有道理**：

```text
https://www.bridgestone.com.cn/passengercartire/premiumtouri
not_play_site  判断点 ① 未选中该站点。该链接是普利司通 TURANZA T001
               轮胎产品介绍页，不是视频播放页。
```

**根因**：`title` 缺省时拿 `task_id` 顶上，于是检索式成了
**`T001 在线观看`**——搜回来的是**轮胎** T001（泰坦途 Turanza 胎压监测）。
模型答得完全正确，只是被问了一个错误前提下的问题。

**为什么这是最贵的一种静默**：它不报错、不空转、每条记录自身自洽。
读存档时看到的是一份「模型很有理的拒绝记录」，
**没有任何东西提示片名是错的**——片名就写在存档顶层的 `title` 字段里，
而那个字段写着 `T001`，谁会去看它一眼。

**纪律**：片名是判断点 ① 的**唯一判据来源**（`_title_link_sufficiency`
靠它核对链接文本），缺它就必须 fail-closed——与 `OBSCURA_EXE`、
LLM 后端配置同一条：**缺件即报错，不猜**。已在三处设防：
CLI 手工路径、CLI 计划路径（逐条列出没片名的 task）、`Orchestrator.run`
（`ValueError`，且在**建记录与导航之前**抛，不给半批产物落池的机会）。

**通用形态**：「默认填上某个值」比「报错」贵得多，
因为填上的那个值**看起来是对的**。编号、ID、占位符都属于这一类——
它们能通过所有类型检查与存在性检查。

### 5.14 负分支的前置事实不成立时，降级为 `unresolved`

**症状**：一条 `component_unverified` 负样本，理由是

```text
LLM 判 False：页面未检测到任何 video 或 iframe 元素，且仍显示影片详情
和"立即播放"按钮，并非实际播放页。
```

点开存档才发现：点击前后两次观察的正文与元素数**完全相同**
（390 字 / 37 元素 / `video_tag_count=0`），说明**点击根本没把页面带进
播放页**。而这个站有《功夫》、有播放按钮，只是我们没点进去。

**根因**：分支名是**结论的标签**，而每条负分支的定义里都带一个前置事实——
`component_unverified` 的定义是「**有 video 标签**但播放器未正常加载」。
映射只看「模型说了 False」，前置事实不成立时照样贴标签。

**为什么这类错最贵**：负样本池的全部价值是「这里真的看不了」。
贴错标签不是噪声小一点，是**把可看的站写成看不了的**，
而这类样本进了池，人工也未必再看得出它是错的——
理由写得通顺、结论看着专业、`component_unverified` 听起来完全合理。

**纪律**：贴标签前核前置事实（`BRANCH_PRECONDITION`），
不成立就降级为 `unresolved` 交人工，并**把模型原话保留在证据里**——
降级不是改写结论，读的人需要看到「它当时说了什么」。

**通用形态**：任何「按结论映射标签」的地方，
都要问一句**「这条标签的定义里有哪些前提，而输入满足吗」**。
映射函数看不见 `Observation`，它只看得见一个 bool。

### 5.15 「0 个交互元素」不等于「没有控件」——两版实现必须同一口径

**症状**：`no_play_control` 负样本一条，理由是
「0 个交互元素中，词表与模型均未找到非预告播放控件」。
而那份观察的正文有 100 个字符，里面明明白白写着**「立即播放」**。

**根因**：`RulePerceptor` 早就写了 `not obs.interactive_elements → None`
的守卫，**`LLMPerceptor` 没有**。obscura 对空页面返回哨兵文本
（`No interactive elements on this page.`）而不是错误，
所以 `degraded` 抓不到它；而正文与元素来自**两个独立的 tool**，
正文成功不代表元素也采到了。

**关键**：不能拿「有正文」当「渲染完了」的证据。现有的
`not body_text and not interactive_elements` 是**两者皆空**才判不足，
于是「100 字正文 + 0 元素」这一格从守卫底下漏了过去——
而这一格恰恰是视频站最常见的形态。

**纪律**：同一道题在两个实现下的口径必须由**同一组契约测试**钉住
（`IMPLEMENTATIONS` 参数化跑七不变式 + 这条）。否则「换 `--perceptor`
就换一批标签」，而报表上完全看不出来。

**通用形态**：**加了一个新实现，就是加了一份要保持一致的行为。**
只在新实现上补测试，等于默认旧实现是对的。

### 5.16 `@property` 上的括号——「命令写完了」不等于「命令能跑」

**症状**：`cli purge-run --run-id b3a3548a --apply` 抛
`TypeError: 'WindowsPath' object is not callable`，
而**预演（不加 `--apply`）一切正常**。

**根因**：`negative_pool_path` 是 `@property`，`apply_purge` 里多写了一对
括号 `self.negative_pool_path()`。预演走的是 `purge_run`，那里写法正确——
**预演与执行是两条路径**。而 `purge_run` / `apply_purge` 写完时**一条测试
都没有**，所以这条路径从来没被真正执行过。

**顺带查出的两个真隐患**（都在同一个函数里，靠补测试才暴露）：

1. **回滚顺手清掉全池坏行。** 池子被回滚时整体重写一遍，而读的时候坏行
   是跳过的——不保留就等于**每回滚一次顺手把全池的坏行清干净**。
   坏行可能是被人手工截断、正等人查的，不该由一个 run 级回滚顺手决定。
2. **传错的 `rows` 会连坐别的 run。** 原实现是「取所有传入行的 `run_id`
   集合，删掉命中集合的行」——签名说「删这些行」，实现说「删这些 run_id
   的所有行」。两者在正常路径上**完全等价**，只有调用方混进一行别的 run
   的行时才分辨得出来，而爆炸半径是静默扩大的。

**纪律**：**破坏性命令的「执行路径」必须和「预演路径」分别有测试。**
预演绿只证明**列表逻辑**对，不证明**删除逻辑**对——而后者才是会毁数据的那半。

**变异时测试自己也要变异**：补这条测试时第一版构造的「库里不存在的行」
只改了 `url`、没改 `run_id`，于是它压根没扩大爆炸半径，
**按 run_id 删的老实现照样全绿**。断言写完要拿老实现打一遍，
确认它真的会红——绿色的变异说明断言没测到东西。

**通用形态**：**任何会重写/删除既有产物的代码路径，
「读得对」和「写得对」要分别验证。**只测读的那半，
写的那半会带着 bug 活到第一次真实执行。

### 5.17 三支「没判出来」合并成一支，复核队列就失去分工

**症状**：报表上 `unresolved` 一支占了大半，看不出该修什么。
问「这些 run 卡在哪」，答不上来——**它们卡的地方不一样**。

**根因**：`unresolved` 这一支同时装着三种成因：

| 情形 | 不确定的是什么 | 该修的 |
|---|---|---|
| 环节①–④ 返回 `None` | **能不能到**播放页 | 感知层能力（`RulePerceptor` 只会返回 None） |
| 环节⑦ 返回 `None` | 组件**能不能用**（播放页就在眼前） | 采集充分性 / 判据 |
| 词表判不准 | 是不是预告 | 词表覆盖 |

「修感知层」与「修采集」是两条完全不同的路。混在一支里，
报表既指不出该修哪条，复核员也分不出「请补一条判据」（环节①–④）
与「请看一眼这个页面」（环节⑦）——后者手上就有页面。

**已修**：2026-10-09 环节⑦ 的 `None` 拆成 `player_unverified`
（`RunLedger.record_unresolved_reached`）。**分流点必须在 `record_from` 之前**——
`record_from` 会把 `None` 一律记成 `unresolved`，那正是它管不到的情形。

**净影响比看上去小**（这决定了改它的风险等级）：

- `negative.jsonl` **不变**——三支都不是负样本，都不并池；
- 复核队列**条数不变**——`unresolved` 本就在 `REVIEW_BRANCHES` 里；
- 只有标签变准。而报表的 `by_branch` 变了。

**历史存档不回填**（项目纪律：并池是写入时的动作，不是读取时的推导）。
于是批次边界两侧不可比：`unresolved` 降、`player_unverified` 升，
不记批次就会被读成「fail-closed 修好了」。

**通用形态**：**分类的粒度要对着「该怎么修」划，不是对着「是不是失败」划。**
「不是负样本」回答的是第一个问题，「为什么不是」回答的才是第二个——
而报表和队列都只会问第二个。

## 六、环境与外部依赖

### 6.1 搜索引擎会限流

**症状**：同批连跑，第 1 条正常，后 2 条被重定向到
`wappass.baidu.com/static/captcha/tuxing_v2.html`（标题「百度安全验证」）。

**处置**：加请求间隔，或 `--engine bing`（实测 11 候选 vs 5 候选，
分支覆盖 4 种 vs 2 种）。**直接重跑同一引擎大概率仍是验证码页。**

**纪律**：这类拦截**必须在 `report` 里排在分支分布之前**并单列统计——
它是运行级的，一次拦截会让后面所有分支分布都偏小，先看分支会被带着往下读。

### 6.2 `OBSCURA_EXE` 必须显式设

**症状**：`[FAIL] 未设置 OBSCURA_EXE`。

**纪律**：代码**故意不查 PATH**（猜命令名换机器时会静默走到别的实现上）。
即便 exe 已在 PATH 里也要设：

```powershell
setx OBSCURA_EXE "C:\Users\klpc\workspace\tool\obscura-x86_64-windows-stealth\obscura.exe"
```

`--stealth` 仅在 stealth build 存在该 flag；目录名带 `-stealth` 的即为 stealth build。

### 6.3 Windows GBK 控制台

**症状**：探针上的 ✅/⚠️ 把整条链带崩；`pytest` 输出中文全是乱码。

**纪律**：脚本内加 `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`；
Bash 里跑 Python 用 `PYTHONIOENCODING=utf-8`。

`cli._reconfigure_stdio()` 分两种情况：
`tty` 时只放宽 `errors` **不改 `encoding`**（PowerShell 下当前编码本就正常，
不该替用户改掉）；**非 tty 时强制 `encoding='utf-8'`**——
重定向或走管道时 Python 按 locale 输出，也就是 cp936，
实测 `cli check-archives > out.txt` 写出的首字节是 `0xB4 0xE6`（GBK 的「存」），
按 UTF-8 读直接报错。**CI 日志、重定向文件、任何读档的下游脚本全是坏的**，
而那恰恰是没有控制台代码页、消费方是程序的场合。

### 6.4 终端乱码 ≠ 存档内容坏了

**症状**：读存档看到 `evidence` 是一串 `U+00FD` 加一串 U+FFFD 加 `video/audio=0`，
第一反应是「P1 里中文全烂了，落盘编码写错了，去改 `archive.py`」。

**实测反过来**：2026-10-09 拿现存 12 份真实存档逐条查，
**37 条 outcome 的 `evidence` 无一损坏**——那串乱码是 Windows 控制台
把 UTF-8 渲染成 cp936 造成的，`sys.stdout.reconfigure` 一下就正常。
落盘路径一直是干净的（`archive.py` 显式 `encoding="utf-8"`）。

**真正坏掉的是别的东西，而且范围小得多**：4 份 T001 存档的 `visits[3]`
（tv.sohu.com）`body_preview` 中间 109..225 那段，以及同页一个 `<a>` 的 label。
同一段里 `导航` / `倍速` 这些中文与 ASCII 都是好的，只有中间夹着
U+01F3 / U+0439（Latin 扩展与西里尔字母）的一小片烂成 U+FFFD——
**整档换编码写错会把正常中文一起烂掉，实测它们是好的**，所以触发条件是
站点声明的 charset 与实际内容不一致。同一批 11 个站没事、同一个站 4 次全坏，
**重跑同一批不会变好**。

**纪律**：判断「文件里是不是真有 U+FFFD」必须**落盘后重新解码**，
且用 `strict`——在终端里 `print` 出来的样子不作数。
`cli check-archives` 的 `mojibake` / `evidence_mojibake` 干的就是这件事，
两种结果分两档严重度（坏在观察里只降级那条，坏在 `outcomes[*].evidence`
才让那条结论作废）：混成一档的话，「1 个站的正文烂了」会把整批 20 个
访问点一起判死，而门禁一旦老报 FATAL，人就会开始整体忽略它。

## 七、测试与验证

### 7.1 每条纪律配一个「反过来仍成立」的反例

**要点**：只有正例的检查可能是恒过的假检查。
探针在真实骨架上 189/189 通过之后，必须用反例验证它**不是恒过**：

| 反例 | 期望 |
|---|---|
| 同义改写（网址→地址） | 放过 |
| 掉「网址」要求 | 抓到 |
| 掉「全集」要求 | 抓到 |
| 只剩语气词 | 抓到（过短） |
| 空串 | `FAIL_EMPTY` |
| 正常骨架 | 189/189 通过 |

### 7.2 测试写错 ≠ 守卫有问题

**两次实例**：

1. 断言「片名不在结果里」——错，半指代**本就**保留片名
2. 用例文本「没有网址也没有集数」**含探针词**，探针正确放行——用例本身写错

**纪律**：测试失败先问「是守卫错了还是用例错了」。反例用错措辞比没反例更坏。

### 7.3 绕过前置过滤的测试会撞上早退路径

**症状**：直接调 `renderer.render()` 时 `applied: {}`，返回骨架原文。

**根因**：`纯描述 × single_title` 是**不兼容组合**，渲染器**早退返回原文**——
这是设计行为（说不出片名却要求找到那一部，逻辑不可能）。

**纪律**：测渲染必须先过 `renderer.is_compatible()`；
并断言实际覆盖了足够条数（如 `checked >= 20`），
否则检查可能在少量样本上空转。

### 7.4 只有真读一遍才会暴露的缺陷

**要点**：4.1–4.4 的四个措辞缺陷，**探针全绿、测试全过、离线体检全过**，
是接线之后第一次端到端真读渲染文本才看见的（16 条里 14 条有粘连）。

**纪律**：跑长批前 `--dry-run` 看一眼；产出新格式的**人能读的文本**时，
必须**真读一遍**——判分保真探针管不到表达质量。

### 7.5 绿测试不等于有覆盖（变异测试）

**症状**：全部测试通过，而守卫其实从没执行过。一个恒假的 `if` 也能让门禁全绿。

**根因**：断言只覆盖了**会走的那条路**。新增的守卫（预检、白名单、
优先级）都写在 `if` 分支里，而"正常路径"的测试根本进不去那些分支。

**纪律**：给每条新守卫配一条**变异测试**——把它删掉/改坏，确认对应测试变红，
再恢复。`output/pipeline/mutation_check.py` 是本次的一次性工具（12 条变异，
含「把变异标成 CRASH」的判据：**报 `error` 而非 `failed` 说明代码被改崩了，
不构成有效验证**）。通用形态：**"删掉它测试还过" = 那条守卫不存在。**

## 八、边界纪律

### 8.1 存档是不可变真值源

**风险**：`to_json()` 是**归档那一刻**才序列化。若 `RunRecord` 只存
provenance 的引用，调用方在归档前改一次入参字典，存档内容就跟着变——
而文件名、报告、切片脚本全都不知道发生过。

**纪律**：值对象自己的边界上拷贝（`RunRecord.__post_init__`），
不靠每个调用点自觉。`orchestrator.run` 里已有的 `dict(...)` 是**有意的冗余**。

### 8.2 交接面是文件格式，不是 import

**纪律**：`executor/plan.py` **不 import** `taskgen`。

理由不止于整洁：plan 是**要长期存着的**，切片分析、失败归因、
半年后回看读的都是那个 JSON 文件。若消费端 import 生成端，
则「能读这份文件」==「生成端还在原地」，生成端一改字段旧计划全废。
**按格式读，格式就冻住了。**

### 8.3 计划文件要能说清自己怎么来的

**纪律**：`SamplingReport` 落盘 `seed`。否则「重跑一批对照」只能碰运气重跑同一个 `-n`——
而 `-n` 变了组合也全变了。`library_digest` 只锁住画像库，锁不住抽样本身。

### 8.4 默认跳过归一退回的样本

**理由**：`rewritten=False` = persona 没落地，跑出来的结果在切片表里
**长得跟「这个 persona 组合表现差」一模一样**。

**纪律**：`run --plan` 默认跳过，要跑必须显式 `--include-unrewritten`。

### 8.5 长批先 dry-run

**纪律**：`run --plan --dry-run` 只读计划并打印（真实浏览器每条约几十秒）。
跑之前值得先看一眼「到底会跑哪些条目、跳过了哪些、为什么跳」——
`--limit` 生效时也要告警，少跑的那些不留痕就等于没发生过。
