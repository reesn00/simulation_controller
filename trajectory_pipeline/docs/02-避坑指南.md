# 新树工程避坑指南

这份文档记的是**会踩什么坑、怎么一眼认出它**，不是设计决策的记录
（那些在 [`设计方案/00-总体方案.md`](设计方案/00-总体方案.md)）。

**每条的「症状」都写成你在终端、报告或测试输出里真正会看到的东西**，
这样可以直接全文搜索命中。方案文档回答「为什么这么做」，
这份回答「看到这句就该想起什么」。

条目按**复发频率**排序，不按发现时间。同一个坑踩两次比第一次更难查——
因为第一次的痕迹还在，第二次已经被误读成别的东西了。

## 一、同源纪律（本项目最高频的坑）

> **同源 = 同一个事实的推导侧与检查侧必须取自同一处数据。**
> 不同源的后果不是报错，是**两边安静地互相打架**，且没有任何告警。

### 1.1 渲染源 ≠ 约束推导源

**症状**：归一接受率 4%，12 条采样里 9 条退回骨架原文，persona 特征全部失效，
但所有测试全绿，表象只是「通过率偏低」。

**根因**：改写按 `intent.goal` 渲染，约束却按 `initial_request` 推导。
T001 的 `goal` 比 `initial_request` 少一个「全集」→ 探针必然判失败。

**纪律**：`renderer` 统一用 `skeleton.initial_request`（它才是首轮消息的来源），
`goal` 只作元数据。改写与判分要求检查必须读同一份文本。
→ `taskgen/persona/renderer.py`

> 通用形态：**症状与病因隔着三层时，调症状那一侧必然把纪律静默拆掉。**

### 1.2 检测词 ≠ 探针词

**症状**：最典型的 T001 反而不含 `has_episode_range`，约束检查形同虚设。

**根因**：检测词写死 `("集数", "季数", …)`，探针词多一个「全集」。
带空格或省略的写法处处漏。

**纪律**：检测与检查**共用 `CONSTRAINT_PROBES` 一份词表**。
两套词不同源 = 推导与检查互相打架且无任何报错。
→ `taskgen/skeleton.py::_derive_constraints`

### 1.3 判定逻辑 ≠ 使用点

**症状**：`FakeDriver` 构造的观察识别不出反爬拦截，真实路径却能——
测试与生产行为不一致。

**根因**：早一个版本把 `detect_block` 放进 `obscura_driver.observe()` 并落成
`Observation.blocked_reason` 字段，采集层于是要懂「什么页面是反爬页」这种业务语义。

**纪律**：**判定逻辑必须在使用点**（`orchestrator.run` 里直接调
`detect_block(obs.url, obs.page_title, obs.body_text)`）。
让任何 `Observation`——不论谁构造的——走同一条判定路径。
→ `executor/orchestrator.py` 环节 0.5

### 1.3b 评分器的映射表 ≠ 注册表（D-5 实测，三次判反）

**症状**：D-5 打分器上线，196 条真实样本里 **54 条判 3 分**，
每条的 `why` 都写着「分支走错」——理由通顺、看着专业，
而那 54 条**全是正确的结论**。报表上只表现为「有样本得分低」，
**看不出是评分器错了**。

**根因**：`d5_scorer.QUESTION_TO_BRANCHES` 是**手写字面量**，
而同一张表在 `perception/questions.py` 的 `REGISTRY[].negative_branch` 里
已经定义过一次。手写的那份漏了 `unresolved`——而它是
`RunLedger.record_from` 的**通用 fail-closed 出口**
（`decision.answer is None` 时**一律**记它，与判断点无关）。实测 48 条
`find_play_control → unresolved` 因此被判错。

**后两版又各错一次**，同一个根因的另外两面：

- v2：前置事实**按分支一刀切**（`unresolved` 整条要求「已到播放页」）。
  而 `unresolved` 有两种语义：环节①②③ 的「**能不能到**」未决（实测 48 条，
  合法且正常）与环节④ 的「**能不能用**」未决。只有后者要求播放页。
  **61 条正确记账被判错。**
- v3：推导映射时漏了 `player_unverified`——它走 `record_unresolved_reached`，
  **不经过** `record_from`，所以压根查不到 `negative_branch`。**3 条判错。**

**纪律**：
- **从注册表推导 + 显式叠加注册表没表达的规则**，不手写第二份。
  叠加的三条各有各的原因：`unresolved` 是通用出口；`player_unverified`
  走另一条记账路径；`component_unverified` 在 `find_play_control` 侧是
  I6 违约的显式记账。
- **「一条记录有几种语义」按 `(分支, 判断点)` 二元组判，不按分支判。**
  `component_unverified` 与 `unresolved` 各有两个判断点能产出，
  其中只有一个发生在播放页上。
- **代码判定的分支不参与 question 配对**（`unreachable_hard` /
  `trailer_only` / `trailer_suspect` 的 question 本就是空的）。
- **取值顺序也要对**：「question 缺失 → 不可判定」的检查必须排在
  「代码判定分支放行」**之后**——反了会把最该能判的三条判成不可判定。

**通用形态**：**评分器判反比不判更贵。**不判只是没有覆盖，
判反是往训练数据里掺「本来正确的东西是错的」。
而它的症状永远只是「分数低了」，所以**真实数据回归测试是必需的**：
`test_真实样本上不得出现低分误判` 这条断言在开发中真的红过三次。

→ `evaluation/scorers/d5_scorer.py`、`tests/unit/test_d5_scorer.py`

### 1.5 筛选的那份判据 ≠ 处置的那份（降级脚本实测，**两版都静默**）

**症状**：`downgrade` 跑完报「降级 N 条」，清单整齐，而：

- 第一版 N 里有 **8 条本来就该是 `unresolved`** 的记录被盖上了
  `[原判 成功(branch=None)]` 戳——把一条 fail-closed 记录改写成
  「当初判成功、被人工推翻了」，并翻了 21 个 `visits[].success`；
- 改完再读存档，**一条没变**。

两者都**零报错**，且都长得像成功。第一版跑完只有一句总数，
第二版的返回值还明写「降级 8 条」。

**根因**：两处同一个错误的两面，都是**筛选与处置没走同一份东西**。

- 遍历函数用 `predicate` 预筛「有没有命中」，处置函数**自己按参数重筛一遍**。
  于是 predicate 说「不算」的记录照样被降级——**处置范围静默扩大**。
- 处置函数收 `path` 并**内部自己重读一份**再写盘，而调用方传的 `hits`
  来自**它自己读的那一份**：改的是 A 对象、写的是 B 对象，**什么都没落盘**。

外加一层：为求幂等把匹配条件从 `branch is None` 放宽成
`branch in (None, "unresolved")`——**命中条件放宽 ≠ 判据放宽**。
幂等判断该看「有没有处置戳」（`evidence` 头），不靠 branch 值。

**纪律**：
- **筛选归调用方，处置只归处置方，但处置拿的是调用方筛完的那一批**，
  不重筛。一份判据两处都用，分家就会分叉。
- **对象全程持有到底**：读 → 筛选 → 处置 → 写盘在**同一个对象**上，
  「改的不是写的那个」结构上不可能发生。
- **不落盘就别收 `path`**：函数名与签名上就要让人看出它只改内存，
  否则「以为它写过了」是这整份代码里最贵的一类错。

→ `executor/downgrade.py`、`tests/unit/test_downgrade.py`
（`test_报告说降了就真落盘了` 断言的是**文件**变了，不是返回值）

### 1.6 分发的那份清单 ≠ 注册的那份（新增子命令必踩）

**症状**：新加的子命令**跑完了、清单整整齐齐打完了**，然后
`ValueError: a coroutine was expected, got 0` 崩在最后。
退出码非零，而输出看着像干完了活。

**根因**：`main()` 里有一份**手写的命令名清单**决定「这个要不要走
asyncio」。它与 `set_defaults` 是两件事，必须手工保持一致——
加子命令忘了改清单，同步命令就被塞进 `asyncio.run`，而 `asyncio.run`
要的是协程。

**纪律**：**别让第二份存在**。要判断「是不是异步」，看
`inspect.iscoroutinefunction(args.func)`——**从函数本身推**。
判据就在被判断的对象上时，不需要清单。

→ `executor/cli.py::main`、
`tests/unit/test_cli_dispatch.py::test_没有第二份命令名清单`

> 通用形态：**每加一个注册项就要记得改的那张表，就是下一个静默 bug。**
> 判据应当来自对象自身，而不是来自另一处对它的记载。

### 1.7 写含正则/转义的源码禁用 Bash heredoc

**症状**：源码里 `\xNN` 变成真控制字符，`re.compile` 在运行期才炸。

**纪律**：用 Write / Edit 工具写源码，**不要** `python << EOF`。
→ 见 memory `bash-tool-escapes-backslash-x`

### 1.8 把 `{tag,label}` 统一改名成 `{role,name}`：名字统一了，值域没统一

**症状**：契约测试绿、跑分正常、`element` 长成 `{"role": "button", "name": "播放"}`
比 `{"tag": "button", "label": "播放"}` 顺眼得多。但拿这批样本和前一批**并池**统计
`role` 分布时，`button` 里混着 ARIA 角色而不是 HTML 标签名——同一个 `<input type=button>`
在 obscura 面记 `input`、在 camoufox 面记 `button`。**没有任何报错**，分布悄悄变成两套口径的并集。

**根因**：`role` / `name` 是**槽位名**（「元素的种类 / 元素的文字」），两个执行层往同一个槽位里填的是
**两份不同词表的值**（`html_tag` 面 vs `aria_role` 面）。把键名统一成一套看起来是「清理」，
实际是把两份值域并成了一份——**口径标记被抹掉了**，混池从此没有依据。
名字统一 ≠ 语义统一；最难查的正是这种「改了名但没人报错」的漂移。

**纪律**：**槽位统一、值域不统一、不互译**。键名按方言投影——`obscura-1` 面写 `{tag,label}`
（与 361 条存量 P2 样本逐字节同形），`camoufox-1` 面写 `{role,name}`；`input` **永不**变成
`textbox`。方言不手填：P1 `RunRecord.driver` → `surface_of_driver()` → `dialect_of()` 一对一折算，
**认不出的 driver 直接抛，不猜、不静默回落**。并池前先按面分组。
不做这一步的代价是「报告上看不出异常」——所以它由三表同键的契约测试封着。

→ [`common/elements.py`](../common/elements.py) `ELEMENT_KEYS` ·
[`toolcatalog/__init__.py`](../toolcatalog/__init__.py) `SURFACES`/`DIALECTS` ·
`tests/contract/test_element_dialect.py::Test一条轴` / `Test存量口径`

### 1.9 方言由调用方传参：值对、键错，报告上看不出异常

**症状**：一个 camoufox Run 的存档里 `role`/`name` 的值全对，落盘的键却是
`{"tag": "textbox", "label": "搜索"}`——`tag` 里装着 ARIA role。契约照过、运行不报错，
渲染出来的 `- <textbox> 搜索` 甚至「挺好看」。**是写新契约测试时被断言当场抓出来的**，
不是运行暴露的。

**根因**：`_obs_json(obs, vocabulary=...)` 的方言**由调用方传**，默认值 `html_tag`。
多一个调用点忘传，就静默回落——这正是 [1.6](#16-分发的那份清单--注册的那份新增子命令必踩)
的老形态：**判据就在被判断的对象上**（`obs.element_vocabulary`），却被抄成一份调用方要维护的参数。

**纪律**：观察的方言**从数据自己推**——`_obs_json(obs)` 内部读 `obs.element_vocabulary`，
**不接受调用方指定**；只有整条 Run 的顶层元数据（`RunRecord.to_json`）走
`_vocabulary_of_run()`，它先读观测、观测一条都没有才退回 driver，且认不出仍然抛。

→ [`executor/orchestrator.py`](../executor/orchestrator.py) `_obs_json` / `_vocabulary_of_run` ·
编年史 [§增量六十七](计划进展/90-增量编年史.md)

## 二、计数与记账

> **计数说谎比不计数更坏。** 不计数让人知道这里有损失；
> 说谎的计数让人**基于错的数字下结论**，而且毫无察觉。

### 2.1 字段名与字段值不同语义

**症状**：`gen` 打印「排除 98 个」，而 `--all-modes` 下**一个都没排除**。

**根因**：`excluded_by_skeleton_mode` 填的是**全库 mode 分布**。
字段名说 excluded，值里却含「未排除」的项（81 个 single_title 是被用上的）。

**后果**：`--all-modes` 时报「98 次因骨架模式排除」；读的人会以为真排掉了 98 个，
进而以为「剩下 81 个都被用上了」，而实际用的是 98 个里的任意若干。

**纪律**：
- `excluded_by_skeleton_mode` 只记**真被排除**的（判据取 `runnable_in_w1` 属性本身，
  不硬编码模式名——属性才是真值源）
- `mode_distribution` 记全库分布，无条件
- 加**自洽性测试**：排除数 + 可跑数 == 全库
→ `taskgen/sampler.py`

### 2.2 静默剔除让损失不可见

**症状**：存档写着 11 个候选，没人知道引擎原本给了 50 个链接、其中多少被规则扔掉。

**纪律**：剔除**必须带原因计数**。`extract_candidates(..., stats=...)`
是可选出参，填 `{"excluded_host:baidu.com": 16, "duplicate_host": 1}`。
`engine_self` 与 `excluded_host:<root>` 分开记——读的人处置不同。
→ `executor/steps/search.py`

### 2.3 缺字段 ≠ 空值

**症状**（三次，同一款病）：

1. persona 切片全落到 `(无 provenance)`——分不清「不是 taskgen 跑的」与「taskgen 没生效」
2. `report` 把存量存档（字段引入前跑的）算成「可跑」——
   而那批**恰恰最不该算**（被验证码页拦下的）
3. **D-6 把 20 条老存档判成「播放页 URL 缺失」**——
   而那 20 条的 `play_page_url` **键压根不存在**（字段 2026-10-10 才补），
   结论本身完全正确

**根因**（三个各不相同，但都是「把两件事折叠成一个值」）：

1. `provenance.get("persona_id")` 与 `data.get("search_blocked") or ""`
   把「字段不存在」与「字段为空」折叠成同一个值。
2. 同上。
3. ⚠️ **而这条最隐蔽**：缺字段信息在 **`to_json` 之后已经丢了**——
   `OutcomeRef` 无条件输出 `site_url`/`play_page_url`，
   老存档的「键不存在」渲染成 `""`，与「键在但值为空」**完全同形**。
   于是评分器里的 `_has_key(outcome, "play_page_url")` **恒为 True**，
   守卫写了、看着在、实际从不生效。

**纪律**：
- 空 `dict` 的含义**固定为「不是 taskgen 跑的」**，绝不兼表「没生效」
- 存量存档缺字段时，用**同一个判定函数**从存档里确定性重算，
  并在输出里**标注「存量存档重算」**
- **经过序列化之后，缺字段信息必须单独记一条**
  （`OutcomeRef.p1_missing_fields` 逐条记「P1 里没有这个键」）。
  靠序列化后的形状推断「键在不在」是**恒过的假检查**。
- **判缺失之前先问一句：这个键在源头真的存在吗**——
  拿一个本就不该存在的字段去核，得到的是**采集器缺件**，不是**轨迹不合格**。

→ `executor/plan.py`、`executor/cli.py::cmd_report`、`assembler/schema.py`、
`evaluation/scorers/d6_scorer.py`

### 2.4 中位数混了不同尺度的观察：整体读数会**翻号**

**症状**（2026-10-21 第二轮双跑）：`compare-drivers` 的判据②③ 报
「B 面正文更长」，按族拆开却是**三个族里有两个 B 更短**；
判据③' 的共享口径另报「播放页族 A 60 / B 35（B 更少）」——
**两个判据指向相反方向**，而报表上只有一行数。

**根因**：「一个观察」不是同一个尺度的东西。`search` / `step` /
`visit_step` / `site_obs` / `player_obs` 五族，正文长度与元素数
**差一个量级**。把它们塞进**同一个中位数**，得到的数**由各族占比决定**——
某族多一条，整体就翻向。

**纪律**：
- 跨族比大小**一律分族**：报告按观察槽族分列，**族内比，族间不比**
- **不出「总计行」**：各族**不投票、不合成**——合成就是把不可比的数加起来
  （与「禁止投票/集成」同一条纪律）
- 「归因表」里各档的**中位数不可相减**：各中位数来自**不同的观察**
  （实测 candidates 52 − hidden 3 ≠ visible 31）。要逐观察看落差，
  跑 `research/probes/inc72_ladder_identity.py`
→ `executor/dual_run.py`、`executor/browser/element_basis.py`

### 2.5 「没测出来」不是「测出来是好的」——**缺基线的项不许进分母**

**症状**（2026-10-21 增量七十四）：判据⑥ 的动作重放读数里，
3 条旧批次存档的条目**没有可比基线**（既没标题也没正文长度）。
若把「页面没漂」写成 `False`（= 没漂），报表上就长成
「3 条**验过**，页面没漂，定位到了」——而真相是**这 3 条从来没比过**。

**根因**：「没读到」与「读到的是这个」在布尔值里**同形**：
`False` 既可以是「读到了，确实没漂」，也可以是「没读，漂不漂不知道」。
把两种情况塞进同一个 `False`，**失败就消失了**。

**纪律**：
- **缺基线 ⇒ 记 `null`（未知），不许记 `False`**；分母只取「**真的量到了**」的条目
- 归因要**三列并排**：读数 × 当时在不在采集面阶梯里 × 页面漂没漂——
  少一列就会把「站点改版」误记成「动作不可移植」
- 同一族的坑：**拦截率不分桶**（§3.7）、**中位数不分族**（§2.4）、
  **降级表不可相减**（§2.4）——都是「把不同口径的数字摆到一张表上」

→ `research/probes/inc73_action_replay.py`

## 三、判定与感知边界

> 铁律：**代码层做护栏，LLM层做探索。**
> 判据必须是 URL / 标题 / 标签计数这类**客观字符串**，
> 一旦需要「理解这句话的意思」，就该问 Perceptor。

### 3.1 绝不 fail-open

**症状（正确行为，别改）**：搜狐页面 200 个交互元素无一命中词表，
但页面已有 `<video>`×1 → 判 `unresolved`，**不判 `no_play_control`**。

**证据文本**（落进存档的原文）：
> 「200 个交互元素无一命中词表，但页面已有 `<video>`×1——「没有播放控件」与观察自相矛盾，不判负」

**纪律**：观察与判定**自相矛盾**时，一律 `unresolved`（fail-closed）。
矛盾点要写进 `evidence`——那是复核时唯一能看出问题的地方。
→ `perception/rule_perceptor.py`

### 3.2 iframe 数量不作判据

**症状（要避免的回归）**：导航站满屏 iframe，早期版本据「有 15 个 iframe」
把 hao123 判成播放页。

**纪律**：`PLAYER_OK` 只认 `<video>` / `<audio>` **标签存在性**；
iframe 数量只写进 `evidence` 作排查线索，不进判据。

### 3.3 正文有歧义时不要拿它当判据

**症状**：百度验证码页正文是「网络不给力，请稍后重试」。

**风险**：拿它当反爬判据 → **真网络故障会被误判成反爬，正好与目的相反**
（网络故障 → 重试；反爬 → 换引擎/加间隔）。

**纪律**：反爬判定**只看 URL 路径与页面标题**（`/captcha`、`wappass`、「安全验证」），
正文只认「访问过于频繁」这类**明确限流措辞**，且与网络故障措辞不重叠。
→ `executor/dom.py::detect_block`

### 3.4 反爬是运行级状态，不是失败分支

**纪律**：`search_blocked` **不进** 8 条 outcome 分支体系。
那套分支每一支都对应「这个站点看完之后的结论」，而拦截发生在**取候选之前**，
根本没有 outcome。塞进去会让负样本池混入**连站点都没访问到的条目**。

### 3.5 被拦的必须排除出切片

**症状**：persona 切片里出现 `half-悬疑 0/1`，读作「这个 persona 组合表现差」，
真相是「这条压根没跑」。

**纪律**：切片只含**实际跑过**的 task，且行数变化时**明说排除了几个**。
切片表的说服力会被这种行毁掉。

### 3.6 结构上不可能 ≠ 页面上没有

**症状**：bing 结果里混进 `help.bing.microsoft.com`、`beian.miit.gov.cn`（ICP 备案查询），
全判 `no_play_control` **直接进负样本池**。

**纪律**：
- 域名剔除按**注册域族**（带点边界：`host == root or host.endswith("." + root)`），
  不用裸 `endswith`——后者让 `help.bing.microsoft.com` 逃过 `www.bing.com` 的判定，
  且会误杀 `notbing.com`
- 只放**结构性不可能**的域（`gov.cn`），**不加 `edu.cn`**：
  部分高校图书馆确有影视资料页，误杀虽代价更低但**可避免**；
  `gov.cn` 不可能有影视资源，无误杀可能
- 「页面上没有播放控件」仍归感知层，**不在代码层判**
→ `executor/steps/search.py`

### 3.7 把登录墙算进「反爬拦截率」：同一批数据，两个相反的结论

**症状**（2026-10-21 第二轮双跑）：合并口径报
「A 19.15% / B 34.09%」⇒ 读作「camoufox 被拦得更凶」；
只留**真·反爬**读作「A 14.89% / B 9.09%」⇒ 读作「camoufox 被拦得更少」。
**同一批存档，两个相反的结论**，而前者是顺手就会用的那个。

**根因**：合并口径把**登录墙**（`login_required` / `login_wall_or_blocked`）
与**真·反爬**（`blocked`）算成一类。登录墙是**内容侧的访问控制**，
反爬是**采集侧的拦截**——两者处置完全不同（前者可能是负样本，
后者是**运行级状态**、压根不进分支体系，见 §3.4）。
混在一起算出来的「拦截率」**没有处置含义**。

**纪律**：
- 报拦截率**必须分桶**：`blocked`（真·反爬）单列，登录墙单列，**不合并**
- 报之前先问「**这个数是用来决定什么的**」：反爬率高 ⇒ 换执行层没意义；
  登录墙高 ⇒ 那是内容问题，与执行层无关
- ⚠️ 合并口径**看起来更严**，所以更容易被顺手采用——
  而它**恰好在这批数据上把结论读反**
→ `executor/dual_run.py`（`ANTI_BOT_BRANCHES` / `ACCESS_WALL_BRANCHES`）

## 四、判分保真 ≠ 表达质量

> **探针全绿 ≠ 话是人话。**
> `CONSTRAINT_PROBES` 只覆盖**判分要求**，
> 句法通顺、措辞自洽、语义不打架**全都不在判分要求里**，探针一条都抓不到。

### 4.1 双句边界

**症状**：`…两天给我就行。啊。`——closer 以「。」收尾、tail 自带句号，**两个句子边界**。

**纪律**：拼 tail 前剥掉 closer 的尾部标点，让语气词落在**句内**。
→ `taskgen/persona/renderer.py::_join_tail`

### 4.2 片段粘连

**症状**：`…做版本对比慢慢找也没关系`、`对比表格这周内给我就行`。
存量 `initial_request` **大多不以标点结尾**（16 条抽样里 14 条如此）。

**纪律**：closer 前无标点则补「，」。
→ `renderer.py::_join_closer`

### 4.3 tail 接不上 closer

**症状**：`今晚要看求求了真的`——原 tail「求求了真的。」本是独立句子。

**纪律**：`VERBAL_TAILS` 每条**必须以语气词起头**（啊/呀/呢/吧/嘛/哦/噢）。
这条判据**不用中文分词**（太脆），旧词表一条都过不了。

### 4.4 措辞内部自相矛盾

**症状**：`不急，这两天给我就行`——一句里既说不急又给紧期限。

**纪律**：同档 `CLOSERS` 内部不得同时出现「不急」与紧期限词；
不得跨维度借用别档信号（「求求了」属"急"，出现在「闲时」档就是冲突）。

### 4.5 persona 只能改「怎么说」，改不了「要什么」

**症状**：产出「确认电影**类似《功夫》那样的动作片**的**版权方**」——
骨架要版权方，与动作片无关。persona 的品类偏好被冒充成用户需求。

**纪律**：`genre` 落到**检索侧**，不进表述；`OPENERS` / `SPECIFICITY_RENDER`
都不注入 `{genre}`。persona 未生效的维度**显式记进 provenance**
（`genre_in_prompt: "no:检索侧维度，不改用户表述"`），好让人区分
「有意不做」与「忘了做」。

### 4.6 opener 不带主语

**症状**：`有点想看，我想找电影…`——opener 与 goal 主语重复，拼出病句。

**纪律**：`OPENERS` 模板只留语气前缀（`嗯，` / `说起来，`），不带主语。

## 五、fail-closed 的边界

### 5.1 `unresolved` 不是负样本

**纪律**：`unresolved`（没判出来）与 `trailer_suspect`（词表判不准）
**不进负样本池**。混进去会让「负样本纯度」这个指标失去意义，
而**指标失效是察觉不到的**。

### 5.2 人工复核不得覆盖真负样本

**风险**：verdicts 文件可能混入真负样本的 url（手填 / 跨批次粘贴 /
对着旧队列编辑新存档）。无差别回填时**一次误填就把 `no_play_control` 改成成功**，
而负样本池的全部价值就是「这里真的看不了」，破坏是**静默**的
（分支分布只显示「成功 +1、负样本 −1」，看不出那条从哪来）。

**纪律**：`apply_verdicts` 只对 `REVIEW_BRANCHES` 内的分支生效，
其余计入 `ignored` 原样保留，CLI 显式告警。

### 5.3 保留原判才能测分歧率

**纪律**：回填保留 `branch_before_review` 与 `source=human`。
覆盖掉就永远测不出「人工与代码的分歧率」。

### 5.4 能力边界要诚实说出来

**症状（全 0 时）**：`共 20 个 task，成功 0`——读的人会当成「这批素材没价值」。

**纪律**：0 成功时**明说** W1 的三处能力边界
（`IS_REACHABLE` 恒为 None / `PLAYER_OK` 只认标签 / 存在性判定带 fallback_used），
让人能区分「素材质量差」与「这版规则判不了」。**不猜是哪一条原因**——
分支分布已经印在上面了，让读的人对着数字自己对。

### 5.5 LLM 不会替你 fail-closed（**W3 实测，最贵的一条**）

**症状**：iqiyi 播放页明明 `video_tag_count=1`，LLM 版 `PLAYER_OK` 判**否**，
evidence 是一段通顺的分析：「`body_text` 为空、`interactive_elements` 为空，
说明页面未渲染或采集失败，应判为不是播放器页」。

**根因**：模型**看不到采集层发生了什么**。它只看到「空的」，于是按常识推理
「空的 = 页面没内容」，然后给出一个**自信的错答案**。规则版早就防住这条
（`test_零个交互元素不判无播放控件`：哨兵返回分不清「没渲染完」与「确实为空」），
但那层保护在 `RulePerceptor` 里，**换成 LLM 就没了**——而它是最需要那层保护的地方。

**纪律**：**采集充分性在代码层预检，且发生在问模型之前**
（`llm_perceptor._sufficiency`）。可断言的硬证据是「预检失败时
`fake.calls == []`」——守卫的意义在于不把采集故障送去让模型编结论。
通用形态：**LLM 只会推理「我看到的东西」，不会推理「我没看到东西意味着什么」。**
→ `perception/llm_perceptor.py`、`tests/unit/test_llm_perceptor.py::TestSufficiencyGuard`

### 5.6 推理模型的思考与正文共用 `max_tokens` 一个预算

**症状**：`判断点 ① 未取得结论（LLM 不可用（shape:ValueError））`，
每道题都这样，报表上像「LLM 判不了」。

**根因**：`_ask` 里写死 `max_tokens=600`。本机后端是推理模型，
**思考与正文共用这个预算**，600 全花在思考上，正文一个字没吐：

```text
max_tokens= 600  finish_reason=length  content=null     （599 tok 全在思考上）
max_tokens=2048  finish_reason=length  content 截断
max_tokens=8192  finish_reason=stop    content 干净（2096 tok）
```

客户端按红线**故意不读** `reasoning_content`（那是 raw CoT），于是正文为空
这件事最终只表现为一句 `shape:ValueError`——看不出是「预算不够」还是
「后端坏了」，两者要采取的动作完全不同。

**为什么没人会去改那个数字**：症状摆在那里的是「模型答不出来」，
顺着这条线索想到「提示词不对」「模型不行」，想不到「预算被思考吃了」。

**纪律**：预算归 `LLMConfig`（`TRAJECTORY_LLM_MAX_TOKENS`，默认 8192），
**调用点一律不传**——签名默认值给 `None` 而不是数字，给了数字调用点就会
各写各的。预算用尽报 `budget:` 而不是 `shape:`，因为处置动作不同
（调参数 vs 查后端）。

**副产物**：预算调大后响应变慢，默认 30s 超时成了新瓶颈，
实测判断点 ① 在 3/5 个 task 上 `transport:ReadTimeout`。
调一个参数会撞出下一个——**改完必须重跑，不能凭推理宣布修好了**。

**排查步骤**（`budget:` 与 `transport:` 前缀怎么分诊、调完怎么验证）：
见 [04-运行手册.md「排查」小节](04-运行手册.md#排查判断点①空回传-模型没答)。

### 5.7 同一份输出契约不能认两题

**症状**：`FIND_PLAY_CONTROL` 静默返回 `None`，而 fake 明明回了一个 `ref`——
fake 把这次请求当成了 `IS_REACHABLE` 回答。

**根因**：fake 靠 system prompt 里的契约串反查题目，而 `IS_REACHABLE` 与
`PLAYER_OK` 的契约**字面完全相同**（同为 `bool + evidence`），先匹配到的
永远是前者。判定的 `ref` 字段就无声地丢了，答案从 `True` 掉成 `None`。

**纪律**：`question` **写进请求正文**，不靠任何文本比对推断。
通用形态：**当两个标识符可能取到相同值时，"认出来"就是猜。**
→ `llm_perceptor._ask`、`tests/fakes.py::_request`

### 5.8 嵌套 JSON 从后往前找会静默返回内层

**症状**：`{"selected":[...],"rejected":[]}` 解析成内层那个对象，
外层键全丢。判断点 ① 于是返回 `None`，且**没有任何报错**。

**根因**：为了「避开 JSON 后面的解释文字」而从后往前找 `{`——内层对象的 `{`
位置更靠后，于是被优先选中，而它恰好是合法 JSON，于是「解析成功」。

**纪律**：**从前往后**逐个 `{` 试平衡括号，第一个能 parse 的就是最外层。
通用形态：**一个能跑的解析器 ≠ 对所有形态都对。** 这条当时测试全绿——
只有判断点 ① 的 payload 是嵌套的，其余三题扁平单层，从后往前照样能取对。
→ `llm/schema_parse.py::extract_json`、`tests/unit/test_llm.py::TestExtractJson`

### 5.9 别把 fail-closed 的 `None` 当成一个判断

**症状**：两份实现对比时把「一版答了 True、另一版答 None」算成「一致」
（或反过来算成「分歧」），于是报表上「W1 判这站不行」——
而真实情况是 **W1 根本没判**，它 fail-closed 了。

**实测（2026-10-09，`cli replay` 在 12 份真实存档上回放 49 道判断题）**：
规则版只答得出 **9 道（18.4%）**，其中判断点 ② `IS_REACHABLE` 是 **0/20**、
① `SELECT_PLAY_SITES` 是 **0/4**。把这两类混在一起看，会得出
「规则版判断力很差」；分开看才知道它是**诚实**的——判不出来就说判不出来。

**纪律**：三态分开数——`AGREE` / `DIVERGE`（都答了且不同）/
`ONE_SILENT`（一方 fail-closed）/ `BOTH_SILENT`。
**渲染时 `None` 必须显式印出来**，省略成空白正是这个误读的来源。
→ `perception/replay.py::Comparison.verdict`

### 5.10 基线本身是错的时，任何准确率都是假数字

**症状**：算出「LLM 版准确率 95%、规则版 40%，所以 LLM 版更好」。

**根因**：拿 rule 的答案当真值。而实测 12 份真实存档里 rule 判成功的 3 条
**有 2 条是假阳性**（纯导航站 hao123 首页 iframe=15、youku iframe=1——
早于「iframe 不作判据」的修正）。**拿一个 1/3 正确的基线去算另一个实现
有多准，结论没有意义。**

**纪律**：对比工具**只输出分歧发生在哪里、两版各自说了什么**，
判断交人；准确率要等人工标注集——那也是 `CONFIDENCE_JUDGED` 校准的
前置条件，两件事一起做。
→ `perception/replay.py` 模块 docstring

### 5.11 模型的 fail-closed 也会产出**错的负样本**（W3 实测，判断点 ①）

**症状**：判断点 ① 接线后报表首次出现 `not_play_site`，看着分支终于活了。
翻 `negative.jsonl` 才发现 9 条里有 1 条与同一批的**成功记录直接矛盾**：

```text
negative.jsonl  not_play_site  v-wb.youku.com/…id_XNDE0NjYzODAzNg==…
    理由：现有检索摘要未显示作品标题，无法确认对应《功夫》
T011__d6badc6f  成功            同一条 URL
    理由：LLM 判 True：页面为《功夫》优酷视频播放页
```

**根因不是模型，是输入**。取 obscura 的 `browser_links` 原始 NDJSON 才发现，
bing 结果的 `text` 字段只有面包屑：

```text
{"text":"qq.com https://v.qq.com › cover","href":"https://v.qq.com/x/cover/…"}
```

片名在 `body_text` 里（同一份观察含「功夫」16 次，
`功夫 (普通话版)_电影_高清完整版视频在线观看_腾讯视频`），但**与 URL 无对应关系**。
模型被问「哪些链接是该片的播放站」，输入里没有任何一条链接写着片名——
它答「检索摘要未显示作品标题，无法确认」是**对输入的准确描述**，
随后按契约 fail-closed 成 `False`，而 `not_play_site` 是负样本分支。

**为什么这条特别危险**：fail-closed 的 `None` 不入负样本池（安全），
而**输入不足导致的 `False` 会入池**。同一个 `False`，一个安全一个污染，
区别不在模型，在**有没有能力判**——而 fail-closed 的定义正是
「没能力判就返回 `None`」。缺这层预检，W3 的守卫就只守了后端故障，
没守输入不足。

**纪律**：每道题问模型之前先问「**这个输入支持这道题吗**」。
④ 已有 `_sufficiency`（正文与元素皆空时不问模型），① 缺同款——
`links[].text` 全都不含目标片名时，① 就没有判别力，此时必须 `None`。
真要修输入（`browser_extract` 的 `field[]` 并行数组能一次取到
`li.b_algo h2 a` 的 title 与 href），那是让 ① 真能用的正路，
但**在修好之前 ① 必须先 fail-closed**，不能拿坏输入换分支覆盖率。

**通用形态**：接线一个新判断点时，「它有产出」不等于「它有用」。
负分支一接上就会往池子里写东西，**输入不足的题产出的是假负样本**，
比不产出更糟——不产出只是没覆盖，产出是往训练数据里掺错。

### 5.12 `browser_extract` 的入参叫 `schema`，返回的键不带 `[]`（一个坑，两处症状）

**症状**：判断点 ① 修完输入重跑，`result_titles` 恒为 0，
报表上 ① 仍是全 `unresolved`。看起来像**选择器失效**——
而选择器是好的。

**第一处**：`extract()` 传的是 `{"fields": {...}}`，
上游实参键叫 **`schema`**，回 `Error: Missing schema object`；
而 `extract` 的 `on_error="empty"` 把它吞成空字典。

**第二处（更阴）**：键名改对之后仍然抽不到。obscura 的 `[]` 是**入参**
约定（`titles[]` 表示取全部匹配、值为数组），**返回的 JSON 键不带 `[]`**：

```text
入参 {"titles[]": "li.b_algo h2 a", "urls[]": "li.b_algo h2 a@href"}
返回 {"titles": [...9项...], "urls": [...9项...]}      ← 键名没有 []
```

按 `titles[]` 读永远读到 `None` → `result_titles` 恒返回空字典 →
① 恒 fail-closed。**同一个症状，两层不同的错。**

**为什么两个坑叠在一起特别难查**：obscura 的 `tools/list`
**不返回 `inputSchema`**（实测四个采集 tool 全是 `null`，
它把 schema 放在自定义的 `input_schema` 键里），所以键名只能靠
`probe_returns.py` 取证；而 `[]` 的不对称只在真实响应里才看得见，
fixture 天然会照着入参写，于是**离线测试全绿**。

**纪律**：接一个没验过的 tool，**先跑探针拿原始返回**，再写解析。
参数名与返回形状是两回事，且都不能靠类型标注或文档推断。

**修复后的实测**（`probe_result_titles.py`，2026-10-09）：

```text
bing  : 9 对，标题含片名 9 条   面包屑含片名 0/32   ← 对照组
baidu : 9 对，标题含片名 9 条   面包屑含片名 26/99
```

**注意 baidu 那一行**：默认引擎的 `browser_links` 本来就带片名，
而 bing 不带。也就是说判断点 ① 的输入缺陷**只在 bing 上出现**——
这正是 §5.11 里「实测 bing 面包屑」那条的补充：**别把一个引擎的
观测推广成全体**。

### 5.13 缺 `--title` 拿 `task_id` 顶替：整批作废且**零报错**（W1 实测）

**症状**：`run --engine bing --perceptor llm`（忘了 `--title`）跑完，
报表一切正常：候选 7 个、站点 6 个、分支齐整、警告只有一行
「判断点 ① 选出 0/6」。逐条读 evidence，**每条都很有道理**：

```text
https://www.bridgestone.com.cn/passengercartire/premiumtouri
not_play_site  判断点 ① 未选中该站点。该链接是普利司通 TURANZA T001
               轮胎产品介绍页，不是视频播放页。
```

**根因**：`title` 缺省时拿 `task_id` 顶上，于是检索式成了
**`T001 在线观看`**——搜回来的是**轮胎** T001（泰坦途 Turanza 胎压监测）。
模型答得完全正确，只是被问了一个错误前提下的问题。

**为什么这是最贵的一种静默**：它不报错、不空转、每条记录自身自洽。
读存档时看到的是一份「模型很有理的拒绝记录」，
**没有任何东西提示片名是错的**——片名就写在存档顶层的 `title` 字段里，
而那个字段写着 `T001`，谁会去看它一眼。

**纪律**：片名是判断点 ① 的**唯一判据来源**（`_title_link_sufficiency`
靠它核对链接文本），缺它就必须 fail-closed——与 `OBSCURA_EXE`、
LLM 后端配置同一条：**缺件即报错，不猜**。已在三处设防：
CLI 手工路径、CLI 计划路径（逐条列出没片名的 task）、`Orchestrator.run`
（`ValueError`，且在**建记录与导航之前**抛，不给半批产物落池的机会）。

**通用形态**：「默认填上某个值」比「报错」贵得多，
因为填上的那个值**看起来是对的**。编号、ID、占位符都属于这一类——
它们能通过所有类型检查与存在性检查。

### 5.14 负分支的前置事实不成立时，降级为 `unresolved`

**症状**：一条 `component_unverified` 负样本，理由是

```text
LLM 判 False：页面未检测到任何 video 或 iframe 元素，且仍显示影片详情
和"立即播放"按钮，并非实际播放页。
```

点开存档才发现：点击前后两次观察的正文与元素数**完全相同**
（390 字 / 37 元素 / `video_tag_count=0`），说明**点击根本没把页面带进
播放页**。而这个站有《功夫》、有播放按钮，只是我们没点进去。

**根因**：分支名是**结论的标签**，而每条负分支的定义里都带一个前置事实——
`component_unverified` 的前提是「**到了播放页**，且页面上没有可验证的
播放组件」（2026-10-10 口径裁定，按 rubric 决策树第四行）。
映射只看「模型说了 False」，前置事实不成立时照样贴标签。

**判据的坑（2026-10-10 补）**：守卫第一版用 `video_tag_count<1` 当
「不在播放页」的信号——**选错了代理**。真实视频站全是 iframe/JS 播放器，
真播放页上 `video=0` 是常态，这个信号会把「到了播放页确实没组件」的
合法排除一起杀掉。现行判据是**点击前后是否同页**
（`branches._same_page`：url / 元素数 / 正文三个粗粒度特征；
逐字段比对会把 http→https 跳转与懒加载微调判成换了页）。

**为什么这类错最贵**：负样本池的全部价值是「这里真的看不了」。
贴错标签不是噪声小一点，是**把可看的站写成看不了的**，
而这类样本进了池，人工也未必再看得出它是错的——
理由写得通顺、结论看着专业、`component_unverified` 听起来完全合理。

**纪律**：贴标签前核前置事实（`BRANCH_PRECONDITION`），
不成立就降级为 `unresolved` 交人工，并**把模型原话保留在证据里**——
降级不是改写结论，读的人需要看到「它当时说了什么」。

**通用形态**：任何「按结论映射标签」的地方，
都要问一句**「这条标签的定义里有哪些前提，而输入满足吗」**。
映射函数看不见 `Observation`，它只看得见一个 bool。

**已发生的实例（2026-10-21，台账 H-15）**：这条纪律**被绕过了一次**——
判断点② 的兜底路径（模型答 False 却**没填** `access_control_type`）
落进合并态 `login_wall_or_blocked`，而**墙 / 验证码 / 反爬这三个前提
一个都没观测到**（LLM 自己的 evidence 里从没提过它们）。
实测 **10/39 = 26% 的负样本池是这么造出来的**。
⇒ **owner 裁定：兜底 fail-closed 落 `unresolved`，不开新支**
（`executor/branches.py::decision_branch`：`fallback in DEPRECATED_BRANCHES`
⇒ `unresolved`——**按语义判，不按题号判**）。
⚠️ **合并态是「说不清」的代名词**——拿它兜底，等于把「没判出来」
写成了「判定是墙」。

### 5.15 「0 个交互元素」不等于「没有控件」——两版实现必须同一口径

**症状**：`no_play_control` 负样本一条，理由是
「0 个交互元素中，词表与模型均未找到非预告播放控件」。
而那份观察的正文有 100 个字符，里面明明白白写着**「立即播放」**。

**根因**：`RulePerceptor` 早就写了 `not obs.interactive_elements → None`
的守卫，**`LLMPerceptor` 没有**。obscura 对空页面返回哨兵文本
（`No interactive elements on this page.`）而不是错误，
所以 `degraded` 抓不到它；而正文与元素来自**两个独立的 tool**，
正文成功不代表元素也采到了。

**关键**：不能拿「有正文」当「渲染完了」的证据。现有的
`not body_text and not interactive_elements` 是**两者皆空**才判不足，
于是「100 字正文 + 0 元素」这一格从守卫底下漏了过去——
而这一格恰恰是视频站最常见的形态。

**纪律**：同一道题在两个实现下的口径必须由**同一组契约测试**钉住
（`IMPLEMENTATIONS` 参数化跑七不变式 + 这条）。否则「换 `--perceptor`
就换一批标签」，而报表上完全看不出来。

**通用形态**：**加了一个新实现，就是加了一份要保持一致的行为。**
只在新实现上补测试，等于默认旧实现是对的。

### 5.16 `@property` 上的括号——「命令写完了」不等于「命令能跑」

**症状**：`cli purge-run --run-id b3a3548a --apply` 抛
`TypeError: 'WindowsPath' object is not callable`，
而**预演（不加 `--apply`）一切正常**。

**根因**：`negative_pool_path` 是 `@property`，`apply_purge` 里多写了一对
括号 `self.negative_pool_path()`。预演走的是 `purge_run`，那里写法正确——
**预演与执行是两条路径**。而 `purge_run` / `apply_purge` 写完时**一条测试
都没有**，所以这条路径从来没被真正执行过。

**顺带查出的两个真隐患**（都在同一个函数里，靠补测试才暴露）：

1. **回滚顺手清掉全池坏行。** 池子被回滚时整体重写一遍，而读的时候坏行
   是跳过的——不保留就等于**每回滚一次顺手把全池的坏行清干净**。
   坏行可能是被人手工截断、正等人查的，不该由一个 run 级回滚顺手决定。
2. **传错的 `rows` 会连坐别的 run。** 原实现是「取所有传入行的 `run_id`
   集合，删掉命中集合的行」——签名说「删这些行」，实现说「删这些 run_id
   的所有行」。两者在正常路径上**完全等价**，只有调用方混进一行别的 run
   的行时才分辨得出来，而爆炸半径是静默扩大的。

**纪律**：**破坏性命令的「执行路径」必须和「预演路径」分别有测试。**
预演绿只证明**列表逻辑**对，不证明**删除逻辑**对——而后者才是会毁数据的那半。

**变异时测试自己也要变异**：补这条测试时第一版构造的「库里不存在的行」
只改了 `url`、没改 `run_id`，于是它压根没扩大爆炸半径，
**按 run_id 删的老实现照样全绿**。断言写完要拿老实现打一遍，
确认它真的会红——绿色的变异说明断言没测到东西。

**通用形态**：**任何会重写/删除既有产物的代码路径，
「读得对」和「写得对」要分别验证。**只测读的那半，
写的那半会带着 bug 活到第一次真实执行。

### 5.17 三支「没判出来」合并成一支，复核队列就失去分工

**症状**：报表上 `unresolved` 一支占了大半，看不出该修什么。
问「这些 run 卡在哪」，答不上来——**它们卡的地方不一样**。

**根因**：`unresolved` 这一支同时装着三种成因：

| 情形 | 不确定的是什么 | 该修的 |
|---|---|---|
| 环节①–④ 返回 `None` | **能不能到**播放页 | 感知层能力（`RulePerceptor` 只会返回 None） |
| 环节⑦ 返回 `None` | 组件**能不能用**（播放页就在眼前） | 采集充分性 / 判据 |
| 词表判不准 | 是不是预告 | 词表覆盖 |

「修感知层」与「修采集」是两条完全不同的路。混在一支里，
报表既指不出该修哪条，复核员也分不出「请补一条判据」（环节①–④）
与「请看一眼这个页面」（环节⑦）——后者手上就有页面。

**已修**：2026-10-09 环节⑦ 的 `None` 拆成 `player_unverified`
（`RunLedger.record_unresolved_reached`）。**分流点必须在 `record_from` 之前**——
`record_from` 会把 `None` 一律记成 `unresolved`，那正是它管不到的情形。

**净影响比看上去小**（这决定了改它的风险等级）：

- `negative.jsonl` **不变**——三支都不是负样本，都不并池；
- 复核队列**条数不变**——`unresolved` 本就在 `REVIEW_BRANCHES` 里；
- 只有标签变准。而报表的 `by_branch` 变了。

**历史存档不回填**（项目纪律：并池是写入时的动作，不是读取时的推导）。
于是批次边界两侧不可比：`unresolved` 降、`player_unverified` 升，
不记批次就会被读成「fail-closed 修好了」。

**通用形态**：**分类的粒度要对着「该怎么修」划，不是对着「是不是失败」划。**
「不是负样本」回答的是第一个问题，「为什么不是」回答的才是第二个——
而报表和队列都只会问第二个。

### 5.18 判断点 ② 不修，错误页/下载墙就漏进 LLM 判 True（W3 真实批次实测）

**症状**：`v.qq.com/error.html`（标题「那条视频不见了-腾讯视频」）被判 `is_reachable=True`，
`m.ixigua.com/.../6582085495839261...`（正文写着「以下内容需下载西瓜视频查看」）也被判 `True`——
这两个站根本不是「可访问的播放页」，是错误页和下载墙。下一环节 ③ 把它们判成
`no_play_control` 才漏出，**但代价已经付了**：错误页走完了整条搜索→访问链，浪费访问预算；
下载墙在 ② 已被错误地放进候选池，下一次重跑会再次触发同一路径。

**根因**：[05-现状与验收.md](05-现状与验收.md) 早就标过这条
（"判断点 ② 让错误页通过了"），归因是**提示词质量问题不是机械缺口**——
"页面正常显示"在错误页上只是模板文案（"那条视频不见了"+"还有很多精彩的内容"），
LLM 看到的页面骨架完整，**没法从「页面是错误页」和「页面是正常首页」之间
靠可机械验证的信号分清楚**。

**但 2026-10-09 的 5 条 LLM 真实批次实测出了一个未预期的解**：
判断点 ③ 的 LLM prompt **能正确识别**「00:00/00:00 空播放器占位」+「仅导航无视频标题」
+「下载应用提示」这三种特征，分别判出 `login_wall_or_blocked`（错误页与下载墙都
属这一支，**rubric v1.1 分支定义里就这么定的**）。换言之：
**② 端判不出的，③ 端能在不增加 LLM 调用次数的前提下兜住**，
只是分支会落到 `login_wall_or_blocked` 而非在 ② 早退。

**纪律**：

- **不要去 ② 改 prompt**——`v.qq.com/error.html` 与正常首页对 ② 来说**观察无法区分**，
  改 prompt 只会让 LLM 把更多正常首页误判为错误页（`false positive`），
  那才是真的污染。**② 保持原样，接受它在错误页上漏。**
- **复核队列看到 `login_wall_or_blocked` 来自错误页/下载墙，不要当 bug 修**——
  那正是 ③ 在按分支定义接管 ② 的漏网。
- **真正的待办是 §2.3 那个底层缺口**（错误页特征码可机械捕获吗？——
  `error.html` URL 段、HTTP 200 但正文里 "404"/"视频不见了"/"页面不存在" 词表、
  `<title>` 里的"错误"/"不存在"/"Error"）。这条**仍未建**，
  本节只是把"③ 兜住"这条经验记下来，免得将来读 `login_wall_or_blocked` 报表时
  把它当"判定收紧了"或"LLM 在替代码层发挥"。

**实测证据**（`trajectory_pipeline/output/pipeline/T011__d29f5cee.json` 与
`T048__1517da29.json`，outcomes 里 `login_wall_or_blocked` 行的 `evidence`）：

```text
v.qq.com/error.html        LLM 判 False：标题「那条视频不见了-腾讯视频」，
                          正文仅显示「但是我们还有很多精彩的内容」及导航/页脚，
                          属于视频不存在的错误页，未加载目标内容
m.ixigua.com/.../...       LLM 判 False：页面主体仅显示影片基本信息与
                          「以下内容需下载西瓜视频查看」等下载应用提示，
                          无视频播放器（video_tag_count=0、iframe_count=0），
                          实质内容被应用下载墙挡住
v.qq.com/cover/.../...     LLM 判 False：页面仅有腾讯视频导航栏外壳
                          （电视剧/电影/综艺等链接与"00:00/00:00"空播放器占位），
                          无视频标题、剧集信息或任何正文内容
```

**通用形态**：**修不动的一层，后一层在同一个调用链上能兜住。**
如果兜得住（分支没被错配、报表能区分），不要在前一层硬上 prompt 修补——
那会把"修不动"扩散成"修错"。先核一遍分支定义（`branches.BRANCH_PRECONDITION`）
与 ③ 的判据覆盖域，确认兜得住再走这条捷径；兜不住的再回头补 ②。

### 5.19 **解析失败**不是「判不出来」，而 403 不是 503

**症状一**：某个模型「判不了」，每道题都返回 `None`。看起来像 fail-closed，
实际是**响应没解析出来**。

**根因**：模型在 JSON 字符串值里写**未转义的 ASCII 双引号**：

```json
{"thinking": "标题只是笼统的"腾讯视频"，正文只有导航。", "conclusion": "无法确认"}
```

**大括号是配平的**——`_balanced` 取出来那一段**看起来完全正常**，
只有 `json.loads` 知道它坏了（`Expecting ',' delimiter`）。

实测（2026-10-10，同一端点、同一提示词、同一 `max_tokens`）：
`deepseek-v4.1-flash` **4 次坏 2 次**、`MiniMax-M3` 4 次坏 1 次、
`MiniMax-M3.1-Flash-Preview` 4 次坏 0 次。**同一句话时好时坏**，
所以「换个模型就好了」不成立。

**为什么这条特别凶**：感知层的 `_ask_json` 走的是**同一条路**。
坏掉的症状是解析失败 → fail-closed 成 `None` → 站点记成 `unresolved`
→ **采集故障被记成「模型判不出来」**。这正是 §5.5 在**解析层**的复刻。

**修法**：**报错位置驱动**的转义修复（`schema_parse.extract_json_reporting`）。
`json.loads` 精确指出错误在第几个字符，把**那一个**引号转义后重试。

⚠️ **别用「引号后面跟的是不是逗号」那种局部规则**——实测那条上就是错的：
`只是笼统的"腾讯视频"，正文` 里**两个**引号后面都不是 ASCII 逗号
（一个是中文逗号，一个是真正的结束引号），局部规则会把结束引号也转义掉，
于是永远解析不出来；而每轮又「成功」修掉一个，症状变成另一种失败。

**修可以，账要记**：修复记录随结果返回，调用方写进 `degraded_from`。
不记的话「被修过」与「原样解析出来」形状一样、可信度不同。

**症状二**：模型名明明在清单里，却一直 403。

**根因**：**模型名大小写敏感**，而 403 与 503 是**两种不同的失败**：

| 模型名 | 结果 | 含义 |
|---|---|---|
| `deepseek-V4.1-Flash` | http:403 | **名字未注册**（一个字符都没匹配上） |
| `DeepSeek-V4.1-Flash` | http:503 | 已注册，但服务过载 |
| `deepseek-v4.1-flash` | OK | — |

**纪律**：403 是**改一个字**的事，503 只能等。**分不清这两者就会得出
「后端有问题，模块先别建」这种结论**，而真实原因是一个大小写。

**通用形态**：**「拿不到结果」必须分出「拿不到」的三种**——连不上、
拿到了但解析不出来、解析出来了但内容不完整。三者都表现成 `None`，
而处置动作完全不同（改环境变量 / 改解析层 / 改提示词）。

### 5.20 预检与渲染看的**不是同一个窗口**（W3 真实批次实测，判断点 ①）

> 症状：整批候选全落进 `not_play_site` 负样本池，evidence 写着
> 「模型未给出排除理由」——**代码明知没有理由，仍把它记成了
> 「这个站看不了」**。

**实测（2026-10-10 T001《功夫》，baidu）**：搜索页 123 条链接里
前 12 条是 `登录 / 抗击肺炎 / 新闻 / hao123 / 地图 / 视频 / 贴吧 /
学术 / 设置 / 更多产品`——**导航栏排在搜索结果之前**，而真正写着
「《功夫》电影完整版-爱奇艺」的结果标题排在后面。

| | 看的是 | 结果 |
|---|---|---|
| `_title_link_sufficiency`（预检） | **全量** 123 条 | 数到 3 条含片名 → **放行** |
| `_render`（喂模型） | **前 20 条** | 全是导航 → **模型没一次机会看到片名** |

于是模型判 True 且 selected/rejected 全空，5 个候选全落选。

**修法不是调阈值，是让两处同源**：① 题把「链接文本含目标片名」的
链接**前置**，预检与渲染都走 `_ordered_links()` 再截同一个
`LLM_LINKS`。两处改成同源后，「预检说有判别力」与「模型真的看得到
判别力」是同一条判据在同一批链接上的两个说法。

**通用形态**：**任何「先检查输入够不够，再把输入送出去」的设计，
两处必须读同一个集合。** 它们一旦分叉，症状是「放行了一道模型答不了的题」，
而**全链路零报错**——报表上只看到一批负样本。

⚠️ 与 §5.11 的分工：§5.11 是「links 里压根没有片名」（bing 的面包屑），
本条是「links 里有片名但送不进去」。**两个引擎各中一条**，
所以别把任一条的结论推广成「所有引擎都这样」。

### 5.21 **「没被选中」不等于「被否决」**（W3 真实批次实测，判断点 ①）

承 5.20：① 返回 True，但模型的 `rejected` 里只有它**实际看到**的那 20 条
导航链接；那 5 个候选排在第 25 条之后，**模型压根没见过它们**。
控制流却把「不在 selected 里」一律记成 `not_play_site`。

**修法**：判据从「模型给了理由」改成「**模型点名**了这个候选
（URL 出现在 `rejected` 里）」。点名的记 `not_play_site`，
未点名的记 **`unresolved`**——人工复核分支，**不入负样本池**
（§5.1）。

**通用形态**：「整体结论」不蕴含「逐条结论」。批量判断题里，
`answer=True` 只说明「我判断过了」，**不说明「我逐条否决过其余项」**。
拿一个整体 False/True 去派生出 N 条逐条负样本，就是把
「模型没答」批量写成「这些都不行」。

**为什么这类样本特别危险**：它理由通顺、格式完整、模型签名齐全，
人工复核时**看不出它是错的**——和 §5.13 那批假负样本同级。

## 六、环境与外部依赖

### 6.1 搜索引擎会限流

**症状**：同批连跑，第 1 条正常，后 2 条被重定向到
`wappass.baidu.com/static/captcha/tuxing_v2.html`（标题「百度安全验证」）。

**处置**：加请求间隔，或 `--engine bing`（实测 11 候选 vs 5 候选，
分支覆盖 4 种 vs 2 种）。**直接重跑同一引擎大概率仍是验证码页。**

**纪律**：这类拦截**必须在 `report` 里排在分支分布之前**并单列统计——
它是运行级的，一次拦截会让后面所有分支分布都偏小，先看分支会被带着往下读。

### 6.2 `OBSCURA_EXE` 必须显式设

**症状**：`[FAIL] 未设置 OBSCURA_EXE`。

**纪律**：代码**故意不查 PATH**（猜命令名换机器时会静默走到别的实现上）。
即便 exe 已在 PATH 里也要设：

```powershell
setx OBSCURA_EXE "C:\Users\klpc\workspace\tool\obscura-x86_64-windows-stealth\obscura.exe"
```

`--stealth` 仅在 stealth build 存在该 flag；目录名带 `-stealth` 的即为 stealth build。

### 6.3 Windows GBK 控制台

**症状**：探针上的 ✅/⚠️ 把整条链带崩；`pytest` 输出中文全是乱码。

**纪律**：脚本内加 `sys.stdout.reconfigure(encoding='utf-8', errors='replace')`；
Bash 里跑 Python 用 `PYTHONIOENCODING=utf-8`。

`cli._reconfigure_stdio()` 分两种情况：
`tty` 时只放宽 `errors` **不改 `encoding`**（PowerShell 下当前编码本就正常，
不该替用户改掉）；**非 tty 时强制 `encoding='utf-8'`**——
重定向或走管道时 Python 按 locale 输出，也就是 cp936，
实测 `cli check-archives > out.txt` 写出的首字节是 `0xB4 0xE6`（GBK 的「存」），
按 UTF-8 读直接报错。**CI 日志、重定向文件、任何读档的下游脚本全是坏的**，
而那恰恰是没有控制台代码页、消费方是程序的场合。

### 6.4 终端乱码 ≠ 存档内容坏了

**症状**：读存档看到 `evidence` 是一串 `U+00FD` 加一串 U+FFFD 加 `video/audio=0`，
第一反应是「P1 里中文全烂了，落盘编码写错了，去改 `archive.py`」。

**实测反过来**：2026-10-09 拿现存 12 份真实存档逐条查，
**37 条 outcome 的 `evidence` 无一损坏**——那串乱码是 Windows 控制台
把 UTF-8 渲染成 cp936 造成的，`sys.stdout.reconfigure` 一下就正常。
落盘路径一直是干净的（`archive.py` 显式 `encoding="utf-8"`）。

**真正坏掉的是别的东西，而且范围小得多**：4 份 T001 存档的 `visits[3]`
（tv.sohu.com）`body_preview` 中间 109..225 那段，以及同页一个 `<a>` 的 label。
同一段里 `导航` / `倍速` 这些中文与 ASCII 都是好的，只有中间夹着
U+01F3 / U+0439（Latin 扩展与西里尔字母）的一小片烂成 U+FFFD——
**整档换编码写错会把正常中文一起烂掉，实测它们是好的**，所以触发条件是
站点声明的 charset 与实际内容不一致。同一批 11 个站没事、同一个站 4 次全坏，
**重跑同一批不会变好**。

### 6.5 成因已查实（2026-10-10）：**声明与实际是一致的**

上一节最后那句「触发条件是站点声明的 charset 与实际内容不一致」——
**2026-10-10 实测证明它是错的**，且错在方向上。逐层排除：

| 层 | 判据 | 结论 |
|---|---|---|
| MCP 传输 | `stdio_client` 用 `encoding="utf-8"` + **`errors="strict"`** | **排除**：strict 下一旦坏就抛异常，产不出 U+FFFD |
| 落盘 | `archive.py` 显式 `encoding="utf-8"`，文件是合法 UTF-8 | **排除**（上一节已验） |
| DOM 解析 | `dom.py` 全文无任何编码操作 | **排除** |

直接取证的形态：`tv.sohu.com` 响应头是 `Content-Type: text/html`（**不带
charset 参数**），编码只由 HTML 里唯一的 `<meta charset=GBK">` 声明；
**实际字节按 GBK 严格解码成功、0 个替换符，按 UTF-8 解则产出 6874 个**。
页面里 `content="爱奇艺视频"` 那行，GBK 下完好、UTF-8 视角下整片烂掉。

横向对比七个站，**只有 sohu 是 GBK**（baidu / iqiyi / bilibili / youku /
mgtv 全是 UTF-8，v.qq.com 无 meta 靠浏览器猜）——精确对上「同一批 11 个站
没事、同一个站 4 次全坏」。

**所以损坏发生在页面内容经 MCP 传出时被按 UTF-8 处理**，与站点无关。
原始字节是对的，我们拿到的字符串已经坏了，**这一侧无法还原**。

⚠️ **换浏览器/执行层解决不了它**：QwenPaw 走浏览器解码同样会拿到这个
GBK 页面。真要根治是给 obscura 提 issue，不是换采集层。

**本仓库做的是采集侧防护**（`executor/dom.py::is_mojibake` +
`obscura_driver.snapshot`）：正文与标题**分开**检测，命中即记进
`Observation.degraded`。闸门侧 `gates.observation_shortfall` 见到
`degraded` 非空就拒绝判幻觉——**不在闸门里加第二道门**。

为什么这条防护不是锦上添花：坏正文进感知层后，rationale 闸门会把
「模型引用了页面上真实存在、但已损坏的实体」判成**幻觉**，
**凭空造出一条理由通顺、不报错的负样本**。这与「观察被截断 → 不判幻觉」
是同一条纪律：判断建立在残缺事实上时，记不可判定，不指控模型。

阈值 `MOJIBAKE_MIN_COUNT = 3` 而非「出现即降级」——单个 U+FFFD 可能来自
页面真实内容（页脚符号、图标字体损坏），一见到就降级会让「观察不充分」
这条路径过于宽松，最后人人都忽略它。实测坏站一个正文里数十个、好站 0 个，
两侧都离阈值很远。

### 6.6 纪律：判断「文件里是不是真有 U+FFFD」必须**落盘后重新解码**

且用 `strict`——在终端里 `print` 出来的样子不作数（§6.4 的整个教训）。
`cli check-archives` 的 `mojibake` / `evidence_mojibake` 干的就是这件事，
两种结果分两档严重度（坏在观察里只降级那条，坏在 `outcomes[*].evidence`
才让那条结论作废）：混成一档的话，「1 个站的正文烂了」会把整批 20 个
访问点一起判死，而门禁一旦老报 FATAL，人就会开始整体忽略它。

⚠️ **门禁信号与 P2 的 `degraded_from` 是两套东西，不要合并。**
`integrity.degraded_marker_map` 刻意**不收** `mojibake`，而
`schema._obs_missing` 答的是「P1 里没有哪个键」——乱码是「键在、内容坏了」。
混进去会让「正文被截短」与「正文是烂的」在 `degraded_from` 里长得一样，
而后者更糟：截短只影响落在截断外的实体，乱码让**整段正文都不可信**。
那张表是平铺的，扛不住这个轻重之分。
（`test_integrity.py::TestDegradedMarkersMatchSplit::test_损坏不进degraded_from词表`
钉住这条，改那张表时会红。）

## 七、测试与验证

### 7.1 每条纪律配一个「反过来仍成立」的反例

**要点**：只有正例的检查可能是恒过的假检查。
探针在真实骨架上 189/189 通过之后，必须用反例验证它**不是恒过**：

| 反例 | 期望 |
|---|---|
| 同义改写（网址→地址） | 放过 |
| 掉「网址」要求 | 抓到 |
| 掉「全集」要求 | 抓到 |
| 只剩语气词 | 抓到（过短） |
| 空串 | `FAIL_EMPTY` |
| 正常骨架 | 189/189 通过 |

### 7.2 测试写错 ≠ 守卫有问题

**两次实例**：

1. 断言「片名不在结果里」——错，半指代**本就**保留片名
2. 用例文本「没有网址也没有集数」**含探针词**，探针正确放行——用例本身写错

**纪律**：测试失败先问「是守卫错了还是用例错了」。反例用错措辞比没反例更坏。

> **新增形态：fixture 自己含被测对象。** 模块 4 实测——测「任务给的片名
> 是豁免域」这条时，夹具的 `page_title` 恰好是「功夫 - 腾讯视频」，
> **观察本身就含片名**，于是豁免域不起作用测试照样绿；
> 去掉豁免域逻辑后那条测试仍然是绿的。
>
> 判据：**测「豁免/跳过」这类逻辑时，夹具里必须真的没有那个东西**。
> 默认夹具顺手带了它，于是这条测试压根没测到那条分支。
> 修法是在该用例里**显式构造一个不含它的夹具**，并 `assert` 一次
> 「夹具里确实没有」——让这个前提本身可查。

### 7.3 绕过前置过滤的测试会撞上早退路径

**症状**：直接调 `renderer.render()` 时 `applied: {}`，返回骨架原文。

**根因**：`纯描述 × single_title` 是**不兼容组合**，渲染器**早退返回原文**——
这是设计行为（说不出片名却要求找到那一部，逻辑不可能）。

**纪律**：测渲染必须先过 `renderer.is_compatible()`；
并断言实际覆盖了足够条数（如 `checked >= 20`），
否则检查可能在少量样本上空转。

### 7.4 只有真读一遍才会暴露的缺陷

**要点**：4.1–4.4 的四个措辞缺陷，**探针全绿、测试全过、离线体检全过**，
是接线之后第一次端到端真读渲染文本才看见的（16 条里 14 条有粘连）。

**纪律**：跑长批前 `--dry-run` 看一眼；产出新格式的**人能读的文本**时，
必须**真读一遍**——判分保真探针管不到表达质量。

### 7.5 绿测试不等于有覆盖（变异测试）

**症状**：全部测试通过，而守卫其实从没执行过。一个恒假的 `if` 也能让门禁全绿。

**根因**：断言只覆盖了**会走的那条路**。新增的守卫（预检、白名单、
优先级）都写在 `if` 分支里，而"正常路径"的测试根本进不去那些分支。

**纪律**：给每条新守卫配一条**变异测试**——把它删掉/改坏，确认对应测试变红，
再恢复。`trajectory_pipeline/tests/mutation_check.py` 是本次的一次性工具（12 条变异，
含「把变异标成 CRASH」的判据：**报 `error` 而非 `failed` 说明代码被改崩了，
不构成有效验证**）。通用形态：**"删掉它测试还过" = 那条守卫不存在。**

> **「绿色的变异」比红色更贵**，因为它给出的信号是「已验证」——
> 而实际上那条守卫从没被测到。D-6 实测踩过一次：
> 删掉「键缺失判不可判定」的守卫后测试全绿，而真实数据从
> 151 不可判定 / 45 五分变成 133 / 63（18 条老存档被误判成「齐全正确」）。
>
> 补的第一版断言也抓不住它——查的是「5 分的样本是否还带着
> 『老存档没这个键』的理由」，而那条理由**正是被变异删掉的分支产生的**，
> 所以断言在**结构上不可能成立**。改成**回源头核真值**
> （凡判 5 分者 `p1_missing_fields` 必须为空）才抓住。
>
> **形态**：断言写在**被测代码自己产出的东西**上时，它可能随代码一起变。
> **断言要回到独立真值源**（源文件、原始存档、手算的期望值）。
>
> ⚠️ **「形态一致」是最容易蒙混过关的一种**。D-4 实测：断言写的是
> 「低分条目全部属于 `premature` 档」，而把管辖范围改坏之后，
> 新增的那条误判**恰好也是** `premature` 档——形态一致，断言全绿，
> 而真实数据已经变了。补的断言改成**直接盯判断点 id**
> （D-4 只核 `player.ok`）才抓住。
> **形态断言抓的是「这一类问题」，抓不住「这一条恰好也像这一类」。**
>
> ⚠️⚠️ **最隐蔽的一种：变异压根没生效，而「全绿」被读成「守卫无效」。**
> D-6 实测：用 `str.replace()` 做变异时字符串转义没匹配上、文件没被改，
> 而我看到「55 passed」就记成了「这条守卫不需要」，然后去改**测试**。
> 实际那条守卫是有效的——改成**按行号精确改**后立刻变红。
>
> **纪律**：
> - 变异之后**先确认文件真的变了**（打印改后的那几行，或看文件 mtime），
>   再看测试结果；
> - 优先**按行号改**而不是 `str.replace` 长字符串——后者会静默不匹配；
> - `assert t2 != t` 这类「变异确实应用了」的断言要**每次都写**，
>   它比事后核对便宜得多。
>
> **通用形态**：**绿色的变异说明断言没测到东西**；
> 而**没生效的变异会被读成绿色的另一种解释**——后者更坏，
> 因为它会让人去改本来正确的测试。

#### 死守卫：加上去的那道限制**从来没起作用**

**症状**：为了「限定范围」加了一道条件判断，变异测试把它删掉，测试**照样全绿**。

**根因**：真正在拦的是**另一条**条件，两条串在一起看着像双重保险。

**实测（2026-10-10，JSON 修复层）**：给「转义修复」加了一道
「只修 `Expecting ',' delimiter` 这一类错误」的白名单。删掉它 13 条测试全绿；
进一步枚举才下结论——17 种畸形输入 + 把一条真含坏引号的合法 JSON
**从每个位置截断**（58 个截断点），**没有一种**是靠它救回来的。
真正在拦的是那句「解析器报错的位置恰好是一个双引号」。

**死守卫比没守卫更坏**：它看起来在限定范围，于是**没人再去验证真正起作用
的那道**——于是那条一旦被改坏，还是全绿。

**纪律**：
- 加限制条件时，**问「删掉它，哪条测试会红」**。答不上来就别加。
- 真正在起作用的那条判据，要有一条**只针对它**的断言；
- 能写成**性质断言**就别写样例断言。「任意位置截断都不得被修成假对象」
  覆盖 58 个截断点，比「这 6 种畸形不许修」强得多——样例只覆盖已想到的形态。

#### 残留标记表与已覆盖的规则重叠 = 死守卫的另一种形态

**症状**：一张「残留即拒写」的表里列了几个标签，删掉表测试全绿。

**根因**：那几个标签**已经被上游的剥离规则吃掉了**，永远到不了这张表。
实测：`strip_think` 连**未闭合**的 `<reasoning>` 都会连同其后内容一起删，
而 writer 第一版仍把 `<reasoning>` 列进残留表。

**纪律**：表与上游规则的覆盖范围**必须不重叠**，并配一条**结构性断言**：
「表里每个标记都必须能挺过上游规则」。有人日后加一个已覆盖的标签，那条立刻变红。

> 附带一条口径：**只测开标签**。孤立的闭标签（`</think>` 后面没有开标签）
> 上游不删，而它**也不该删**——闭标签前面若真有思维链，那段在开标签那里
> 已经连根删了，剩下的闭标签是**空壳**，不构成 CoT 泄漏。
> 按闭标签也拒写只会白白丢掉正常样本。

#### ⚠️ `.pyc` 字节码缓存让整份变异清单的结论作废（2026-10-10 实测）

**症状**：同一条变异**两次运行一次 RED 一次 ALIVE**，而读回校验显示
变异确实写进了文件。手工复现同一条变异却是红的。

**根因**：`write_text` 之后，源文件 mtime 的粒度可能与 `__pycache__`
里记录的**一致**，CPython 判定「这个模块没变过」直接复用 `.pyc`。
于是**被测进程根本没跑到变异代码**，全绿，而报表上记的是
「守卫无效」。

**修法**：变异后**删掉被改模块的 `.pyc`**，并在恢复时也删。
（[`tests/mutation_check.py`](../../tests/mutation_check.py) 的
`_drop_pyc`。只删被改文件对应的缓存——全量删会让整份清单慢一个量级。）

**为什么这条最阴**：本文件 §7.5 记的那条「一次没生效的变异会被读成
『这条守卫不需要』」，在没有清缓存时**每一轮都在悄悄发生**，
而报表上只显示一个安静的 `ALIVE`。**所以此前所有变异测试结论都应视为
待复核**——重跑一次 `uv run python -m trajectory_pipeline.tests.mutation_check`
才是可信的。

**通用形态**：**任何「改文件 → 起子进程验证」的测试工具，
都必须处理子进程的编译缓存。** 与「子进程是否真的读到了改后的文件」
是两件事：读到**改后的源文件**不等于读到**改后的字节码**。

## 八、边界纪律

### 8.1 存档是不可变真值源

**风险**：`to_json()` 是**归档那一刻**才序列化。若 `RunRecord` 只存
provenance 的引用，调用方在归档前改一次入参字典，存档内容就跟着变——
而文件名、报告、切片脚本全都不知道发生过。

**纪律**：值对象自己的边界上拷贝（`RunRecord.__post_init__`），
不靠每个调用点自觉。`orchestrator.run` 里已有的 `dict(...)` 是**有意的冗余**。

### 8.2 交接面是文件格式，不是 import

**纪律**：`executor/plan.py` **不 import** `taskgen`。

理由不止于整洁：plan 是**要长期存着的**，切片分析、失败归因、
半年后回看读的都是那个 JSON 文件。若消费端 import 生成端，
则「能读这份文件」==「生成端还在原地」，生成端一改字段旧计划全废。
**按格式读，格式就冻住了。**

### 8.3 计划文件要能说清自己怎么来的

**纪律**：`SamplingReport` 落盘 `seed`。否则「重跑一批对照」只能碰运气重跑同一个 `-n`——
而 `-n` 变了组合也全变了。`library_digest` 只锁住画像库，锁不住抽样本身。

### 8.4 默认跳过归一退回的样本

**理由**：`rewritten=False` = persona 没落地，跑出来的结果在切片表里
**长得跟「这个 persona 组合表现差」一模一样**。

**纪律**：`run --plan` 默认跳过，要跑必须显式 `--include-unrewritten`。

### 8.5 长批先 dry-run

**纪律**：`run --plan --dry-run` 只读计划并打印（真实浏览器每条约几十秒）。
跑之前值得先看一眼「到底会跑哪些条目、跳过了哪些、为什么跳」——
`--limit` 生效时也要告警，少跑的那些不留痕就等于没发生过。

### 8.6 模型原文进 evidence 前必须剥 think

**症状**：在存档的 `outcomes[].evidence` 里搜到 `<think>`，
或看到「模型内部推理」「让我看看页面上有什么」这类句子。

**风险**：CLAUDE.md 红线「**不保存 raw CoT**」。`evidence` 是
`SiteOutcome` 的持久字段，直接落 P1——剥晚了就是存档里躺着推理模型的
思考段落。

**纪律**：任何把模型输出写进 evidence 的地方，
**先 `schema_parse.strip_think` 再截断**。落盘点有两个，
都要过：`llm_perceptor._why_unparsable`（解析失败时的原文片段）与
`rationale/writer.py`（已过）。

> ⚠️ **剥完为空是另一件事**，要单独说：「模型只吐了思考、没有正文」
> 与客户端报的「预算被思考吃光」症状同源而成因不同——
> 后者压根没返回正文。写成一句话会让人以为该去调预算。

**为什么它漏了很久而门禁全绿**（2026-10-11 修复）：根因在 **fake**
——`FakeLLM` 的 `prose=True` 在套 think 之前就 `return`，
于是 `think=True, prose=True` **组合不出「带思考且正文不是 JSON」这个形态**，
没有任何测试造得出它。

> **fake 造不出的形态 = 不存在的守卫。** 加 bad-output 形态时要问一句：
> 「这两个开关能同时打开吗？」答案是否，就等于没测。

### 8.7 枚举出的元素列表必须能自证「为什么这么短」

**症状**：`interactive_elements` 是空列表 / 只有三条。查不到报错，日志也干净。
判「页面上没有可点目标」→ 负样本。**实际上元素都在，是枚举把它们丢了。**

**根因**：采集面的过滤是**静默**的。camoufox 的 `interactive` 有三层丢弃，每一层
都不抛异常：词表外 role（`generic`/`heading`/`option`）、**没有可访问名的元素**
（实测真实页面占 41%，`get_by_role(role, name="")` 命中 0 **且不报错**）、
**真同名的元素整组丢弃**（strict mode 会报错，留着等于埋雷）。

三层叠起来，症状与「这页真的没东西」**完全同形**——而这正是本项目最贵的一类错。

**纪律**：列表短了必须能解释。`CamoufoxDriver.last_enumeration` 记
`nodes / role_matched / nameless_dropped / ambiguous_dropped / kept / truncated`，
`check --driver camoufox` 每次都打出来。看元素列表之前**先看这份账目**：

```text
过滤账目: nodes=101  role_matched=34  nameless_dropped=0  ambiguous_dropped=0  kept=34
```

`nameless_dropped` 大 = 页面把按钮做成了纯图标（该换 `aria-label` 判据或走路径 3）；
`ambiguous_dropped` 大 = 页面列表项同名（该看是不是提取了错的层级）。
两者都是**页面事实**，不是驱动故障——但**不记账就分不出来**。

> 通用形态：**任何「过滤后仍返回成功」的接口，都要把过滤计数带出来。**
> 只返回结果、不返回账目的过滤器，等于把「没有」与「被丢」写成同一个值。

### 8.8 导航之后拿上一页的名字去动作：不报错，点中了新页的同名元素

**症状**：`last_action` 记的是 `{'op': 'click', 'role': 'link', 'name': '首页', 'outcome': 'ok'}`。
**点了，成功了，但点的是另一个东西**——轨迹从这里开始就是错的，
而整条链路上**没有任何一处会报错**。负样本、分支、理由全都写得通顺。

**根因**：camoufox 面的目标是 `role + name`，这是**页面级**定位，不是会话句柄。
导航换页之后：
- `ref`（obscura 面）**必然失效**——它是会话内句柄，指向的元素已经没了，会报错；
- `role + name` **不失效**——`get_by_role("link", name="首页")` 在新页上重新求值，
  新页只要也有个叫「首页」的链接，**它就点下去并返回成功**。

「失效」这件事被 `role+name` 的可移植性**换走了**，而可移植性正是 D12 要的东西。
代价就是这道保护：**旧名字在新页上仍然合法**。

**第二个入口，同一个坑的另一面：`click()` 返回时不保证导航已经开始。**
动作之后**立刻**读，可能读到**整个旧页**——而旧页在导航开始前是**天然稳定**的，
所以「连续两次读数一致」这种「读稳」判据在这里恒真，会给出「没跳」的错误结论
（2026-10-20 的冒烟就这么骗过一次：报告停在 `/s?…`，0.5s 后它其实跳到了首页）。
更早一版读到的是**过渡态**（`title == ''`，页面上明明有标题）。

**纪律**：**任何一次导航之后必须重新枚举，才允许下一次动作**；
而「导航发生了没有」只能靠**URL 相对动作前变了没有**判断，且分两段等：
①等 URL 变化 → ②等 `(url, title)` 连续两次一致。

```python
before = await driver.snapshot(max_chars=1)
await driver.fill(role="textbox", name="搜索", text="冒烟测试")
await driver.press("Enter", role="textbox", name="搜索")   # ← 这一下已经换页了
mid = await _after_action_snapshot(driver, clicked_from=before.url)  # ①等变化 ②等读稳
if mid.url != before.url:                # 别猜「大概没跳」，比 URL
    elements = await driver.interactive()  # 名字全部按新页重算
```

导航的来源不止 `goto`——`fill` + `press("Enter")` 提交搜索会跳转、
`click` 一个链接会跳转、页面自己跳转也会。

> **为什么这条写进避坑而不是设计**：它的症状是「一切都对」——
> `outcome` 是 `ok`、URL 变了、页面有内容、样本能组装。
> 只有把「我点的那个元素当时是哪一页的」对回去，才看得出错。
> **凡是不报错又能把轨迹带偏的，都得靠纪律，不能靠报错。**

> 相关：§8.7（列表短了要能解释）、[设计方案 04 §4.6](../设计方案/04-camoufox执行层替换方案.md)
> （动作面的三态映射与这条的取证过程）。

### 8.9 动作超时把两件事混在一个预算里：点击随机失败，而页面看起来完全正常

**症状**：同一个站、同一个按钮，**时灵时不灵**：

```
camoufox 动作失败（click）: Locator.click: Timeout 5000ms exceeded.
Call log:
  - waiting for get_by_role("link", name="百度首页", exact=True)
    - locator resolved to <a href="/" class="toindex">百度首页</a>
  - attempting click action
```

> ⚠️ **预算已从 5s 提到 15s**（2026-10-21），所以现在看到的是
> `Timeout 15000ms exceeded`——**这条记的是当时那批存档的原文**，
> 搜 `5000ms` 搜得到的是历史记录。⚠️ **且这条与 §8.13 是两回事**：
> §8.9 的根因是「超时覆盖了两件事」，§8.13 的根因是「窗口不可渲染」——
> **量级撞在一起，日志长得很像**。分它们的方法见 §8.13 纪律③。

四次跑，两三次失败。看起来像页面卡、像反爬、像元素被遮挡——**都不是**。

**根因**：`locator.click()` 的超时覆盖了**两件不同的事**：
①动作本身（等可见/可用/稳定、滚入视口、发鼠标事件）；
②**等这次点击触发的那次导航「完成」**。实测（baidu 结果页点「百度首页」）：

| 量 | 读数 |
|---|---|
| 元素 `count` / `visible` / `enabled` | `1` / `True` / `True` |
| 包围盒 12 次采样（每 100ms） | 首帧后**恒定**（稳定） |
| `elementFromPoint` 命中 | 就是它（没被遮挡） |
| `click(no_wait_after=True)` | **1.1s** 完成，页面正常跳转 |
| `goto` 同一地址 | **0.3s** |
| `click()`（默认等待） | **9–13s**，5s 预算下直接超时 |

**5s 预算对①绰绰有余、对②远远不够**——而②等的那个「完成」比 `goto` 的 `load`
苛刻得多（多半挂在页面里某个慢 iframe 上）。

**纪律**：**动作超时只该覆盖动作。** 关掉动作自带的导航等待
（`no_wait_after=True`），动作之后再**有界**地等一次「新文档 DOM ready」
（`domcontentloaded`，2s 上限），结果记进账目（`settle: ok|timeout`）。
等不到**不抛**（点击确实发出去了），但**必须说出来**——否则下一步读到旧页时
归因不了（§8.8 第 2 条）。

> 通用形态：**一个超时只该管一件事。** 把「我做完了」与「世界因此改变了」
> 捆进同一个 deadline，超时就变成两种完全不同的故障的同一个报错，
> 而报错本身还看起来像对方的错（这里是「页面卡」，实际是「我们在等一个
> 没人需要的信号」）。
>
> **附带一条**：报错要保留 playwright call log 的**末尾**几行
> （`element is not stable` / `performing click action` 在那里），
> 按头截断 `str(exc)[:200]` 恰好把原因切掉——三次失败的日志会长得一模一样。

### 8.10 只取 `innerText` 抽标题：抽到一串空串，**看着像选择器随改版失效**

**症状**：`steps/search` 抽出来 10 个标题、**全是空串**，
或者 `result_titles` 报「长度不等或为空」→ 判断点 ① 直接退回 fail-closed。
第一反应是「bing 改版了，选择器废了」——**改选择器没用，换哪个都对**。

**根因**（2026-10-20 本机实测）：bing 结果页 `li.b_algo h2 a` 的 10 个锚，
**`innerText` 全是空串**，标题只在 `textContent` 里。而 `textContent` 单用会把
`<script>` 里的话当文本——**两者单独都不对，组合才对**。

**纪律**：采集面取文本一律 **`innerText || textContent`**（优先 + 兜底，不是替换），
`links` 的文本同理。**证据要留**：`probe_result_titles --driver <面>` 打「对数 / 条数含片名」，
一个面 10 个空串、另一个面 10/10——这不是页面差异，是取文本的路宽窄不同。

> 通用形态：**「抽不到」要先分清是「页面上没有」还是「我用来看它的那条路太窄」。**
> 两者的症状是同一个空列表，后者改选择器永远改不好。

### 8.11 `links` 不去重：`links_total` 高 30%，并池比出来的分布是假的

**症状**：没有任何报错。两版实现跑同一对搜索页，`Observation.links_total`
一边 `131`、一边 `168`（`33` vs `48`），报告上看着像「新实现采得更全」。

**根因**：obscura 的 `browser_links` **恒 `total == distinct`**（实测 `131/131`、`33/33`），
camoufox 面直接 `eval_on_selector_all("a", …)` 会把 **href 重复的锚全返回**
（`168/133`、`48/35`）。`links_total` 要进 D-2 口径——
**两面不同义，并池之后任何按条数算的分布都在比两个不同的量**。

**纪律**：`links` **按 href 去重、保留第一次出现的那条**，且**去重在前、`limit` 截断在后**
（顺序反了条数同样对不上，而这次不报错、只是少几条）。

> 相关：§5.15（两版实现必须同一口径）、§8.7（被过滤的不许和「没有」同形——
> 这里是**反面**：多采的那部分也得先归一，否则「多」也是不同义）。

### 8.12 关掉最后一个 tab，把「页面」关空了：之后每一次观察都在读死句柄

**症状**：`link_check` 跑完一轮，下一段所有原语都报「页面读不到」、
`body_text` 恒空。**像浏览器崩了、像反爬清了上下文**，重跑还复现。

**根因**：页面是**栈**（`new_tab` 压栈、`close_tab` 弹栈回上一页），
但如果关掉的**就是最后一页**，栈就空了——`session.page` 取到的是**已关闭的句柄**，
读它不报错、返回空。真正的错是我们自己关空的。

**纪律**：三条配套语义不能省：
① 关**最后一页**时**先开一张空白页再关**，栈永不为空；
② `close_tab(tab_id)` 认不出 id **直接抛**（静默返回 = 关错页不报错，后面全错却没人知道）；
③ `new_tab(url)` 导航失败**先把这个新页收掉再抛**——留着它，当前页停在
`about:blank`，一次外链失败会连带弄丢**上一页**的证据。

> 通用形态：**「当前对象」如果是从外部状态（栈/列表）推出来的，
> 那么「清空」这个动作本身必须保证它非空。** 否则「空」会伪装成「读不到」。

### 8.13 headful 窗口不可渲染时，点击**慢到超时**：元素在、事件也落了

**症状**：双跑（P5）里 camoufox 面点击 **3/3 全部**
`Locator.click: Timeout 5000ms exceeded`（预算提到 15s 后是
`Timeout 15000ms exceeded`——**两个数都搜得到**：前者是 2026-10-20 那批存档里的原文），
日志停在
`- performing click action`；同一批站点 obscura 点得动、有成功记录。
下游读到的却是 `component_unverified`——**「点击没做成」被读成了「页面就是这样」**，
理由通顺、指不出异常。

**根因（六轮探针定位，2026-10-20）**：不是挂死，是**慢过超时**，触发条件是
**浏览器窗口不可渲染**（最小化 / 息屏 / 锁屏 / 被完全遮挡）。

| 读数 | 窗口可见 | 最小化 |
|---|---|---|
| 同一次 `locator.click` | 0.4–1.5s | **5–13s** |
| `humanize=False` | 82ms | **9.1s** |
| `humanize=0.3`（maxTime） | 386ms | **9.1s** |
| `headless=True` | 34–71ms | 不适用（从不慢） |

四条把误判逐个排掉：

1. **事件其实落地了**：超时那次点击之后，页内 `pointerdown`/`click` 计数器**涨了**。
   → 不是「点不动」，是「确认回来之前超时」；
2. **不是「新开的 tab」**：headful 下**会话首页同样超时**；当初「首页 0.74s 点得动」
   只是那次点击恰好落在窗口还可见的时候。`headless=True` 从不慢；
3. **不是 `humanize`**：它只把 9.1s 放大到 13.3s，关掉治不了；
4. **页内 `requestAnimationFrame` 整段停**：实测滞后 0.9s→62s，说明窗口那段时间
   **一帧没画**。Firefox 对不可渲染窗口会节流渲染、定时器与输入处理，单次
   动作因此变成秒级——而 `ACTION_TIMEOUT_MS` 是 5s。
   关 `widget.windows.window_occlusion_tracking.enabled`、调
   `dom.min_background_timeout_value` / `background_throttling_max_budget`
   **都治不住**（最小化仍 5.1–9.4s，已实测）。

所以这是**环境×依赖的交互**，不是我们的接线 bug；但它在生产主路径上
（一个 Run 要开 tab 遍历多站），因此是 P5 切换的**唯一硬阻塞**。

> ✅ **已处置（2026-10-21，owner 拍板）**：无人值守批次改走 **`headless=True`**
> ——「保证桌面可渲染」在真无人值守场景里保证不了（跑一夜 / 合盖 / 远程桌面断开
> 都会触发），而无头实测 34–71ms **从不慢**。口径反转的完整理由与代价见
> [设计方案 04 §4.9.5](../设计方案/04-camoufox执行层替换方案.md)。
> 代价是**指纹口径变了**，所以 `headless` 进批次元数据（`fingerprint` 第九项）。
> 配套：`ACTION_TIMEOUT_MS` 5s → **15s**（盖住实测上界 13323ms）、
> **超时不重试**（已加测试）、`steps[]` **记单步耗时**（`duration_ms`）。

**纪律**：

① **别在这个症状上改业务判断**——把点击超时当成「没有播放控件」会产出整批假负样本；
② **超时的点击不能重试**：事件可能已经落地，重试就是点两次（这条比超时本身更贵）；
③ 遭遇「元素在、可见、稳定、点不动」，**先量同一动作在「窗口最小化 / 恢复」两种状态
   下的耗时**——一次就能分开「依赖坏了」与「环境在节流」，比读 playwright 源码快；
④ **无人值守批次要么保证桌面可渲染**（不息屏、不锁屏、窗口不最小化、不被全屏覆盖），
   **要么跑 `headless=True`**——后者会换掉指纹口径，所以这是个**要记账的选择**，
   不是随手改的开关（**现已定为默认无头**，见上方处置条）；
⑤ `steps[]` **现在记单步耗时**（`duration_ms`，2026-10-21 起）——事后分得出
   5s 与 13s。**注意口径**：它是**整步**（动作 + 随后的观察），
   失败路径上 ≈ 动作耗时；成功路径上**别当成动作耗时读**。

### 8.14 改了标签却没改**池**：训练侧吃的是**池行**，不是存档

**症状**：`cli check-archives` 报
`negative_not_pooled`（DEGRADED）——「存档里这条真负样本的
`(task_id, url, branch)` 不在负样本池里」；而报告上**只多一行「没并池」**，
看不出是「改标签写了一半」。反过来（只改了池没改存档）也一样报，
**两个方向的症状完全一样**。

**根因**：负样本池（`negative.jsonl`）是**派生资产**，而**训练侧读的是它**——
`evaluation/golden.builder._scan_negative_pool` 读的是**池行**的 `branch` /
`branch_label`，**不是存档**。⇒ **只改存档等于没改**：训练数据一个字没变，
而存档看起来已经改好了。

**纪律**：任何**改分支**的处置动作，必须**存档 + 池**一起改，
且**两边都按同一个键** `(task_id, url, branch)` 落：

- 同一个键在**几份存档**里各有一条时（改一份不改另一份 ⇒ 另一份当场报
  `negative_not_pooled`），要**一起改**；
- **复核档（`.reviewed.json`）也要改**——读侧 `archive.select_archives`
  **优先取复核档**，只改原档 ⇒ 复核档里还是旧键 ⇒ 门禁照样红；
- **撞键要「并入」不是「新建」**：同一个 `(task_id, url)` 在池里已有新标签
  那一行时（两次跑出互相矛盾的标签），改判后会同键 ⇒ 违反池的去重约定 ⇒
  保留已有的那条、**删掉**贴错标签的那条。

→ `executor/relabel.py`（`cli relabel`，2026-10-21 增量七十八）

### 8.15 注释说「旁路生效」，代码早就把它退役了

**症状**：`executor/branches.py::_has_strong_paywall_signal` 的 docstring
写着「LLM 给出强付费墙信号时旁路同页守卫」，`_precondition_failed` 的注释
还写着「强信号旁路**始终命中**」——而这条旁路**在 2026-10-19 就随同页守卫
窄化（同守卫集合 5 条 → 1 条）失去了拦截对手**，那个函数**一个调用点都没有**。
**读代码的人会以为有一条保护在生效**——而它保护的东西早就不存在了。

**根因**：**退役的机制不会自己删自己**。守卫集合窄化时，改的是**调用处**，
那段说明与那个适配函数留在原地；注释随即变成**反向的误导**。

**纪律**：动一处口径时，把**引用它的地方一起搜一遍**——
`grep -rn "<函数名>"` 找到的**每一个**引用都要问「它现在还成立吗」；
退役的机制**连注释一起删**（或明确标注「已退役 + 为什么退役」）。
⚠️ 判据本身没死时要**写清它现在归谁**——本例里强弱信号仍是
`gatekeeper.is_paywall`（**拦截**口径）的判据，只是**不再用于贴分支**。

→ `executor/branches.py` · `perception/rule_perceptor.py`
