## 常用命令

```powershell
uv sync --group dev

# ── 执行层 ─────────────────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli check              # 探 obscura 能力 + 报两个感知实现的边界（唯一需真实浏览器的自检）
uv run python -m trajectory_pipeline.executor.cli run --task-id T001 --title 功夫
uv run python -m trajectory_pipeline.executor.cli run --plan <plan.json> --limit 20 --dry-run
uv run python -m trajectory_pipeline.executor.cli run --plan <plan.json> --limit 5 --perceptor llm   # 覆盖 TRAJECTORY_PERCEPTOR

# ── 任务生成层（不联网）────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli gen -n 20 --seed 7 --out <plan.json>
uv run python -m trajectory_pipeline.executor.cli check-persona      # 画像覆盖度 + 判分保真探针，分开报

# ── 组装（P2 / P3）────────────────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli build                        # P1 → P2 → P3（不联网）
uv run python -m trajectory_pipeline.executor.cli build --stage p2              # 只切 P2（读 P1）
uv run python -m trajectory_pipeline.executor.cli build --stage p3              # 只渲 P3（读 P2）
uv run python -m trajectory_pipeline.executor.cli build --overwrite             # 覆盖已落盘产物（**默认不覆盖**）

# ── 人工复核与报表 ─────────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli review --write <queue.jsonl> --show 3
uv run python -m trajectory_pipeline.executor.cli review --verdicts <queue.jsonl> --apply
uv run python -m trajectory_pipeline.executor.cli review-queue <queue.jsonl> --prefill --settle   # 改队列工作稿（**不动 P1**）
uv run python -m trajectory_pipeline.executor.cli report --out trajectory_pipeline/output/pipeline
uv run python -m trajectory_pipeline.executor.cli check-archives      # 存档完整性门禁（不联网）
uv run python -m trajectory_pipeline.executor.cli replay --perceptor rule   # 感知层回放（不开浏览器）

# ── 取证探针与取证后处置（两个都改结论，先看清单）────
uv run python -m trajectory_pipeline.executor.cli probe <url> [<url> …]          # 开浏览器看现场事实
uv run python -m trajectory_pipeline.executor.cli downgrade --evidence '\(?<!\d\)0 个交互元素' --reason "…"   # **默认 dry-run**
uv run python -m trajectory_pipeline.executor.cli downgrade --url v-wb.youku.com --reason "…" --apply

# ── 整批回滚（默认只列不删）────────────────────────────
uv run python -m trajectory_pipeline.executor.cli purge-run --run-id <run_id>
uv run python -m trajectory_pipeline.executor.cli purge-run --run-id <run_id> --apply

# ── 门禁 ───────────────────────────────────────────────
uv run python -m pytest -q
```

| 命令 | 联网 | 作用 |
|---|---|---|
| `check` | ✅ | 探 obscura 能力握手与 `observe` 契约，报两个感知实现的边界 |
| `run` | ✅ | 跑一个 task / 一份计划，落 P1 |
| `gen` | ❌ | 骨架 × persona 采样，产出执行计划 JSON |
| `check-persona` | ❌ | 画像覆盖度 + 判分保真探针（**分开报，不合成一个数**） |
| `review` | ❌ | 导出 / 回填人工复核裁定 |
| `review-queue` | ❌ | 改**队列工作稿**：按形态预填、同 URL 裁定收敛。**只动 jsonl，不动 P1** |
| `probe` | ✅ | 取证探针：开浏览器看**现场事实**，用来分清存档里两边互相矛盾的证据 |
| `downgrade` | ❌ | 取证后把判定不成立的 outcome 降为 `unresolved`。**默认 dry-run**，`--reason` 必填 |
| `report` | ❌ | 汇总 P1 分支分布 + 成功站点域名分布（D7 验收） |
| `check-archives` | ❌ | P1 存档完整性体检 |
| `replay` | ❌ | 在存档的真实观察上跑感知实现 |
| `build` | ❌ | P1 → P2 → P3 组装。**默认不覆盖**已落盘产物，重建整批要显式 `--overwrite` |
| `purge-run` | ❌ | 回滚一个 run：删它的存档 + 它并进 `negative.jsonl` 的行 |

### 评估（**另一个入口，不挂 `executor.cli`**）

```powershell
uv run python -m trajectory_pipeline.evaluation.cli                       # D-2/D-4/D-5/D-6 汇总
uv run python -m trajectory_pipeline.evaluation.cli --only-undetermined   # 只列不可判定/扣分的样本
uv run python -m trajectory_pipeline.evaluation.cli --json out.json       # 落全量 JSON
uv run python -m trajectory_pipeline.evaluation.goto_trace                # 批次级 goto 溯源（A3-2）
```

`goto_trace`（方案 13 §6.2）：核每个 `origin=model` 的 goto 的 `params.url`
是否可溯源（候选池 ∪ 已观察链接，锚点随轨迹递推），产出**批次级**幻觉
goto 计数/明细并按 `executor_mode` 分桶——agent 批的幻觉计数从
`[agent]` 行读。不进 D-2 样本级（幻觉记账决策 A），有违规**不非零退出**：
这是 A/B 对比要收集的质量信号，不是闸门。

| 参数 | 作用 |
|---|---|
| `--out` | P1 存档目录（默认 `output/pipeline`，**优先取 `.reviewed.json`**） |
| `--dimension` | 逗号分隔，默认 `d2,d4,d5,d6`。**D-3 未建**（判据依赖黄金集） |
| `--per-sample` / `--only-undetermined` | 逐条明细 / 只列有问题的 |
| `--json` | 落全量结果 |

⚠️ **看汇总先看「缺件分布」，分档只当线索**。各档都进总分母，
分档不改变任何数字，它只用来定位差异来源。

**先说清楚现存数据是什么状况**（2026-10-10 实测 38 份存档）：
**全部 38 份都没有 `schema_version`**，也就是说事实上的「当前批次」
一条都没有。报表里那两档切的是**字段齐不齐**，不是批次新旧——
其中 16 份缺 `run_config`，而那 16 份的 74 个 `outcome` 一个都没有
`site_url` / `play_page_url` **键**，另 22 份的 131 个全都有，相关性 100%。
所以档名按判据起：`未标版本·缺 run_config` / `未标版本`，
**不写「旧批次 / 当前批次」**——那是在替没有版本号的存档断言新旧。

报表因此分两段读：

| 段 | 是什么 | 能怎么用 |
|---|---|---|
| **分档** | **推断**（缺件代理切出来的） | 指向差异可能在哪，不能当结论 |
| **缺件分布** | **事实**（P1 里压根没这个键） | 直接回答「哪些不可判定是采集缺件造成的」 |

现存数据上两个方向都要看：D-6 那个「74% 不可判定 ⚠」里，
`outcome.site_url` 缺键那 65 条**出分 0**，而全量是 57/221；
D-4 的 8 条扣分全落在 `archive.run_config` 缺件那 77 条里。

⚠️ **代理警告在混合档下照样会打**（2026-10-10 修的缺陷）。判据是
「只要有任一条 `schema_version` 为空」，**不是**「整批都没版本号」——
新存档落盘那一刻会变成混合档，恰恰是最该警告的状态，
原先按 basis 字符串判断会让警告自动消失。

分档判据本身是**两级**：优先按 P1 的 `schema_version`（写入时记的格式
版本），没这个键的存档退回 `run_config` 缺件**代理**。**不回填历史
存档**——没有依据断定一份没版本号的存档是哪一批。
判据与它的局限见增量档案的「增量七」与「增量九」两节（`07-增量档案.md`，全文搜这两个词）。

### scripted / agent A/B 双跑（五指标验收，2026-10-18 A3-4）

两批用**同一份执行计划**（输入一致是 A/B 的前提），落盘分开目录：

```powershell
# 0) 采样一份计划（与模式无关，两批共用）
uv run python -m trajectory_pipeline.executor.cli gen -n 40 --seed 42 --out plan-ab.json

# 1) scripted 批（默认模式，参数可省）
uv run python -m trajectory_pipeline.executor.cli run --plan plan-ab.json --task-id AB-S --out output/ab/scripted

# 2) agent 批（需配齐 TRAJECTORY_LLM_*；升配可选，见环境变量表）
uv run python -m trajectory_pipeline.executor.cli run --plan plan-ab.json --task-id AB-A --out output/ab/agent --executor-mode agent
```

五指标读法（**分别跑、分别算，两批目录就是两个 `--out`**）：

| # | 指标 | 命令 / 数据源 | 通过线 |
|---|---|---|---|
| ① | D10 等价类一致率（主口径） | `uv run python -m trajectory_pipeline.evaluation.golden.builder agreement --version N`（黄金集冻结版对照，两批各算一次） | agent 批不降（上岗线 0.90 不变） |
| ② | D-2/D-5/D-6/D-9 得分不降 | `uv run python -m trajectory_pipeline.evaluation.cli --out output/ab/<批> --include-llm-judge --json <批>.json` | 四个维度分别不降；D-9 随 2026-10-17 拍板纳入（§6.4 决策记录） |
| ③ | agent 步数预算内完成率 | 存档 `outcomes[].reached_play_page` 命中比例；未完成候选由 agent_loop 预算（max_steps=8）截断，表现为 unresolved/预算类分支 | 与 ④ 合读——「没到播放页」要分得清是站点失败还是预算烧完 |
| ④ | unresolved 簇占比 | 存档顶层 `outcomes[].branch == "unresolved"` 占比，按模式分桶（对照方案 12 §3 的两类主张：body 反爬降级、JS-heavy 失败） | agent 批不升（核心主张恰是它该降） |
| ⑤ | 幻觉 goto 计数 | `uv run python -m trajectory_pipeline.evaluation.goto_trace --out output/ab/agent`，读 `[agent]` 行 | 批次级信号，**不进 D-2 样本级**（幻觉记账决策 A），有计数不非零退出 |

三条必须随批记录的口径：

- **D-9 走 CLI 是快路径**（`gate_result=None → sample.gate.status`）；要 d9/gates 的 detailed 判据（temporal_leak 之类）得显式调 `gates.gate()`——那是给 A3-3 判据修订验收用的，成本约 +200% 跑时代码，不进常规批次报表；
- **站点时变**：两批尽量同时段跑；间隔超过一天以上时，④ 的对比结论要带时差保留——「agent 修好了 unresolved」与「站点刚好能爬了」在单次对比里分不开；
- **单元全绿 ≠ 批次达标**（方案 13 §6.6）：门禁记账与批次验收分开记，prompt 调优 × 站点时变是两端最大的不可控项，A/B 重跑取分布不取单点。

同一次双跑还顺手收口 **A1 遗留**两项（方案 13 §6.6）：①判断准确率 A/B 对比、golden alignment ROUTED 口径复核。

### scout 工作流（rubric 评分门禁，2026-10-14 增量）

主流程的轨迹在进黄金集之前要先过一次 rubric 评分门禁 —— 不然黄金集里
混进一批没跑过评分的「裸轨迹」，74.7% 那类数字根本靠不住。完整链路：

    scout → from-scout → annotate → freeze → agreement

`scout` 跑四维评分（D-2/D-4/D-5/D-6），输出三件套（positive / negative
/ quarantine）；`from-scout` 把三件套投影成黄金集候选；剩下的 annotate /
freeze / agreement 是已有命令。详细设计见 `09-rubric-gate改造方案v04-实施
细节.md`，本节只给命令。

```powershell
# 1) 跑 scout：四维评分，落三件套 + scout.jsonl + --stats
uv run python -m trajectory_pipeline.evaluation.scout.cli `
    --p2-root output/pipeline `
    --out output/scout/v1 `
    --mediabrowse-dir output/pipeline/mediabrowse `
    --stats

# 2) 把 scout 产物投影成黄金集候选（quarantine 不进）
uv run python -m trajectory_pipeline.evaluation.golden.builder from-scout `
    --scout-dir output/scout/v1

# 3) 之后照旧：人工标注 → 冻结 → 一致性测量
uv run python -m trajectory_pipeline.evaluation.golden.builder annotate `
    --input evaluation/golden/data/labels.jsonl
uv run python -m trajectory_pipeline.evaluation.golden.builder freeze `
    --version 1
uv run python -m trajectory_pipeline.evaluation.golden.builder agreement `
    --version 1
```

| 参数（scout） | 作用 |
|---|---|
| `--p2-root` | P1 存档 + P2 samples 的共同根，默认 `output/pipeline` |
| `--out` | 三件套落盘目录（自动创建） |
| `--mediabrowse-dir` | 可选，指向 `output/pipeline/mediabrowse`；开启后挂 L5 证据到 `evidence_supplement` |
| `--dry-run` | 只跑四维评分、不落盘（看分布） |
| `--stats` | 只打四类计数（positive/negative/quarantine/skip），不写文件 |

输出三件套：

| 文件 | 是什么 | 是否进黄金集 |
|---|---|---|
| `positive_candidates.jsonl` | 四维都高分，可作校准集 | ✅ |
| `negative_candidates.jsonl` | 任一维 ≤ 2 或 veto，**带 tags 字段** | ✅ |
| `quarantine.jsonl` | 任一维 `score=None`（采集/门禁问题），**不是差评** | ❌ |
| `scout.jsonl` | 三者汇总（不含 skip） | — |

⚠️ **score=0 ≠ score=None**：前者走 negative（判了零分），后者走
quarantine（没判）。quarantine 永不入黄金集 —— 它是上游缺陷信号，
不是负例。`from-scout` 只读 positive + negative。

⚠️ **fail-closed 不算差**。当样本采集/仲裁层主动 fail-closed（凭
`L5_FAIL_CLOSED_NOTES` / `AUTO_REVIEW_NOTES`）时，scout 标 `not_run` →
不参与四维评分、也不落盘 —— 它是「主动放弃」不是「结果差」，与
quarantine 语义不同。

## 取证探针（`cli probe`）

存档里两边的证据互相矛盾时，**存档自己分不出来**——只能开浏览器看现场。

```powershell
uv run python -m trajectory_pipeline.executor.cli probe <url> [<url> …]
uv run python -m trajectory_pipeline.executor.cli probe --from-archive trajectory_pipeline/output/pipeline --limit 5
```

`--from-archive` 从存档的待复核项里取 URL，**不用手打**——手打就又是一次
「凭 URL 形状猜」，而 URL 形状猜的是站点性质，不是页面事实。

⚠️ **它只报事实，不报结论**：`video/iframe/交互元素` 计数、正文前 N 字、
播放控件词表命中数。**「所以这是不是播放站」是人的结论**，不由它下——
判据属于那批数据，见下面的 `downgrade`。

## 取证后处置（`cli downgrade`）

判据成立时把 outcome 降为 `unresolved`（人工复核分支，**不入负样本池**，§5.1）。

```powershell
# 默认 dry-run：只报清单
uv run python -m trajectory_pipeline.executor.cli downgrade --url v-wb.youku.com --reason "现场实测无渲染"
uv run python -m trajectory_pipeline.executor.cli downgrade --evidence '\(?<!\d\)0 个交互元素' --reason "采集缺件，非业务结论"
# 看完清单再落盘
uv run python -m trajectory_pipeline.executor.cli downgrade --evidence '…' --reason "…" --apply
```

| 参数 | 作用 |
|---|---|
| `--out` | P1 存档目录（默认 `output/pipeline`）。**只动原档，不动 `.reviewed.json`** |
| `--url` / `--evidence` | 两个选择器，**互斥**——同用会让人猜是 AND 还是 OR |
| `--branch` | 限定分支。**不受理 `unresolved`**（它已是降级后的状态） |
| `--reason` | **必填**，原样进 `evidence`。它是半年后唯一能说清「这条当初凭什么被降」的依据 |
| `--apply` | 落盘。**默认只报清单** |

`--evidence` 走 Python `re`，且**只看原始判定正文的第一段**——
每次降级追加的中文理由里也含判据关键词，全文匹配会把自己刚降的再降一次
（真发生过，见[避坑指南 §1.5](02-避坑指南.md)）。

处置动作只有一份（证据戳、`branch_before_downgrade`、ledger 记账、
`visits[].success` 同步），**判据由 `--url` / `--evidence` 传进来**：
判据是那批数据的结论，不是通用参数。

## 浏览器媒体复核（`cli mediabrowse`，2026-10-13 增量二十三 / 二十四 / 三十四）

阶段 4 七层 L2/L3/L4 串接：开真浏览器看 `<video>` / `<audio>` 真实状态，叠加规则层与 VLM 复核，输出 `BrowserProbeResult.l5_outcome`。**默认走 `FakePageDriver` 不开真浏览器**，`--driver obscura` 切真浏览器。

```powershell
# 默认 fake——不开真浏览器，只跑 in-process mock（CI 友好）
uv run python -m trajectory_pipeline.executor.cli mediabrowse --from-urls urls.txt --task-id P023

# 真 obscura 浏览器（v.qq.com 13/13 = passes 实证）
uv run python -m trajectory_pipeline.executor.cli mediabrowse --driver obscura --from-urls urls.txt --task-id P024

# L4 复核实现切换（2026-10-13 增量三十四）：
# --reviewer heuristic    默认走 HeuristicVLMReviewer（纯文本启发式）
# --reviewer multim       走 MultimVLMReviewer（OpenAI / Anthropic 双通道，无 key 自动降级）
uv run python -m trajectory_pipeline.executor.cli mediabrowse --driver obscura --reviewer multim --task-id P034
uv run python -m trajectory_pipeline.executor.cli mediabrowse --driver obscura --reviewer heuristic --task-id P034-heur
```

| 参数 | 作用 | 默认 |
|---|---|---|
| `--driver {fake,obscura}` | 浏览器驱动 | `fake` |
| `--reviewer {heuristic,multim}` | L4 复核实现类 | `heuristic` |
| `--from-urls <file>` | URL 列表文件路径，每行一个 URL | — |
| `--task-id <id>` | 产物命名空间（`output/pipeline/mediabrowse/P<id>__*.json`） | — |
| `--title <text>` | 任务标识 | — |
| `--no-l1` / `--l1-timeout <s>` | 跳过 L1 ffprobe / ffprobe 超时 | L1 默认开 / 60s |

**L4 `--reviewer` 选 multim 时**：缺 key 不报错，直接降级到 heuristic，source 打 `multim_fallback`。**真视觉要 OpenAI / Anthropic key**——

```powershell
# MultimVLMReviewer 配置（增量三十四）：
# OpenAI 通道（首选，gpt-4o-mini 自带 response_format=json_object 约束）
setx OPENAI_API_KEY "sk-..."
# Anthropic 通道（次选；只 ANTHROPIC_API_KEY 设了才走）
setx ANTHROPIC_API_KEY "sk-ant-..."

# 模型与超时（2026-10-13 默认值；按需覆盖）：
# INC34_OPENAI_MODEL = gpt-4o-mini
# INC34_OPENAI_TIMEOUT_S = 12.0
# INC34_ANTHROPIC_MODEL = claude-3-5-haiku-latest
# INC34_ANTHROPIC_TIMEOUT_S = 12.0
```

**三处纪律**（[§5.25](02-避坑指南.md) 详）：

1. **降级显式**——无 key / API 错 / label 非法都走 `HeuristicVLMReviewer` 兜底，`source="multim_fallback" + note="multim_fallback:<reason>"`。**不冲掉 L4 标签**。
2. **OpenAI 优先**——双 key 同时设时 OpenAI 优先；`elif` 改相等权重是**合同变更**，不要悄悄改。
3. **空字符串 key 与 unset 同语义**——`OPENAI_API_KEY=""` 是 falsy 走 fallback，不是调通网络收 401。

**真 obscura 受限于 SSRF guard**：默认拦 127.0.0.1 / 10.0.0.0/8 / 192.168.0.0/16 导航，本地测试用 `FakePageDriver.set_body_text()` 鸭子兼容；真测试用公开 URL。

**multim 通道 v.s. heuristic 的取舍**：

## 环境变量

> ⚠️ **`run` 的 `--title` 缺省即报错**，不拿 `--task-id` 顶替。
> 实测：少了它就搜成 `T001 在线观看`（**轮胎** T001），产出整批理由通顺的
> 假负样本且**零报错**。见[避坑指南 §5.13](02-避坑指南.md)。

`run` / `check` 需要 `OBSCURA_EXE` 指向 obscura 可执行文件，**缺失即报错，不猜路径**：

```powershell
setx OBSCURA_EXE "C:\Users\klpc\workspace\tool\obscura-x86_64-windows-stealth\obscura.exe"
```

`--perceptor llm` / `TRAJECTORY_PERCEPTOR=llm` 另外需要 LLM 后端，**同样缺失即报错不猜**：

```powershell
setx TRAJECTORY_LLM_BASE_URL "http://<host>/v1"
setx TRAJECTORY_LLM_MODEL "<model>"
setx TRAJECTORY_LLM_API_KEY "<key>"    # 本机 vLLM 不校验时可留空
```

**key 只走环境变量**：代码里没有任何凭据字面量，`LLMConfig.__repr__` 刻意不吐 key，`test_llm.py::TestNoCredentialInSource` 盯着源码里不许出现 `sk-` / `bgw_` 这类前缀。

| `TRAJECTORY_LLM_MAX_TOKENS` | 8192（**采集时设 16384**） | 单次请求的**输出**预算，**默认 8192 但对采集不够**（2026-10-11 增量校准）。推理模型的思考与正文共用这一个预算，预算小了正文一个字都吐不出来（`finish_reason=length` + `content=null`）→ 判断点 ① **空回传**、`kept=None`、走启发式全遍历，D-2 全批不可判定。实测 `MiniMax-M3.1-Flash-Preview`：600 思考吃光、2048 正文被截断、**8192 在小输入有干净正文但真实采集场景（候选 14 条/长输入）仍被吃光**（TPIN02 首跑 `finish_reason=length`、content 为空）；**设 `TRAJECTORY_LLM_MAX_TOKENS=16384` 后判断点 ① 恢复正常**（TPIN02 实测选出 8/15、kept=8）。换机器/换模型先设 16384 |
| `TRAJECTORY_LLM_TIMEOUT_S` | 90 | **默认 90**（2026-10-11 校准：30s 对判断点 ① 不够，实测 5 条里超时 3 条，已写进 `llm/client.py::DEFAULT_TIMEOUT_S`）。②③④ 在站点内正常远快于 90s，极端拖满由 `per_site_timeout_s`（单站 90s）兜底 |
| `TRAJECTORY_EXECUTOR_MODE` | `scripted` | **执行器模式的 fallback 关口**（2026-10-17 A3-1 转正，见 [13-A2A3 实施设计 §6.1](../设计方案/13-A2A3-agent循环与双模灰度实施设计.md)）。正门是 run 子命令的 `--executor-mode` 参数；本键只在**参数缺省**时读，优先级 `--executor-mode` > 本键 > 默认 scripted，A3 结束后撤。`agent` = 站内自主导航，**需同时配齐上面的 `TRAJECTORY_LLM_*`，缺了即报错不猜**——agent 模式没有后端时**不静默退回 scripted**（那会让「agent 批失败了 40%」被读成「scripted 跑得好好的」）。默认值刻意不是 `auto`：有 LLM 后端 **不等于**该让它开方向盘，后端是为判断题配的 |
| `TRAJECTORY_LLM_ESCALATE_BASE_URL` / `_MODEL` / `_API_KEY` | 未配置 | **升配后端三键**（2026-10-17 A2a-4，见 13 号文档 §3.5）。agent 模式下连续 2 次动作指令不可解析时切到这条后端救场。三态：**全没配 = 无升配**（EscalateModel 只落事件不切后端，不 fail）；**全配 = 接上**（KEY 缺省走 `not-needed` 占位，且继承主后端的 `TIMEOUT_S`/`MAX_TOKENS` 校准值）；**只配一半 = 启动报错**——有 BASE_URL 没 MODEL 或反之都算配置错误，静默当无升配会让那一半配置成尸体。升配调用照样落 `llm_calls[]` 账本（`model` 字段看得出哪条后端花的钱） |

`setx` 只对新开的终端生效——配完发现仍报缺变量，先开新终端。

> ⚠️ **`budget:max_tokens 用尽` 与连接失败是两回事**（[§5.19](02-避坑指南.md)）：
> 前者只调 `TRAJECTORY_LLM_MAX_TOKENS`，后者调超时或查后端。
> 症状都表现为「模型没答」，而处置完全不同——把它当连接问题去查会白查半天。

⚠️⚠️ **模型名大小写敏感，而 403 与 503 是两种不同的失败**（[避坑指南 §5.19](02-避坑指南.md#519-解析失败不是判不出来而-403-不是-503)）。实测：

| 症状 | 含义 | 处置 |
|---|---|---|
| 每道题都返 `None`，终端像「LLM 判不了」 | 可能是 **403**：名字**未注册**（精确匹配失败） | `/models` 清单逐字核对大小写 |
| 同上，但名字在清单里 | 可能是 **503**：已注册，**服务过载** | 只能等，或换一个可用的 |
| 少数题偶发解析失败 | 模型写了**未转义引号**（大括号配平，肉眼看不出来） | 已由 `schema_parse` 容错；仍失败就看日志里的 `last_error` |

**先看清单再改配置**：

```powershell
uv run python -c "from trajectory_pipeline.llm.client import LLMConfig, probe; cfg=LLMConfig.from_env(); print([m['id'] for m in probe(cfg, 15.0)['data']])"
```

**代码不猜模型名**——按「缺件即报错，不猜」这条纪律，清单里挑一个是**人的决定**。

感知实现由 `TRAJECTORY_PERCEPTOR=rule|llm|auto` 选（默认 `auto`）。

### 排查：判断点① 空回传 / 「模型没答」

症状都是「判断点 ① 未取得结论（LLM 不可用（…））」。**先读括号里的错误前缀再动手**——前缀不同，处置完全不同：

| 存档 `warnings` / 终端错误前缀 | 根因 | 处置 |
|---|---|---|
| `budget:max_tokens 用尽（finish_reason=length，content 为空）` | 推理模型**思考吃光了输出预算**（思考与正文共用 `max_tokens`），不是后端坏了 | 调大 `TRAJECTORY_LLM_MAX_TOKENS`（**16384**，TPIN02 实测；默认 8192 对真实采集不够）→ 重跑 |
| `transport:ReadTimeout` | **请求超时**（判断点① 输入大，默认 90s 不够） | 调大 `TRAJECTORY_LLM_TIMEOUT_S`（默认 90）→ 重跑；仍超时查后端负载（[§5.6](02-避坑指南.md#56-推理模型的思考与正文共用-max_tokens-一个预算) 副产物教训） |
| `shape:...` / 解析失败 | 模型回复格式坏了（未转义引号等） | `schema_parse` 已容错；仍失败看日志 `last_error`（[§5.19](02-避坑指南.md#519-解析失败不是判不出来而-403-不是-503)） |
| `http:403` | 模型名大小写不匹配/未注册 | `/models` 清单逐字核对（见上表） |
| `http:503` | 服务过载 | 等，或换可用模型 |

**步骤**：

1. 重跑一条已知样例（`run --task-id TPIN02 --title 功夫`）复现，先排除偶发；
2. 从存档 `warnings` 读出错误前缀，按上表定位根因；
3. **只调对应参数，且改完必须重跑同一条验证**——判断点① 有结论（`heuristic_candidates=0`、`kept>0`）才算修好，不能凭推理宣布修好（[§5.6 副产物](02-避坑指南.md#56-推理模型的思考与正文共用-max_tokens-一个预算)）；
4. 换机器/换模型后第一件事：用 `LLMConfig.from_env()` 打印实际生效的 `max_tokens` / `timeout_s`（`setx` 只对新终端生效，防「配了没生效」被当「模型坏了」）。

## 两条固定动作

**每次真实运行后都要逐条打开存档读 evidence 核对**——这是固定动作不是可选项。设计上五类缺陷全部是离线测试测不出来的（fixture 是我们自己造的，规则和 fixture 一起错，测试照样绿），只有把真实站点喂进去、逐条读存档，才会看见「结论」和「证据」在打架。踩坑全记录在 [避坑指南](02-避坑指南.md)。

**这条现在是命令了**：`cli check-archives`（[`executor/integrity.py`](../executor/integrity.py)）是它的机械版——查证据链完整性、结论与观察是否自相矛盾、真负样本有没有并池。**纯手工的固定动作等于没有**：它靠人记得做，而它恰恰是最容易在赶批次时跳过的一步。选档案走 `archive.select_archives`，与 `report` 同一口径，否则会出现「门禁说全过、报表说有 5 个档有问题」。三档严重度：

| 档 | 含义 |
|---|---|
| `FATAL` | 不可信，只能重跑 |
| `DEGRADED` | 缺件，不能直接当训练数据 |
| `INFO` | 看一眼 |

**判断「结论对不对」仍然不在门禁里**——那要人读证据，它只保证「值得人读的东西没悄悄烂掉」。

## 感知层回放（`cli replay`）

[`perception/replay.py`](../perception/replay.py) 把 P1 存档里的**真实观察原样**喂给感知实现，**不开浏览器**。P1 存的是 `_obs_json` 落下来的结构化观察——`video_tag_count` / `iframe_count` / `interactive_elements` / 正文 / `degraded` 全在，那正是 `Observation` 的字段。

- **验**：感知层在真实数据上的判得出来率、两版答案差在哪。
- **不验**：ref 点击、播放器探测、跳转、反爬、加载时序——**所以它不能替代真实批次**。

`--perceptor rule` **不需要任何 LLM 后端**，于是「W1 在真实数据上答得出来几道」完全离线可测。

⚠️ **只报分歧，不报准确率**：拿 rule 的答案当真值会得到一个漂亮的假数字（rule 判成功的 3 条里 2 条是假阳性）。真要算准得先有人工标注集——那也是 `CONFIDENCE_JUDGED` 校准的前置条件，两件事一起做。

实测数字见增量档案的「附录 B」（`07-增量档案.md`，全文搜「附录 B」）——**已随清空作废，须重跑**。
