## 常用命令

```powershell
uv sync --group dev

# ── 执行层 ─────────────────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli check              # 探 obscura 能力 + 报两个感知实现的边界（唯一需真实浏览器的自检）
uv run python -m trajectory_pipeline.executor.cli run --task-id T001 --title 功夫
uv run python -m trajectory_pipeline.executor.cli run --plan <plan.json> --limit 20 --dry-run
uv run python -m trajectory_pipeline.executor.cli run --plan <plan.json> --limit 5 --perceptor llm   # 覆盖 TRAJECTORY_PERCEPTOR

# ── 任务生成层（不联网）────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli gen -n 20 --seed 7 --out <plan.json>
uv run python -m trajectory_pipeline.executor.cli check-persona      # 画像覆盖度 + 判分保真探针，分开报

# ── 组装（P2 / P3）────────────────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli build                        # P1 → P2 → P3（不联网）
uv run python -m trajectory_pipeline.executor.cli build --stage p2              # 只切 P2（读 P1）
uv run python -m trajectory_pipeline.executor.cli build --stage p3              # 只渲 P3（读 P2）
uv run python -m trajectory_pipeline.executor.cli build --overwrite             # 覆盖已落盘产物（**默认不覆盖**）

# ── 人工复核与报表 ─────────────────────────────────────
uv run python -m trajectory_pipeline.executor.cli review --write <queue.jsonl> --show 3
uv run python -m trajectory_pipeline.executor.cli review --verdicts <queue.jsonl> --apply
uv run python -m trajectory_pipeline.executor.cli report --out trajectory_pipeline/output/pipeline
uv run python -m trajectory_pipeline.executor.cli check-archives      # 存档完整性门禁（不联网）
uv run python -m trajectory_pipeline.executor.cli replay --perceptor rule   # 感知层回放（不开浏览器）

# ── 整批回滚（默认只列不删）────────────────────────────
uv run python -m trajectory_pipeline.executor.cli purge-run --run-id <run_id>
uv run python -m trajectory_pipeline.executor.cli purge-run --run-id <run_id> --apply

# ── 门禁 ───────────────────────────────────────────────
uv run python -m pytest -q
```

| 命令 | 联网 | 作用 |
|---|---|---|
| `check` | ✅ | 探 obscura 能力握手与 `observe` 契约，报两个感知实现的边界 |
| `run` | ✅ | 跑一个 task / 一份计划，落 P1 |
| `gen` | ❌ | 骨架 × persona 采样，产出执行计划 JSON |
| `check-persona` | ❌ | 画像覆盖度 + 判分保真探针（**分开报，不合成一个数**） |
| `review` | ❌ | 导出 / 回填人工复核裁定 |
| `report` | ❌ | 汇总 P1 分支分布 + 成功站点域名分布（D7 验收） |
| `check-archives` | ❌ | P1 存档完整性体检 |
| `replay` | ❌ | 在存档的真实观察上跑感知实现 |
| `build` | ❌ | P1 → P2 → P3 组装。**默认不覆盖**已落盘产物，重建整批要显式 `--overwrite` |
| `purge-run` | ❌ | 回滚一个 run：删它的存档 + 它并进 `negative.jsonl` 的行 |

## 环境变量

> ⚠️ **`run` 的 `--title` 缺省即报错**，不拿 `--task-id` 顶替。
> 实测：少了它就搜成 `T001 在线观看`（**轮胎** T001），产出整批理由通顺的
> 假负样本且**零报错**。见[避坑指南 §5.13](02-避坑指南.md)。

`run` / `check` 需要 `OBSCURA_EXE` 指向 obscura 可执行文件，**缺失即报错，不猜路径**：

```powershell
setx OBSCURA_EXE "C:\Users\klpc\workspace\tool\obscura-x86_64-windows-stealth\obscura.exe"
```

`--perceptor llm` / `TRAJECTORY_PERCEPTOR=llm` 另外需要 LLM 后端，**同样缺失即报错不猜**：

```powershell
setx TRAJECTORY_LLM_BASE_URL "http://<host>/v1"
setx TRAJECTORY_LLM_MODEL "<model>"
setx TRAJECTORY_LLM_API_KEY "<key>"    # 本机 vLLM 不校验时可留空
```

**key 只走环境变量**：代码里没有任何凭据字面量，`LLMConfig.__repr__` 刻意不吐 key，`test_llm.py::TestNoCredentialInSource` 盯着源码里不许出现 `sk-` / `bgw_` 这类前缀。

⚠️ **`TRAJECTORY_LLM_TIMEOUT_S` 默认 30s 对判断点 ① 不够**（实测 5 条里超时 3 条），跑真实批次先把它调到 90。`setx` 只对新开的终端生效——配完发现仍报缺变量，先开新终端。

⚠️⚠️ **模型名大小写敏感，而 403 与 503 是两种不同的失败**（[避坑指南 §5.19](02-避坑指南.md#519-解析失败不是判不出来而-403-不是-503)）。实测：

| 症状 | 含义 | 处置 |
|---|---|---|
| 每道题都返 `None`，终端像「LLM 判不了」 | 可能是 **403**：名字**未注册**（精确匹配失败） | `/models` 清单逐字核对大小写 |
| 同上，但名字在清单里 | 可能是 **503**：已注册，**服务过载** | 只能等，或换一个可用的 |
| 少数题偶发解析失败 | 模型写了**未转义引号**（大括号配平，肉眼看不出来） | 已由 `schema_parse` 容错；仍失败就看日志里的 `last_error` |

**先看清单再改配置**：

```powershell
uv run python -c "from trajectory_pipeline.llm.client import LLMConfig, probe; cfg=LLMConfig.from_env(); print([m['id'] for m in probe(cfg, 15.0)['data']])"
```

**代码不猜模型名**——按「缺件即报错，不猜」这条纪律，清单里挑一个是**人的决定**。

感知实现由 `TRAJECTORY_PERCEPTOR=rule|llm|auto` 选（默认 `auto`）。

## 门禁

```powershell
uv run python -m pytest -q
```

> 门禁 `testpaths = ["trajectory_pipeline/tests"]`（v1 测试树 2026-10-09 随代码归档退役出默认门禁，手动跑法见 [`archive/v1/README.md`](../../archive/v1/README.md)）。
> 历史教训仍然有效：gdr/tests 曾漏在门禁外，360+ 条不跑，掩盖了 2 处生产代码从未执行——
> **门禁必须显式枚举每一棵在开发的树，漏一棵 = 静默失效不可见**。

## 输出目录

- **`trajectory_pipeline/output/pipeline/`** —— 新树全部产物（D8，gitignored）：P1 存档、负样本池、复核队列、`obscura_tools.json` 等探针取证
  - `samples/<sample_id>.json` —— P2 单条样本（六件套，**已按决策单元切条**）
  - `views/<sample_id>_{messages,openai,meta}.json` —— P3 训练视图
- `output/agent_trajectory|refined|refine_data/` —— 存量 C1/C2/C3（冻结，不迁移、不双写）
- `output/orchestration/dead/` —— 存量死信；`refine_data/*.jsonl` —— 存量旁路审计通道

## 两条固定动作

**每次真实运行后都要逐条打开存档读 evidence 核对**——这是固定动作不是可选项。设计上五类缺陷全部是离线测试测不出来的（fixture 是我们自己造的，规则和 fixture 一起错，测试照样绿），只有把真实站点喂进去、逐条读存档，才会看见「结论」和「证据」在打架。踩坑全记录在 [避坑指南](02-避坑指南.md)。

**这条现在是命令了**：`cli check-archives`（[`executor/integrity.py`](../executor/integrity.py)）是它的机械版——查证据链完整性、结论与观察是否自相矛盾、真负样本有没有并池。**纯手工的固定动作等于没有**：它靠人记得做，而它恰恰是最容易在赶批次时跳过的一步。选档案走 `archive.select_archives`，与 `report` 同一口径，否则会出现「门禁说全过、报表说有 5 个档有问题」。三档严重度：

| 档 | 含义 |
|---|---|
| `FATAL` | 不可信，只能重跑 |
| `DEGRADED` | 缺件，不能直接当训练数据 |
| `INFO` | 看一眼 |

**判断「结论对不对」仍然不在门禁里**——那要人读证据，它只保证「值得人读的东西没悄悄烂掉」。

## 感知层回放（`cli replay`）

[`perception/replay.py`](../perception/replay.py) 把 P1 存档里的**真实观察原样**喂给感知实现，**不开浏览器**。P1 存的是 `_obs_json` 落下来的结构化观察——`video_tag_count` / `iframe_count` / `interactive_elements` / 正文 / `degraded` 全在，那正是 `Observation` 的字段。

- **验**：感知层在真实数据上的判得出来率、两版答案差在哪。
- **不验**：ref 点击、播放器探测、跳转、反爬、加载时序——**所以它不能替代真实批次**。

`--perceptor rule` **不需要任何 LLM 后端**，于是「W1 在真实数据上答得出来几道」完全离线可测。

⚠️ **只报分歧，不报准确率**：拿 rule 的答案当真值会得到一个漂亮的假数字（rule 判成功的 3 条里 2 条是假阳性）。真要算准得先有人工标注集——那也是 `CONFIDENCE_JUDGED` 校准的前置条件，两件事一起做。

实测数字见[现状与验收](05-现状与验收.md)。
