## 一、一句话主线

```text
骨架（存量任务，人写的）
  └─ persona 画像 ──采样──→ 计划条目 ──执行──→ P1 存档
                                                  ├─→ P2 样本 ─→ P3 三视图
                                                  ├─→ 负样本池 negative.jsonl
                                                  └─→ 复核队列 ─人工─→ .reviewed.json

阶段 4 浏览器媒体复核（独立流程，不进 P1/P2/P3）：
  URL 列表 ──cli mediabrowse──→ BrowserProbeResult（含 L2/L3/L4/L5 + l5_outcome）
                                                  └─→ output/pipeline/mediabrowse/P<id>__*.json
```

采集的是**可归因的证据**，所以每一层只做一件事，且交接面是**文件格式**——理由见 §四。

## 二、四条命令线

`gen` 与 `run` **分成两条命令**而不是一条命令的两步：跑不出数据时分不清是 taskgen 挂了还是 obscura 起不来，而这两者的处置完全不同。`run --plan <file>` 是把两步接起来的方式，但仍然是两条命令。

| 命令 | 读 | 写 | 联网 | 落点 |
|---|---|---|---|---|
| `gen` | 骨架 + persona 库 | 计划 | ❌ | `--out` 指定的 JSON |
| `run` | 计划 或 `--task-id/--title` | **P1** + 负样本池 | ✅ 需 `OBSCURA_EXE` | `output/pipeline/<task_id>__<run_id>.json` |
| `mediabrowse` | URL 列表（`--from-urls`）或 `--url` | **L2/L3/L4/L5 probe + l5_outcome** | ✅ 默认 fake（不开浏览器）/ `--driver obscura` 接真浏览器 | `output/pipeline/mediabrowse/<task_id>__*.json` |
| `build` | **P1** | **P2** → **P3** | ❌ | `output/pipeline/samples/<sample_id>.json` |
| `review` | **P1** | 复核队列 → 回填 | ❌ | `<queue>.jsonl` / `<run>.reviewed.json` |
| `report` / `check-archives` / `purge-run` | **P1** | 终端 / 索引 | ❌ | — |
| `evaluation.cli` | **P1** | 评分 JSON | ❌ | `--json` |

```powershell
uv sync --group dev

# 生成（不联网）
uv run python -m trajectory_pipeline.executor.cli gen -n 20 --seed 7 --out plan.json

# 执行（联网）
uv run python -m trajectory_pipeline.executor.cli run --plan plan.json --limit 20 --dry-run
uv run python -m trajectory_pipeline.executor.cli run --plan plan.json --limit 5 --perceptor llm

# 组装（不联网，默认不覆盖）
uv run python -m trajectory_pipeline.executor.cli build
uv run python -m trajectory_pipeline.executor.cli build --stage p3 --overwrite

# 复核与报表（不联网）
uv run python -m trajectory_pipeline.executor.cli review --write queue.jsonl
uv run python -m trajectory_pipeline.executor.cli review --verdicts queue.jsonl --apply
uv run python -m trajectory_pipeline.executor.cli report --out trajectory_pipeline/output/pipeline
uv run python -m trajectory_pipeline.executor.cli check-archives

# 评估（不联网，读 P1）
uv run python -m trajectory_pipeline.evaluation.cli --per-sample --only-undetermined
```

> ⚠️ `run` 的 `--title` **缺省即报错**，不拿 `--task-id` 顶替。实测少了它就搜成 `T001 在线观看`（**轮胎** T001），产出整批理由通顺的假负样本且**零报错**。见[避坑指南 §5.13](02-避坑指南.md)。

## 三、数据形态

| 形态 | 是什么 | 谁写 | 谁读 |
|---|---|---|---|
| **计划** | 采样产物：一条 = 一个 `(骨架, persona)` 组合 | `taskgen/sampler.py` | `executor/plan.py` |
| **P1** | `RunRecord`——一个 task 的完整运行记录：观察全文、动作流、账本、运行参数 | `executor/orchestrator.py` | assembler / evaluation / review / report |
| **P2** | `Sample`——六件套（见 [03-数据契约](03-数据契约.md)） | `assembler/builder.py` | `assembler/views.py` |
| **P3** | 三视图：`messages` / `openai` / `meta` | `assembler/views.py` | 训练框架 / 人工复核 |

### P1 的形状

```text
output/pipeline/<task_id>__<run_id>.json     ← 平铺，不是目录
output/pipeline/negative.jsonl               ← 负样本池
output/pipeline/<task_id>__<run_id>.reviewed.json   ← 回填后取代原档，不并列计两份
```

存档挑选只认 `<task_id>__<run_id>.json` 形状——同目录还躺着 `obscura_tools.json` / `probe_observe.json` 等**探针取证**，按 `*.json` 收会把它们当存档。

### P1 → P2 的切法

**一条 P2 = 一个决策单元**：搜索阶段一条，每个站点一条。

> **两条执行链切出来的 P2 同形**（2026-10-17 A2）。`executor_mode` 是
> P1 顶层字段、**不进 P2 六件套**——训练视图里没有它，A3 的 A/B 对比
> 因此必须回到 P1 存档上按批次做，不能在样本层做。这也是
> `executor_mode` 必须落进存档的理由：两批的 `steps` / `observations`
> 逐字段同形，没了它就只能靠文件名猜这批是谁跑的。

不把「选哪个站」与「这个站行不行」压进同一次预测——那是两种不同的选择。切条逻辑的唯一所有者在 [`assembler/schema.py`](../assembler/schema.py)，`builder.py` 只负责把内存里的 `Sample` 变成磁盘 JSON。

### P1 是取证态，P2/P3 是训练态

| | P1 | P2 |
|---|---|---|
| 正文 | 全文（`max_chars` 默认 6000） | 裁到 2000 |
| 元素 / 链接 | 80 / 50 | 40 / 30 |

裁剪规则只在 [`assembler/observation_view.py`](../assembler/observation_view.py) 一处，两边各取所需但不自成一套。

⚠️ **P1 正文全文落盘**（不只留摘要）：站点会失效下线改版，重抓拿到的是**另一个页面**，而存档里那条结论的证据已经不存在了；被反爬拦截时根本重抓不回来。P1 是批次唯一真值源，证据链断了不可逆，体积只是磁盘。

## 四、模块边界：交接面是格式，不是 import

四个跨模块交接点**全部按文件格式**，没有一个是 Python 导入：

```text
taskgen  ──计划 JSON──→  executor
executor ──P1 JSON ──→  assembler
assembler──P2 JSON ──→  views
P1 JSON  ───────────→  evaluation
```

理由是 **P1 贵、P2 便宜**：重建一批 P2 必须独立于 `executor` 的当前版本。一旦 `import executor`，executor 改一个 dataclass 字段就可能让半年前那批 P2 重建不出来，而重建不出来的那批是**永久损失**。计划文件同理——它要长期存着，切片分析、失败归因、半年后回看读的都是那个 JSON。

由 [`tests/contract/test_p2_contract.py`](../tests/contract/test_p2_contract.py) 用 AST 强制。

**依赖方向**单向，禁止回指（详见 [01-架构总览](01-架构总览.md)）：

```text
common ← llm ← {taskgen, perception, rationale}
              ↑
           executor  ──→ storage
              ↓
          assembler ──→ storage
              ↓
          evaluation ──→ storage
```

`evaluation` **单独一个 CLI**，不挂进 `executor.cli`：`executor → evaluation` 是横向依赖且方向相反，评分器要读 P1 而 executor 不该知道下游有个验收方。

## 五、执行期：一个 task 的完整时序

[`executor/orchestrator.py`](../executor/orchestrator.py) 的 `run()`。**不抛异常**——异常折算进 `warnings`，唯一允许抛的是 `title` 为空（那是调用方漏了必填项，不是采集故障）。

模式在**构造期**定下（2026-10-18 A3-1 转正）：`RunConfig.executor_mode`，取值经 `--executor-mode` 参数门（参数 > `TRAJECTORY_EXECUTOR_MODE` fallback > 默认 `scripted`）。`agent` 模式没注入后端时**构造期报错**，不静默退回 scripted——退回的那批在存档上写着 `scripted`，「agent 批失败了 40%」会被读成「scripted 跑得好好的」。

```text
环节 0    goto 搜索页 → observe                    → record.search_obs
环节 0.5  detect_block 反爬判定        ← 必须在取候选【之前】短路
环节 ①    browser_extract 取结果标题    → 写回 search_obs.links[].text
          extract_candidates 代码层结构性过滤
环节 ①.5  判断点 ①.5 CLASSIFY_SEARCH_LINKS → 四分类按路径分发/记账
环节 ①.6  站点首页核（确定性事实）      → path 为 `/` 记 not_play_site
环节 ②    ┌ for 每个候选:
          │   环节②  goto + observe     → 判断点 ② IS_REACHABLE
          │   环节④  找播放控件          → 判断点 ③ FIND_PLAY_CONTROL
          │   环节⑤  new_tab + click     ← 每站点一个 tab
          │   环节⑥  重新 observe        ← 判的是播放页
          │   环节⑦                       → 判断点 ④ PLAYER_OK
          │   _write_rationales（模块 4，执行期逐步生成）
          └ 逐条记进 ledger
```

各环节的代码落点：

| 环节 | 文件 | 产出 |
|---|---|---|
| 0 | [orchestrator.py](../executor/orchestrator.py) | `search_obs` |
| 0.5 | [gatekeeper.py `detect_block`](../executor/gatekeeper.py)（2026-10-16 阶段 G 自 dom.py 迁入，dom 反向再导出） | `search_blocked`（**运行级字段，不进分支体系**）+ `gatekeeper_events[]` 事件账本 |
| ① | [steps/search.py](../executor/steps/search.py) | `candidates` + `candidate_filter` |
| ①.5 | `_classify_candidates`（2026-10-16 阶段 A1 接管旧 `_apply_selection`；分批 ≤ `PERCEPTION_LINK_WINDOW` + `_CLASSIFY_DISPATCH` 按路径分发） | 目标类保留 / 点名记负分支 / 未点名 `unresolved` |
| ①.6 | `_drop_site_homepages` | 首页候选记 `not_play_site`，不访问 |
| ②–⑦ | [steps/visit.py](../executor/steps/visit.py)（scripted）/ [steps/agent_visit.py](../executor/steps/agent_visit.py)（agent） | `VisitResult` + `ledger` |
| 中间页 | [steps/aggregator.py](../executor/steps/aggregator.py) / [steps/article.py](../executor/steps/article.py)（scripted）/ [steps/agent_intermediate.py](../executor/steps/agent_intermediate.py)（agent，2026-10-17 A2b） | `intermediates[]` + 最终候选 + `ledger` |
| rationale | `_write_rationales` | `steps[i].rationale` |

### 环节 ②–⑦ 的两条走法（2026-10-17 方案 12 阶段 A2）

分派在 `_visit_guarded` 里按 `RunRecord.executor_mode` 二选一，
**一条候选只走一条链**（候选内不 fallback，混合轨迹不可归因）：

```text
scripted   ② goto+observe → ③ IS_REACHABLE → ④ FIND_PLAY_CONTROL
           → ⑤ new_tab+click → ⑥ observe → ⑦ PLAYER_OK

agent      ② goto+observe（共用 enter_site）→ new_tab
           → agent_loop：站内自主导航（每步 observe → 拦截 → 决策 → I6
             → 预算 → 执行 → 死循环）
           → ⑦ PLAYER_OK（共用 judge_player）
```

两条链**共用** `enter_site`（进站）与 `judge_player`（⑦），差别只在中间：

- agent 链**不跑 ② `IS_REACHABLE` / ③ `FIND_PLAY_CONTROL`**——那两道
  「页面里有没有、是哪个」的判断正是交给模型的部分；
- ⑦ 不做「复观」：`PLAYER_OK` 判的是 `AgentOutcome.final_obs`，
  即**agent 据以决策的那一份观察**。循环外再取一次快照，判的就是另一份
  快照了（播放器会自转、广告会轮换），而 D-2/D-5 判的正是观察正文；
- 动作流形状完全一致（同一套 `StepLog`、同一个六值动作空间），所以
  P1 落盘对下游**零差异**——这也是 A3 能只加一个 `executor_mode` 字段
  就做 A/B 的前提。

> ④ 的 `trailer_suspect` / `trailer_only` 两条短路是 scripted 链特有的：
> agent 链里「这个控件是预告还是正片」由模型自己在页面内判断，
> 判断错了就是它自报放弃（记 `unresolved`，不进负样本池）。

### B/C 路径中间页的两条走法（2026-10-17 方案 13 §4，A2b）

分派在 `_intermediate_visit` 里，与站点链 `_visit_guarded` 同为**模式的
唯二两处**：

```text
scripted   ① 导航+observe → ⑤ IS_AGGREGATOR（B）→ ⑥ SELECT_SITE_ENTRIES
           / ⑥C SELECT_REFERRAL_LINKS（C）→ 逐外链 resolve_referral

agent      ① 导航+observe（共用 probe_and_observe）
           → agent_loop（任务③ / 任务④）：页面内自主找链接
           → 逐外链 resolve_referral（共用 resolve_into_candidates）
```

两端共用，中间换人：

- **外链校验一段都没放**。agent 只决定「哪些链接值得引荐」，**存不存在
  由 `link_check.resolve_referral` 说了算**（跳转确认页、结构剔除、落地
  观测都是代码事实，模型猜不出来）；
- 终局自报的 URL 要过**轨迹内见过的链接白名单**（与 I6 的 ref 白名单
  同一条纪律的另一端）；被挡下来的落 `RejectedReport` 事件——**挡下来是
  处置，记账是事实**，A3 的批次级幻觉计数读的就是它；
- 三道判断题一道都不跑，所以 `not_aggregator` /
  `aggregator_no_entries` / `article_no_links` 三支在 agent 模式下
  **没有产地**（agent 说没找到一律 `unresolved`）。三支名字仍在 22 支
  封闭集里，由 scripted 独占产出。

### 三个分叉点的答案怎么用

**①.5 的答案**（四分类清单 `video_site / aggregator / article_post / noise`，2026-10-16 阶段 A1 起）决定候选集：目标类保留（**引擎原序**——重排等于用模型判断覆盖引擎相关性排序）、点名非目标类记路径负分支（evidence 带模型 why）、未点名记 `unresolved`（**无证据不记负样本**：漏分类可能是模型漏答，不是「这个站看不了」）。direct / B / C 三条发现路径共用这一道题，目标类分别是 `video_site` / `aggregator` / `article_post`。整批没作答（四类全空 = 没作答 / answer=None）该批候选仍按代码启发式全跑、不记账——旧 ① 的 `True/False/None` 三分语义收敛为分发结果：目标类 kept=0 且逐条点名记负，遍历自然没有目标，同一份账面（不再需要专门的 False 中断文案）。`zhihu/douban/weibo` 自结构排除表移出后走的就是这道题（direct 批次判 `article_post` 记 `not_play_site` 是有证据的真负样本）。

**①.6 不看 ①.5 的分类结果**——三条路径都要过这道核，因为「URL 的 path 是 `/`」是结构性事实，与模型是否作答无关。位置在分类分发**之后**而不是里面：分类的各类分发路径（包括 fail-closed 批启发式保留的）都要过这道核。

**② 的答案**：`False` 直接返回并记分支；`None` **不中断**，继续往下走——fail-closed 管的是「结论」不是「采集」，继续走不等于断言「页面可达」，而是继续收集证据。

**③ 的答案**：带出 `ref`，**代码拿 ref 去点**。`trailer_suspect` / `trailer_only` 两条在点击前就短路；`answer=True` 但无 `ref` 是 I6 被违反，记 `component_unverified` 而不是硬点一个。

**④ 的答案**：`True` = 成功；`None` = `player_unverified`（**在 `record_from` 之前分流**，它会把 `None` 一律记成 `unresolved`）；`False` = 按 `BRANCH_PRECONDITION` 核前置事实后落分支。

> `None` 不中断采集、只有显式负结论才中断——规则版对 ①.5② 只能返 `None`（链接分类与「是否登录墙」都不是规则能判的），若据此中断，W1 批次一个候选都跑不到，负样本池永远空。这不是缺陷，是 fail-closed 的正常表现（①.5 阶段 A1 起整批 `None` = 该批启发式全跑，见上文分发语义）。

### 三条与直觉相反的时序约定

1. **点击后必须重新 observe。** 不重新观察就拿旧观察判播放页，等于判的是**站点页**——一个非常常见的静默错误：代码明明点了，结论却完全没用到点击结果。
2. **点击不抛异常。** 元素不存在是业务事实（该站没播放控件），让它变成异常会把一个正常负样本变成一次运行失败。
3. **重定向不判负。** 「是不是登录墙」是语言层的题，归判断点 ②。

## 六、执行期 vs 组装期：rationale 的两段

```text
生成在执行期（orchestrator._write_rationales）    ← CLI 注入 rationale_writer
        ↓ steps[i].rationale
   P1
        ↓ schema.align_rationales() + gate_of()   ← 逐条跑 gates.gate
组装期核查
        ↓
   P2 six.rationales[] + gate
        ↓ views._rationale_text()
   P3 messages / openai 的逐步思考段
```

两个位置都是设计决定不是漏掉的：

- **生成在 orchestrator 而不在 `visit_site`**：动作流是**记录**、rationale 是**补记**，两者在一次访问结束时才都完整。放进 `visit_site` 会让执行层直接依赖 LLM 模块。CLI 注入可调用对象，所以 [`steps/visit.py`](../executor/steps/visit.py) 完全不知道 rationale 的存在。
- **核查在组装期**：时序核查需要全序列（判「引用了后续步才出现的实体」），执行期那一刻后续步还不存在。

## 七、复核回路

```text
review --write      P1 → queue.jsonl（正样本的唯一来源）
      ↓ 人工填 verdict
review --verdicts --apply    写 <run>.reviewed.json（覆盖式，不并列）
      ↓
report / check-archives / evaluation.cli   一律优先取 .reviewed.json
```

⚠️ `assembler.iter_samples` **刻意跳过** `.reviewed.json`（挑选权留给 `select_archives`）；`evaluation` 走的是 `select_archives` 那条路径。用错入口会把刚人工确认的正样本全滤掉，而 D-5 判的正是这一批。

## 八、贯穿流程的硬约定

1. **负样本不是副产品，是强制产出。** 每条分支都必须有对应样本入库——中断若不记账，这批结论就没有任何样本，而报表上只会看到「这批没跑出东西」。
2. **`unresolved` / `trailer_suspect` / `player_unverified` 不入负样本池。** 三者成因不同、刻意不合并（能不能到 / 页面证据够不够 / 词表判不准）。
3. **并池是写入时的动作，不回填历史存档。** 批次边界前后分布会跳变，不记批次元数据就会读成「质量变好了」。
4. **贴标签前核前置事实**（`BRANCH_PRECONDITION`）：前置事实不成立就降级 `unresolved`，模型原话保留在证据里。
5. **缺件必须看得见。** 闸门三值 `passed` / `failed` / `not_run`——「没跑」渲染成「通过」会让批次上线时看起来像过了闸。老存档缺的键逐条记进 `degraded_from`。
6. **不猜。** `OBSCURA_EXE`、LLM 后端、片名，缺件即报错。凭经验猜路径在换机器时会静默走到别的实现上。
7. **红线不可绕过。** 凭据只走环境变量；不保存 raw CoT / Cookie / Authorization Header / 浏览器 Profile（`FORBIDDEN_TOOLS` 永不提供，不是「暂时没需求」）。refined CoT 不受此限。
8. **禁止投票/集成**（生产链上），分歧必须暴露给人看。

## 九、`cli mediabrowse` 阶段 4 浏览器媒体复核（独立流程）

`run` 走搜索→候选→站点访问→P1 的整链；`mediabrowse` 是**阶段 4** 另一条独立流程——拿一批 URL 直跑 L2（媒体探针）+ L3（规则层）+ L4（VLM 复核）+ L5（仲裁），**不**写 P1/P2/P3，**不进**负样本池（`provenance.source = "mediabrowse"` 标记）。详见 [架构总览 §L4 复核层](01-架构总览.md) 与 [运行手册 浏览器媒体复核](04-运行手册.md)。

```text
URL 列表（--from-urls 或 --url）
   └─ per URL: probe_browser_media (L2) ─→ rule_perceptor (L3) ─→ VLMReviewer (L4) ─→ arbitrate (L5)
                                                  └─ l5_outcome: SiteOutcome | None
   └─ BrowserProbeResult（含 vlm_review / l5_outcome）
   └─ 写 output/pipeline/mediabrowse/P<task_id>__<url-hash>.json
```

| 阶段 | 文件 | 备注 |
|---|---|---|
| L2 媒体探针 | [`executor/probe/media_probe.py`](../executor/probe/media_probe.py) | `MEDIA_PROBE_JS` 单行 IIFE；两次采样间隔 `PROBE_WAIT_S=2s` |
| L3 规则层 | [`executor/perception/rule_perceptor.py`](../executor/perception/rule_perceptor.py) | `access_kind` / `paywall_type` 词典 |
| L4 VLM 复核 | [`executor/review/`](../executor/review/) | `VLMReviewer` Protocol；`HeuristicVLMReviewer` + `MultimVLMReviewer` 双实现 |
| L5 仲裁 | [`executor/arbitration.py`](../executor/arbitration.py) | N-of-M 加权；L2 真播放一票否决 |

**与 `run` 的关键差异**：

- **不进 P1/P2/P3 契约**——产物是 [`BrowserProbeResult`](../executor/probe/media_probe.py)（含 `vlm_review: VLMReviewResult | None` / `l5_outcome: SiteOutcome | None`），与 G1 黄金集对齐但不属于 G1。
- **per-URL fail-soft**——单站超时 / driver 错 / 凭据漏走 `note=timeout` / `note=driver_error` / `note=credential_leak`，不影响下一站；fail-closed 闸门守 L5 / 人工复核不会拿错误产物当结论。
- **driver 双轨**——`--driver fake`（默认，CI 友好，不开浏览器）+ `--driver obscura`（真浏览器，需要 `OBSCURA_EXE`）。
- **reviewer 双轨**（2026-10-13 增量三十四）——`--reviewer heuristic`（默认，纯文本启发式）+ `--reviewer multim`（OpenAI / Anthropic 双通道，无 key 自动降级到 heuristic + `source="multim_fallback"`）。

为什么 `mediabrowse` 不并入 `run`：搜索→候选→访问的链路判断的是「这个站点行不行」，需要控制流里的多步观察；浏览器媒体复核判断的是「这条 URL 直访能不能播放」，是单步证据采集。两件事的输入（计划 vs URL 列表）和产物（P1 vs `BrowserProbeResult`）不同，并入会让 L1 fail-closed 状态机撑不住（详见 [避坑指南 §5.25](02-避坑指南.md)）。
