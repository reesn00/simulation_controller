# 架构总览

v2 轨迹合成管线的架构说明。**规范与纪律见仓库根 [`CLAUDE.md`](../../CLAUDE.md)**——本文只讲「是什么、怎么走」，不讲「不许怎么做」。

一句话：采集**可归因**的 Agent 浏览器操作轨迹。核心主张是**代码层做护栏、LLM 层做探索、persona 管输入分布**。

**分界（2026-10-20 方案 15 重定义）**：**agent runtime 是探索者，代码是护栏与调度。**代码必须保留的五样——步数/llm_calls/超时预算、终止判定、处置映射、分支记账（22 类封闭集）、fail-closed——一样不交出去。感知层不再是「传感器」，退位成三块静态资产（判断题文本进 agent 任务指令 · 分支记账映射表 · 规则检测器进 gatekeeper），在热路径上只剩**终局验收**一个岗位（④ `PLAYER_OK`）。**观察由谁发起决定它进不进动作流**：执行器推的回执 = 观察（不进训练 `tool_calls`），agent 主动拉的读 = 动作（进）。

旧表述「LLM 是传感器，不是驾驶员」**已作废**（A1/A2/A2b 把站内导航整段交给 agent 之后就不成立）。完整重定义见[设计方案 15](设计方案/15-执行器与agent-runtime重新定义.md)。

## 模块地图

```text
trajectory_pipeline/
├─ taskgen/       模块 1  任务生成 + persona 画像库
├─ executor/      模块 2  代码执行循环（控制流在这里，不在任何 LLM 里）
├─ perception/    模块 3  语义感知（可替换插件：rule / llm + 注入工厂）
├─ rationale/     模块 4  rationale 边写边生成 + 一致性闸门三查
├─ assembler/     模块 5  组装与切分（schema + observation_view + builder + views）
├─ evaluation/    模块 6  评估体系（黄金集 + 三层瀑布 + LS 双向）
├─ common/        跨模块地基（无业务逻辑）：元素方言原语 `elements.py`
├─ llm/           LLM 客户端 + 结构化输出解析（全树唯一出口）
├─ storage/       P3 视图读写收拢点（write_p3/read_p3）
├─ toolcatalog/   训练侧工具声明的**唯一真源**（跨层地基）
├─ docs/          本目录：指引 + 设计方案 + contracts/
└─ output/pipeline/   全部产物（D8，gitignored）
```

依赖方向**单向、禁止回指**：

```text
common ← llm ← {taskgen, perception, rationale}
              ↑
      executor ──→ assembler ──→ storage
         │              ↑
         └──────────────┘（executor.cli 聚合 build/review 入口，方向仍单向）
evaluation ──→ {executor, assembler, perception}   ※ 唯一的例外，见下
```

> **只有一处例外，且方向是反的**：[`evaluation/cli.py`](../evaluation/cli.py)
> 要 import `executor.archive`（存档选取）与 `assembler.schema`（切样本）——
> 见[「模块 6 的入口」](#模块-6-的入口evaluationclipy)。约束不变的是
> **`executor` 不得反向 import `evaluation`**：验收方不该被生产方知道。
>
> storage 不是中间层，是**末端收拢点**：只有 P3（训练视图）的读写
> （`write_p3` / `read_p3`）收在 `storage/`；P1 路径权威在 `executor.archive`、
> P2 落盘在 `assembler.builder`，都不经 storage——三个模块的产物同根
> （`output/pipeline/`，D8），但那不是 import 边。
>
> `toolcatalog/` 同款定位——**跨层地基**，不 import 任何功能模块，
> 只放字面量与纯函数。它挂在 `trajectory_pipeline/` 顶层而不是
> `assembler/` 下，是因为 **P3 与 T 互不 import**（契约测试用 AST
> 强制）：工具清单得有个两边都能用的地方，否则挂哪边都会被另一边的
> 禁令扫到。P2 的 `six.tools`、P3 的 `openai.tools`、T 的
> `openai.tools` 三处都是它的**投影**。口径见
> [`toolcatalog/__init__.py`](../toolcatalog/__init__.py) 的模块 docstring。
>
> **投影要按「面」取**（2026-10-20 方案 15 §5.5）：一份工具声明有两个身份——
> **工具面**（执行层叫哪些名字、收哪些参数）与**方言**（属于哪套实现）。
> 后者**不是第二个独立轴**，它由前者**一对一折算**（P1 的 `driver` →
> `surface_of_driver()` → 面），所以填错的机会只有一处、且那处由代码产生。
> 三个面值：`obscura-1`（13 条声明 / 11 可见，`click(tag, label)`）·
> `camoufox-1`（16 条 / 14 可见，`click(role, name)` + 采集面 3 条）。
> 面随样本落在 P2 顶层 `tool_surface`、P3/T 的 `meta.tool_surface`。
>
> **同一个面也决定元素的键名（2026-10-20 P4，方案 04 §4.8）**：`element` 的
> **槽位统一**（`role` / `name` 是槽位名，指「元素的种类 / 元素的文字」），
> **值域不统一**——`obscura-1` 面填 HTML 标签名（`html_tag`：`a` / `input`），
> `camoufox-1` 面填 ARIA role（`aria_role`：`link` / `textbox`）。
> 落盘与进 prompt 时**按面投影**：`obscura-1` 写 `{tag,label}`（与存量 P2 样本
> 逐字节同形）、`camoufox-1` 写 `{role,name}`，**值一律不翻译**（`input` 永不变成
> `textbox`）。原语（`ELEMENT_KEYS` / `element_role` / `element_name` /
> `element_json` / `vocabulary_of_archive_elements`）在
> [`common/elements.py`](../common/elements.py)——放 `common/` 是因为
> `rationale` / `assembler` / T 都有「不 import 上游」的 AST 禁令，而这是一段**纯格式**。
> 方言来源：驱动实现自己置 `Observation.element_vocabulary`，replay 从存档键反推；
> `_obs_json(obs)` **不接受调用方指定**（见[避坑指南 §1.9](02-避坑指南.md)）。
> 三表 `SURFACES` / `DIALECTS` / `ELEMENT_KEYS` 必须同键，由
> `tests/contract/test_element_dialect.py::Test一条轴` 封着；perceptor 的候选词表
> 按面收窄，**认不出的面直接抛**，不回落成并集（并集会掩盖「执行层换了」这件事）。

两条不可破的依赖约束：

1. `executor` 只依赖 `perception` 的**协议**（`perception/base.py`），不依赖任何实现——这是 W1 规则版与 W3 LLM 版能无痛替换的唯一保证。
2. `perception` **不得 import `executor`**。感知层的输入只有 `Observation` 值对象，不持页面句柄、不回调控制流。
3. `executor` **不得 import `llm`**（2026-10-17 A2 起，与第 1 条同一条边）。LLM 客户端与「text → dict」的解析器由 `cli` 在边界组装后**注入**（`rationale_writer` / `AgentBackend`），与 `rationale` 那条边同款姿势。有 AST 用例守着：运行时 import 里不得出现 `trajectory_pipeline.llm`。

## 控制流与四个判断点

`executor/orchestrator.py` 里有 `if`，但**没有一句在判断业务语义**——「这是不是播放站 / 有没有播放控件 / 是不是播放页」全在 `Perceptor` 里，控制流只负责按答案分流：

```text
环节 0    构造查询 + 检索          → 搜索页观察
环节 0.5  反爬拦截判定            ← 必须在取候选【之前】短路
环节 ①    取候选（代码层启发式）  → ▸ 判断点 ①.5 CLASSIFY_SEARCH_LINKS
          for 每个候选:
            可达性预检（代码）    → ▸ 判断点 ② IS_REACHABLE
            找播放控件            → ▸ 判断点 ③ FIND_PLAY_CONTROL（拿 ref 去点）
            进播放页 + 媒体探测    → ▸ 判断点 ④ PLAYER_OK
```

| # | 判断题 | 输入 | 输出 | 代码拿它做什么 | agent 链 |
|---|---|---|---|---|---|
| ①.5 | `CLASSIFY_SEARCH_LINKS` | 候选视图（分批，每批 ≤ 20） | 四分类清单 `video_site / aggregator / article_post / noise` + 理由 | 按发现路径取目标类分发：保留 / 记负分支 / `unresolved` | ✅ 问（搜索页不归 agent 管） |
| ② | `IS_REACHABLE` | 站点页观察 | 是否正常访问 | 跳过登录墙 / 地区限制 / 错误页 | ❌ 不问（gatekeeper 逐步拦截更早也更硬） |
| ③ | `FIND_PLAY_CONTROL` | 站点页观察 | `{has_control, ref, trailer_only}` | **拿 ref 去点** | ❌ 不问（agent 自己找，即交给它的那 8 处语义判断） |
| ④ | `PLAYER_OK` | 播放页观察 + **代码测的 media_count** | 是否正常播放、有无组件 | 成功 or 标记未验证 | ✅ 问，**且只问它** |

> ①.5 是 2026-10-16 方案 12 阶段 A1 起的搜索页一级判断（前身为 ① `SELECT_PLAY_SITES` 二元筛选）。① `SELECT_PLAY_SITES` **保留未删**：`site_search.py` 站内搜索结果页复用 + 金标重放。分发语义见[06-端到端流程 §五](06-端到端流程.md)。

`RulePerceptor` 对 ①.5 `CLASSIFY_SEARCH_LINKS` / ② `IS_REACHABLE` **只能返回 `None`**（链接分类与「是否登录墙」都不是规则能判的），所以走规则版时这两环全是 `unresolved`。这不是缺陷，是 fail-closed 的正常表现；`LLMPerceptor` 已接上，同一份控制流不需要改动一行。

### 两条执行链：scripted 与 agent（2026-10-17 方案 12 阶段 A2）

站内那一段有两种走法，**其余全部共用**（`enter_site` 进站 / `judge_player`
⑦）：

```text
scripted  ① ② ③ ③.5 ④ ⑤ ⑥ ⑦        七段固定序列（黄金基线 + A3 fallback）
agent     ① ② ──── agent_loop ───── ⑦   站内交给模型
          └ 共用 ┘                    └ 共用 ┘
```

| 判断点 | scripted 链 | agent 链 |
|---|---|---|
| ② `IS_REACHABLE` | ✅ 问 | ❌ 不问（页面级「能不能看」交给 gatekeeper 逐步拦截，更早也更硬） |
| ③ `FIND_PLAY_CONTROL` | ✅ 问 | ❌ 不问（agent 自己看着页面找，**这就是交给它的那 8 处语义判断**） |
| ④ `PLAYER_OK` | ✅ 问 | ✅ 问，**且只问它** |

**中间页单元（B/C 路径，2026-10-17 A2b）同理，两条链共用进站段与外链
校验段**：

```text
visit_aggregator        ① ⑤ IS_AGGREGATOR ⑥ SELECT_SITE_ENTRIES  外链校验
visit_aggregator_agent  ① ──────── [agent 任务③] ────────  外链校验
visit_article           ① ⑥C SELECT_REFERRAL_LINKS        外链校验
visit_article_agent     ① ──────── [agent 任务④] ────────  外链校验
                        └ 共用 ┘                            └ 共用 ┘
```

| 判断点 | scripted 链 | agent 链 |
|---|---|---|
| ⑤ `IS_AGGREGATOR` | ✅ 问 | ❌ 不问 |
| ⑥ `SELECT_SITE_ENTRIES` | ✅ 问 | ❌ 不问 |
| ⑥C `SELECT_REFERRAL_LINKS` | ✅ 问 | ❌ 不问 |

三类的差异只是**终局的产出形态**（`play` = 到达一个位置；`entries` /
`referral` = 报出一串链接），动作契约与流水线完全同一份
（`TASK_KINDS` 三值，见 [`agent_loop`](../executor/agent_loop.py)）。

ⓘ 三支负分支 `not_aggregator` / `aggregator_no_entries` /
`article_no_links` **在 agent 模式下没有产地**——它们的前提是「判断题判了
False」这个真结论，而那三道题一道都不跑，agent 说「没找到」一律落
`unresolved`。三支名字仍留在 22 支封闭集里（scripted 独占产出）。
**A3 的 A/B 报表要按它解读：agent 批的负样本变少不是质量变好，是产地变
少了。**

三条纪律：

- **agent 永不直接产分支**——出口是 `AgentOutcome` 三形态，分支由
  `agent_loop._FALLCLOSED_BRANCH` 查表折算，落进的还是这 22 支封闭集；
- **一个候选一种模式，候选内不 fallback**（混合轨迹不可归因）；批次级
  fallback 由 A/B 双跑本身承担；
- **模式是批次级属性**，记在 `RunRecord.executor_mode`。分派恰好两处
  （`_visit_guarded` 站点链 / `_intermediate_visit` 中间页链），且
  `test_executor_mode` 用 AST 钉住了**位置**而不只是数量——第三个出现的
  地方几乎一定是逐候选判断，那会让「这条轨迹是谁产的」变成逐条才能
  回答的问题。

> ⚠️ 「LLM 是传感器不是驾驶员」这句**在 A2 之后就已经不成立了**——
> A1/A2/A2b 把站内导航整段交给 agent 之后，探索权就不在感知层了。
> 当前口径见本文开头「分界」一段。

**判断点全部有调用方**：搜索页一级问 ①.5 `CLASSIFY_SEARCH_LINKS`，旧 ① 的 True/False/None 三分语义收敛为四分类的分发结果（目标类为空且逐条点名记负 = 旧 False 中断的同一份账面），整批没作答 = 旧 None 的启发式全跑。① `SELECT_PLAY_SITES` **保留未删**（站内搜索结果页复用 + 金标重放），不再进搜索页主链。

### 搜索结果的输入修复（bing）

`browser_links` 对 bing 结果页给的是**面包屑**而非标题（实测 32 条没有一条写着片名，片名在 `body_text` 里但与 URL 无对应关系）——分类判据之首就是结果标题，**修输入（`RESULT_SELECTORS` + `browser_extract` 取 `li.b_algo h2 a` 的 title 与 href 作为平行数组写回 `search_obs.links[].text`）仍活跃在环节 ①**。

三条跟着它踩出来、现在仍然生效的约束：

- **baidu 的 `browser_links` 本来就带片名**，只有 bing 不带。别推广成「所有引擎的 links 都是面包屑」。
- **「带片名」还不够，「送得进模型」才算**（[§5.20](02-避坑指南.md)）。baidu 是导航栏排在结果之前：预检扫全量数到 3 条命中就放行，而渲染只送前 20 条——那 20 条全是导航。**预检与渲染必须同源**（`_ordered_links()` 前置命中项，两处走同一个函数再截同一个 `LLM_LINKS`）。
- **写回 `links[].text` 时只按原始 href 查会一条都命不中**：`browser_extract` 给的 `urls[]` 是**解包后**的 URL，而百度结果页的 `links[].href` 是 `/link?url=` **包裹形态**。两处（写回观察、取候选 text）共用 `search_step.title_for()`——**口径分叉时失败的是其中一处而另一处照常工作，零报错**。

`_title_link_sufficiency` 预检现在只作用于 ① `SELECT_PLAY_SITES` 的**站内搜索结果页复用**（`site_search.py`）；搜索页一级的 ①.5 是**类型判定**（这条链接是什么站）而非片名↔URL 对应判定，预检只查候选视图链接非空，该预检不适用。

| ② | `login_wall_or_blocked` | 登录墙 / 地区限制 / 错误页（**deprecated**：历史合并态，新代码不再产出，旧存档不回填） | ✅ |
| ② | `login_required` | 登录后可免费看；agent 无登录态 → 不通过（合并态的细分） | ✅ |
| ② | `blocked` | 地区限制 / 验证码 / 反爬环境阻断（合并态的细分） | ✅ |
| ② | `broken` | 内容损坏（404 / 媒体不可解码 / duration=0），与 `unreachable_hard` **刻意分离**——到不了 与 到了但坏了不是一回事 | ❌ 代码判定 |
| ③ | `no_play_control` | 无剧集也无播放控件 | ✅ |
| ③ | `trailer_only` | 只有预告片，无正片资源 | ❌ 代码判定（词表） |

| ⑦ | `site_search_routed` | 站内搜索派发了子候选（路由去向，结论由子候选记） | ❌ 代码判定（**不入负样本池**） |

**每条分支都必须有对应样本入库**——负样本不是副产品，是强制产出。反过来，`unresolved` / `trailer_suspect` / `player_unverified` / `site_search_routed` **不是负样本**：把它们混进负样本池会污染它，「这里真的看不了」这条训练信号就此失真。

**三支「没判出来」成因不同，刻意不合并**（[避坑指南 §5.17](02-避坑指南.md)，rubric v1.1 的对照）。`unresolved` 是「连播放页都没到，不确定能不能到」（代码能力不足）；`player_unverified` 是「控件点了、快照拿到了、播放页就在眼前，只是判不了组件能不能用」（页面证据不足）；`trailer_suspect` 是「词表判不准」（需语义判断）。合并之后复核队列就分不出「请补一条判据」与「请看一眼这个页面」这两种待办，而报表也指不出该修代码还是该修采集。

⚠️ **`player_unverified` 不回填历史存档**（并池是写入时的动作，不是读取时的推导）。批次边界之前 `unresolved` 高、之后 `player_unverified` 高，不记批次就会读成「fail-closed 修好了」。**批次元数据要人工记这条。**

**贴标签前核前置事实**（`branches.BRANCH_PRECONDITION`，[避坑指南 §5.14](02-避坑指南.md)）。分支名是**结论的标签**，而每条负分支的定义里都带一个前提：`component_unverified` 的前提是「**到了播放页**，且页面上没有可验证的播放组件」（2026-10-10 口径裁定，按决策树第四行）。映射只看「模型说了 False」，于是 2026-10-09 真实跑出一条 `component_unverified`——点击前后两次观察完全相同（390 字 / 37 元素 / `video=0`），说明点击没把页面带进播放页，而那个站有《功夫》也有播放按钮。**把可看的站写成看不了的**，这类样本进了池，人工也未必再看得出它是错的。前置事实不成立就降级为 `unresolved`，并把模型原话保留在证据里。⚠️ 守卫判据是「**点击前后是否同页**」（`branches._same_page`：url / 元素数 / 正文三个粗粒度特征），**不是** `video_tag_count`——真实视频站全是 iframe/JS 播放器，真播放页上 `video=0` 是常态，拿它当「不在播放页」的信号会把合法排除一起杀掉（旧守卫的毛病）。当前只有 `component_unverified` 一条需要核——**这张表要短**，长得跟分支表一样长就没人维护了。

**反爬拦截刻意不进这套分支体系**：拦截发生在**取候选之前**，根本没有 outcome 可记。它单开运行级字段 `RunRecord.search_blocked`——代价是 `report` 要多统计一次，换来的是「被拦」与「没素材」在报表上永远分得开。

### `subscription_wall`：付费墙为什么单独一支（2026-10-10 口径裁定）

用户裁定「**有播放页但要付费不算成功**」。但它也不是 `component_unverified`——
控件是有的，卡在付费。混进去就丢掉这个区别，而两者训练出来的东西完全不同：
一个学「识别付费墙并退出」，一个学「控件没渲染」。

- **分支 id 是 `subscription_wall`**（snake_case，与封闭集里其余分支一致——
  它是落进 P1、报表与契约的 key）；**人读标签是 `Subscription-based playback`**。
- **代码层词表判，不问模型**（口径一「确定性事实优先」）：
  [`rule_perceptor.classify_paywall`](../perception/rule_perceptor.py) 只收
  **完整短语**（「开通会员」「订阅后观看」「buy this episode」），
  **不收「免费观看」「在线观看」**——后者在导航栏里的频率远高于付费提示
  （实测百度页正文就有），收了会把大批正常站点判成付费墙。
- **两边一致才落这一支**：模型判 True 而词表命中时**不升级**——
  那多半是导航栏文案。两个信号不一致就按模型那个未定的结论记。
- **同页守卫适用**：「开通会员」出现在**站点页**上是导航文案，不是付费墙。
  所以它有前置事实（`BRANCH_PRECONDITION`），点击前后同页则降级 `unresolved`。

- **★ 前置事实核验（2026-10-21，H-16 修复①）**：这条分支的前提是
  「页面**明说**不给钱/不订阅就看不了正片」，而不是「页面上有会员字样」。
  核验用**门禁语境**判据（`rule_perceptor.paywall_evidence`）——
  两层：**L1 门禁命题**（短语本身就是完整命题，如「订阅后观看」）·
  **L2 CTA + 同句观看语境**（「您可以试看5分钟，点击开通会员」）。
  ⚠️ **裸 CTA 不成立**（「开通会员 享更多精彩」「续费 充值」——导航栏广告高频短语）。

- ⚠️ **「强信号旁路同页守卫」已于 2026-10-19 退役**（增量六十·方案 X 把同页守卫
  窄化为只覆盖 `component_unverified` ⇒ 旁路失去拦截对手；
  2026-10-21 H-16 修复① 删除 `branches._has_strong_paywall_signal`）。
  **强弱信号判据本身没死**——它是 `gatekeeper.is_paywall`（**拦截**口径）的判据，
  唯一所有者仍是 `rule_perceptor`：**强付费墙信号** =
  `≥1 strong + ≥1 weak` 或 `≥2 strong` 或 `≥1 strong + 价格`；
  强关键词集（`STRONG_PAYWALL_KEYWORDS`）：VIP / 订阅 / 续费 / 包月 / 包年 /
  专享 / 特惠；弱关键词集（`WEAK_PAYWALL_KEYWORDS`）：开通 / 会员。
  ⚠️ **两套判据不许互相顶替**：强弱信号答「这页**像**付费墙吗」（**拦页面**），
  门禁语境答「这页**是不是**付费墙」（**贴标签**）——
  人工复核判强弱组合是**营销**（实测池里 12 条 `subscription_wall` 没有一条站得住）。

- **L3 `not_found` 关键词必须两处同步**：L3 规则层
  `ACCESS_HINTS["not_found"]`（`infer_access_from_evidence` 用）与
  `L3_ACCESS_HINTS["not_found"]`（`decide_business_signal` 用）覆盖英文 / 5xx /
  nginx / 腾讯 error 页：`404 Not Found` / `Not Found` / `Internal Server Error` /
  `500 Internal` / `502 Bad Gateway` / `nginx` / `那条视频不见了`。
  **两处都补是设计要点**——`L2` 错误页与 `L3` 错误页必须同分支才能让
  L5 仲裁不出现 `L2=broken` / `L3=access_blocked` 的双源冲突。只覆盖中文短语时，
  英文 / 混合形态会落到 `ACCESS_BLOCKED` 而非 `broken`，与黄金集 `broken` 标签不一致。

> **P0–P6 全部落地**（2026-10-20 ~ 2026-10-22）。
>
> **owner 裁定原文**：「不计划再继续比对 obscura 与 camoufox，选定 camoufox
> 做默认浏览器调用主力，注意**反爬拦截与页面获取页面内容是主要，速度次要**，

> 换层门槛，而 owner 判的是「不做双跑了，直接换」）——**覆盖这件事本身
> 是 owner 的决定，本节只记录事实与后果**。
>
> **为什么这个方向有实测支撑**（三条读数，不是「camoufox 更好看」）：
>
> 1. **反爬**：真·反爬拦截率 B（camoufox）**9.09%** < A（obscura）**14.89%**，
>    配对子集同向。⚠️ 必须用「真·反爬」口径——合并口径（反爬 + 登录墙）
>    给出**相反**的结论（A 19.15% / B 34.09%）。
> 2. **页面内容**：obscura 在爱奇艺这类**客户端渲染**站上正文一个字都抽不出
>    （`body_len=0` + `degraded=['body_text']`，19 条），A 侧 60% 的站点
>    是「没测到」（H-14）。**抽不到正文的浏览器对「页面内容获取为主」的
>    项目没有价值**。
> 3. **速度不是目标**：本项目的目标是**减少被拦截 + 拿到页面内容**，
>    速度排在后面——为此接受 camoufox 的等待时间（真人鼠标轨迹回放）。
>
> **obscura 没被删掉**：它是存量 P1/P2 产物的方言（工具面 `obscura-1`

## 感知层（模块 3，可替换插件）

`perception/base.py` 定协议，`questions.py` 定判断题注册表，`rule_perceptor.py` 是规则版实现，`llm_perceptor.py` 是 LLM 版实现，`factory.py` 做注入与灰度。

输入是 DOM 预处理后的结构化观察（`Observation`），不是原始 HTML；输出必须是 schema。**七不变式由契约测试强制**（[`tests/contract/test_perception.py`](../tests/contract/test_perception.py)，`IMPLEMENTATIONS` 一行一个实现，两个实现跑同一套）：

| | 不变式 | 2026-10-20 起 |
|---|---|---|
| I1 | evidence 可溯源到 `Observation` | 保留 |
| I2 | `confidence ∈ [0,1]` | 保留 |
| I3 | 幂等——同一 `(question, obs)` 重复调用返回相同答案 | 🔴 **退役**（感知层退位后不在热路径，幂等无对象） |
| I4 | fail-closed——能力不可用返 `None`，**绝不猜** | 保留，**但收口到执行器**（agent 自报「不确定」≠ fail-closed） |
| I5 | 无副作用——只读 `obs`，不触网、不持页面句柄 | 🟡 **改写**：「不持页面句柄」移交 agent runtime；「不触网」留在感知层 |
| I6 | decision 型题 payload 完整，`ref` 可溯源到 `obs.interactive_elements` | 🔴 **退役**（ref 机制退场，替代物是执行层的 `count()` 预判 + strict mode） |
| I7 | `answer=True` 时 payload 不得为空 | 保留 |

> **I3 / I6 的退役是 [设计方案 15](设计方案/15-执行器与agent-runtime重新定义.md) 唯一真正破坏不变式的地方**（owner 明确授权）。保留的五条一条不动——它们是产物可审计的地基。**契约测试要跟着改口径**（`tests/contract/test_perception.py`），否则它会盯着一批不再存在的保证。

### `LLMPerceptor` 是混合体，不是纯 LLM

两条可检查的落法，缺一条就会把采集故障写成业务结论——**这两条与「谁在探索」无关**，感知层退位后依然要守：

1. **确定性事实优先，LLM 只做语义补位。** `<video>` 标签存在性是代码事实（`video_tag_count`），**不问模型**；预告片词表是**本项目的业务规则**，模型不知道也不该猜。
2. **采集充分性在代码层预检，在问模型之前**（`_sufficiency`）。这条是实测逼出来的，也是最贵的一条：**模型不会替你 fail-closed。** 实测 iqiyi 播放页 `video=1` 被判「否」，模型的分析是「`body_text` 为空、`interactive_elements` 为空，说明未渲染或采集失败」——它把**采集失败**讲成了一条通顺的错结论。规则版早就防住这条（哨兵返回分不清「没渲染完」与「确实为空」），换成 LLM 就丢了那层保护，而它恰恰是最需要的地方。

第 2 条的**最窄形态**（`FIND_PLAY_CONTROL` 撞上 `interactive_elements == []`）现在两版口径一致，并由 `test_perception.py::TestZeroElementsBothImplementations` 锁住：实测 m.ixigua.com/video/6582085495839261192 正文 100 字符、元素 0 个，模型仍判了 False。**别拿「有正文」当「渲染完了」的证据**——正文与元素来自两个独立的 tool，一个有值不代表另一个有值，而只看着正文那个就会把「没渲染完」写成「这个站没控件」。

另外：**不采信模型自报的 confidence**（[`llm/__init__.py`](../llm/__init__.py) 记着「自报普遍虚高」）。给的是未校准先验 `CONFIDENCE_JUDGED = 0.8`，evidence 里写明「非模型自报」，拿到标注集后按题校准。

**灰度只在构造期**（`factory.build_perceptor`），不做运行期切换：运行期切换会让 `Decision.source` 分不清「LLM 判的」与「LLM 挂了所以规则版顶上来的」，而后者不是 fail-closed，是拿不确定的输入驱动确定的输出。要对比两条链就跑两批——`RunRecord.perceptor` 字段已经把两者分开。

配置：`TRAJECTORY_PERCEPTOR=rule|llm|auto`（默认 `auto`，配了 LLM 后端就用 LLM 版，否则退回规则版**且不报错**，让无后端的机器也能跑通；`run --perceptor` 可临时覆盖）。显式 `llm` 而未配置则**报错**——静默退回会让人以为跑的是 LLM 版。后端配置见 [`llm/__init__.py`](../llm/__init__.py)。

## 模块 4 · rationale 与一致性闸门（`rationale/`）

[`rationale/lexicon.py`](../rationale/lexicon.py) 实体抽取 + 套话 + 后见之明 + 语气标记，[`rationale/gates.py`](../rationale/gates.py) 三查，[`rationale/writer.py`](../rationale/writer.py) LLM 生成。**闸门是纯代码、零 LLM 调用**——所以「实体核查 100% 覆盖」这条承诺靠的是代码而不是模型。

### 接线

`writer → P1 → 闸门 → P2/P3` 整条链已通：

```text
orchestrator._write_rationales()   ← CLI 注入的 rationale_writer（执行期，逐步）
        ↓ actions.ActionStep.rationale
   P1  steps[i].rationale          {status, rationale:{text,conclusion}, reason, degraded}
        ↓ schema.align_rationales() + schema.gate_of()（组装期，逐条跑 gates.gate）
   P2  six.rationales[] + gate      ← 按 step_index 与 actions 对齐
        ↓ views._rationale_text()
   P3  messages / openai 的逐步思考段
```

**生成在 `orchestrator` 而不在 `visit_site`**：动作流是记录、rationale 是补记，
两者在一次访问结束时才都完整；放进 `visit_site` 会让执行层直接依赖 LLM 模块。

**生成在执行期、核查在组装期**——这是设计决定不是漏掉的。D2 要「边写边生成」
（否则 rationale 是事后编的），而**时序核查需要全序列**才能判「引用了后续步
才出现的实体」，执行期那一刻后续步还不存在。所以「没跑」绝不能渲染成「通过」。

**先建闸门而不是 writer**：writer 每步都要调 LLM，在闸门缺席时生成的 rationale **没人能判**。先有判据再有生成，顺序反了的话第一步产出的就是无法评估的批次。

三条口径：

- **不用中文分词。** 切词工具换一版就换一套结果，而闸门要跨批次可比。实体只抽 **URL 与成对引号**两类高置信形态；单字不抽（「有」「的」几乎不可能出现在观察里，判它「不在观察里」是纯假阳性）。
- **任务给的实体是豁免域。** rationale 提到片名而观察里没有它，**不是幻觉**——片名来自任务。把任务给的词当「模型引入的实体」，会把每一条提到片名的 rationale 都判成幻觉。
- **观察不充分时不判幻觉，只记「查不了」。** rubric D-9 边界规则原文。这是 §5.5 那条最贵教训的落点（模型把**采集失败**讲成了通顺的错结论）。三处守它：本步及前置步都不完整则不判；一份完整即可定案；后续步的**不完整**观察里出现过该实体则不判（它当时**可能**就在而只是没采到）。

**软信号与硬发现分开**：「通篇套话」「措辞上的后见之明」是 `soft`（只记录不让闸门 fail）——一条只有一步、且那一步什么都没发生的样本，thinking 里全是「无法确认」完全正常。硬判它 fail 会把一批好样本判死。

### writer 的边界在**发出去之前**

一半的职责发生在返回值看不见的地方，所以断言必须回到「payload 里到底有什么」：

- **采集降级必须写进提示词。** 闸门是**事后**判，而模型是**当场**编故事（§5.5 那条实测就发生在这里）。所以「这份观察不完整：<原因>」直接进 user 提示词——**闸门是第二道防线，不是第一道**。
- **不把 `ref` 句柄喂给模型。** 它是 obscura 的会话内句柄，换个 session 就失效，进训练数据等于让模型学一个随机数，且样本永远不可回放。
- **提示词不提 obscura / MCP / ref / 控制流。** 模型要学的是判断，不是怎么驱动某个浏览器。

> ⚠️ **D12 之后这条有个对称的反面，别「顺手统一」**：感知层提示词**不点名任何浏览器**，
> 但**训练侧的工具声明要点名 camoufox / `get_by_role`**（[设计方案 04 §5.1](设计方案/04-camoufox执行层替换方案.md)）。
> 两者不是一条规则的两半，是**两件不同的事**：
> 感知层是**裁判**（看观察写结论，不该知道怎么驱动浏览器）；
> 训练侧的动作模型是**探索者**（必须会用执行层的 API，否则轨迹脱离本项目就不成立）。

**三个状态而不是两个**：`written` / `unavailable` / `empty`。「键在但值是空串」是**数据事实**（模型这一轮确实什么都没说），「键根本没有」是**流水线形状漂移**——合成一个空串就分不出这两者，而 `empty` 不该进负样本池、`unavailable` 会。

**「剥完 `<think>` 是空串」判不可用，不是「模型没说话」**：推理模型被 `max_tokens` 截断时留下**未闭合**的 `<think>`，`strip_think` 会把它连同后面全删，于是拿到空串——而空串在下游与「模型这轮没说话」完全同形。处置是**显式记原因**，因为观测到什么推出空串本身就是一条要修的信号。

> ⚠️ **哪几个后端返内联 `<think>` 是实测的，不能假定**：同一端点、同一提示词下 `MiniMax-M3` / `M2.7` **返**（2286/2320 字符），而 `M3.1-Flash-Preview` / `deepseek-v4.1-flash` / `qwen3.8-*` / `GLM-5.3-Flash` **不返**（209–490）。**同产品族里两种行为都有**，换一次配置就可能换到一个会返的。
>
> 真正踩到的第三种漂移是**字符串值里写未转义的 ASCII 双引号**——**大括号配平**，看起来完全正常，只有 `json.loads` 知道它坏了。共享解析层做**报错位置驱动**的转义修复（`schema_parse.extract_json_reporting`），**修可以、账要记**：修复记录随结果返回，由调用方写进 `degraded_from`。

- 输入 `VLMReviewInput`：`signal` (MediaSignal) + `body_excerpt` + `snapshot_excerpt` + `page_quotes` + `final_url`。
- 输出 `VLMReviewResult`：6 字段对齐设计方案 §4.4（`label` / `paywall_type` / `evidence` / `price` / `currency` / `confidence`）+ `source` / `note` / `screenshots`。`screenshots` 默认空元组——obscura MCP 37 个 tool 里**没有**截图原语，等 `browser_take_screenshot` 暴露再填，**契约不变**。
- `source` 字段区分实现：`heuristic` / `gpt4o_text` / `claude_text` / `multim_fallback`。

**实现类三纪律**——任何新实现都必须守住：

1. **协议先行**：换实现类不改 Protocol，加字段先开 §3.5 提案；`__init__` 形参必须能在调用点无感替换。
2. **fail-soft + 降级显式标记**：`review()` 不抛异常；任何失败（无 key / API 错 / 响应坏 / label 非法）走 `HeuristicVLMReviewer` 兜底并打 `source="multim_fallback"` + `note="multim_fallback:<reason>"`。降级必须**显式**，让 L5 仲裁 / 人工一眼看出「这本是 multim 通道、结果走了 heuristic」。
3. **不重叠 L3 rule**：内部**不读** L3 词典；与 L3 是 L5 仲裁双源对账，不是单源投票。系统 prompt 与配置层都要明令此条。

**调用点**——[`cli.py::_run_l4_review_async`](../executor/cli.py) 接受 `reviewer_name: str = "heuristic"` 关键字参数；[`_mediabrowse_with_driver`](../executor/cli.py) 通过 `getattr(args, "reviewer", "heuristic")` 透传。`build_reviewer(name)` 工厂返回实例，非合法值 `ValueError("--reviewer")`。

**为什么不是单源实现**——`MultimVLMReviewer` 不直接调 GPT/Claude 然后归档，让 `HeuristicVLMReviewer` 兜底——是因为：(1) 多源仲裁才有「加权」可言，单源直落是**复述**；(2) 兜底使黄金集冻结 manifest 的双源对账不会因为换通道而漂移。

**截图字段预留**——`VLMReviewResult.screenshots: tuple[str, ...] = ()` 是**契约公开状态**，不是实现 bug。`MultimVLMReviewer._SYSTEM_PROMPT` 当前只接文本输入（DOM / page_quotes / snapshot_excerpt / MediaSignal 6 字段），不消费 screenshots。等执行层暴露截图原语时，prompt 加 image 字段，screenshots 填路径——实现层不动，契约零修改。

**测试守门**——三层：`tests/unit/test_vlm_reviewer.py::TestVLMReviewerProtocol`（协议各实现一致性）+ `tests/unit/test_multim_vlm.py`（27 单元）+ `tests/unit/test_cmd_mediabrowse.py::TestMultimVLMCLIWiring`（CLI 接线）。任何协议变更先把 `test_vlm_reviewer_protocol_runtime_checkable` + `test_multim_vlm_reviewer_also_satisfies_protocol` 守住。

**已知后续路径**：

1. 等 OpenAI / Anthropic key 配齐时跑真视觉 KPI 复跑，与启发式的命中分布对比；
2. 执行层暴露截图原语后启用图像输入，把 `_SYSTEM_PROMPT` 从文本切到 image+text 双模；
3. L4/L5 在 `_mediabrowse_with_driver` 内串接完成，但 **L6 人工触发器未接**——当前人工复核走 `cli review-queue` 手动拉，不是 `proberun` 自动派发。

## 模块 5 · 组装（`assembler/`）

[`assembler/schema.py`](../assembler/schema.py) 定义六件套值对象并**按文件格式**读 P1 切成样本；[`assembler/observation_view.py`](../assembler/observation_view.py) 渲染训练态观察（纯代码，不用 LLM）；[`builder.py`](../assembler/builder.py) 落 P2 + [`views.py`](../assembler/views.py) 出 P3 三视图（`cli build` 命令接线）。

口径（逐条读，不按「几条」核对——数字会漂，条目不会）：

- **一条 = 一个决策单元**（搜索阶段一条 / 每个站点一条）。设计方案 §3.5 早期同时写了「各自独立成条」与「前几步走摘要」，两者矛盾；按决策单元切唯一确定，且不把「选哪个站」与「这个站行不行」压进同一次预测。
- **读 P1 不 import `executor`**——与 `executor/plan.py` 不 import taskgen 同一条纪律。理由是 **P1 贵、P2 便宜**：重建一批 P2 必须独立于 executor 的当前版本，否则老 P1 切不出样本。由 `tests/contract/test_p2_contract.py::TestNoExecutorImport` 用 AST 强制。
- **P3 的输入是 P2 的 JSON，不是 `Sample` 对象**——同款纪律的延伸：交接面是格式。于是「只改视图口径重渲 P3」不需要重读 P1，也不需要 executor 的任何东西。
- **训练动作空间在 assembler 侧冻结**，既不从 P1 反推（反推会让每条样本各带各的动作空间），也不从 `executor.actions.TOOLS` import。漂移由契约测试 AST 读那个字面量来查。
- **缺件必须看得见**：闸门三值 `passed` / `failed` / **`not_run`**——**一条 `written` 都没有的样本一律 `not_run`**（没跑 ≠ 跑过）；「没跑」渲染成「通过」会让批次上线时看起来像过了闸。老存档缺的键（`steps` / `user_prompt` / 全文正文）逐条记进 `degraded_from`，不与新样本混用。
- **可见性由 `ToolSpec.visible_to_model()` 唯一决定**。`new_tab` 是执行器自己的会话隔离动作，**留在动作流里**（删掉就无法回放）但**不进工具声明**（模型永远不该输出它）。`views.py` 不重新判断这条，只复现同一个规则。
- **声明按「面」取**（2026-10-20 方案 15 §5.5）：P2 顶层 `tool_surface` 定面，
  渲染期按面查 `toolcatalog`。同名工具在两个面里参数不同
  （`click` 是 `tag`/`label` 还是 `role`/`name`）——**拿错面 = 声明与真实调用
  对不上**，而报告上看不出异常。面由 P1 的 `driver` 一对一折算，不手填。
- **`element` 的键名是方言的投影**（2026-10-20 P4，方案 04 §4.8）：`render()` 与
  `element_line()` 按存档键反推出的词表出键——`obscura-1` 面是 `{tag,label}` 与
  `  - <button> 播放`，`camoufox-1` 面是 `{role,name}` 与
  `  - [button] 播放`（**方括号不是排版**：`<link>` 会被读成 HTML 标签）。
  两批样本**标记为不同口径、不混池**：`meta.tool_surface` 在，`element` 的键形状也在。

### P3 三视图

| 视图 | 形态 | 给谁 | 是主形态吗 |
|---|---|---|---|
| `openai` | function-calling：assistant 带 `tool_calls`，观察是 `role: "tool"` + `tool_call_id` | OpenAI 系训练框架 / 任何能识别 `tool_calls` 的训练栈 | ✅ **训练工具调用智能体的主形态** |
| `messages` | 通用 `{role, content}`，动作降级成纯文本 `[动作] goto(url=…)`，**观察降级成 `role: "user"`** | 不认识 `tool_calls` 的老聊天框架 | ⚠️ **降级形态，不应作为智能体轨迹主形态**——见下 |
| `meta` | 来源 / 可用性（`gate` / `degraded_from` / `rationale_missing`）/ 结论 / 可回放性自查 | 训练代码不看它，人工复核与批次筛选看它 | — |

> ⚠️ **`messages.json` 是降级形态，不是合规的智能体轨迹**。
> [`assembler/views.py` 模块 docstring 第 1 条](../assembler/views.py)
> 已经把这件事写明——`tool_call_id` 让模型学到「这条观察是对**那个**动作
> 的回应」，退成 `role: "user"` 把关联抹平了，而关联正是 agent 轨迹的
> 训练信号。**新读者容易把它误读为项目主形态**（因为它是最朴素的
> `{role, content}` 形态），实际训练送模型请用 `openai.json`。
>
> 合规轨迹的样子：整条样本里**只有第一条** `role: "user"` 是真正的
> 用户原话；**后续每一条**观察都是 `role: "tool"`，靠 `tool_call_id`
> 与前一步 `tool_calls[].id` 关联。智能体依据「先前观察 + 自己思考
> + 系统提示」**自主**做下一步决策，**不依赖用户原话重复出现**——
> 每一步的 `assistant` 消息由 `rationales[i].text`（思考段） +
> `tool_calls[i]`（动作）构成。

`tool_call_id` 由 step 序号派生（`call_0`…），不取自 P1 的任何字段——**能从数据算出来的不另找来源**。

## 模块 6 · 评估（`evaluation/`）

[`evaluation/scorers/code_scorer.py`](../evaluation/scorers/code_scorer.py) 实现 **D-2 观察-动作一致性**，
[`d5_scorer.py`](../evaluation/scorers/d5_scorer.py) 实现 **D-5 记录/排除决策正确性（★ 一票否决）**，
[`d6_scorer.py`](../evaluation/scorers/d6_scorer.py) 实现 **D-6 记录字段完整性**，
[`d4_scorer.py`](../evaluation/scorers/d4_scorer.py) 实现 **D-4 播放组件验证正确性**，均按 rubric v1.1（[`在线视频场景rubric.md`](设计方案/在线视频场景rubric.md)）。

**每个维度都要先问「它管辖哪些结论」**。D-4 不能把「应判未验证」套在**所有**分支上——判断点的结论说的是「这个站能不能到」，与「播放组件在不在」无关。管辖范围写死在 `GOVERNING_QUESTION`。

**判据要从 rubric 的语义落到可机械检测的形态**。D-4 的边界规则写「组件懒加载需触发 → 正确行为是标记待验证」，而存档里没有「懒加载」这个字段；它的可机械形态是**点击前后是不是同一个页面**（url / 元素数 / 正文三个粗粒度特征）。⚠️ 不能拿 `truncated` / `degraded` 当「采集不充分」，也不能拿 `video_tag_count` 当「不在播放页」——前者与采集无关，后者来自**独立的 `browser_count` 调用**、不受 `max_chars` 影响，而真实视频站全是 iframe/JS 播放器，真播放页上 `video=0` 是常态。判据错一次就误判一整批。

**D-4 补的是 `check-archives` 漏掉的一类**：门禁查「判成功但 `video_tag_count=0`」，而真实视频站**有 iframe**，从门禁判据下滑过去了；D-4 查的是「点击前后同一页却给了确定结论」，两条判据不重合。

**三条都必须从单一真值源推导，别手写表**（避坑指南 §1.3b 的又一次兑现）：D-5 的
「判断点 → 分支」映射从 [`perception/questions.py`](../perception/questions.py) 的
`REGISTRY` 推导。手写字面量一定会漏 `unresolved`——它是 `record_from` 的**通用
fail-closed 出口**，任何判断点判 `None` 都走它。

**「缺字段」与「字段为空」必须分得开**（避坑指南 §2.3）。`OutcomeRef` 的
`p1_missing_fields` 逐条记「P1 里压根没有这个键」——因为 `to_json` 之后两者同形
（都渲染成 `""`），不记就分不出「老存档没这个字段」与「采集时确实没落」，
而后者判缺失、前者只该判不可判定。

**`skipped` 不阻断出分**：那是**已知的、不依赖数据**的边界（D-6 的验证证据
原文在 P1，由 `check-archives` 的 `evidence_empty` 把关），不是「这一条查不了」。
把它算进不可判定，于是任何样本都不可能判 5 分。

**rubric 内部口径冲突要显式暴露，不替它选边**。`component_unverified` 曾在
决策树里是「播放页**无** video/组件」、在 `BRANCH_PRECONDITION` 里是
「**有** video 标签但播放器未正常加载」，两者互斥而实测数据站在两边都有样本。
D-4 一度判 `undetermined` 并把冲突写进 `reasons`——猜一个方向就是系统性误判
一整批。**已人工裁定（按决策树侧 A）**：分支语义定为「到了播放页，没有可验证的
播放组件」，`BRANCH_PRECONDITION` 的守卫判据同步从 `video_tag_count` 换成
「点击前后是否同页」。裁定前的旧批次**不回填**（并池是写入时的动作）。

**三态而非两态**：`score=None` 表示**不可判定**，与 5 分严格分开。两个方向都不能含糊——「没查」渲染成「查过了」等于凭空白发通行证；「不可判定」并进「引用不存在」等于把采集器的取舍记成轨迹的缺陷。不可判定的入口：元素/链接裁剪、采集降级、正文截断、观察三项全空、`target=None`、P2 缺 `question`/`site_url` 字段（老批次）。

**`goto` 的 URL 刻意不校验**：它要核的「这个 URL 在搜索页链接里吗」需要**另一条样本**的观察（决策单元切分的结果）。在本样本内查它必然查不到，于是每条 `goto` 都记一条不存在、全批恒 1 分。恒定分数没有区分力——与 D-1 被划到批次级 B-1 同源。

**D-3 已建但默认关**：`score_d3` 判的是「与黄金集类别一致」，走 LLM 裁判层
（`LLM_SCORERS`，需显式 `--include-llm-judge`）——默认关的理由有三条：CLAUDE.md
红线禁止生产链上投票/集成、每条样本 1–3s 的延迟与成本、以及**跑 CLI 没有黄金集
对照等于裸跑出 1–5 分，对账无门**。

### 模块 6 的入口：[`evaluation/cli.py`](../evaluation/cli.py)

四个评分器此前**只被各自的测试 import**，在真实批次上一次都没跑过——

**它刻意不挂进 `executor.cli`**，而是单独一个 `python -m` 入口：挂进去等于让

evaluation.cli --→ assembler.schema   （吃 Sample 对象，与 builder 落 P2 同一路径）
executor       ┈┈→ evaluation          （不知道它的存在——这是纪律，不是巧合）

遍历，等于把刚人工确认的正样本全滤掉。

为空」**——按 basis 字符串判断会让警告在混合档（新数据落盘那一刻）自动消失，
那批样本仍在用推断分档却没人被提醒。

| `gdr/` | C1→C2 精修。Session/Message/Block 三级模型、13 种缺陷标签（规则 + LLM 三票投票）、obs_denoiser/thought_refactor/tool_fixer、L1/L2/L3 三级验证。⚠️ 双导入姿势（顶层风格 + `gdr.` 前缀）导致同源码产生两套类对象，跨边界**不要用 `isinstance` 认类型** |
| `etl/` | C2→C3 格式转换。`qwenformat/`（trajectory 重放 `load.parse_trajectory` + transform + chat_template）、`parsers/`（C2 入口 `load_refined_session`）、`writers/`（C3 入口 `render_to_4_views`）、`pawsession/`（平行旧路，**不在 orchestration 主链路**） |
| `label_studio/` | **流水线终点**，单向推送不回流。`scorecard.v1` 分层评分卡（L0–L5，每维带 `source` 与依据）；R11 凭据扫描 fail-closed 拒推；`push_index.py` 本地台账（LS 1.23 无原生去重，删台账等于每次推重复样本）。入口 `python -m label_studio` |
