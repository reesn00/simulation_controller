# 12 · 组装层不清理「本轮未产出」的陈旧派生产物

> **一句话**：P1 → P2 → P3 → T 的组装层**只写不删** ⇒ 任何让一份存档「本轮不产出样本」的条件
> （判分不可信 · `--rationale-era` 筛掉 · 切不出样本）发生时，**它上一轮留下的派生产物仍留在交付目录里**
> ⇒ **被剔除的数据照样能被下游读到**（最严重的一档：**P3 视图 ⇒ 进训练语料**）。
>
> ⚠️ **仓库已经有「把不该在交付目录里的东西挪出去」的机制**（`pool.migrate_*`），
> **但它的判据只认「工具面」**（旧面存量），**不认「本轮名单之外」** ⇒ 新判据剔除出来的东西**没有归处**。
>
> **状态**：🟢 **已实施**（2026-11-12 · 分支 `handle_leftover`）——**方案 A + C 的体检部分**已落地，
> 端到端读数见 [§十 · 处置结果](#十--处置结果2026-11-12--分支-handle_leftover)。
> ⚠️ **台账 §H-33 的现状断言待补**（并发会话仍在改同一份台账 ⇒ 按约定等它提交后 rebase 再折回）。
> **台账**：[§H-33](计划进展/10-TODO台账.md)（唯一权威的现状断言）
> **首次撞到**：2026-11-11 全量合成（`build --overwrite` 重建 247 份存档时）

## 一 · 现象

### 1.1 人能看到的形态

跑完一轮 `cli build --overwrite` + `cli task-view --all --overwrite` 之后：

- **交付目录里的条数，比这一轮实际产出的多**；
- 多出来的那些**文件是旧的**（内容是上一轮的渲染），
  但**它们看起来和正常产物一模一样**（同名、同目录、同 schema）；
- ⚠️ **最要紧的是：它们不会被「这轮没产出」这件事提示到** ——
  `build` 打印「切出 180 条 / 写出 114 条」，**不提目录里还躺着多少别的**；
  `task-view` 打印「写出 167 份」，**也不提目录里多出来的那 53 份**。

⇒ **读的人只能靠「数一遍目录」才发现**，而那 53 份在报告上**完全隐形**。

### 1.2 本轮实测读数（2026-11-11 · 全量 247 份存档）

| 时刻 | `samples/` | `views/` | `task_views/` | 备注 |
|---|---|---|---|---|
| ① 重建前（上一轮遗留） | 90 | 261 | 87 | 旧口径产物 |
| ② `build --overwrite`（无剔除） | **114** | 342 | — | 切出 180 / 写出 114（**66 旧面未渲染**） |
| ③ `task-view --all --overwrite` | — | — | **167** | 写出 167 = **107 正常 + 60 空壳/其它** |
| ④ 补键剔除 7 份后 `build --overwrite` | **114**（本轮只写 **107**） | **342**（渲染了 **114** 条） | — | ⚠️ **7 份陈旧样本仍在** ⇒ P3 连它们一起渲了 |
| ⑤ `task-view --all --overwrite`（补键后） | — | — | **160**（写出 160） | ⚠️ 比 P2 的 107 **多 53** |
| ⑥ 手工归位后 | **107** | **321** | **107** | `P2 == P3/3 == T` 口径归一 |

⚠️ **④ 是要害**：判分不可信的那 7 份**已经被判「不出样本」**了，
但它们的 **P2 样本文件还在** ⇒ 于是 **`views/` 也把它们渲了** ⇒
**剔除在 P2 层生效、在 P3 层失效**。

### 1.3 复现（最小步骤）

```powershell
# ① 造一个「会被剔除」的存档：给它补上判分不可信标记
#    （H-31 机制；见 §H-31 补记）
#    ⇒ 在其 P1 JSON 顶层加一行 "judgement_trustworthy": false,
uv run python -m trajectory_pipeline.executor.cli build --overwrite
# ② 观察：build 打印「切出 N 条 / 写出 M 条」，且「⚠️ 判分不可信 1 份存档」
#    ⇒ 但 samples/<那个 sample_id>.json **仍然在目录里**（内容是上一轮的）
ls trajectory_pipeline/output/pipeline/samples/<那个 sample_id>.json

# ③ 观察：P3 也把它渲了（views/ 多出 3 份）
ls trajectory_pipeline/output/pipeline/views/<那个 sample_id>_*.json

# ④ 危害落地：下游按 sample_id 直读目录，不问 P2 在不在
#    ⇒ 训练侧读_views / golden_ls 的 ⑩ SFT 块照样读得到它
```

**更隐蔽的一条**（不需手工改档，命令就能触发）：

```powershell
# --rationale-era pre_action  ⇒ post_hoc 样本「本轮不产出」
#   ⇒ 它的旧 P2/P3/T 文件**原地留着** ⇒ 混批进交付
uv run python -m trajectory_pipeline.executor.cli build --overwrite --rationale-era pre_action
```

## 二 · 根因（代码事实）

### 2.1 写侧：三条组装路径都是「只写不删」

| 路径 | 位置 | 行为 |
|---|---|---|
| P1 → P2 | [`assembler/builder.py::build_all`](../assembler/builder.py#L463) | 遍历存档 → **写**本轮产出的样本；**不删**任何旧文件 |
| P2 → P3 | [`assembler/views.py::build_views_from_dir`](../assembler/views.py#L879) | 遍历 `samples/` → **写**三份视图；**不删** |
| P1 → T | [`assembler/task_view.py::build_all_task_views`](../assembler/task_view.py#L1340) | 遍历 P1 → **写** T 视图；**不删** |

⚠️ 三者**都没有「拿本轮名单和目录求差」这一步** ⇒
**目录里凡是本轮没写到的文件，一律原样留着**。

### 2.2 三条「本轮不产出」的路径，只有一条被兜住

[`builder.py::build_from_archive`](../assembler/builder.py#L394) 的分派逻辑：

| 条件 | 行 | 本轮写盘？ | 旧文件会消失吗？ |
|---|---|---|---|
| 旧面（`tool_surface ≠ camofox-1`） | [402-407](../assembler/builder.py#L402) | ✗ | ✅ **会** —— `pool.migrate_samples` 已把它挪进 `legacy/` |
| `--rationale-era` 筛掉 | [394-398](../assembler/builder.py#L394) | ✗ | ❌ **不会** ⇒ **残留** |
| 判分不可信（`judgement_trustworthy is False`） | [`schema.py:1374`](../assembler/schema.py#L1374) → `split_archive` 返空 | ✗ | ❌ **不会** ⇒ **残留** |
| 切不出样本（`search_blocked` / 搜索采集失败 / 坏档） | [`schema.py:1378`](../assembler/schema.py#L1378) | ✗ | ❌ **不会** ⇒ **残留**（若它上一轮产出过） |

⇒ **「旧面」那一条之所以没事，是因为分池机制把它挪走了**；**其余三条没有归处**。

### 2.3 关键：仓库**已有**分池机制，判据只认「面」

[`assembler/pool.py`](../assembler/pool.py) 三条迁移函数
（[`migrate_samples`](../assembler/pool.py#L231) ·
[`migrate_views`](../assembler/pool.py#L241) ·
[`migrate_task_views`](../assembler/pool.py#L251)），
调用点齐全（[`builder.py:512`](../assembler/builder.py#L512) ·
[`views.py:898`](../assembler/views.py#L898) ·
[`task_view.py:1395`](../assembler/task_view.py#L1395)），
**都在批次开始时执行**。

⚠️ 但它们的判据是 `_surface_of_sample` / `_surface_of_view` / `_surface_of_task_view`
⇒ **「这个样本的 `tool_surface` 是不是交付面 `camofox-1`」**
⇒ **只管「旧面存量」**。
⇒ **「本轮名单之外」这件事，机制里根本没有对应的判据**。

> 💡 **这条最关键**：修复不需要新造机制 —— **是给已有的分池机制加一个判据**
> （「本轮名单之外 ⇒ 进隔离区」）。

### 2.4 读侧：下游**按 id 直读目录**，不问 P2 在不在

| 读者 | 位置 | 行为 |
|---|---|---|
| 训练侧（P3） | [`storage/read_p3.py::read_views`](../storage/read_p3.py#L27) | 按 `sample_id` 直读 `views/{id}_{messages,openai,meta}.json` |
| LS 的 ⑩ SFT 块 | [`golden_ls/exporter.py::read_sft_sample`](../evaluation/golden_ls/exporter.py#L609) | 同上（`read_views(tid, root=p2_root)`） |
| scout | [`scout/io.py::list_p2_samples`](../evaluation/scout/io.py#L72) | 遍历 `samples/*.json` |
| LS 推送 | [`ls_bridge/exporter.py::export_trajectory_one`](../evaluation/ls_bridge/exporter.py#L548) | 按 `trajectory_candidates.jsonl` 里的 id 找 T 视图 |

⇒ **没有一处会问「这份产物这一轮还该不该在交付集里」**。

## 三 · 危害分级（按下游读者的实际后果）

### 3.1 🔴 P3 视图残留 ⇒ **进训练语料**（最严重）

`read_views` 按 `sample_id` 直读目录 ⇒ **只要文件在，训练侧就吃**。
⇒ 一份被判「不进训练集」的档（判分不可信 / 口径筛掉），
**它的 P3 视图残留 ⇒ 照样进了 SFT 语料**。
⚠️ 这条**直接违反 H-31 的处置口径**（「**P2 不出样本、T 不出训练视图**」——
实测**只挡住了 P2，T 那侧因为是独立渲染、且多了 53 份多渲染的空壳**，
「两边都挡」在**产物目录层面**并没有真正成立）。

### 3.2 🟠 P2 样本残留 ⇒ scout 评分 ⇒ aggregate ⇒ LS

`scout run` 遍历 `samples/*.json` ⇒ 残留样本会被读入。

⚠️ **但危害程度取决于残留的成因**（这一点必须分清，否则会误判风险）：

| 残留成因 | `_resolve_sample` 回溯 P1 档的结果 | 后果 |
|---|---|---|
| 判分不可信（补键） | `split_archive` **返空** ⇒ 找不到该 `sample_id` ⇒ 返回 `None` | ✅ **被 skip 挡住**（本轮实测：`skip=7`，三件套里 **0 命中**）——**侥幸安全** |
| `--rationale-era` 筛掉 | P1 档是好的 ⇒ `split_archive` **正常切出** ⇒ **找得到** | 🔴 **不被挡** ⇒ 正常评分 ⇒ 进三件套 ⇒ 进 LS ⇒ **口径混批进交付** |

⇒ **「补键那次侥幸没出事」不是机制生效，是 `_resolve_sample` 的副作用。**
⚠️ **不能据此认为残留无害** —— era 筛选这条路是**真的会被污染**。

### 3.3 🟡 T 视图残留 ⇒ 复核队列噪声

`ls_bridge upload` 按 `trajectory_candidates.jsonl` 驱动 ⇒ **残留 T 视图不会被推上去**；
但**人工复核列举 / golden_ls 的轨迹级项目**会看到它们 ⇒ 噪声。

### 3.4 🟡 口径分叉：T 比 P2 多 53 份（P2 不出、T 出）

**这不是残留，是两侧判据不一样**：

- P2 侧对**退化空壳**不出样本（`build` 报「切不出样本的存档」）；
- T 侧**照样出了训练视图**（T 的判据里没有「切不出样本 ⇒ 不出 T」这一条）。

⚠️ 本轮那 53 份是 **3.5–3.9 KB 的退化空壳**（H-29/H-30 的 429/503 建页失败件：
`outcomes=0` · `steps=1` · `candidates=0`）⇒ 与 H-29 的处置口径
（「退化存档**不落盘**或落隔离区」）**不一致**。
⚠️ 它们**不进 P3**（P3 是 P2 的渲染）⇒ **不进训练集**；**不进 LS 上传** ⇒
**对本轮交付无实际影响**，但它是**交付目录里的噪声**，且**读的人会以为「T 有 = 这条轨迹成立」**。

### 3.5 ⚪ 门禁查不出来

[`scout/verify.py::_check_task_views`](../evaluation/scout/verify.py#L208)
是**单向**的：只查「`trajectory_candidates` 里的 id 在 T 视图里**能不能读到**」，
**不查「T 视图目录里多出来的」**。
⇒ 本轮那 53 份多渲染的空壳，**`scout verify` exit 0 放过了**。
⚠️ **同一个洞**：`check-archives` 只体检**存档**，不体检**派生产物目录的构成**。

## 四 · 本轮的临时处置（可逆）

残留与多渲染的一并**移入隔离目录**（**移走，不是删**）：

```
trajectory_pipeline/output/pipeline/_quarantine_judgement_untrusted/
├── samples/     7 份   （判分不可信那 7 条的陈旧 P2 样本）
├── views/      21 份   （由上面 7 份样本渲出的 3×7 份 P3 视图）
└── task_views/ 60 份   （7 条判分不可信 + 53 份退化空壳）
                    ── 合计 88 份
```

⇒ 归位后：**P2 107 == P3/3 321 == T 107**（三件套口径归一）。

⚠️ **为什么「移走」而不是「删」**：P1 存档原样在盘上（**那是证据**），
派生产物可从 P1 重渲染 ⇒ **隔离可逆**。
⚠️ **负样本池不在此列** —— 「并池是写入时的动作」，池的清理走 `pool-drop` 自己的纪律。

## 五 · 建议处置（三选一，**需 owner 裁**）

### 方案 A · 给分池机制加一个判据：「本轮名单之外 ⇒ 进隔离区」（**推荐**）

复用 [`assembler/pool.py`](../assembler/pool.py) 已有的迁移框架
（`_migrate` + companion 规则：P3 三份成组、P2/T 各自成组），
新增一个**按本轮名单**求差的迁移：

- `build_all` / `build_views_from_dir` / `build_all_task_views` 结束时，
  拿**本轮实际写出的 id 集合**与目录求差 ⇒ 多出来的**移进隔离区**；
- 隔离区**复用** `legacy/` 的形态（同构 ⇒ 恢复只需搬回），
  或新开一个 `quarantine/` 目录（**需裁**，见 §六·边界）。

**代价**：需要定「隔离区语义 + 恢复路径 + 是否影响 `pool_meta.json` 的计数口径」。

### 方案 B · 只报不删（**最小改动**）

`build` / `task-view` 的输出里**显式报出**：

```
  目录里有 7 份本轮未产出的旧产物（samples/）：<id 列表>
```

⇒ 符合仓库既有纪律（「**跳过必须看得见**」），
且**不碰任何数据** ⇒ 处置权留给人。
⚠️ **只是把隐形变成可见**，不自动归位。

### 方案 C · 读者侧加闸

`scout` / `read_views` 读之前先确认该 id 在「本轮名单」里。
⚠️ **不推荐做在训练侧** —— 训练侧**不该**有闸，
**训练侧该吃的就是干净的交付集** ⇒ 闸应该修在**写侧**（A），
读者侧只补一条**体检**（见 §七）。

> 💡 **推荐 A + C 的体检部分合起来做**：
> **写侧清点并归位（机制）** + **门禁查得出多出来的（体检）**。

## 六 · 边界（做的时候**不许**误伤）

1. ⛔ **不许删 P1 存档** —— 那是**证据**（人工复核要看的就是它）。
2. ⛔ **不许动 `legacy/`** —— 旧面是**只读存量**（owner 裁定 2026-10-10），
   新的迁移逻辑**必须幂等**、不得重复处理它们。
3. ⛔ **不许碰负样本池** —— 「并池是写入时的动作，不是读取时的推导」；
   池的增删走 `pool-add` / `pool-drop` 自己的纪律。
4. ⚠️ **隔离 ≠ 删除** —— 派生产物可从 P1 重渲染 ⇒ 隔离**必须可逆**。
5. ⚠️ **「本轮名单」的定义要写清楚** —— 是「本次 `build` 写出的 id 集合」
   还是「交付集应有的 id 集合」？两者在 `--include-legacy` 下**不等**
   ⇒ 判据写错会把旧面拖回来。
6. ⚠️ **不要用「目录里有几个文件」当分母** ——
   `pool_meta.json` 记的是**面**的计数，加了「按名单」这一维要**新开字段**，
   不能改旧字段的含义（改了会漂读数）。

## 七 · 验收条件

| # | 条件 | 判据 |
|---|---|---|
| 1 | 剔除一批存档后重建，**交付目录里没有它们的旧产物** | `samples/` 的 id 集合 **==** 本轮写出的 id 集合（P3 / T 同理） |
| 2 | 「本轮未产出的旧产物」**在输出里看得见** | `build` / `task-view` 显式打出条数与 id 列表 |
| 3 | 门禁**查得出**多出来的产物 | `scout verify` 增加**反向检查**（T 视图目录里不在 `trajectory_candidates` 的 id 至少报 warning）；`check-archives` 增加派生产物目录构成体检 |
| 4 | 隔离**可逆** | 隔离区里的文件能搬回原位并被读侧正常读到 |
| 5 | 旧面**不受影响** | `legacy/` 的文件数与内容**逐字节不变**；`pool_meta.json` 旧字段读数不变 |
| 6 | **回归门禁** | 新增单测：① 剔除 → 重建 → 断言目录无残留；② 造一份多出来的旧产物 → 断言它被报出/被归位；③ 断言 `legacy/` 未被动过 |

⚠️ **第 3 条是本条最容易被漏的**：现在的门禁**只查读侧**，
「写侧多出来的东西」**在报告上完全隐形** ⇒
**光修组装层、不补体检 ⇒ 同一个洞还会再踩**。

### 10.2 「本轮名单」的口径（§六·5 那条待决项的答案）

**每个 kind 各用自己的名单**，三个名单分别是：

| kind | 名单 = 「本轮该产出」的 id | 为什么 |
|---|---|---|
| P2 `samples/` | 本轮 build 切出、过了口径筛选 + 交付面的样本 id | 源头是 P1 |
| P3 `views/` | **P2 目录里的样本 id** | P3 是 P2 的渲染 ⇒ 镜像 |
| T `task_views/` | 本轮 task-view 判为该产出的 trajectory id（**判据与 P2 同源**）**∪ P2 目录里的 id** | 源头是 P1；**P2 是下限**（它说在交付集里的不许被清掉） |

⚠️ **T 的名单是并集，不是「只有 P2 目录」**——这是合并两套并行实现时的取舍：
拿 P2 目录当 T 的唯一名单，**P2 还没重建时**（主树实测 P2 137 / T 已是更新的批次）
会把本轮刚渲出来的**合法** T 视图当残留搬走
⇒ LS 上传时**候选来自 P2、视图却不齐** ⇒ 那些轨迹推不上去。
⇒ **P2 是下限**：并集里 P2 那一半保证「P2 说在交付集里的，T 视图不会被清掉」。

⚠️ **是「该产出」不是「实际写出」**：默认不覆盖（`overwrite=False`）时，
已存在的文件是**跳过**不是**没产出**——拿「写出的」当名单会把整池都判成残留。

⚠️ **旧面不在任何一个名单里**——但旧面在**清点之前**就已被
`pool.migrate_*` 挪进 `legacy/` ⇒ 清点看不见它 ⇒ **旧面逐字节不受影响**。

### 10.3 安全阀（都是「宁可不清，不误伤」）

1. **`prune_stale` 默认关**——只有**整批重建**（名单 = 全部存档）才开；
2. **路径指错 ⇒ 不清点**——**P1 源目录不存在**、**读侧 P2 目录不存在**、
   **读侧 P2 目录不是交付目录** ⇒ 那是**路径指错了**，不是「本轮一条都没有」
   ⇒ 报出**原因**（`StaleSweep.reason`）不搬任何东西
   （源目录不在时名单必然是空 ⇒ 清点会把**整个交付集**搬走 = 毁数据）；
3. **「本轮没点名的存档」的产物保守保留**——`archive_filter` 收窄时，
   未点名的存档**这轮没被构建**，它的产物**不是**陈旧残留
   （可能是**别的批次**的交付物）⇒ 它们的 id **按存档名推**出来
   （`_sample_id_of_archive`——``.reviewed`` 与原档同 id），一并留在名单里；
   ⇒ 仍能清掉「**存档已经从盘上删了、产物还留着**」的那些真残留
   （**这正是 H-33 的正题**）；
4. **读不出面的文件原样留着**——坏档不隔离（**不猜**它在哪个池），
   且**列出来**（`StaleSweep.unclassified` ⇒ CLI 印出来等人看）。
