## 三 · 问题清单（按严重级别）

### P0-1 · 执行层故障被降级成 warning，**整批退出码 0**

**症状**：53 条建页失败的产物照常落盘，批次以 **exit 0** 结束，日志里 **0 处 `[FAIL]`**。

**证据**：
- [`orchestrator.py:1230-1237`](../executor/orchestrator.py#L1230)：
  `except Exception as exc:` 把 `DriverSessionError`（执行层故障）兜住，
  记一条 warning 后**提前 return**。
- [`cli.py:958`](../executor/cli.py#L958)：`return 1 if failed else 0`
  ——批次级失败清单 `failed` **始终为空**，因为异常根本没冒到批次层。
- [`cli.py:929-931`](../executor/cli.py#L929)：`records.append(rec)` 之后
  `archive.write(rec, …)` 对 0 候选 0 访问的记录**照写不误**。

**影响**：CI / 调度器看到 exit 0 即认为批次成功；下游按「文件存在」筛选，
会把 53 份退化壳当正常样本入库。**这比直接崩更危险——崩了你会知道，没崩你不会。**

⚠️ **失败的形态要写准：不是「绕过了失败通道」，是「压根没进通道」**。
批次层确实有两条 `[FAIL]` + 失败清单通道——浏览器起不来
（[`cli.py:900-906`](../executor/cli.py#L900)）与 `orch.run` 抛异常
（[`cli.py:919-928`](../executor/cli.py#L919)）。而本次的故障是
**在 orchestrator 内部就被吃掉的**：`except Exception` 兜住 →
记一条 warning → **提前 return 一份已封口的记录** ⇒ `orch.run`
**正常返回** ⇒ 第二条通道一次都没触发；第一条更无从谈起。
⇒ 准确的因果链是「**异常没冒到批次层**」，不是「通道被绕过」——
后者会让人误以为通道的判据写错了要去改通道，而真相是
**执行层与批次层之间缺一个「这条没跑成」的信号**。

### P0-2 · camofox tab 泄漏，第 28 条起整批集体猝死

**症状**：T034 起**每条不到 1 秒**建页失败，错误分两种：
`429 Maximum tabs per session reached`（**47 条**）与
`503 Maximum concurrent sessions reached`（**6 条**）。

**根因链**：
1. [`visit.py:234`](../executor/steps/visit.py#L234) /
   [`agent_visit.py:108`](../executor/steps/agent_visit.py#L108)：
   **每访问一个候选就 `open_tab`，遍历结束后从不 close**。
2. ⚠️ **2026-11-11 复核更正（原判「关页失败被吞掉」，机制说错了）**：
   [`camofox_session.py:405-412`](../executor/browser/camofox_session.py#L405)
   的 `close()` 里那一行是 `await self.close_tab(tab_id)`，
   而 **`CamofoxSession` 根本没有 `close_tab` 这个方法**——
   它的方法叫 **`close_page`**（`:516`）；`close_tab` 只存在于
   `CamofoxDriver`（`:1374`）与 `PageDriver` 协议层。
   ⇒ 这一行**每次都抛 `AttributeError`**，被同一处的
   `except Exception: pass` 吞掉 ⇒ **关页从未发起**，
   不是「关页失败被吞」。实测（构造真实类实例、桩掉 `close_page` 记录调用）：
   `upstream tabs actually closed: []`，而本地 `_pages` 栈照清。
   ⇒ **一个 Run 一会话的隔离是假的**：会话结束时一张 tab 都没回收。
3. 放大项：[`visit.py:503-507`](../executor/steps/visit.py#L503)
   `open_tab` 自己也用 `except Exception` 吞掉开页失败并「继续用当前页」
   ——**泄漏完全无声无息**。

**「上游 tab 上限跨 session 全局」已由读数佐证（原标「未直接验证」）**：
按日志真实执行顺序累计**上游新建页数**。计数口径（**与代码一致**）：
agent 模式下 `open_tab` 在 `admit_landing_host` **之后**
（[`agent_visit.py:100-108`](../executor/steps/agent_visit.py#L100)），
⇒ **「同 host 跳过」的候选不开 tab**；搜索页走 `goto` 复用当前页，**也不开 tab**
⇒ 每次候选访问**恰好 1 张**新建页。

| 任务 | 本任务新建页 | 累计 | 状态 |
|---|---|---|---|
| T021 | 7 | 24 | 正常 |
| T022 | 12 | 36 | 正常 |
| T023 / T024 | 2 / 3 | 38 / 41 | 正常 |
| T025–T028 | 0 | 41 | 正常（0 候选） |
| T029 | 12 | 53 | 正常 |
| T030 | 11 | 64 | 正常 |
| T031 | 12 | 76 | 正常 |
| T032 | 12 | 88 | 正常 |
| **T033** | 12 | **100** | 正常（**最后一个成功建页的**） |
| **T034** | 要第 **101** 张 | — | **首个 429** |

⇒ **T033 建到第 100 张、T034 要第 101 张就 429** ⇒ 上游配额 **= 100**，
且**跨 session 累计**（每个 Run 一条 MCP 通道，但浏览器是同一台 ⇒ 配额是全局的，
报错文案里的 "per session" 指上游的浏览器会话，不是我们的 MCP 通道）。
⇒ **加延迟无济于事**（本仓库一 Run 一次 launch，
[`cli.py:557-588`](../executor/cli.py#L557)，本该天然隔离），
必须**每候选访问后关页** **且** `session.close()` **真能关页**。

**⇒ 修复面比「上报关页失败」更小也更硬**：`close_tab` → `close_page`
（一个词）即让会话级回收立刻生效；再叠加每候选关页（治本，
避免单任务内堆到上限）；`open_tab` 失败不许静默「继续用当前页」；
`session.close()` 的失败**上报**不吞。

### P1-5 · 乱码标记的真实成因被误判

**证据**：[`camofox_driver.py:632-634`](../executor/browser/camofox_driver.py#L632)
```python
if (body and degraded is not None and body_source == "inner_text"
        and is_mojibake(body)):
    degraded.append("body_mojibake")
```
**只有 `body_source == "inner_text"` 时才判 mojibake** ⇒ 这批「乱码」实际是
**snapshot HTML 抓取失败后回落 innerText** 的表现，**不是内容真乱码**。

⇒ 代码把**采集失败的症状**当成了**内容质量的结论**。
正确处置方向是「重取 snapshot / 修 charset」，而不是丢掉候选。

### P1-6 · 13.72 小时静默空档，无心跳、无看门狗、无恢复自检

**现象**：T027（11-10 19:05:33）→ T028（11-11 08:48:39）之间**日志完全空白**。

**证据（本次复核补上）**：空档不是「什么都不知道」，而是**一次在途的 HTTP 请求**：

1. **空档两侧紧邻的两行就是全部**（日志第 679–680 行，中间零行）：
   - `19:05:37,126` `[T027] 搜索页未提取到候选，run 提前结束`
   - `08:48:39,314` `httpx | POST …/chat/completions "401 Unauthorized"`
2. **那行 401 就是 T027 的 rationale writer 请求**：对照 T025/T026 的同一形态——
   orchestrator 收尾后 **3–4 s** 内必跟一条 httpx 行
   （`19:05:24,462` / `19:05:33,054`，均 200 OK），那是 rationale writer 的调用；
   T027 的对应位置就是空档后的第一条。⇒ **空档 = 一个请求在途 13.72 h**，
   **不是**进程死了，**不是**机器闲着。
3. **进程跨越空档活着**：恢复后先落 T027 的存档（`T027__f7b02bcc.json`）、
   再起 T028 ⇒ 排除「进程被 kill」「机器断电」。
4. **客户端自己的 90 s 超时没有触发**（默认 `DEFAULT_TIMEOUT_S=90`，
   [`client.py:67`](../llm/client.py#L67)）⇒ 阻塞**不是**普通网络等待——
   那种会在 19:07:07 前变成 `transport:ReadTimeout` 并被记进账本。

⇒ **最自洽的解释**：机器在 19:05:37 后**挂起/休眠**，08:48:39 恢复。
Windows 上 socket 超时的计时随系统 tick 走、**休眠期间不推进** ⇒
客户端的超时**看不见这次挂起** ⇒ 请求在途 13.72 h 后照常返回。
⚠️ **这一条是推断不是实测**（本轮没有电源/休眠事件日志可查），
但上面 1–4 条是硬事实，且**不影响处置方向**。

⚠️ **真正的代价不在「慢」，在「静默」**：恢复后的第一个请求就是 401 ⇒
**LLM 端在空档期就已失效**，而空档期间**没有任何告警**。
（可确定的只有两端：key 在 T026 的最后一次 200 OK（`19:05:33,054`）时**还有效**，
在 T027 那次请求被应答时**已失效**；至于服务端是**空档前**换的 key 还是
**空档中**换的，日志分不出来——**但两种读法都不改变处置**：
空档与 401 是**两件叠在一起的事**，且**空档期间没有一样东西报了警**。）
⇒ 恢复后应做一次环境自检（LLM ping + camofox ping），
而不是直接接着跑第 22 条。
