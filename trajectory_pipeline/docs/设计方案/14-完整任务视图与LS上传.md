## 0. 为什么总到不到位——per-unit 标注看不到任务全貌

[数据契约](../03-数据契约.md) 把新树切成 P1 / P2 / P3 三层：

| 契约 | 落点 | 粒度 |
|---|---|---|
| **P1 观察存档** | `output/pipeline/<task_id>__<hash>.json` | 一份 = 一个完整任务流水（顶层 `steps[]` + `visits[i].steps`） |
| **P2 单条样本** | `output/pipeline/samples/<id>.json` | N 条 / 任务：搜索阶段 1 条 + 每站点 1 条 |
| **P3 训练视图** | `output/pipeline/views/<id>_{messages,openai,meta}.json` | N×3 份 / 任务：per-unit 三视图 |

P2 切条是**训练侧的刻意设计**——「**一条 = 一个决策单元**」，理由是 SFT 模型需要学「在这种情形下该选什么动作」，把选站与验站压进同一条样本里反而训不出来（见 [P2-sample.md §切条粒度](../contracts/P2-sample.md)）。

但**这一刀切碎了另一条真实需求：人工复核**。

### 0.1 标注员看到的现实（per-unit 切碎的副作用）

把 per-unit P3 视图作为 LS task 上传后（[ls_bridge.exporter.build_task_data](../../evaluation/ls_bridge/exporter.py) 现状），标注员一次只看到一段决策：

- **不知道用户原本问的是什么** —— `user_prompt` 在 search unit 的 P3 里，site-N 单元的 P3 没有 user 消息；
- **不知道 agent 为啥跳到这个站** —— 前序 site-1 / site-2 的失败理由与原文不可见；
- **看不到任务级结论** —— outcome 在 site-N 单元里，但「最后整体上算成功还是失败」需要跨 unit 聚合；
- **rationale 缺失的判断不可靠** —— 一个 unit 的 `gate=passed` + `rationale_missing=true` 既可能是「这步没思考」也可能是「这条任务根本没接 writer」；前者是样本级，后者是工序级——单看一个 unit 分不开。

更隐蔽的是：**per-unit 正常 ≠ P3 给 SFT 训练时也正常**。这是用户原话。例子：

- 一条 site-2 P3 看上去动作流完整、rationale 齐全、gate=passed；
- 但它在 per-unit 视角下「找不到播放页」是合理的，因为 site-1 之前已经被否决过了——agent 跳到 site-2 是基于已有信息的合理转移；
- 把这条样本喂给 SFT 模型时，**模型只看到 site-2 的上下文，判定不了「为什么跳过 site-1」**，于是学到「找不到就放弃」或别的偏置。

这种「per-unit 看起来正常，整条轨迹偏置」的样本，单看 P3 看不到，必须**把整条任务铺开**。

### 0.2 现状已暴露的两个具体问题

1. **L4 VLM 复核层看不到全貌** —— `VLMReviewInput` 是单站点的 `MediaSignal` + `body_excerpt` + `page_quotes`（见 [vlm_reviewer.py §VLMReviewInput](../../executor/review/vlm_reviewer.py)）。它判 `paywall` 时看不到「用户在第几个站走到这一步」；判 `partial_free` 时看不到「这是不是首个能解析的站」——这两类语义都依赖任务级上下文。已记入 [`docs/计划进展/04-探针七层域.md` §L4 TODO](../计划进展/04-探针七层域.md)，本文不展开，留作单独议题。

2. **LS 上传是 per-unit P3 渲染** —— `ls_bridge.exporter.read_views(record["sample_id"])` 读一份 P3；`render_messages_text` 把单 unit 的对话渲染成 `── [i] role ──` 文本块；同一个 (task_id, run_id) 的 N 个 unit 上传为 N 个独立 LS task（[`scout/types.py::ScoutRecord.sample_id`](../../evaluation/scout/types.py) 形式 `<task_id>__<run_id>__<unit>`）。

## 1. 决策

| # | 议题 | 决策 |
|---|---|---|
| **D14.1** | P2 / P3 形态 | **不改**。它们是 SFT 训练契约，本节新增视图层与它们解耦，不动字段、不动切条、不动渲染。 |
| **D14.2** | 新增视图层代号 | **T · Trajectory Views**（per-Run 完整任务视图），与 P1 / P2 / P3 平级 |
| **D14.3** | 渲染源 | **直接读 P1**，不从 N 份 P2 反推。理由：P1 已经是 per-run 的完整流水（含 `ref` 句柄、原始 `steps[i].observation`、`visits[i].steps`），动作流时序连续性天然存在；从 P2 反推要重编全局 `step_index`、合并降级 `degraded_from`、跨单位聚合 outcome，反而引入一处新的拼接逻辑——而 P1 已经在手上。 |
| **D14.4** | T 视图与 P3 的可见性关系 | **不替代**——T 给 LS / 人工复核 / L4 任务级分析；P3 给 SFT 训练。两者在同一批数据上从不同视角独立产出，互不消费对方的代码路径。 |
| **D14.5** | LS 上传走 T | ls_bridge 的上传入口**新增一个 `--task-views-root` 参数**；上传时优先读 T（按 `<task_id>__<run_id>` 主键），T 缺失时**回退**读 per-unit P3 拼成对话流（fail-soft，不阻塞现有路径）。回退路径打 `note="task_view_missing_fallback"` 标签供人查。 |
| **D14.6** | T 视图与 LS 数据契约的关系 | T 是**渲染层**产物（文本 + 原始视图 JSON 双写），不是新数据契约；task.data 的字段表与 `exporter.build_task_data` 现状一致，**只换渲染源**。 |

## 2. T 视图 · 形状

**落点**：`trajectory_pipeline/output/pipeline/task_views/<task_id>__<run_id>.json`

**单一文件，包含三个键**（与 P3 同款三视图形态，但**主键变成 `<task_id>__<run_id>`**，不是 `<task_id>__<run_id>__<unit>`）：

```json
{
  "trajectory_id": "T001__b98b3e56",
  "task_id": "T001",
  "run_id": "b98b3e56",
  "title": "功夫",
  "schema_version": "task-view.v1",
  "messages": [ ... 完整对话 ... ],
  "openai":   { ... 同款 function-calling 形态 ... },
  "meta":     { ... 同款元数据 ... }
}
```

### 2.1 三视图的合并口径

#### `messages` 数组

按时间顺序拼：search 单元的 system + user → search 单元的 assistant（动作+思考）→ user（观察）→ …… → site-1 单元的 assistant / user 对 → …… → site-N 单元的 assistant / user 对 → **任务级收尾 assistant**。

要点：
- **user 消息只有一条**（来自 search 单元的 `user_prompt`）—— 后续每个 site-N 不再追加 user prompt；
- **system 消息也只有一条**（`SYSTEM_PROMPT` 冻结，与 P2 一致）；
- **观察回执（user 消息）保持每步一条**，且跨 unit 连续；
- **`role: "assistant"` 收尾消息**（任务级 summary）—— 内容从 `outcomes[]` 聚合 + 整条 ledger 的 `by_branch` 派生，不复述任何 unit 级别 `reflection`；
- **step_index `step_index` 全局重编**——从 0 开始在整条轨迹上重排（P2 是 unit 内编号）。`rationales` 同步重编（按 P1 的 `steps[i].rationale` 全局位序）。

#### `openai` 对象

同款 `messages` + `tools`，但 `tool_call_id` 全局稠密重编（`call_0` ... `call_<N-1>`，N = 全局动作数）：
- search 单元的若干步 → `call_0 ... call_<a>`
- site-1 单元的若干步 → `call_<a+1> ... call_<b>`
- ……

`arguments` 平铺合并（与 P3 同款）；`origin == "infrastructure"` 的步**整步跳过**（P3 判断 2 同款）。

#### `meta` 对象

与 P3 `meta` 同构，但补充：

| 键 | 类型 | 说明 |
|---|---|---|
| `trajectory_id` | str | 与 P3 的 `sample_id` 同位（`<task_id>__<run_id>`） |
| `unit_count` | int | 单元数（search + site-N） |
| `unit_sample_ids` | list[str] | 各单元的 P3 `sample_id` —— **从 T 反查 P3 的入口** |
| `unit_outcomes` | list[{unit, branch, branch_label, evidence, site_url, play_page_url}] | 每个 unit 的 outcome 摘要，**完整不省略**（per-unit P3 的 outcome 只标一个，T 把所有 unit 列开） |
| `overall_branch` | str \| null | 任务级聚合分支：`success` / `success_<x>_<y>` / `failed_<x>`；缺任一律空 |
| `ledger_summary` | object | P1 `ledger` 原样（`total_sites` / `succeeded` / `negative_samples` / `by_branch` / `missing_branches` / `heuristic_candidates`） |
| `task_gate` | object | 整条任务的闸门汇总：`passed` 当且仅当全部 unit `gate=passed` 且无 degraded |
| `gate_breakdown` | list[{unit, gate, rationale_missing}] | 逐 unit 闸门状态 |

其余键与 P3 `meta` 一致：`step_count` / `observation_count` / `infrastructure_actions` / `observation_complete` / `missing_observation_count` / `closing_summary` / `rationale_steps` —— **数值是全局的，不是 per-unit 的**。

### 2.2 与 P3 的语义差异表

| 维度 | P3 (per-unit) | T (per-run) |
|---|---|---|
| 主键 | `<task_id>__<run_id>__<unit>` | `<task_id>__<run_id>` |
| `messages` 长度 | 单 unit 的 N 步 | 全 run 的 ∑M 步 |
| `messages[0].role` | `system` 或 `user`（来自 search unit 的同一行） | `system` 或 `user`（同一句，唯一） |
| `step_index` | unit 内编号（0..n-1） | 全 run 重编（0..N-1） |
| `tool_call_id` | `call_<step>` per unit | `call_<step>` 全局重编 |
| `meta.outcome` | 单 unit outcome | **不存在**（移到 `meta.unit_outcomes[]` + `meta.overall_branch`） |
| `meta.unit_count` | 不存在 | 存在 |
| `meta.unit_sample_ids` | 不存在 | 存在 |
| `meta.ledger_summary` | 不存在 | 存在 |
| `meta.task_gate` | 不存在 | 存在 |
| `closing_summary` 内容来源 | unit outcome + unit reflection | outcomes[] + ledger + （可选）整条任务 reflection（**未在 P1 顶层预留**，留空） |

## 3. 渲染源选择：D14.3 为什么从 P1 而不从 P2

候选两条路：

### 路 A · 从 P1 渲染 T 视图
- **优点**：
  - 动作流时序天然连续（顶层 `steps[]` + `visits[i].steps` 已经按时间顺序）；
  - `rationale` 写在 P1 的 `steps[].rationale` / `visits[i].steps[].rationale`，原生就是全局位序；
  - `outcomes[]` 是 per-run 阵列；`ledger.summary()` 是 per-run 字段——T 需要的整条汇总在 P1 一处拿齐；
  - 不引入新的拼接逻辑——**T 渲染器像 P3 渲染器一样，**「读一份 JSON 写一份 JSON」**。
- **缺点**：
  - **多一道工序**（`assembler.views` 之外再写一个 `assembler.task_view`）；
  - 与 P3 渲染源**不共享代码**（不直接调 `views.to_messages`），因为输入形态从 `Sample`（per-unit）变成 `RunRecord`（per-run）。

### 路 B · 从 N 份 P2 拼接成 T 视图
- **优点**：
  - 与 P3 共享 `assembler.views` 的渲染代码；
  - 「trainability 已经过测试」等于「T 渲染经过了测试」——间接复用。
- **缺点**：
  - `step_index` 重排要写一套对齐代码（per-unit 编号 → 全局编号）；
  - `tool_call_id` 重编要写一套对齐代码（沿全局稠密序列）；
  - `outcomes` / `ledger` / `task_gate` 都要聚合——这套聚合逻辑**没有现成代码**，要在 P2 之上写一层；
  - **降级标记合并语义不清** —— per-unit `degraded_from` 合到任务级时，是「任一 unit 降级则任务降级」还是「全部 unit 都未降级才算干净」？这又是个新决策；
  - P2 的 `system_prompt` 与 P1 的 `system_prompt` 不完全等价（P2 把 `SYSTEM_PROMPT` 冻结进文件）；拼接时**必须**用 P2 的 search unit 的 `system_prompt`，否则训练样本与 T 视图不一致——这条要在拼接代码里写显式选择；
  - **P2 不是真值源**——P1 才是。改 P2 不影响 P1，但改 P2 影响 T（走 P2 拼接时 T 跟着 P2 漂）。

**结论**：走路 A。P1 是真值源、T 是 P1 的另一份渲染——与 P3 是 P2 的另一份渲染**对称**。代价是新建一个 `assembler/task_view.py` 模块，渲染代码与 `views.py` 同构（消息行 / openai 形态 / meta 字典各自写一份），但**不互相 import**——交接面是格式不是对象（D14.6）。

### 3.2 例外：D14.3 的回退路径

当 T 视图缺失时（D14.5 提到的 fallback）：
- 不读 P2 拼接，而是 **直接读 P1，按 P1 的形态渲染成对话流**——渲染实现就是 `task_view` 的渲染代码本身，只是不落盘直接喂给 LS；
- **P2 渲染路径与 T 渲染路径不共享**——即使临时 fallback 也不走 P2，原因同 §3 路 B 的缺陷。

回退路径只是「不落盘 vs 落盘」的差别，渲染源都是 P1。

## 4. ls_bridge.ts 上传层改动（D14.5 落地）

### 4.1 新增参数

```
python -m trajectory_pipeline.evaluation.ls_bridge upload \
    --scout-dir output/scout/<date> \
    --task-views-root trajectory_pipeline/output/pipeline/task_views  # 默认
    --views-root output/pipeline/views                                # 现有，P3 根
```

`--task-views-root` 指向 T 视图根；不传时取 storage 默认根（与 `--views-root` 平级）。

### 4.2 scout 三件套的聚合

**这是 D14.5 的关键改动**：当前 scout 三件套（`positive_candidates.jsonl` / `negative_candidates.jsonl` / `quarantine.jsonl`）是 per-unit 的——每条记录的 `sample_id` 形式 `<task_id>__<run_id>__<unit>`。LS 上传时会把同一 `(task_id, run_id)` 的 N 条记录上传为 N 个 task。

D14.5 要求上传走 T 视图（per-run），于是 scout 的输出**新增一条聚合步**：

```
P2 → scout 三件套（per-unit，正/负/缺判）       [现状]
P2 → scout 三件套聚合 → trajectory_candidates.jsonl  [新增]
                            ↓
                     按 (task_id, run_id) 聚合
                            ↓
                     T 视图 → task.data
                            ↓
                     LS project（创建）
```

`trajectory_candidates.jsonl` 字段：

| 键 | 类型 | 说明 |
|---|---|---|
| `trajectory_id` | str | `<task_id>__<run_id>` |
| `task_id` / `run_id` | str | 切片轴 |
| `status` | `"scored"\|"undetermined"\|"not_run"` | 任务级 status（四维 score 全到齐 = scored；任一维 None = undetermined；全 None = not_run） |
| `scores` | list[DimensionScore] | 四维 score 的**聚合**策略见下 |
| `tags` | list[ScoutTag] | 任一 unit 的 tag 都计入（并集） |
| `unit_outcomes` | list[str] | 各 unit 的 `sample_id`（per-unit P3 反查入口） |
| `evidence_supplement` | dict | **任一 unit 提供的都合并**（键冲突时取第一个非空，决策记录在 `aggregation_log` 字段） |
| `aggregation_log` | list[{unit, action, reason}] | 聚合期所有决策的留痕（打 tag / 选 score / 合并 evidence）——给人工复查 |

### 4.3 score 聚合策略

四维 score 的聚合：

- **d2 / d4 / d5**：取**最差 unit**的 score（min）—— 任一 unit 站错，整条轨迹站错；
- **d6**：取**最差 unit**的 score（min）；
- **任一维 is_veto=True**：任务级 `is_veto=True`（**短路**）；
- **任一 unit 的 score=None**：任务级 score=None，走 quarantine（**短路**）；
- **缺 unit**：不补——`unit_count` < 期望数时记录 `aggregation_log` 一行 `action="missing_unit"`。

聚合后的 `status`：
- 全部 `to_scored=True` → `scored`
- 任一维 `to_quarantine=True` → `undetermined`
- 全部 `to_skip=True` → `not_run`

聚合逻辑独立模块 `evaluation/scout/aggregate.py::aggregate_to_trajectory(units: list[ScoutRecord]) -> TrajectoryRecord`，单测独立。

### 4.4 LS 上传侧改动

`ls_bridge.exporter` 新增 `trajectory_candidates.jsonl` 读取路径：

```python
TRAJECTORY_BUCKET_FILE = "trajectory_candidates.jsonl"

def read_trajectory_records(scout_dir, buckets=("positive","negative","quarantine")):
    """读 trajectory 聚合产物, 返回 list[(bucket, record)]."""
    ...

def export_trajectory_one(record, bucket, *, task_views_root=None, ...):
    """TrajectoryRecord + T 视图 → (task, prediction, scan_hits)."""
    views = read_task_views(record["trajectory_id"], root=task_views_root)
    if views is None:
        return None, None, []  # → fallback 路径
    ...
```

主入口 `_cmd_upload` 默认走 `trajectory_candidates.jsonl`（D14.5）；旧路径（per-unit P3）保留为 `--legacy-unit-trajectory` 旗标，**默认弃用**——给存量 scout 配置三周过渡期。

### 4.7 评分卡（scorecard）的对接

scorecard.v2 当前是 per-unit 的——一个 sample 对应一个 scorecard。T 上传时 scorecard 怎么办？

- **保留 per-unit scorecard 进 `task.data.scorecards`**（list of {sample_id, scorecard_dict}）—— 让 LS 标注员能看到每个 unit 的评分细目；
- **新增任务级聚合 scorecard** —— `task.data.scorecard_text` 内容是聚合后的（min 策略），单字段不变；`task.data.scorecards` 是明细列表；
- `risk_hints_text` 内容来自聚合 scorecard，per-unit risk 合并（任一命中或 `missing_*` 维度都计入 hints）。

## 8. 风险

1. **过渡期指标解读混乱** —— 旧 scout 三件套（per-unit）与新 trajectory_candidates（per-run）共存时，报告侧读哪个？默认走新；旧路径加 `--legacy-unit-trajectory` 后**必须在报表文档里加注**，否则报告读起来「N 个 negative」与「N 个 trajectory negative」分母不同看着乱；
2. **score 聚合策略可能被反复调整** —— min 策略是最保守的；有人后怕就换成加权平均或最权重 unit。每次调整都要重跑历史批次，**不能回填**（P3 的 `unit_outcomes` 里有 per-unit 原始 scorecard，重算即可；但报告里的批次级断言会变）；
4. **T 视图不能纯替代 P3** —— SFT 训练仍吃 P3，T 不能替（per-run 训练轨迹会破坏「一条 = 一个决策单元」的设计假设）。LS 与 SFT 是两个消费方，不要混。
