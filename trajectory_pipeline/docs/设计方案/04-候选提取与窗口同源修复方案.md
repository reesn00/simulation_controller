## 1. 根因证据链（已确认事实）

### 1.1 候选提取：全量 → 5 个候选

`executor/steps/search.py::extract_candidates`（L316–370）：

- 遍历**全量** `obs.links`（111 条），**保持原始顺序**；
- 用 `exclusion_reason`（L181–212）逐条过滤：
  `engine_self`（命中 89 条）、`excluded_host:baidu.com`（命中 17 条）、
  `impossible_content` / `path_noise` / `redirect_wrapper`；
- 按 host 去重，取前 `limit`（默认 20，来自 orchestrator `max_candidates=20`）。

过滤后剩 **5 个候选**：hao123、爱奇艺、西瓜、搜狐、优酷。
候选 `Candidate`（L140）携带 `source_href`（原始链接）/ `url`（`_unwrap_redirect` 剥掉百度 `/link?url=` 包裹后的直链）/ `rank` / `text`。

### 1.2 窗口构建：20 条里只有 1 个候选

`perception/llm_perceptor.py`：

- `LLM_LINKS = 20`（L90），`_link_window`（L670–679）=
  `_ordered_links(obs, question, target_title)[:20]`；
- `_ordered_links`（L638–667）把「text 含目标片名」的链接提到最前（hit 区），其余保原序（miss 区）；
- 百度首页导航占据窗口前 12+ 条；hao123 是窗口内**唯一**候选（text 恰含片名被提前）；
- 爱奇艺 / 西瓜 / 搜狐 / 优酷的原始 index ≥ 50，**模型看不见**。

### 1.3 选中项与候选零交集 → kept=0 → 全 unresolved

- 模型只能从窗口 20 条里选，选中了 `baidu.com/s?wd=…` 站内搜索链接
  （text 含片名，被 `_ordered_links` 提前进窗口）；
- `_apply_selection`（orchestrator L289–369）用候选 `source_href or url`
  匹配模型 selected URL（L326–329）——站内搜索链接被 `excluded_host:baidu.com`
  剔出候选，**选中项与候选集合零交集**；
- 结果：`kept=0`，5 个候选全判 `unresolved`；批次 D-2 不可判定（prototype 无引用）。

### 1.4 诚实披露

模型 selected 的实际内容**未落盘**（`to_json` L196–236 不序列化 selection）。
根因靠 `candidate_source=perceptor` + `kept=0` + 窗口重放**推断**，属**推断级结论**而非模型原文直证。
不排除「模型即使看见 4 个真实候选也选错」的残余可能——这正是 §6 待确认的内容。

## 2. 同源修复设计

### 2.1 「同源」的精确定义

> **候选集合 ⊆ LLM 窗口**，且**窗口内可见候选的 href 与候选 `source_href` 一一对应**。

两条同时成立时：
- 模型「看得见」每一个候选（这是可归因的前提）；
- 模型选中的窗口链接，`_resolve_rows` 回映的 href 一定落在候选集合里，
  `_apply_selection` 的匹配不再是碰运气。

修复要改变的是**数据流**，不是模型行为：候选钉进窗口是被动可见，
不要求模型「学会挑候选」——决定权仍在代码（窗口构建），LLM 层只做探索。

### 2.2 主方案（推荐）：executor 把候选钉进窗口

在环节① `extract_candidates`（orchestrator L603）返回之后、
`decide(Q.SELECT_PLAY_SITES, …)`（L628）**之前**，插入一次链接重排：

```
record.search_obs.links
    → 按候选 rank 序，把「候选 source_href 对应的 LinkItem」提到最前
    → 其余链接保持原相对顺序
    → dataclasses.replace(record.search_obs, links=ordered)
```

原理：

1. 候选对应的 LinkItem 的 `text` 已被 `title_for` 写回标题（L575–597），
   `_ordered_links` 分桶时它们落在 **hit 区开头**（含片名 + 已在前列）；
2. `_link_window = _ordered_links[:20]` 从前 20 条里截——候选 ≤ 20（`max_candidates=LLM_LINKS`），
   只要候选 text 含片名就**必在窗口内**；
3. 窗口顺序变化不破坏任何既有机制：
   - `known = {link.href for link in obs.links}`（L196）是全量集合，重排不改变成员；
   - `_resolve_rows` 仍用同一窗口把编号 `i` 回映为 href；
   - `_apply_selection` 的匹配口（source_href or url）不受链接顺序影响；
   - `_drop_site_homepages`（L387–426）在 decide 之后，行为不变。

**依赖边零破坏**：感知层不 import executor、executor 不 import 感知层实现，
重排发生在 executor 侧 `search_obs` 上，感知层只需「收到什么就看什么」。

### 2.3 备选方案与取舍

| 方案 | 做法 | 结论 | 否决理由 |
|---|---|---|---|
| **A（主）** | executor 重排 links，候选钉进窗口 | ✅ **推荐** | 感知层不动、七不变式不动、W1 规则版天然兼容 |
| B | 修改 `decide` 契约，把候选集合显式传给感知层 | ❌ 否决 | 破坏 `perception/base.py` 协议与七不变式；W1 规则版不需要候选概念；契约改动波及 `replay` 与存档 |
| C | 先问 LLM「这 20 条里哪些是可看站」，再与候选求交 | ❌ 否决 | 候选不在窗口时依旧零交集（没解决错位，只换了提问方式）；把「钉入责任」压给语义层，违背「代码层做护栏」 |
| D | 候选从窗口内派生（窗口先定，再在窗口内候选化） | ❌ 否决 | 百度导航占窗口 12+ 条，过滤后候选剧减甚至为空 → 整批无正样本；且把「候选提取」从代码事实降级为「模型视野的残片」 |

### 2.4 边界情况

1. **候选 text 不含片名**（`title_for` 未命中，text 是面包屑/域名）：
   候选落 `_ordered_links` 的 miss 区（保原序），排在 hit 区之后，**可能被挤出窗口**。
   → 实施时必须补「窗口 ⊇ 候选」的强制校验（见 §4.3），不静默放行。
2. **候选数量 = 20 = `LLM_LINKS`**（`max_candidates` 上限恰好等于窗口宽）：
   全部候选进窗口时模型无任何导航上下文。可接受（候选本身含 title text，
   模型只需判断「可看 / 不可看」），但需在验证口径确认窗口前 20 条 = 候选全集。
3. **候选数量 > 20**（未来 `max_candidates` 调大而 `LLM_LINKS` 未同步）：
   窗口装不下全部候选 → 超出部分不可见 → 错位复现。
   → 修复要点：`max_candidates` 与 `LLM_LINKS` 必须保持 ≤ 关系（§2.2 已利用该等式），
   并在 orchestrator 加断言/告警，防止静默超窗。
4. **重排对下游的潜在影响**：`record.search_obs.links` 顺序在存档中变化。
   需逐一核对是否有下游逻辑依赖 links 的**原始顺序**（如 `rank` 从 0 递增的语义、
   review/report 的展示序）；实施时全文检索 `obs.links` / `search_obs.links` 的消费方。

## 5. 风险与回退

- **风险 R1：候选 text 无片名 → 钉窗失败（§2.4-1）**。概率低（实测百度结果标题基本命中
  `title_for`；hao123 是唯一疑似不命中者，但它已是窗口内候选）。
  缓解：§4.1-3 强制校验 + evidence 标注，失败可见、不影响采集继续。
- **风险 R2：links 顺序被下游依赖（§2.4-4）**。实施前先做消费方检索；若发现依赖，
  改为「重排只发生在传给感知层的副本上」，存档保留原始顺序，`decide` 传副本。
- **风险 R3：`rank` 语义与 links 顺序耦合**。`Candidate.rank` 若取过滤后索引（0 起），
  重排不改变它与源 `links` 的对应，仅展示序变化——复核 review/report 即可。
- **回退**：改动集中在 orchestrator 一处重排 + 可拆的辅助函数，删掉重排两行即回退，
  无 schema 迁移、无存档回填（**并池不回溯历史**的红线不变）。

## 6. 待确认项

   当前根因为**推断级**。验证口径（§4.3-3）只能证明「候选可见后 kept>0」，
