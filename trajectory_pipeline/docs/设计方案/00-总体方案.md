## 0. 为什么新树不 import 存量代码

不是洁癖，是有前车之鉴：

- **双导入 → 双类对象**：存量里 gdr 走顶层风格（`from domain import ...`）而 orchestration 走
  `gdr.` 前缀，同一份源码被加载成两套类对象，跨边界 `isinstance` 静默判 False，
  `usage_prune` 因此**从未真正执行**过。
- **门禁盲区**：`gdr/tests/` 长期不在 `testpaths` 内，360+ 条测试不跑，掩盖了 3 处陈旧导入和
  2 处生产代码静默失效。

新树一旦 import 存量，就会继承这两类问题——而 v2 的核心卖点正是「事实层由代码掌控」，
一个 `isinstance` 恒 False 的依赖足以让整条链失效。故：**只读参考，不建依赖**。
可复用的仅限第三方库（**playwright** / pydantic / httpx）。

### D7 的执行层：obscura

**决策链**：初版定「playwright-only」（放弃 Camoufox 指纹伪装）→ 侦察发现本地已有
Playwright MCP 可经标准 MCP 协议直调（存量的 `camel.toolkits.MCPToolkit` 只是适配层，
`browser_navigate` / `browser_snapshot` / `browser_run_code` 这些原子原语本就可被任意
MCP client 调用）→ 用户指定改用 **obscura**。

**obscura 已确认**（context7 两个官方条目）：

| 事实 | 来源 |
|---|---|
| Rust 编写的无头浏览器引擎 | `/h4ckf0r0day/obscura` 库描述 |
| 面向 web 抓取与 AI agent 自动化，**内置反检测** | 同上 |
| headless Chrome 的 drop-in 替代，兼容 Puppeteer / Playwright | `/websites/obscura_sh` 库描述 |

**obscura 待验证**（文档暂不可得，见 §7 待决 1）：

- MCP server 的启动命令与配置文件格式（stdio / http / sse）
- 暴露的 tool 清单，以及是否覆盖 v2 需要的原子操作：
  **导航 / 取页面快照 / 点击 / 填表 / 执行 JS / 元素计数**
- 安装要求（运行时、浏览器二进制、依赖）
- 反检测的实际通过率（宣传与实测常有差距）

**这个选择解掉了初版 playwright-only 的最大代价**：内置反检测意味着
「成功样本多样性塌缩」风险基本撤销。剩余风险是**实测通过率未知**——
W1 交付时仍必须产出「成功站点域名分布」报告，用数据验证宣传。

**架构上不变的点**：无论 obscura 还是 Playwright MCP，**新树都只经标准 MCP 协议
连 server**，自己只写 `PageDriver` 协议与一个 MCP client。这与「不 import 存量」
完全不冲突（MCP 是跨进程协议，不是 Python 导入边），也与存量是否用 CAMEL 无关。

**被排除的选项**：

| 选项 | 排除原因 |
|---|---|
| 自建 Playwright driver | 已被 obscura 取代；且自建要重造 DOM 清洗与等待逻辑 |
| 远端 QwenPaw 当执行器 | 它只有 `chat/task` 入口（吃自然语言、agent 自决策），是 v2 要换掉的那颗心脏；观察经 LLM 转述，rationale 的锚被削弱 |

### D9 的代价（一人打分）

单人打两次只能测 **test-retest reliability（自相关）**，**不是 inter-coder agreement**。

- 统计上：自相关必然 ≤ 评分者间一致性（同一人两次判断共享同一套标准解读偏差，误差不会相互抵消）。
- 经验值：test-retest Cohen's kappa 通常落在 **0.4–0.6**（中等），**0.7 属于强一致**。
- 因此把 0.7 平铺到所有维度是不现实的。

**方案按此分层**（阈值待你确认，见 §7）：

| 维度类型 | 示例 | 指标 | 阈值 |
|---|---|---|---|
| **硬维度**（有客观真值） | schema 校验、字段完整性、实体核查、时序 | Cohen's kappa | **≥0.7**（按原案） |
| **软维度**（判读为主） | rationale 吻合度、内容相关性 | 加权 kappa / ICC | **≥0.50**（放宽） |

即：**0.7 保留但只施加于硬维度**，软维度单列阈值。总分闸门仍可要求加权后 ≥0.7。

## 3. 模块设计

### 3.1 模块 1 · 任务生成（`taskgen/`）

#### 3.1.1 persona 库（D1 重做）

**与存量 scenario 的关系（正交，不混）**：

| | persona 库（新） | 存量 `scenarios.yaml` |
|---|---|---|
| 回答的问题 | **谁在问**（用户画像） | **被追问时怎么反应**（对话策略） |
| 作用位置 | 生成**首轮任务表述** | 驱动**后续轮次** |
| 复用方式 | 全新 | 只读复用 |

二者**交叉采样**：画像决定首轮怎么说，策略决定后续怎么被引导。
存量 98 个 `tasks.yaml` 提供**任务骨架**（片名 / 应找到的集数 / 必查字段 / 判分标准），
persona 只改**表述**，不改判分。

#### 3.1.2 PersonaProfile 六维度 + 2 标记

```python
class PersonaProfile(BaseModel):
    genre: Literal["动作","悬疑","科幻","喜剧","纪录片","动画","综艺","恐怖","爱情","战争"]
    popularity: Literal["头部","腰部","长尾","冷门"]          # 影响搜索词策略与站点命中预期
    urgency: Literal["立即","本周","闲时"]                    # 影响任务表述的直接程度
    verbal_style: Literal["书面","口语","强口语"]             # 含网络用语/错别字/省略主语
    persona_presence: Literal["无","轻","重"]                 # 背景故事强度
    task_specificity: Literal["指名","半指代","纯描述"]        # "XX 第二季第三集" vs "那个科幻的"

    has_standard: bool = True          # 70% True / 30% False（防"等标准才行动"）
    content_tier: Literal["A","B","C"] # 切片用：来源档位，供评估分层
```

**六维度为什么是这六个**——每条都对应一个可观察的语言特征，而不是凭空设的标签：

| 维度 | 影响的语言现象 | 对执行链的影响 |
|---|---|---|
| `genre` | 领域词汇（"科幻" vs "纪录片"） | 搜索词构造、站点类型预期 |
| `popularity` | 是否用站点名/别名/译名 | 头部站点直达 vs 长尾多站点遍历 |
| `urgency` | 催促语、"快点"、"今晚就看" | 首轮长度、单站点停留预算 |
| `verbal_style` | 句长、语气词、网络用语、错别字 | 表述生成长度与噪声容差 |
| `persona_presence` | 身份线索句（"我是给娃找的"） | 首轮附带信息量 |
| `task_specificity` | 指名 vs 指代 | 搜索查询构造难度 |

**`content_tier` 的来源纪律**：不得由 LLM 自评，必须来自任务骨架的客观属性
（如目标站点是否头部站点）。否则切片轴不可信。

#### 3.1.3 表述生成流水线

```text
任务骨架（存量,只读）× PersonaProfile × Scenario（存量,只读）
    → [70/30 判定 has_standard]
    → renderer.py：代码渲染可确定部分（片名槽位、是否附标准）
    → rewriter.py：LLM 按画像特征润色表述（只改表述，不改判分）
    → normalizer.py：代码归一到标准库（判分维度必须能还原）
    → TaskInstance{task_id, persona_id, scenario_id, prompt_text,
                   has_standard, provenance}
```

**铁律**：persona 与改写**只改表述不改判分标准**。判分维度（记录范围 / 必查字段）
从固定标准库枚举，`normalizer.py` 必须能把任意改写结果归一回去；归一失败即丢弃该改写，
退回骨架原文（原样作为首轮消息，不削弱请求）。

#### 3.1.4 画像档位标签

每条样本落 `provenance{persona_id, genre, popularity, urgency, verbal_style,
persona_presence, task_specificity, content_tier, scenario_id}`，
供评估按切片出分（"强口语 × 长尾" 这类组合的表现是否退化）。

### 3.2 模块 2 · 代码执行循环（`executor/`）

#### 控制流骨架

```python
# ── 阶段 0：构造查询 + 检索（代码执行，LLM 读结果）
query = build_query(persona, skeleton)      # persona 定表述风格，骨架定片名
search_page = await goto(f"https://www.bing.com/search?q={query}")
search_obs = await snapshot(search_page)

# ▸ LLM 判断点 ① SELECT_PLAY_SITES
cand = llm.decide(Q.SELECT_PLAY_SITES, obs=search_obs, target=skeleton.title)
#    → {selected:[{url,title,why}], rejected:[{url,reason}]}   ← rejected 也要落盘

for url in cand.selected:                    # 代码遍历，LLM 不决定顺序
    # ── 阶段 1：访问站点（代码执行 + 代码层预检）
    page = await goto(url)
    if not code_reachable(page):             # 状态码/超时/正文长度，零成本
        rec(negative, "unreachable_hard"); continue
    site_obs = await snapshot(page)

    # ▸ LLM 判断点 ② IS_REACHABLE
    if not llm.decide(Q.IS_REACHABLE, obs=site_obs).answer:
        rec(negative, "login_wall_or_blocked"); continue

    # ▸ LLM 判断点 ③ FIND_PLAY_CONTROL
    ctl = llm.decide(Q.FIND_PLAY_CONTROL, obs=site_obs)
    if not ctl.answer:   rec(negative, "no_play_control"); continue
    if ctl.trailer_only: rec(negative, "trailer_only");      continue

    # ── 阶段 2：进播放页（代码用 LLM 回传的 ref 点）
    player = await click(ctl.ref)             # ← ref 来自 LLM 输出，见下
    player_obs = await snapshot(player)
    media_count = await count("video, audio")  # 代码测得，不是 LLM 数的

    # ▸ LLM 判断点 ④ PLAYER_OK
    ok = llm.decide(Q.PLAYER_OK, obs=player_obs, media_count=media_count)
    if ok.answer is None: rec(unresolved, Q.PLAYER_OK); continue
    if not ok.answer:     rec(negative, "component_unverified"); continue

    rec(success, url, player_obs)            # 记录：代码，无 LLM
```

#### LLM 只有这四个位置（决策权全在代码）

| # | 判断题 | 输入 | 输出 | 代码拿它做什么 |
|---|---|---|---|---|
| ① | `SELECT_PLAY_SITES` | 搜索结果观察 + 目标片名 | **链接列表 + 选中/排除理由** | 决定遍历哪些站 |
| ② | `IS_REACHABLE` | 站点页观察 | 是否正常访问 | 跳过登录墙 / 地区限制 / 错误页 |
| ③ | `FIND_PLAY_CONTROL` | 站点页观察 | `{has_control, ref, trailer_only}` | **拿 ref 去点** |
| ④ | `PLAYER_OK` | 播放页观察 + **代码测的 media_count** | 是否正常播放、有无组件 | 成功 or 标记未验证 |

**每个判断点后面跟着的所有事——遍历谁、按什么顺序、点哪个、记什么、何时终止、
怎么切分、失败样本是否入池——全部是代码，LLM 无否决权。**

#### 三条不可省的 schema 约束

**① 判断点 ③ 必须回传 `ref`，不能只回布尔。**
obscura 的 `browser_interactive_elements` 提供稳定 ref（`e3` 形，导航前有效），
所以 ③ 的输出必须是 `{has_control, ref, ref_label, confidence}`。
**只让 LLM 回答"有按钮"，代码就得自己再猜一遍是哪个按钮**——等于退回规则匹配，
LLM 白做。

**② 判断点 ① 必须同时返回 `rejected` 及排除理由。**
LLM 筛选天然会漏，但**漏掉的候选本身就是负样本**（「这个结果不是该片的可观看站」
是一条有价值的训练信号，教模型别乱点）。不落盘这部分，负样本池会凭空少一大块。

**③ 确定性信号由代码算好再喂给 LLM。**
④ 的 `media_count` 由 `browser_count("video, audio")` 测得——
LLM 只需要判断语义（「有 video 标签但播放器显示加载失败」vs「正常」），
不需要从文本里数标签。同理 ② 的硬失败先由代码层拦掉。

#### `trailer_only` —— 唯一那条**不需要 LLM** 的业务规则

**规则**：播放按钮 / 剧集按钮上的文本是「预告片」→ 该站**没有正片播放资源**，
即使页面有播放控件也不算数。

这是**确定性可测的文本匹配**，不属语言任务——所以它在 `RulePerceptor` 里落地，
W1 即可执行，`confidence` 恒 1.0。LLM 版只作复核（词表覆盖不到的变体）。

判定链（代码，成本递增）：

```text
1. browser_interactive_elements → 取每个候选按钮的 ref + label
2. 精确/正则匹配词表 → 命中即 trailer_only（确定性，零 LLM）
3. 词表未覆盖但 label 含"预告"类词 → 标 trailer_suspect（入 unresolved，人工兜底）
4. 传给 LLM 的 ③ 结果里已过滤掉预告片按钮；LLM 只在剩余候选里找正片控件
```

**词表必须覆盖变体**（否则第 3 步会把大量正片按钮误杀）：

| 类别 | 示例 |
|---|---|
| 明确预告 | 预告片 / 正片预告 / 抢先看 / 预告 / 即将上映 / 上线倒计时 |
| 英文 | trailer / teaser / official trailer / first look |
| 诱饵 | 免费观看预告 / 抢先观看（点进去是预告） |
| **不可误杀** | 预告片·正片、预告与正片、含"预告"的正片按钮 → 须人工确认词表边界 |

⚠️ **误杀代价不对称**：把正片按钮判成预告片 = 丢掉一条成功样本；
把预告片判成正片 = 产出一条"点了预告片也算成功"的**脏数据**，会直接教坏模型。
所以词表宁可漏（走第 3 步 `trailer_suspect`）不可滥。

#### 失败分支全集（`branches.py` 的 `negative_branch` 注册表）

| 判断点 | 分支 id | 语义 | 是否需 LLM |
|---|---|---|---|
| ① | `not_play_site` | 搜索结果非该片可观看站 | ✅ |
| ② | `unreachable_hard` | 状态码/超时/空白页 | ❌ 代码判定 |
| ② | `login_wall_or_blocked` | 登录墙 / 地区限制 / 错误页 | ✅ |
| ③ | `no_play_control` | 无剧集也无播放控件 | ✅ |
| ③ | **`trailer_only`** | **只有预告片，无正片资源** | ❌ **代码判定（词表）** |
| ③ | `trailer_suspect` | 疑似预告但词表未覆盖 | ➖ 人工兜底 |
| ④ | `component_unverified` | 有 video 标签但播放器未正常加载 | ✅ |
| ④ | `unresolved` | 置信度不足且重采样耗尽 | ➖ 人工复核 |

**每条分支都必须有对应样本入库**——负样本不是副产品，是强制产出。

**全程存档**（`archive.py`）：动作、工具参数、观察原文。
观察是**真实回放**，不是 LLM 转述；这条一旦破，rationale 就没有锚。

**执行层（D7：obscura）**：

`browser/` 分三层——`page_driver.py`（协议，唯一稳定契约）、`mcp_client.py`（接入层）、
`obscura_driver.py`（实现）。

`PageDriver` 只暴露原子原语——`goto` / `snapshot` / `click` / `type` / `evaluate` /
`media_probe`——**不封装任何业务语义**。业务语义一律在 `steps/` 里，
这样驱动层没有可被 LLM 触及的决策面，也可以在不改动控制流的前提下换成别的浏览器。

#### obscura 接入路径：**定稿为 C（MCP，stdio）**

实机探针结果（`trajectory_pipeline/output/pipeline/obscura_tools.json`）：
**obscura-mcp 0.2.4，协议 2024-11-05，37 个 tool，会话式**。

| 路径 | 命令 | 会话状态 | 多步交互 | 结论 |
|---|---|---|---|---|
| **A `fetch` CLI** | `obscura fetch URL --dump links` | ❌ 每次全新实例 | ❌ | **已排除**，仅可作单页观察辅助 |
| **B `serve` + CDP** | `obscura serve --port 9222` | ✅ | ✅ | 备选（需引 Playwright/Puppeteer） |
| **C `mcp` server** | `obscura mcp --stealth`（stdio） | ✅ | ✅ | **✅ 定稿** |

选 C 的理由：会话式（`browser_close` 明确 "reset state"、支持 tab 管理）、
原子操作全覆盖、**不引入任何新依赖**、与 obscura 的构建方式解耦。
备用传输 `--http`（默认 3000 端口）留作将来多 worker 编排。

**为什么 A 不行**：`fetch` 每次重新加载页面、无会话状态。v2 的控制流是
「打开播放页 → 观察 → 判断 → 下一步」，一旦点击跳转就丢了会话；
硬要用 `--eval` 拼接多步 JS，等于把决策塞进字符串、且中途无法观察决策——
这恰好是 v2 要消灭的东西。

| `click(ref)` | `browser_click(ref\|selector)` | **会话式**，`isTrusted` 真实 |

#### 清单带来的四项设计变更

**① `Observation` 必须扩展 `interactive_elements`。**
`browser_interactive_elements` 返回可点击/可输入元素 + 稳定 ref，
于是「有没有播放按钮」**不再需要 LLM 去猜 URL/文本模式**——它直接是观察的结构化字段。
`RulePerceptor`（W1）的实现成本因此大幅下降，I1（evidence 可溯源）也更容易满足。

**② 代码断言层获得强援，70–80% 维度里很多不需要 LLM。**
`browser_extract(schema*)` 支持 `{field: css_selector}` 映射、`a@href` 属性语法、
`rows[]` 数组语法——名单匹配 / 字段完整性 / 列表完整性这类维度可直接确定性验证。
另有 `browser_count`（cheap existence probe）、`browser_search`（页内文本定位）、
`browser_network_requests` / `browser_console_messages`（组件加载失败的证据来源）。

**③ Cookie 红线（继承 CLAUDE.md）。**
obscura 37 个 tool 里含 `browser_get_cookies` / `browser_set_cookie` /
`browser_clear_cookies` / `browser_set_storage_state` / `browser_storage_state`
共 **5 个**（原方案只数到 3 个，实测清单为准）。
**v2 观测存档（P1）禁止落盘任何 cookie / storage state**——既有红线，新树继承。
落地方式不只是「不暴露」，而是在 `obscura_driver.py` 里写死
`FORBIDDEN_TOOLS` 常量 + `_assert_tool_allowed` 闸门，所有 tool 调用统一走
`_call`，故这是**唯一入口**。理由不是「暂时没需求」，是：一旦暴露，
将来某次「这个站要登录」的临时需求就会把 profile 写进要推给 Label Studio 的存档。
真撞登录墙时的正确做法是判 negative 并记 `login_wall_or_blocked`，不是绕过登录。

**④ `max_chars` 截断会伤害 I1（实体核查）。**
`browser_snapshot(max_chars)` 与 `browser_markdown(max_chars)` 均带截断。
大页面被截断后，rationale 引用的实体可能落在截断外 → 实体核查误判 `unsupported_entity`。
**截断长度与截断事实必须显式记录进 `Observation`**（不得默认截、不得静默截），
闸门据此判断「实体不在观察内」是幻觉还是「它其实被截掉了」。

**⑤ ⚠️ 实测推翻：正文根本进不来，CSS 抢光预算（2026-10-08）。**

原方案把 DOM 预处理当「优化项」。实测（`executor/browser/probe_observe.py`，
baidu 首页）显示它其实是**唯一可行的正文通道**：

```text
document.body.innerText                →   474 字符  纯正文，47ms
第一个 <style> 块                       → 16675 字符  CSS
browser_snapshot(max_chars=6000) 返回   →  6220 字符  其中【正文字符数为 0】
返回值末尾: ...(truncated, 256798 more chars)
```

`max_chars` 是**在截断前**算的，CSS 与正文抢同一个预算，6000 字符全被样式表吃掉。
LLM 看到的若是这样一份正文，它仍能编出一份像模像样的 rationale——
**这是静默失效，比报错更危险**。

三条实测结论，均已落进代码：

1. **换原语救不了**：`browser_markdown(max_chars=1200)` 同样返回 CSS
   （原方案「markdown 更 token-dense」是未实测的推测，作废）。markdown 只换了
   序列化格式，没有绕过 DOM 里的 `<style>` 节点。
2. **正文走 `innerText`**：`browser_evaluate("document.body.innerText")`，
   浏览器已渲染的文本，零 CSS。正文主来源由 `dom.parse_body_text` 承接。
   `browser_snapshot` 降级为 URL/Title 来源与诊断锚点——它两段式有用，
   因为 innerText **不返回 URL / Title**，而「点击后真实落到哪」只能靠 `URL:` 行读回。
3. **剥离逻辑必须处理未闭合块**：obscura 的 `max_chars` 在 CSS 块**中间**硬截断，
   `</style>` 根本没回来（实测 baidu 首页 `</style>` 计数为 0）。
   配对式正则 `<style>…</style>` 必然失配，CSS 全裸进正文。
   改用「配对优先，失配则截到下一个 `<`」。

另外两处同源的 label 污染（都直接落在判断点 ③「找播放按钮」的输入上）：

- `browser_interactive_elements` 的 label 列格式是 `"文本" 属性="值"`，
  实测 baidu 首页 **20/75** 的行带属性。早期用 `strip('"')` 会解成
  `登录" name="tj_login` —— 标签里混着 DOM 属性会把判断带偏。
  已改为按 JSON 规则找配对闭引号。
- label 里会混进 `<style>` 的 CSS（textarea 的 value 就是样式表，实测 6/75），
  以及**图标字体的私有区字符**（`U+E000–U+F8FF`，实测 ``/``）——
  JSON 转义后的 `""` 字样会**主动误导** LLM 去找这个实体，故在
  字符清洗里剥掉 PUA 区。

由此新增 `Observation.body_source` 字段（`"inner_text"` / `"snapshot"`）：
它是**可审计字段**而非实现细节——`"snapshot"` 意味着正文是被 CSS 抢过预算的残骸，
落在它上面的语义判定可信度更低，人工复核 P1 存档时先看这一列。

**⑥ ⚠️ 首次真实端到端推翻的五条（2026-10-08，`run --task-id T001 --title 功夫`）**

方案层写完、代码跑通、离线测试全绿之后，第一次拿 5 个真实候选站点
（hao123 / 爱奇艺 / 西瓜 / 搜狐 / 优酷）跑完整条链，暴露出五条**只能靠实测发现**的问题。
它们的共同形态是：**代码在正常执行、结论在正常产出，只是结论是假的**——
不报错、不崩，只是素材池里悄悄多出看起来很合理的条目。

| # | 问题 | 实测证据 | 修法 |
|---|---|---|---|
| ⑥.1 | **fail-closed 被读成「拿不到结论就停」** | `IS_REACHABLE` 在链首，W1 只会返回 `None`。据此中断 → **5 站全部落 `unresolved`**，W1 验收要的「负样本池非空」一条都产不出来 | `None` **不中断，继续采集**；只有 `False` 才中断。**fail-closed 管的是「结论」不是「采集」**——继续走不等于断言可达，最终分支仍按「有没有拿到确定性结论」定 |
| ⑥.2 | **采集失败伪装成业务结论** | iqiyi / ixigua / sohu 三站 `body_len=0` + `interactive_elements=0`，被判 `no_play_control` 写进负样本池。实际是 JS 页未渲染完 | `Observation.degraded` + `body_text` 记账（见变更⑤）；**采到 0 个元素 → `answer=None`**，obscura 的空页哨兵 `No interactive elements on this page.` 是正常返回不是错误，`degraded` 抓不到 |
| ⑥.3 | **中文单字词表被日常用语击穿** | `EPISODE_KEYWORDS = ("集","话","期","章","回")` 命中 hao123 首页的「星**期**四」→ 整条链走进导航站 | 换成**带结构的正则**（`第\s*\d+\s*[集话期章回]` / `\bEP?\s?\d{1,3}\b` / `\bS\d{1,2}E\d{1,3}\b` / `正片\|全\s*\d+\s*集\|连载至`）。这五个字在日常用语里密度高到毫无区分度 |
| ⑥.4 | **iframe 数量不是播放器判据** | hao123（纯导航站）`iframe=15` → `PLAYER_OK=True` → 假阳性成功样本 | 只认 `<video>`/`<audio>`；有 iframe 无 video 时返 `None`。iframe 可能是广告/埋点/地图/天气，**数量与「是不是播放器」无关**。代价是优酷（video=0 iframe=1）变 `unresolved`——这是对的，W1 判不出就该说判不出 |
| ⑥.5 | **失败分支表里有一条不可达的分支** | `trailer_suspect` 全程 0 次出现。原因：`trailer_suspect` 的判断**嵌在 `if trailer_only:` 里面**，而感知层发的是 `trailer_only = not suspects`——两者互斥，那条分支永远走不到。疑似预告掉进「answer=True 但无 ref」被记成 `component_unverified`，一条**货真价实的假负样本** | 两个判断**并列**，suspect 优先 |

另有一条**观察与结论自相矛盾**的情况，靠证据文本抓出来的：
搜狐 `title=「功夫 - 搜狐视频」`、`video_tag_count=1`、200 个元素无一命中词表，
被记成 `no_play_control`——但页面自带 `<video>`，「没有播放控件」这句话与观察直接矛盾。
负样本池的全部价值是「这里真的看不了」，混进「能看但没认出来」会直接毁掉它。
现在 `video_tag_count >= 1` 时一律返 `None`（「按钮没认出来」，不是「没有控件」）。

**这五条的共性值得单独记住**：它们全部是**离线测试测不出来**的——
测试的 fixture 是我们自己造的观察，于是规则和 fixture 一起错，测试照样绿。
只有把真实站点喂进去、然后**逐条打开存档读 evidence**，才会看见「结论」和「证据」在打架。
所以每次真实运行后都读一遍存档逐站点核对，是这套流程的固定动作，不是可选项。

| # | 发现 | 实测证据 | 处置 |

| ⑦.1 | **存量 98 个 task 不是同一种任务** | 能提《片名》的 81 个；`周星驰执导的所有电影`/`历届最佳影片`/`豆瓣Top250` 共 15 个是**集合型**；`找一部高分国产电影` 2 个是**片名未知型** | 检索模式三分（`single_title` / `aggregate` / `unknown_title`）。后两类**不在 W1 范围内**——W1 成功判据是"找到一个可播放站点页"，拿去评"找一个集合"会把不完整输出记成成功，**判分标准与判据不匹配比跑不了更糟** |
| ⑦.2 | **渲染源与约束推导源必须同源** | 首版按 `intent.goal` 渲染、却按 `initial_request` 推导约束。T001 的 `goal` 比 `initial_request` **少一个「全集」** → 探针必然判失败 → 实测接受率 4%、12 条采样里 9 条退回原文，**persona 特征全部失效而表象只是"通过率偏低"** | 统一用 `initial_request`（它才是首轮消息的来源）。`goal` 只作元数据 |
| ⑦.3 | **约束推导的检测词与探针词不得是两套** | 检测写 `("集数","季数",…)`、探针多一个「全集」，于是最典型的 T001 反而不含 `has_episode_range`，检查形同虚设 | 检测与检查**共用 `CONSTRAINT_PROBES` 一份词表**。两套词不同源 = 推导与检查互相打架且无任何报错 |
| ⑦.4 | **约束只按"用户说没说过"推导，不按判分标准** | `min_results=5` 推出 `has_count`，而用户表述写的是「找到…的可播放网址」（单数），**从没说要 5 个** → 每条都被判丢失，接受率仍只有 4% | 全部从表述文本反查。判分标准里的条数约束由骨架原文承载，不走探针 |
| ⑦.5 | **persona 只能改「用户怎么说」，改不了「用户要什么」** | `OPENERS` 写成 `我想找{genre}，{goal}` → 产出「我想先确认电影**类似《功夫》那样的动作片**的**版权方**…」——骨架要的是版权方，与"动作片"无关，**persona 的品类偏好被冒充成了用户需求**。且 opener 若带主语会拼出「有点想看，**我想**找…」的病句 | `genre` 按 §3.1.2 的原定义落到**检索侧**，不进表述；opener 模板不带主语。persona 未生效的维度**显式记进 provenance**，好让人区分"有意不做"与"忘了做" |
| ⑦.6 | **半指代在 W1 表达不出来** | 半指代 = "说得出品类线索、说不出片名"，线索必须**来自骨架**；查表渲染器读不懂骨架，唯一能拿的参照物就是片名——那等于半指名 | 半指代**降级为指名**并把原因落 provenance；纯描述 × 单片任务**整条排除**（逻辑不可能：说不出片名却要求找到那一部）。**W1 的实际表达力只有指名一档**，是能力边界不是缺陷 |
| ⑦.7 | **复核回填不能覆盖真负样本** | `verdicts` 只由 `unresolved`/`trailer_suspect` 导出，但文件可能混入真负样本的 url（手填 / 跨批次粘贴 / 对着旧队列编辑新存档）。无差别回填时一次误填就把 `no_play_control` 改成成功——**负样本池的完整性就此静默毁掉**（分支分布只显示"成功 +1、负样本 −1"，看不出那条从哪来） | `apply_verdicts` 只对 `REVIEW_BRANCHES` 内的分支生效，其余计入 `ignored` 原样保留，CLI 显式告警 |

**⑦.2 / ⑦.3 / ⑦.4 三条的共性值得单独记住**：它们全都在离线测试
**全绿**的状态下被发现，因为症状（"归一通过率 4%"）与病因（两处数据源
不同源）隔着三层。**症状与病因不同源时，调症状那一侧（放宽探针 / 调阈值）
必然把纪律静默拆掉**——所以 `check-persona` 把「覆盖度体检」与
「探针体检」分开报：前者答"切片轴撑不撑得起结论"，后者答"渲染有没有丢要求"，
合成一个数字的话，"探针 100% 通过"会被读成"画像库健康"。

| # | 发现 | 处置 |
|---|---|---|
| ⑨.1 | **交接面是文件格式，不是 import** | `plan.py` **不 import taskgen**，只按 JSON 读。理由不止于整洁：plan 是要长期存着的，切片分析、失败归因、半年后回看读的都是那个文件。若消费端 import 生成端，则「能读这份文件」=「生成端还在原地」，生成端一改字段旧计划全废。**按格式读，格式就冻住了** |
| ⑨.2 | **provenance 必须一路进 P1 存档** | `RunRecord` 加 `provenance` 字段。否则 persona 六维只活在计划文件里，切片就变成"计划 ↔ 存档"的一份**人工对表**——而对表错位（存档重跑、计划重生成）是**静默的**。空 `dict` 的含义固定为「不是 taskgen 跑的」，与「taskgen 没生效」严格区分 |
| ⑨.3 | **跳过必须计数，且计数不能说谎** | 三类跳过（模式不匹配 / 检索式为空 / 归一未过）全部记账打印。实测把 `excluded_by_skeleton_mode` 的语义修正了：它原先填的是**全库 mode 分布**，于是 `--all-modes` 下报「98 次因骨架模式排除」，而那次采样**一个都没排除**。现已拆成 `excluded_by_skeleton_mode`（真排除）+ `mode_distribution`（库属性，无条件）。**计数说谎比不计数更坏**——读的人会以为真排掉了 98 个 |

接线顺带暴露的三个**渲染缺陷**——它们都不属于任何一条判分要求，
所以**判分保真探针一条都抓不到**，且只在端到端真读一遍表述时才浮现：

| # | 缺陷 | 实测形态 | 处置 |
|---|---|---|---|
| ⑨.4 | **片段拼接缺分隔** | 存量 `initial_request` 大多不以标点结尾，closer 直接粘上去：「做版本对比**慢慢找也没关系**」「对比表格**这周内给我就行**」。16 条抽样里 14 条如此 | `_join_closer()`：closer 前无标点则补「，」 |
| ⑨.5 | **句尾语气词另起一句** | closer 以「。」收尾、tail 自带句号，拼成「…两天给我就行**。啊。**」——两个句子边界 | `_join_tail()`：剥掉 closer 尾部标点，让 tail 落在**句内** |
| ⑨.6 | **tail 与 closer 粘成词组** | 强口语档原写的「求求了真的。」「拜托哈，越快越好。」本是独立句子，接在 closer 后成「今晚要看**求求了真的**」 | 改词表为可句尾接续的写法，并加**可执行契约**：`VERBAL_TAILS` 每条必须以语气词（啊/呀/呢/吧/嘛/哦/噢）起头——旧词表一条都过不了 |

> **⑨.4–⑨.6 的共性值得单独记住**：判分保真探针的**探针词只覆盖判分要求**，
> 而句法通顺、措辞自洽、语义不打架**全都不在判分要求里**。
> 探针全绿 ≠ 话是人话。判分保真与表达质量是**两件事**，
> 前者可自动验证，后者目前**只能靠真读**——这正是 §8 计划里
> "人工复核" 要覆盖的第二个维度（第一个是正样本的分支判定）。

三个决定性细节：

1. **判定只看 URL 与标题，不看正文。** 百度验证码页正文是「网络不给力，请稍后重试」——**那句话字面是网络错误**，在验证码页上只是模板文案。拿它当判据会把真网络故障误判成反爬，**正好与目的相反**（网络故障 → 重试；反爬 → 换引擎/加间隔）。这条专门有测试守着。
2. **判定逻辑必须在使用点，不在采集层。** 早一个版本把 `detect_block` 放进 driver 并落成 `Observation.blocked_reason` 字段，于是 `FakeDriver` 构造的观察带不上该字段，「被拦」与「没拦」在测试与真实路径上行为不一致——**判定逻辑与使用点分了家**，与 ⑦.2/⑦.3 是同一种病。
3. **缺字段 ≠ 空值。** 存量存档没有 `search_blocked`，若 `report` 直接 `.get(...) or ""`，那些**恰恰最不该算作可跑**的存档会被算成可跑。存档里的观察数据都在，用同一个 `detect_block` 确定性重算并**标注「存量存档重算」**。

> 附带修掉一个**新修复自己引入**的统计问题：被拦截的 task 混进了
> persona 切片，`0/1` 会被读成「这个 persona 组合表现差」，
> 而真相是「这三条压根没跑」。切片表的说服力会被这种行毁掉，
> 所以切片只含**实际跑过**的 task，且行数变化时明说排除了几个。

### 3.3 模块 3 · 语义感知（`perception/`）— 可替换插件

> **完整规格见 [01-模块3-可替换感知层.md](01-模块3-可替换感知层.md)**，此处只给骨架。

全树最关键的接口。**接口一次定死，实现分两期替换**：

```python
# perception/base.py
@dataclass(frozen=True)
class Observation:
    url: str
    page_title: str
    buttons: tuple[str, ...]
    links: tuple[LinkItem, ...]
    video_tag_count: int
    iframe_count: int
    text_snippet: str

@dataclass(frozen=True)
class Decision:
    question: str          # 判断题 id
    answer: bool
    confidence: float      # [0,1]
    evidence: str          # 依据（必须来自 Observation）
    source: Literal["rule", "llm", "model"]

class Perceptor(Protocol):
    def decide(self, q: Question, obs: Observation) -> Decision: ...
```

| | W1 `RulePerceptor` | W3 `LLMPerceptor` | 未来 `ModelPerceptor` |
|---|---|---|---|
| 实现 | URL 特征、video 标签计数、按钮文本正则 | LLM + 结构化 schema（**混合体**，见 3.3.1） | 训练好的小分类器 |
| 置信度 | 固定 1.0（规则确定） | **未校准先验 `CONFIDENCE_JUDGED=0.8`，非模型自报** | 模型概率 |
| 置信度不足 | N/A | 重采样 2–3 次 → 人工兜底标记 | 概率阈值 |

**输入是 DOM 预处理后的结构化观察，不是原始 HTML**（去噪前移到 `executor/dom.py`）。
**输出必须是 schema**，供代码分支——LLM 是传感器不是驾驶员。

> ⚠️ 已知坑（来自存量教训）：本项目 LLM 后端**不强制 json_schema**，模型会漂字段名、
> 套 think、首轮跑偏。`llm/schema_parse.py` 必须自带**别名容错 + 重试 + fail-soft**，
> 且接入时用真实端点验一次。

### 3.3.1 W3 落地：混合体，不是纯 LLM

⚠️ **本节是实现后的增补，规格文档（01 号）未含**。设计时把「W3 = LLM 版」
写得太干净，接入后才发现三条缺一不可的落法——每条都是实测或变异测试逼出来的。

「LLM 是传感器不是驾驶员」在代码里是三条可检查的约束，缺一条就会把**采集故障
写成业务结论**：

| # | 落法 | 不做会怎样 |
|---|---|---|
| 1 | **确定性事实优先**——`video_tag_count` / iframe 计数等代码事实**不问模型**；预告片词表是**业务规则**，模型不知道也不该猜，只在模型选中某 ref 时用它**复核** | 让模型判 `<video>` 存在性，等于把可确定的答案变 probabilistic，且漂移不可测 |
| 2 | **采集充分性在代码层预检**（`_sufficiency`），且**必须在问模型之前** | **模型不会替你 fail-closed。** 实测 iqiyi 播放页 `video=1` 被判「否」，模型的分析是「`body_text` 为空、`interactive_elements` 为空，说明未渲染」——它把**采集失败**讲成了一条通顺的错结论。规则版本就防住这条（哨兵返回分不清「没渲染完」与「确实为空」），换 LLM 就丢了那层保护，而那恰恰是最需要它的地方 |
| 3 | **ref 白名单校验**——模型回传的 ref 必须真的存在于 `obs.interactive_elements` | 模型会编 ref（会话内句柄看着就像可生成的字符串），而代码拿它去 click，**点错不可逆** |

其余三条工程约束：

- **不采信模型自报的 confidence**（本项目后端自报普遍虚高）。给未校准先验
  `CONFIDENCE_JUDGED = 0.8`，`evidence` 里写明「非模型自报」；拿到标注集后按题校准，
  在那之前不得用于阈值判断。
- **灰度只在构造期**（`factory.build_perceptor`），不做运行期切换。运行期切换会让
  `Decision.source` 分不清「LLM 判的」与「LLM 挂了所以规则版顶上来的」，而后者不是
  fail-closed，是拿不确定的输入驱动确定的输出。要对比两条链就跑两批——`RunRecord.perceptor`
  已经把两者分开记。
- **凭据只走环境变量**（`TRAJECTORY_LLM_*`，刻意带前缀不与 v1 的 `LLM_*` 撞名），
  缺失即报错不猜；`LLMConfig.__repr__` 不吐 key，契约测试盯着源码不许出现凭据字面量。

### 3.4 模块 4 · rationale 边写边生成（`rationale/`）

**时机**：每步动作 + 真实观察到位后**立刻**生成，不等全流程结束（D2/D3）。

Prompt 四要素：

1. **信息边界声明**——只依据给定观察，不得引入外部知识
2. **前因后果链**——任务 + 前几步摘要 + 本步动作/观察
3. **认知角色**——写「当时的思考」，不是事后复盘
4. **格式长度约束**——1–3 句，禁套话

**允许表达不确定，禁止编造确定。**

**一致性闸门三查**（`gates.py`）：

| 查 | 手段 | 不通过处置 |
|---|---|---|
| 实体核查 | 抽 rationale 中的 URL / 引号片段 / 标题 token，与本步及前置步 `Observation` 求交；命中集合外 → `unsupported_entity` | 重生成 1 次，仍失败 → 样本标 `gate_failed`，**入库但不进训练集** |
| 因果核查 | rationale 提到的动作名 == 本步实际动作；理由须支持该动作 | 重生成 1 次 → 同上 |
| 时序核查 | rationale 不得含后续步才出现的实体（按步序索引比对） | 同上 |

实体核查纯代码、零成本，是三查里唯一 100% 覆盖的，其余两查为规则近似。

**D3 的直接后果**：闸门不过**没有**合成后兜底路径。样本带 `gate_failed` 标记落
负样本池与人工抽检队列，而不是被悄悄修好。

### 3.5 模块 5 · 组装与切分（`assembler/`）

样本六件套：系统提示词 / 工具参数列表 / 任务提示词（含 provenance）/ 动作+参数 / 观察 / 思考+结论。

**切分粒度：单站点验证、单搜索任务各自独立成条**，不压成长轨迹。
理由：多样性↑、训练信号密度↑、单条失效率↓。

> **落地时的口径修订（2026-10-09）**：本节早期还出现过「前几步走摘要」
> 的措辞，与「各自独立成条」互相矛盾。实现取**一个决策单元 = 一条**：
> 搜索阶段一条（``unit="search"``），每个访问过的站点一条（``unit="site-N"``）。
> 一次 run 因此产出 1 + N 条。这样定义唯一确定，且不把「选哪个站」与
> 「这个站行不行」压进同一次预测里。
>
> **被反爬拦截的 run 产出零条**：拦截发生在取候选之前，搜索阶段的观察是
> 验证码页，切成「模型该怎么做」的样本只会教它对着验证码页编答案。这与
> §控制流「反爬单开字段、不进分支体系」是同一条纪律的延续。

**读 P1 按文件格式，不 import `executor`**（与 §模块 1「plan 不 import taskgen」
同一条纪律：交接面是格式，不是 import）。理由是 **P1 贵、P2 便宜**——重建一批
P2 必须独立于 `executor` 的**当前版本**，否则改一个 dataclass 字段就让半年前
那批 P1 切不出样本，而重建不出来的那批是永久损失。由
`tests/contract/test_p2_contract.py::TestNoExecutorImport` 以 AST 强制。

**训练动作空间在 assembler 侧冻结**（`schema.TOOL_SPECS`）：既不从 P1 的
`steps[]` 反推（反推会让每条样本各带各的动作空间，模型看到的世界随样本变），
也不从 `executor.actions.TOOLS` import（那就违背上一条）。折中是**本模块声明、
契约测试用 AST 读那个字面量来查漂移**。

**缺件必须看得见**：闸门取三值 `passed` / `failed` / `not_run`。模块 4 未落地时
一律 `not_run`——把「没跑」渲染成「通过」会让批次上线时看起来像过了闸，
而它根本没被检查过。老存档缺的键（`steps` / `user_prompt` / 全文正文）逐条记进
`degraded_from`，不与新样本混用。

**训练态观察是 P1 观察的裁剪视图，不是另一份证据**：裁剪项逐条写进 `limits`，
上游 `truncated` 与本层裁剪分列（`truncated.source` / `truncated.view`），
`degraded` 原样透传。渲染器**永不补内容**——观察里没有的，渲染后还是没有。

达标样本 git 版本化冻结，黄金集与训练集**不同目录命名空间**。

## 5. 评估体系（模块 6）

### 5.1 三层瀑布

| 层 | 维度 | 覆盖 | 上岗条件 |
|---|---|---|---|
| **代码断言** | URL 可达、schema 校验、名单匹配、字段完整性、时序 | 70–80% 维度 / 全量 | **vs 黄金集一致率 ≥90%**（D10 = 口径 C） |
| **LLM 裁判** | rationale 吻合度、内容相关性 | 15–25% 维度 / 全量或抽样 | vs 黄金集 ≥85%，逐维度领证；rubric 带禁足条款 |
| **人工** | 分歧仲裁、模糊案例、抽检、黄金集维护 | 5–10% / 抽样 | **永久保留** |

### 5.2 黄金集规格与一致性测量（D9）

- 100–200 条起步
- 切块：校准集 60–70% / 持有集 30–40%，**差距 ≤5pp**
- 版本化冻结；持有集只跑一次，差距 >5pp 即回调

**锚点来源（D5 的后果）**：「两次失败训练的真实轨迹」缺席，首版锚点换源为
① **真实首轮轨迹**（P1/P2 产出）+ ② **人工构造的已知失败样本**（每个失败模式至少 3 条，
直接从 `negative.jsonl` 挑真实分支，**不虚构**）。真实分支样本本来就是 v2 的强制产出，
比虚构的「失败训练」更干净。

**一致性测量（一人，D9）**：

```text
单人评分者 → 间隔 T（建议 14 天）→ 重测 20–30% 子集
    → 硬维度：Cohen's kappa ≥0.7
    → 软维度：加权 kappa / ICC ≥0.50
    → 总闸门：加权后 ≥0.7
```

**必须记录的三条边界**（否则这个数字会被误读）：

1. 这是 **test-retest 自相关**，不是评分者间一致性；对外汇报必须写明，
   否则会被当成"标注员之间的一致度"。
2. 间隔 T 太短（当天打两遍）会把记忆效应算进一致性，虚高；太长会混入标准漂移。
   14 天是折中，**必须固定并记录每轮的实际间隔**。
3. 一人的系统性偏差无法被该指标发现——测不出"这个人整体偏严"，
   只能测出"这个人稳不稳"。治法靠 §5.4 的仲裁层与 rubric 的 5 档锚定描述，
   不靠这个数字。

### 5.3 「代码层一致率 ≥90%」的四个候选分母（D10 待定）

| 口径 | 定义 | 分母 | 测的是 | 问题 |
|---|---|---|---|---|
| **A 断言项通过率**（micro） | 通过的代码断言数 / 全部断言数 | 断言项总数 | 数据本身合不合规 | **被易通过断言稀释**——90% 可以由一堆 URL 可达撑出来 |
| **B 轨迹级通过率**（macro） | 必选断言全过的轨迹 / 总轨迹 | 轨迹数 | 有多少条数据可直接用 | 更像"数据健康度"而非"评估器可信度" |
| **C 与黄金集标签一致率** | 代码判定 == 黄金集人工标签的样本 / 黄金集样本 | 黄金集样本数 | **代码层能否替代人工做仲裁** | 依赖黄金集质量；黄金集有偏则指标有偏 |
| **D 分支路由准确率** | 控制流所选分支 == 黄金集分支标签的样本 / 分支样本数 | 进入分支判定的样本数 | v2 核心创新（分支强制入库）的路由质量 | 是 C 在分支维度的特化 |

**已定稿：D10 = C**（与黄金集标签一致率，分母 = 黄金集样本数）。
理由：代码层的存在意义是"顶替人工仲裁"，C 直接测这个。

A/B 是数据健康度指标，不作主指标；D 是 C 在分支维度的下钻，**建议一并上报**
（分母切换点是「进入分支判定的样本」）。

**若上 D，必须配 F1 而非准确率**——分支判定天然不平衡（负样本远多于成功样本），
单看准确率会被多数类主导，精确率/召回率必须分开报。

> C 的已知软肋：**黄金集有偏则指标有偏**。因此 §5.2 的黄金集来源纪律
> （真实首轮轨迹 + 真实负样本分支，不虚构）不是可选项，而是 C 能成立的前提。

### 5.4 Rubric 规范

每维度六要素：维度名 / 定义 / 5 档锚定描述（可观察行为 + 阈值）/ 正反例（取自真实
`negative.jsonl`）/ 边界规则 / 权重（默认等权）。

维度清单直接来自失败模式库：工具调用正确性、观测-动作一致性、记录判断正确性、幻觉率、完整性。

自检三问：外行能独立打一致分？档位边界不吵架？案例唯一落档？

### 5.5 Label Studio 双向化（D6）

现状是**单向终点**（推送 C3 + 评分卡，不回流）。双向化需在 `evaluation/ls_bridge/`
新建回流通道，并处理以下**存量已踩过的坑**：

| 坑（存量实证） | 双向化后的处置 |
|---|---|
| LS 1.23 **无原生去重**（`inner_id` 是整数、批量 import 静默丢弃） | 沿用本地台账模式：`output/pipeline/ls/push_index__<project_id>.jsonl`，扩展 `last_annotation_updated_at` 用于增量拉取与冲突检测 |
| 每次 upload **PATCH label_config 会覆盖标注员改动** | 双向后**禁全量 PATCH**；结构性变更须人工确认后再发 |
| `editable="true"` → annotation 是**标注员修正稿** | 回流目标**只限黄金集/评估集**；训练制品 P3 永不被 annotation 覆盖 |
| `validate/` 绿灯**不算数**，只有标注页算数 | 通道验收以标注页实视为准，不用 validate 结果当证据 |
| R11 凭据扫描 fail-closed | 原样保留，双向不豁免 |
| `risk_hints` 是预标注唯一落点、不可换 | 保留 |

**冲突策略**：LS annotation = 人工真值，覆盖黄金集标签；
分歧样本 → `arbitration.py` → 评分器错则修评分器，标准漏洞则补指南 + 扩黄金集。
