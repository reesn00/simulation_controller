## 1. 为什么必须是插件（四个理由，缺一不可）

| # | 理由 | 若不插件化会怎样 |
|---|---|---|
| **R1 里程碑可行性** | W1 要跑素材、W3 才上 LLM（总体方案 §6 的依赖倒置修正） | W1 等 W3，或 W3 上线时推翻 W1 的执行器——W1 的几百条素材全部作废 |
| **R2 置信度可比性** | 规则版与 LLM 版必须能在**同一批 Observation** 上并行判定，才能测分歧率 | 无法回答"LLM 到底比规则好在哪"，只能凭感觉切 |
| **R3 fail-closed 兜底** | LLM 超时 / 解析失败时回退规则版并**计数上报** | 静默降级：链看起来正常，质量悄悄掉，没人知道 |
| **R4 长期演进** | 未来可能换训练好的小分类器（`ModelPerceptor`），或换不同 LLM 后端 | 每换一次实现就动一次 `executor` 控制流——控制流是 v2 的心脏，不能被替换实现污染 |

**R1 是硬约束**：插件化不是为了架构优雅，是为了 W1 能在没有 LLM 的情况下先跑出素材。

## 2. 插件契约

### 2.1 值对象（`perception/base.py`）

```python
from dataclasses import dataclass
from typing import Protocol, Literal, Sequence

@dataclass(frozen=True, slots=True)
class LinkItem:
    text: str
    href: str

@dataclass(frozen=True, slots=True)
class Observation:
    """DOM 预处理后的结构化观察——perception 层的唯一输入。

    不变式：
      - 必须可 JSON 序列化（存档 + 契约测试共用同一份语料）
      - 不含任何页面句柄（perception 无权触网）
      - 字段全部为「已清洗」内容，不含原始 HTML
    """
    url: str
    page_title: str
    buttons: tuple[str, ...]
    links: tuple[LinkItem, ...]
    video_tag_count: int
    iframe_count: int
    text_snippet: str

@dataclass(frozen=True, slots=True)
class Decision:
    question: str
    answer: bool | None            # None = unresolved（见 §5.3）
    confidence: float              # [0,1]，语义随 source 而变，见 §4
    evidence: str                  # 依据，出处必须能在 obs 中找到
    source: Literal["rule", "llm", "model"]
    payload: Mapping[str, Any] = field(default_factory=dict)
    #   answer_type="bool" 的题 → 空
    #   answer_type="decision" 的题 → 该题 schema_hint 的全部字段：
    #     ① selected[] / rejected[]
    #     ③ has_control / ref / ref_label / trailer_only
    #   代码直接消费 payload（如 click(payload["ref"])），不经二次解析。
    latency_ms: int = 0
    fallback_used: bool = False    # 本次判定是否走了降级路径（R3）
```

**为什么 `Observation` 不给原始 HTML**：LLM 感知层的输入体积必须可控、噪声必须前移清理。
这既是成本考虑，也是 v2「生成时即干净」的必然要求。

### 2.2 判断题（`perception/questions.py`）

每类判断是一个 `Question`，注册进全局注册表。**`decision` 类型让部分题目能回传
定位与细分标记**——判断点 ③ 若只回布尔，代码就得自己再猜点哪个按钮（见 00 方案 §3.2）。

```python
@dataclass(frozen=True, slots=True)
class Question:
    id: str                        # "site.find_play_control"
    prompt: str                    # LLM 提示词模板（rule 版不用）
    answer_type: Literal["bool", "decision"]  # decision = 除布尔外还回传结构化字段
    schema_hint: dict              # 期望返回结构，供 llm_perceptor 做别名容错
    confidence_threshold: float    # 低于此值 → 重采样 → unresolved
    evidence_required: bool = True # evidence 必填且必须可溯源到 obs
    negative_branch: str | None    # answer=False 时归入的负样本分支 id
    needs_llm: bool = True         # False = 该题 W1 即由规则确定性判定
    prompt_schema_version: str = "v1"   # 换提示词即升版本，便于回溯

# 内置四题（对应总体方案 §3.2 的四处判断）
QUESTIONS = {
    "select.play_sites": Question(
        id="select.play_sites", answer_type="decision", prompt=...,
        # 必须同时返回未选中的条目及排除理由——那部分本身就是负样本
        schema_hint={"selected": [{"url": str, "title": str, "why": str}],
                     "rejected": [{"url": str, "reason": str}],
                     "confidence": float, "evidence": str},
        confidence_threshold=0.7, negative_branch="not_play_site"),

    "site.is_reachable": Question(
        id="site.is_reachable", answer_type="bool", prompt=...,
        schema_hint={"is_reachable": bool, "confidence": float, "evidence": str},
        confidence_threshold=0.7, negative_branch="login_wall_or_blocked"),

    "site.find_play_control": Question(
        id="site.find_play_control", answer_type="decision", prompt=...,
        # ref 必回传：obscura 的 browser_interactive_elements 给稳定 ref
        schema_hint={"has_control": bool, "ref": str, "ref_label": str,
                     "trailer_only": bool,          # 代码词表预过滤后通常已 false
                     "confidence": float, "evidence": str},
        confidence_threshold=0.7, negative_branch="no_play_control"),

    "player.ok": Question(
        id="player.ok", answer_type="bool", prompt=...,
        # media_count 由 browser_count 测得后传入，LLM 只判语义不数标签
        schema_hint={"is_playing": bool, "confidence": float, "evidence": str},
        confidence_threshold=0.7, negative_branch="component_unverified"),
}

class Q:
    """注册表的属性访问简写：``Q.PLAYER_OK`` → ``QUESTIONS["player.ok"]``。

    纯字符串常量，不做查找——查找发生在 ``decide()`` 内部，
    拼错 id 时由注册表 KeyError 暴露，而不是静默取到 None。
    """
    SELECT_PLAY_SITES  = "select.play_sites"
    IS_REACHABLE       = "site.is_reachable"
    FIND_PLAY_CONTROL  = "site.find_play_control"
    PLAYER_OK          = "player.ok"
```

#### `needs_llm=False` 的题：`trailer_only`

「按钮文本是预告片 → 无正片资源」是**确定性文本匹配**，不属语言任务，
所以它不进 LLM 题目表，而是 `executor/steps/` 里的词表规则，在喂给 ③ 之前
就把预告片按钮滤掉：

```text
browser_interactive_elements → 逐个 label 匹配词表
    ├─ 命中「预告片/trailer/抢先看」类 → 该控件排除，标 trailer_only
    ├─ 含「预告」但不在词表边界内    → 标 trailer_suspect（走 unresolved，人工兜底）
    └─ 其余候选 → 才交给 LLM ③ 找正片控件
```

⚠️ 误杀代价不对称：把正片按钮判成预告片 = 丢一条成功样本（可接受）；
把预告片判成正片 = 产出一条「点预告片也算成功」的**脏数据，会直接教坏模型**。
所以词表宁可漏（走 `trailer_suspect`）不可滥。词表变体与边界见 00 方案 §3.2。

**`negative_branch` 是关键字段**：它把「判断题」与「负样本池」显式绑定。
每个 `Question` 都必须回答「我判 false 时，这条样本归到哪个失败分支」——
这从类型层面堵死了「失败分支静默消失」的可能（D11 式保护）。

新增判断题 = 新增一条 `Question` + 一个分支，**不改 `executor` 控制流**。

### 2.3 协议（`Perceptor`）

```python
class Perceptor(Protocol):
    name: str
    def decide(self, q: Question, obs: Observation) -> Decision: ...

    # 契约测试用：实现者必须自证满足不变式
    def health_check(self) -> "PerceptorHealth": ...
```

实现由 `factory.py` 注入：

```python
def build_perceptor(name: Literal["rule", "llm", "model"], **cfg) -> Perceptor: ...
```

## 3. 不变式（所有实现必须满足，契约测试强制）

| ID | 不变式 | 校验方式 | 违反后果 |
|---|---|---|---|
| **I1** | `evidence` 中的实词必须能在 `obs` 中找到出处 | token ⊆ observation token 集 | 依据不可溯源 = 变相幻觉 |
| **I2** | `0.0 ≤ confidence ≤ 1.0` | 数值断言 | 阈值逻辑失效 |
| **I3** | **幂等**：同一 `(q, obs)` 重复判定，answer 必须一致 | 连调 3 次比对 | 轨迹不可复现，重放失效 |
| **I4** | **fail-closed**：能力不可用时返回 `answer=None`，**绝不猜** | 注入故障（超时/空响应/`obs.degraded` 非空）后断言 | 猜出来的 false 会把可用站点误杀 |
| **I5** | **无副作用**：不持页面句柄、不回调控制流、不触网 | 静态检查 + 集成测试 | 感知层退化成耦合，控制流不再纯粹 |
| **I6** | **`decision` 型题的 `payload` 字段完整，且 `ref` 可溯源到 `obs.interactive_elements`** | payload 键集 ⊆ schema_hint；ref ∈ 交互元素集合 | 代码拿不到可点的 ref → 退回规则猜测，LLM 白做（见 00 方案 §3.2） |
| **I7** | **`answer=True` 时 `payload` 不得为空**（`bool` 型题除外） | 空 payload + answer=True → fail | 代码拿到「有但没说是哪个」，必然下一步瞎猜 |

**I3 对 LLM 版的具体要求**：`temperature=0`、固定 prompt 版本、禁止重试时换措辞——
重试只允许在**同一提示词**下重采样，否则幂等性破。

**I4 不可妥协**。这对应存量纪律「工具缺失不能 fail-open」：
感知层没把握时说"不知道"，代码走 `unresolved` 分支（标记未验证、进负样本池），
而不是猜一个 false 去污染成功路径。

### 3.1 I4 的前提：`Observation.degraded`（2026-10-08 实测补）

I4 写的是「能力不可用时返回 None」，但**「能力不可用」本身得能被观测到**。
写第一版实现时踩了这个坑：`observe()` 对 `links` / `interactive` / `count`
一律 `on_error="empty"` 降级（不让单次采集作废），于是

```text
「采到 0 个交互元素」   与   「交互元素采集失败」   在 Observation 里完全一样
```

规则版只能对前者判 `answer=False`，对后者**也**判 False——**基础设施故障被
写进了业务结论**。报表上完全看不出来：负样本池多了一条
`no_play_control`，没人知道它的真实原因是 MCP 超时。

修法是给 `Observation` 加一个字段：

```python
degraded: tuple[str, ...] = ()   # 本次采集降级的项（tool 名）
```

`obs.degraded` 非空时，任何依赖该字段的判定必须返回 `answer=None`。
它是 **I4 的使能条件**，不是可选的诊断信息——没有它，I4 只是纸面承诺。

配套的一条护栏（写反了会退化成躺平）：**采集成功且页面确实没有播放控件时，
`answer=False` 是合法且必需的结论**。契约测试里成对写了这两种情况
（`test_i4_*` 与 `test_i4_采集成功时判_false_是合法结论`），
免得后来者把 I4 读成「永不判 False」——那会让负样本池永远空。

### 3.2 ⚠️ `degraded` 抓不到的第二种「没采到」：哨兵文本（2026-10-08 实测补）

`degraded` 记录的是**工具报错**。但 obscura 对「页面上没有交互元素」
返回的不是错误，而是**哨兵文本**：

```text
No interactive elements on this page.
```

这是正常返回，`_call` 不会记降级，`obs.degraded` 是空的——
但「页面真的一个控件都没有」和「JS 页还没渲染完所以采到 0 个」在观察里长得一模一样。
实测 iqiyi / ixigua / sohu 三站全部命中这个形态（正文 0 字符 + 元素 0 个），
在没有这层兜底时被写成了三条 `no_play_control` 负样本。

所以感知层必须自己再看一眼：

```python
if not obs.interactive_elements:
    return answer=None      # 采到 0 个 ≠ 页面确实没控件
```

**通用形态**：凡是「空结果」既可能是事实也可能是采集失败，
而事实与失败在观察里无法区分时，就**不能**拿它当判据——
除非观察里另有一条独立的证据推翻它（见 §3.3）。

### 3.3 观察自相矛盾时，「没有」这个结论不成立（2026-10-08 实测补）

负样本池的全部价值是「这里**真的**看不了」。所以判 `False` 之前，
得先确认观察里没有**相反的证据**。实测抓到一例：

```text
tv.sohu.com   title=「功夫 - 搜狐视频」   video_tag_count=1
              200 个交互元素无一命中词表   →  判 no_play_control
```

页面自带 `<video>`，人已经站在播放页上，只是按钮文案没进词表。
「没有播放控件」这句话与观察**直接矛盾**——这不是判断，是误读。
判 `False` 会把一个能看的站点塞进负样本池，而负样本池一旦被稀释就不再有信息量。

```python
if not candidates and obs.video_tag_count >= 1:
    return answer=None      # 矛盾：不是「没有控件」，是「按钮没认出来」
```

两条一起，本层的判 `False` 条件收紧成：

> 采到了元素、都不像播放控件、**且观察里没有相反的证据** —— 这才是真的 `no_play_control`。

三条护栏成对写在 `test_perception.py` 里（`TestRealSiteRegressions`），
每条都配一个「反过来仍然成立」的反例，防止把判 `False` 这条路整个封死——
封死了负样本池就永远空，比误判更糟。

### 3.4 fail-closed 的边界：管结论，不管采集（2026-10-08 实测补）

第一次真实端到端暴露了一个把 I4 读过头的坑：`IS_REACHABLE` 在判断链的**第二个环节**，
W1 规则版对它只能返回 `None`。控制流当时写成「`None` → 中断」，
结果 **5 个真实候选站点全部落 `unresolved`**，W1 验收要的「负样本池非空」一条都产不出来。

正确读法：**fail-closed 管的是「结论」，不是「采集」**。

| 感知层返回 | 控制流该做什么 | 为什么 |
|---|---|---|
| `True` / `False` | 据此行动 / 中断 | 确定性结论 |
| `None` | **继续往下采集**，最终分支仍按「有没有拿到确定性结论」定 | 继续走 ≠ 断言可达；只是不放弃收集证据 |

落到 `executor/steps/visit.py` 就是：

```python
reachable = perceptor.decide(Q.IS_REACHABLE, result.site_obs)
if reachable.answer is False:
    return result                       # 只有 False 才中断
if reachable.answer is None:
    result.note("IS_REACHABLE=None（不中断，继续采集）")
```

拿到确定性结论的那一步（`FIND_PLAY_CONTROL` 判 `False`）照样能产出货真价实的
`no_play_control`——「登录墙」与「无播放控件」在人工复核时本来就可由 evidence 区分。
把「判不出」当成「判不出且就此打住」，损失的是整条链的素材，
换来的只是一份看起来更整齐、实则空白的负样本池。

## 4. 三种实现的对照与 `confidence` 的异质性

| | `RulePerceptor`（W1） | `LLMPerceptor`（W3） | `ModelPerceptor`（未来） |
|---|---|---|---|
| 实现 | URL 特征 / `video_tag_count` / 按钮文本正则 | LLM + 结构化 schema | 训练好的小分类器 |
| `confidence` 语义 | **确定性**，恒 1.0 | **模型自报概率，未校准** | **概率，可校准** |
| I3 幂等 | 天然满足 | 靠 temperature=0 满足 | 天然满足 |
| I4 降级 | 不适用（本就无外部依赖） | 超时→`None`；→可回退 rule 版并置 `fallback_used=True` | 加载失败→`None` |
| 失败模式 | 覆盖窄、误判固定 | 漂字段名、套 think、首轮跑偏、置信度虚高 | 分布外样本置信度塌陷 |
| 速度 | ms 级 | 秒级 | ms 级 |

### 4.1 `confidence` 不是同一个东西（重要）

`confidence_threshold` 在 rule 版**永远不触发**（恒 1.0），这意味着：

- **W1 阶段整条重采样/人工兜底路径是死代码**，无法在 W1 验证；
- W3 切到 LLM 版后，`confidence_threshold` 才开始生效，而 LLM 自报置信度**普遍虚高**
  （模型说 0.95 时实际正确率可能只有 0.7）。

**处置（W3 交付物之一）**：用一批**已知答案的样本**（从 W1 规则版跑出的
`negative.jsonl` + 成功样本中人工确认的子集）画 reliability diagram，
把 `confidence_threshold` **经验校准**到实际命中率，而不是照搬 0.75 这个先验值。

未校准就上线，等于阈值形同虚设。

## 5. 灰度、迁移与失败语义

### 5.1 双跑与切换（W3）

```text
W3 双跑期：RulePerceptor 与 LLMPerceptor 对同一 Observation 各判一次
    ↓
分歧样本 → 人工抽检裁定（谁对？）
    ↓
切换判据（预先定死，见下）→ 满足则 default 切 LLM，rule 降为 fallback
```

**切换判据（禁止「感觉 LLM 更好」）**：
1. 抽检裁定中，LLM 正确率 **≥** rule 正确率（允许打平，不允许靠感觉切）；
2. schema 解析成功率 ≥98%（存量教训：后端不强制 json_schema，必须实测真实端点）；
3. 分歧报告中 LLM 的错误**不是**集中在某一类站点（否则是系统性偏差，不是随机噪声）。

未满足任一条 → 保持 rule 为 default，LLM 版继续旁挂观察。

### 5.2 fallback 必须计数上报（R3）

```text
LLM 超时 / 解析失败
    → 回退 RulePerceptor，Decision.fallback_used = True
    → 计数事件 {question, run_id, ts} 写入 _fallback_events.jsonl
    → W3 验收信号之一：fallback 率 < 5%
```

**不计数上报的 fallback 是最危险的降级**：链路全绿、质量下滑、无告警。
`fallback_used` 字段 + 计数文件是 R3 的兑现手段。

### 5.3 三态答案与 `unresolved`

| answer | 语义 | 控制流处置 | 落盘 |
|---|---|---|---|
| `True` | 判定通过 | 继续下一站点步骤 | P2 成功样本 |
| `False` | 判定不通过 | 跳过/排除/标记 | `negative.jsonl`（`branch = q.negative_branch`） |
| `None` | **unresolved**：置信度不足且重采样耗尽 | **标记「未验证」** | `negative.jsonl` + `human_review_required: true` |

**`unresolved` 绝不与 `False` 合并统计**。混进去会污染负样本纯度——
人工抽检分母里混着"其实不知道"，rubric 的边界规则会写出无法执行的档位描述。

## 6. 决策日志

每个 `Decision` 随 P1 观察存档一并落盘，供事后归因与评分器调参：

```json
{
  "run_id": "...", "step": 3, "question": "site.find_play_control",
  "answer": false, "confidence": 0.83, "source": "llm",
  "evidence": "页面标题含「在线观看」，有 2 个 iframe",
  "latency_ms": 1840, "fallback_used": false,
  "obs_url": "https://example.com/movie/123"
}
```

**`evidence` 必须原文落盘**——它是 rationale 层实体核查的锚（模块 4 的 I1 复用同一份存档）。
rationale 里出现的实体如果在这里找不到出处，就判 `unsupported_entity`。

## 8. 扩展点与一条禁令

**可扩展**：新增 `Question`（不改控制流）、新增 `Perceptor` 实现（改工厂一行）。

**禁令：生产链上禁止投票/集成**。

`EnsemblePerceptor`（规则 + LLM 投票）在准确率上通常更好，但**违背 v2 的核心原则**：
分歧必须暴露给人看并进入仲裁队列，投票会把分歧藏进一个数里。
若要在黄金集上研究投票效果，只在 `evaluation/` 下的离线实验里做，**不进 `executor` 链路**。
