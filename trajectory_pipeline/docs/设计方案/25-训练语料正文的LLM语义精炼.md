# 方案 25 · 训练语料正文的 LLM 语义精炼

**一句话**：把训练视图里「取前 320 字」的硬裁剪，换成「**让模型选该保留的行**」——但模型只报行号，**文本由装配层从 P1 原文重建**，所以它只可能漏、不可能造。

**性质**：语料加工侧的补完。**不改采集层**（P1 一个字不动）、**不改装配层的纯代码性质**（模块 5 不调 LLM）、**不改 P1/P2/P3/T 的既有字段语义**（只新增三个留痕字段与一个回执标记）。
**前作**：[方案 23（每任务一轨迹 · 训练轨迹语料整改）](23-训练轨迹语料整改方案.md) —— 本方案是它的 R1-1（训练态正文限量）的**下一棒**：限量的口径没变，变的是「谁来决定留哪几行」。
**现状断言的真源**：[台账 10-TODO台账](../计划进展/10-TODO台账.md) —— 本方案落地后回写。

## 0. 判定标准：什么算「落地了」

落地不是「代码写了」，而是五条**可机械核**的判据。逐条核，核不过就是没落地。

| 编号 | 判据 | 怎么核 |
|---|---|---|
| **A1 不造** | 训练视图里的每一行正文都**逐字来自 P1 原文** | `tests/unit/test_refine_render.py::Test精炼重建`（重建后每行 ∈ 原文行集） |
| **A2 可回退** | 精炼不可用（无旁挂 / 旁挂坏了 / 选中的行对不上原文）⇒ 输出与**没精炼时逐字一致** | 同上 `test_对不上原文就回退规则裁剪` + `test_没有精炼时逐字不变` |
| **A3 保真不放宽** | 「下一步动作目标无条件保留」在精炼分支里**同样成立** | `test_动作目标照旧无条件保留` |
| **A4 留痕可见** | 精炼过的正文必须**说破**（`body_refined` 三字段 + 回执标记 `[内容已精简: 保留 N 行]`） | `tests/unit/test_refine_render.py::Test精炼留痕` + `Test两段投影同款` |
| **A5 装配层仍是纯代码** | `assembler/` 里**没有任何一处** import LLM 客户端，也**不 import 精炼实现** | `tests/contract/test_p2_contract.py::Test精炼分支::test_装配层不import_llm客户端` |

> ⚠️ **A1 与 A2 是本方案的全部价值所在**。如果哪天改成「让模型写摘要」，
> A1 立刻不成立——那时所有防幻觉保证都没了，而**报表上看不出任何异常**。

## 1. 问题陈述：为什么「取前 320 字」是问题

方案 23 R1-1 把训练态正文压到 **320 字**（读步 2000），压的依据是 A5 实测：
单条回执中位数 ≤800、主树 4071 条可见步实测中位 **772**。这个数字本身没错。

错的是**裁法**：现状是「先剔导航噪声，再按任务相关度取前 320 字」。于是：

1. **动作在训练视图里推不出来**。采集时 agent 看到的是 **4000 字全文**
   （`executor/agent_loop.py` 的正文窗口），训练视图只给 320 字 ⇒
   模型看到的是「点了什么」，看不到「当时页面上有什么」——
   训练样本里出现「点了一个观察里没有的东西」（方案 23 的第 6 条硬规矩就是为这条设的）。
2. **「取前 320 字」本身变成了训练目标的一部分**。模型学到的最优策略是
   「找前 320 字里最像答案的那段」，而**真正的答案可能在第 350 字**。
   这不是信噪比问题，是**监督信号错位**。
3. **规则裁剪看不到语义**。相关度只有「片名命中 / 播放词命中」两档分数
   （台账 §2026-11-10「未闭环」第一条）：「相关搜索」与「真搜索结果」
   同分，只能按页面顺序取——而真结果往往排在相关搜索后面。

⇒ 结论：**320 这个上限是对的，裁法是错的**。上限管「训练窗口放得下多少」，
裁法该管「哪些内容对任务有用」——后者是语义问题，规则做不了。

## 2. 三个方案的取舍

| 方案 | 做法 | 防幻觉 | 采集链 | 判定 |
|---|---|---|---|---|
| **A. 重新采集** | 采集时就把正文按任务裁好 | 天然（就是原文） | **要改**（执行端、agent prompt、窗口口径全动） | ✗ 贵、动证据链 |
| **B. 让模型写摘要** | 模型读全文，写一段摘要当正文 | **✗ 结构上做不到**（改写 ⇒ 原文没有的词） | 不动 | ✗ 事实层被污染 |
| **C. 让模型选行**（本方案） | 模型只报**行号**；文本由装配层从 P1 原文重建 | **✓ 结构上不可能造**（只能漏） | 不动（P1 一个字不改） | ✓ 采纳 |

### 2.1 为什么「让模型写摘要」必须排除

摘要的失效模式是**不可验证**的：模型把「简介：…」改写成「这是一部…」，
读样本的人看不出差别，而下游按「逐字能在正文里检索到」判据走的三处
（付费墙词表、片名一致性核、实体锚定）会**同时**开始误判。
更糟的是**同一份正文两次摘要措辞不同** ⇒ 语料不可比 ⇒ 训练/评估对不上账。

⇒ 「只可能漏，不可能造」不是靠提示词约束出来的，是靠**结构**出来的：
**模型不接触输出文本，只接触行号**。

### 2.2 为什么不重新采集

P1 是**取证态**（证据链的起点）。为了训练视图更好看而重采，
等于让**证据跟着训练目标走**——那批存档的历史就废了。
本方案**不重采、不改写 P1**，只做**离线加工**（可重跑、可换模型、可整批丢弃）。

## 3. 架构落点

### 3.1 三层职责

```
P1 存档（取证态，正文全文，一个字不动）
   │
   │  trajectory_pipeline/refine/          ← 新增：精炼层（**唯一调 LLM 的地方**）
   │    ├ prompt.py    提示词（筛选器，不是摘要器）
   │    ├ refiner.py  解析 / 保真校验 / 调用
   │    └ reader.py   按 P1 文件格式读观察清单（不 import 装配层）
   ▼
output/pipeline/refined/<archive>.refined.json    ← 旁挂（**派生物**，可重跑可丢弃）
   │  {正文内容哈希: 保留的行}
   │  ⚠️ 名字与形状都**不能撞 P1 存档**（后缀 `.refined.json` +
   │     顶层键叫 `entries` 而不是 `steps`）——见 §3.4
   ▼
trajectory_pipeline/assembler/observation_view.py
   └ render(..., refined=index)  ← **纯代码**：按保留的行从 P1 原文重建
   ▼
P2 / P3 / T（训练语料）
```

### 3.2 装配层为什么不调 LLM

`docs/01-架构总览.md` 模块 5 把装配层定义为**纯代码**：P2 便宜、P3 更便宜，
重建一批 P2 必须能脱离执行端与 LLM 后端的当前版本独立完成（历史 P1 存档
永久可重建是硬要求）。装配层一旦 import LLM 客户端，就绑死在「后端现在
能不能连上」上——重建一批语料会因为后端 401 而失败。

⇒ 精炼做成**旁挂**：读侧（装配层）只把旁挂当**数据**读，
**不 import 任何精炼实现**。这一点由 A5 盯着。

### 3.3 键怎么选：按**正文内容哈希**，不按步号

旁挂按 `sha256(body_text)[:16]` 索引。理由三条：

1. **P2 与 T 是两份独立渲染**（P2 从 P1 切条、T 从 P1 直接渲），
   步号坐标系不同（per-unit vs per-Run）。按步号索引要维护两套映射，
   映射错了就是「A 步的精炼贴到 B 步」——**静默的语料污染**。
2. **天然幂等**：同一份正文精炼一次，换步号、换渲染口径都不用重算。
   同一个页面被访问两次 ⇒ 正文一样 ⇒ 键一样 ⇒ 一条记录、一次调用。
3. **哈希只用于定位，不用于判真伪**：渲染侧仍要**逐行核对**
   「保留的行确实还在这份正文里」，对不上就回退到规则裁剪。
   哈希碰撞（64 bit 在十万条观察量级上 ≈5e-10）不是可信性的来源，
   逐字核对才是。

### 3.4 旁挂不能长得像 P1 存档（**实测踩出来的**）

旁挂与 P1 存档**同在产物根下**（`output/pipeline/refined/`），而扫存档的
扫描器是**递归**的（`rglob`）——于是两件事会撞：

| 撞法 | 后果 | 处置 |
|---|---|---|
| **文件名**顶着 `<task>__<run>.json` | 按名扫存档的消费者把它当存档收走 ⇒ 解析一份没有 `run_config` 的东西当 P1 | 旁挂带**自己的后缀** `.refined.json` |
| **顶层键**叫 `steps`（其实是**映射**，P1 的 `steps` 是**列表**） | 按形状筛存档的扫描器把它收进来 → `_walk_steps` 把映射的**键**当 step 迭代 → `st.get("action")` 炸掉（`'str' object has no attribute 'get'`） | 顶层键改叫 `entries`：**它一条 step 都没有** |

⚠️ 这两条**不是推演出来的**——真实批次一跑，契约测试立刻红了
（`test_p2_contract.py::TestToolSpaceDrift::test_存档里出现过的动作都在声明内`）。
由 `test_p2_contract.py::Test精炼分支::test_旁挂不会被当成P1存档收走` 盯着，
扫描器本身也改成**按形状**筛（`steps`/`visits` 必须是列表）。

### 3.5 规则层先行：候选行由**地基**统一出

「给模型看的候选集」与「渲染时剔掉的集」必须是**同一份**——两份实现漂了
不报错，只是精炼结果里会多出规则本该剔掉的行（广告、备案号、导航），
而渲染层**不会再去剔一次**（选过 = 保留）。

⇒ 抽 `trajectory_pipeline/common/body_lines.py` 作**唯一真源**，
`observation_view`（渲染）与 `refine`（精炼）各自 import，**不各留一份**。
搬迁是**逐字行为等价**的（现状行为一字不能变），由既有测试守着。

## 4. 契约

### 4.1 观察层新增三个字段（**不进 `limits`、不进 `truncated`**）

| 键 | 类型 | 说明 |
|---|---|---|
| `body_refined` | `bool` | 这条正文是**模型选行**裁出来的（不是「页面前 N 字」） |
| `body_refined_lines` | `int` | 最终正文里留下的行数 |
| `body_refined_dropped` | `int` | 候选行里**没进最终正文**的行数 |

⚠️ **为什么单独三个字段而不塞进 `limits`**：

- `limits` 是**7 键**契约（`body_chars` / `elements` / `links` /
  `body_lines_dropped` / `elements_dropped` / `links_dropped` / `cropped`），
  塞进去就破了 `tests/contract/test_p2_contract.py::TestTruncationIsVisible`；
- `truncated` 是 **2 键**契约（`source` / `view`），加第三个键就破了
  `rationale/gates.py::_truncated_flag` 的语义（上游截断 vs 本层触顶）；
- 精炼是「**换了一种裁法**」，不是「裁了多少」——两笔账**不混算**：
  `limits.body_lines_dropped` 记的是**规则剔的**（导航 / 页脚 / 重复），
  `body_refined_dropped` 记的是**模型丢的**（不相关）。混算就看不出
  「裁掉的是噪声还是内容」，而这两者的后果完全不同（前者无害，后者要人复核）。

### 4.2 回执标记：`[内容已精简: 保留 N 行]`

P3 与 T 的观察回执**逐字同款**（O-5：两段投影刻意不互相 import，
字面一致靠契约测试盯着）。位置：在 `[采集降级: …]` 之后、`[内容不完整: …]` 之前。

**为什么必须说破**：正文被精简过这件事，模型从文本里**看不出来**——
它只会以为「页面就这么多内容」。不说破就是在训练侧教出来的幻觉
（这正是方案 23 第 4 条「本层永不补内容」的反面）。

### 4.3 降级链（三级，每级都留痕）

| 级 | 触发 | 表现 |
|---|---|---|
| `not_needed` | 候选行本来就在预算内 | **不发请求**（成本只花在真会被裁的地方） |
| `llm` | 成功 | 正文按模型选中的行重建 |
| `failed` | 解析不出 / 行号越界 / 动作目标没保住 / 任务词全丢 | **整条作废** ⇒ 渲染层走规则裁剪 |

⚠️ `failed` 是**整条作废**，不是「用了一半」——半份精炼比不精炼更难查。
旁挂里三条分得开，报表上不会出现「精炼了但不知道是哪几条」的糊涂账。

## 5. 成本与预算

- **不选就没有**：候选行本来就在预算内 ⇒ 一次请求都不发。
- **按正文去重**：同一份正文在一份存档里出现多次 ⇒ 只做一次。
- **批次预算**：`--max-calls` 是**整批**的发请求上限（默认 200，0 = 不限）。
  超了就停，**剩下的档案不精炼**（走规则裁剪）——并且**必须印出来**：
  静默少一半是本仓库最贵的那类 bug（报表看不出异常）。
- **没配后端 ⇒ 退 2，不静默跳过**：否则会让人以为「精炼过了但效果不好」，
  而真相是压根没跑。

## 6. 失败与回退的判据（三道关）

渲染侧拿到旁挂后过三道关，任一不过 ⇒ **整条作废**，走规则裁剪
（与今天**逐字一致**，零回归）：

1. **逐行核对**：保留的每一行都必须**逐字**出现在原文里。对不上 ⇒
   旁挂与正文不同源（改了 P1？换了正文？）⇒ 宁可回退，也不要把一份
   对不上的正文写进训练集。
2. **按原顺序重建**：模型可能乱序报行号；最终文本按**页面顺序**排——
   「从上到下」这个结构信号不能因为模型排版乱了就丢。
3. **硬预算**：重建后仍走一遍规则层的填预算逻辑（动作目标无条件保留，
   其余按相关度）。模型只决定「哪些行相关」，**字数预算仍归规则层管**。

另有**两条保真判据**在精炼层（`refine/refiner.py::validate_selection`）：

- **动作目标必须保住**：下一步要点的那个控件/网址所在的行被丢掉 ⇒ 整条作废
  （与 `observation_view` 的 `keep` 同款纪律）。
- **任务词命中的行至少留一条**：全丢掉等于把这一页的核心信息删干净了。

⚠️ 判据只在**候选里确实有**那条线时才生效：页面上根本没有目标文本，
不是「被模型丢了」。

⚠️ **渲染层是最后一道防线**：即使精炼层放过了「没保住动作目标」的
选择，`observation_view._rebuild_from_refined` 也会**自己把目标行从原文
补回来**——换了裁法不等于放松保真口径（第 6 条纪律不因为裁法变了就松）。

## 7. 已知缺口与本轮**没做**的

- **元素与链接没有精炼**：正文做了，元素表（10 条）与链接表（4 条）仍是
  规则限量。本轮只做正文——元素/链接的「相关性」判据更依赖页面结构，
  而 LLM 只看文本时更容易选错（见台账 §2026-11-10「未闭环」：相关度只有两档）。
  ⚠️ 实测（2026-11-13）确认这条边界是对的：精炼分支**只改正文相关字段**，
  元素表 / 链接表 / 降级标记 / 截断标记**逐字不动**（A/B 实测漂移 0 处）。
- **不重采集**：P1 仍是 4000 字窗口的产物；本方案是**语义投影**，
  不是「采集时就想好了要什么」。
- **批次预算的默认值待定**：200 是保守起步值。
  ⚠️ 实测单次调用 **14–51 秒**（MiniMax-M3.1-Flash），`--max-calls 60`
  实际覆盖 **4 份落盘 + 6 份丢弃**（10 份）⇒ 200 次 ≈ **15–20 份存档**
  ≈ 1 小时上下。成本口径见 §9.1。
  ⚠️ **预算用尽是「整份丢弃」**（不是「那份也落盘」）——所以 `--max-calls`
  给小了，代价是**按档案**跳过的，不是按条目。
- **没做读数面板**：A/B 读数是**人工比对**（§9），不是自动报表。

### 9.4 真实批次逼出来的三处修正

**① 旁挂长得像 P1 存档 ⇒ 契约测试红了**（已修，见 §3.4）。
文件后缀加 `.refined`、顶层键 `steps` 改名 `entries`、格式升 `refine.v2`，
并把扫存档的扫描器改成**按形状**筛（`steps`/`visits` 必须是列表）。

**② 报表统计了「算过但没落盘」的条目**（已修）。
批次预算用尽时，那份档案**整份不写盘**——而计数写在每条处理之后，
于是终端报「成功 55 / 规则层够用 17 / 失败 5」（**77** 条），
盘上却只有 **62** 条（47 / 13 / 2）。**报表比真实产出多 15 条**，
而那 15 条的钱花了、词没进语料。
⇒ 落盘统计与「算过」**分开记**，没落盘的**单算一个数字并印出来**
（避坑指南 §2.2b）。

**③ 计划数比真发请求多 45%**（已修）。
重跑那份档案时，终端说「约 **35** 次 LLM 请求」，真发 **24** 次。
真跑时**同一份正文只发一次**（正文一样 ⇒ 精炼结果一样），而计划阶段
**逐条算**——可它打印的字写着「正文键去重后逐份算的」。**字与代码不符**，
而这个数是运营方用来估 `--max-calls` 的（估大了 ⇒ 一半档案被丢弃）。
⇒ 计划阶段也按正文键去重（**去重范围与真跑一致**：每份档案内部）。

### 9.5 预算用尽：`budget:` 那一类失败值得重试一次

整批里有 1 条报了 `budget:max_tokens 用尽（finish_reason=length，
content 为空）`——**请求成功、正文为空**，症状像「后端坏了」，
真相是「**这个数小了**」（推理模型的思考与正文共用 `max_tokens`；
实测 8192 对真实场景不够，**16384 才恢复**）。

客户端内部对这一类**不重试**（重发同一个预算还是同样的空）。
所以处置动作只有一个：**换大预算再发一次**。
⇒ `refine/refiner.py::refine_body` 加了一次**带上限**的重试：
预算从客户端自己的配置**派生**（`cfg.max_tokens × 2`，下界取实测值
16384），**只重试一次**，两次调用的账**合并**并留痕
（`retried` / `retry_max_tokens`）；第二次还失败 ⇒ 整条作废
⇒ 渲染层走规则裁剪（**零回归**）。
⇒ `cli refine` 在启动时**说一次**当前预算（低于实测值就提醒改环境变量）——
不然症状是「精炼效果不好」，而真相是「压根没拿到正文」。
