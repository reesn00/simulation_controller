> P-3=①a 对照金标。** 本文是施工方案，不是已生效的设计。

## 0. 一句话

`d5_scorer` 的四检查只核「结论自洽」，**从不核「分支是不是决策树上那颗事实对应的正确节点」**——
凡它驳不倒的分支就白送 5 分。本方案给两条修法，并说清为什么**不能独立先做其中一条**。

## 1. 根因（已坐实，非猜测）

### 1.1 四处检查核的是什么（`d5_scorer.py`）

| # | 检查函数 | 核的是 | 与「正确性」的关系 |
|---|---|---|---|
| 1 | `_check_branch_matches_question` | 分支与判断点**相容**（在允许集里） | 只问「配不配套」，不问「该落哪」 |
| 2 | `_check_reached_precondition` | 前置事实（是否到播放页） | 只问「前提成不成立」 |
| 3 | `_check_no_skip` | 有没有跳步 | 只问「过程有没有断」 |
| 4 | `_check_claim_evidence` | 付费墙/拦截分支的正文证据 | 只问「声称的事正文里有没有」 |

**四件事全是「自洽」**。rubric 锚点 5 的字面要求「决策树每步分支全对」——
这个断言**从头到尾没被验过**。

### 1.2 「白送 5 分」的三条放行路径

1. 检查 1 对 `CODE_ONLY_BRANCHES` 直接 `ok`（`d5_scorer.py:412-418`）——
   `unreachable_hard` / `trailer_only` / `trailer_suspect` / `site_search_*` **压根没核**。
2. `unresolved` 被加进**每个** question 的允许集（`d5_scorer.py:211`）——
   fail-closed 通用出口，任何判断点产出都放行。
3. 检查 4 对不声称拦截/付费的分支判 `skipped`（`d5_scorer.py:528-539`）——
   `component_unverified` / `no_play_control` / 成功(`null`) **等于没核**。

### 1.3 代价（11 张分诊卡）

- 形态 A（分支名不在树上）6 张：`trailer_suspect` / `trailer_only`(正片页) /
  `unresolved` / `login_wall_or_blocked`(404·地区限制)。
- 形态 B（在树上但落错节点）5 张：`E006` 网易号文章落成功、爱奇艺频道页落
  `component_unverified`、会员页落 `component_unverified`、西瓜「打开App」落
  `no_play_control`。
- **其中 3 张是 1–2 档**（`E006` / `T001-106df089` = 1 档，`T012` = 2 档）⇒
  **不是措辞问题**，是评分器系统性放行错误结论。

## 2. 修法①：增一处「树上节点核对」

### 2.1 核心原则：机器不「学会判对」，只「承认核不了」

机器手上只有 `branch` + `question` + `reached_play_page` + `body_text`，
**没有决策树的语义判定力**（它不知道「网易号文章该落 `not_play_site`」这种结论）。

所以修法①的落点**不是**让 `score_d5` 判出「该落哪个节点」——
那是黄金集对照（口径 C）的本职。落点是：

> **把「白送 5 分」改成「核不了 → undetermined 不出分」**，
> 让这 11 张（乃至 62 条）从「虚假的满分」变成「显式的待人工」。

这是本项目一条贯穿纪律的必然推论（`d5_scorer.py` 模块头原文）：
**「能力不可用时给 None，绝不猜」「评分器判反比不判更贵」**。

### 2.2 具体改动（两段）

#### ①a. 分支「是否在决策树上」的显式判据

在 `d5_scorer.py` 新增一个常量：决策树的**合法节点集合**（与 rubric 决策树六行对齐）：

```python
#: rubric v1.1 D-5 决策树的六个节点（在线视频场景rubric.md §D-5）。
#: 只有落在这六个分支之一，才谈得上「分支走没走对」；落在其外的是
#: 「树上没有节点」——不是「判错」，是「这条分支当前无法用树核对」。
TREE_BRANCHES: frozenset[str | None] = frozenset(
    {
        "not_play_site",          # 非播放站/无关站
        "no_play_control",        # 是播放站，无播放入口
        "component_unverified",   # 播放页无 video/组件
        "subscription_wall",      # 播放页但需订阅/付费
        "player_unverified",      # 有组件但无法确认可用
        None,                     # 有组件且可确认 → 记录成功
    }
)
```

#### ①b. 把「树上没有的分支」从 `ok` 改成 `undetermined`

改检查 1 里 `CODE_ONLY_BRANCHES` 那条分支（`d5_scorer.py:412-418`）：

**现在**：
```python
if branch in CODE_ONLY_BRANCHES:
    return TreeCheck(
        _NODE_BRANCH, "ok",
        f"{branch} 由代码判定（不经 LLM），无 question 可配对")
```

**改成**（保留「无 question 可配对」的语义，但区分「在树上/不在树上」）：
```python
if branch in CODE_ONLY_BRANCHES:
    if branch in TREE_BRANCHES:
        # 在决策树上有节点、且由代码判定（例如 unreachable_hard 补树后）
        return TreeCheck(_NODE_BRANCH, "ok", f"{branch} 由代码判定，且在决策树上")
    return TreeCheck(
        _NODE_BRANCH, "undetermined",
        f"{branch} 由代码判定，但**不在 rubric 决策树上**——"
        f"这条分支当前无法用树核对「落对没有」，不据此判错，也不据此给 5 分")
```

### 2.3 ⚠️ 这一条**不能独立先做**——与 G-2「补树」硬耦合

`①b` 一动，**91 条里 62 条落在树上没有节点的分支**会**瞬间从 5 分变 undetermined**：

| 分支 | 条数（R-2 实测） | ①b 后的后果 |
|---|---|---|
| `unresolved` | 24 | 5 分 → undetermined |
| `unreachable_hard` | 17 | 同上 |
| `login_wall_or_blocked` | 8 | 同上 |
| `broken` | 6 | 同上 |
| `blocked` | 5 | 同上 |
| `trailer_only` | 1 | 同上 |
| `trailer_suspect` | 1 | 同上 |
| **合计** | **62** | **d5 一致率分母崩** |

所以顺序必须是：

- **先补树（G-2 / R-2）**：把 `unreachable_hard` / `unresolved` / `blocked` /
  `broken` / `login_wall_or_blocked`（或按 R-2 建议的责任方拆分）补进决策树，
  让这 62 条重新有节点可落。
- **再上 ①b**：此时 `TREE_BRANCHES` 已扩，`①b` 只会把**真正的树上缺口**
  （如 `trailer_only` / `trailer_suspect`，或仍未补进树的分支）判成 undetermined。

**「先补树还是先补检查」是 owner 要定的次序**（台账 M-35 末句原话），
本文把它明确成一个**排期依赖**，不替 owner 决定。

### 2.4 受影响测试（①b 会打红的）

`tests/unit/test_d5_scorer.py` 里**明确断言「CODE_ONLY 分支 → 5 分」**的用例：

| 用例 | 行 | 现断言 | ①b 后 |
|---|---|---|---|
| `Test同源::test_代码判定分支不参与配对` | 129-135 | `unreachable_hard`/`trailer_only`/`trailer_suspect` → **5 分** | 改：这些不在树上 → **undetermined** |
| `Test同源::test_站内搜索收尾分支不参与配对` | 137-143 | `site_search_*` → **5 分** | 改：**undetermined** |
| `Test同源::test_站点首页核可判5分` | 145-153 | `not_play_site`(question 空) → **5 分** | 不受影响（`not_play_site` 在树上） |

另需**新增**正向用例：补树后 `unreachable_hard` 等在树上的分支应回 5 分；
以及「树上缺口分支 → undetermined 且 `wrong_nodes` 为空」的负向用例。

## 3. 修法②：改 rubric 锚点 5 的措辞

### 3.1 现状（`在线视频场景rubric.md:111`）

```
- 5 = 决策树每步分支全对
```

### 3.2 改成（承认机器能力的真实边界）

```
- 5 = 决策树每步分支全对
  （代码评分器当前只核四件事：分支与判断点相容、前置事实成立、无跳步、
   证据与正文一致；「分支是否落在正确节点」的语义判定由人工复核 / 黄金集
   对照承担——机器侧判不出时落 undetermined 不出分，不据此扣轨迹的分）
```

### 3.3 为什么**现在就能做、且必须做**

- **纯文档**，不碰评分器、不碰基线、不打红任何测试。
- M-33 已记录同款教训：**「理由串写着『判对』，实际没查过」** ——文案不修，
  rubric 就会持续「声称它核过正确性」。这是「不撒谎」纪律（方案 16）的直接要求。
- 它是 ①b 的前置声明：先把 rubric 边界写清楚，①b 的「undetermined 不判错」
  才有文本依据。

## 4. 排期与依赖（给 owner 的拍板点）

### 4.1 依赖图

```
修法②（改 rubric 文案）──────────── 可立即做，无依赖，无基线风险
        │
        ▼
G-2 / R-2 补树（把 62 条落点补进决策树）── 必须先于 ①b
        │
        ▼
修法①b（CODE_ONLY 分支改 undetermined）── 依赖补树 + ② 的文本依据
        │
        ▼
v10 冻结（`freeze --version 10`）───────── 三条一起生效，才是可比对
```

### 4.2 三个拍板点（✅ 全部已定）

#### P-1 · 补树的范围 —— ✅ **已定：A 档**（补 4 个确定分支，共 52 条）

**先厘清「谁该上树」**：D-5 决策树只管「一个站点 visit 的最终归宿」，
`all_branches()` 的 20 条里有 7 条是**路径 B/C 发现链**（`not_aggregator` /
`aggregator_no_entries` / `not_article` / `article_no_links` / `no_site_search` /
`site_search_no_results` / `site_search_routed`），它们的语义是「选题 / 路由」，
**不是「这个站点能不能看」** ⇒ **一律不上树**。

真正落在树上之外的站点级分支是 **7 个、62 条**（R-2 实测），分三档：

| 档 | 补什么 | 覆盖 | 说明 |
|---|---|---|---|
| **A（最小，推荐起步）** | `unreachable_hard` / `unresolved` / `blocked` / `broken` | 52 条 | 四个责任方清晰、无争议；`login_wall_or_blocked`（弃用合并态）与 `trailer_*`（③ 误杀风险）**不补**，继续落 undetermined |
| **B** | A + `trailer_only` / `trailer_suspect` | 54 条 | 补上 ③ 的两支，但须把「预告误杀」边界写进树：预告必须**明说**是预告（M-12：央视网正片页曾被误判），否则落 `player_unverified` |
| **C（最全）** | B + `login_wall_or_blocked` 弃用标注 | 62 条 | 连弃用合并态也标注「已拆分，历史兼容」，62 条全有落点；代价是引入合并态语义含糊（它不区分登录墙/阻断，证据核本就「方向不明 → undetermined」） |

**建议 A 档起步**：`login_wall_or_blocked` 已是 `DEPRECATED_BRANCHES`、
H-15 起不再主动产出，补它只服务历史存档却引入语义含糊，**不值得**；
`trailer_*` 等 M-12 的误杀边界在树上写死之后再补，避免「补了树却把正片页判成预告」。

**A 档落定后的具体范围**：决策树从 6 节点扩到 **10 节点**，新增 4 个
「标记未决 / 排除」分支：

```
传输层失败（没打开）       → 标记"未决" ✅  branch=unreachable_hard   ← 采集失败，非站点性质
代码能力不足（没走到判断） → 标记"未决" ✅  branch=unresolved         ← 责任方=代码能力不足
地区 / DRM / 验证码 / 反爬 → 排除 ✅        branch=blocked
内容不存在（404/媒体损坏） → 排除 ✅        branch=broken
```

**A 档明确不补、继续落 undetermined 的 3 个分支**（共 10 条）：
`login_wall_or_blocked`(8，弃用合并态) / `trailer_only`(1) / `trailer_suspect`(1)。
它们的处理走 ①b 的「树上缺口 → undetermined」，**不是判错**，待后续立项再补。

#### P-2 · 次序 —— ✅ **已定：先补树，再 ①b**

依赖链：`补树（P-1） → ①b（CODE_ONLY 改 undetermined）`。
反序会让 62 条瞬间 undetermined、d5 分母崩，**否决**。

#### P-3 · ①a 是否对照金标 —— ✅ **已定：要对照（且已由校准回路承担，无需改 `score_d5`）**

> **2026-10-24 读码订正**：对照金标**不是** `score_d5` 单机该做的事，而是
> `evaluation/calibration/snapshot.py::_soft_entry`（第 335-355 行）**已经在做**的事——
> 它拿 `gold_dims.get("d5")`（人工 1–5 档）与 `pred_dims.get("d5")`（`score_d5`
> 打的分数）做 `dim_agreement` 比对，产出 `VERDICT_AGREE` / `VERDICT_TIER_GAP`。
> D-5 一致率 86.2%（69/80）正是这一环的产物。

所以 P-3 的正确结论是：**「对照金标」的职责在 `agreement` 口径，不在 `score_d5`**。
把金标 label 塞进 `score_d5` 签名，会把评分器与校准回路耦合起来，违反方案 16 的分层
（评分器只出「这一条轨迹自洽性如何」，金标对照是「机器 vs 人工」的独立比对层）。

**①a 的真正落点因此收窄**：`score_d5` 不需要「对照金标」，它要做的只有一件事——
**新增 `TREE_BRANCHES` 常量 + 把「树上缺口分支」从 `ok` 改成 `undetermined`**（即 ①b）。
「分支落对没有」的语义核对，由 `agreement` 里已经存在的金标对照承担。

### 4.3 验收条件（三条都落地后）

1. 11 张 d5 分诊卡的 `E006` / `T001-106df089`（1 档）、`T012`（2 档）**不再拿 5 分**；
   落在树上的分支（补树后）恢复正常 5 分。
2. `d5` 维度不再有「白送的 5 分」：树上缺口分支一律 `undetermined` 且 `wrong_nodes` 为空。
3. P-3 对照金标：有金标 label 且存档分支 ≠ 金标分支的样本，`score_d5` 产出 `wrong`
   （而非静默 5 分）；无金标 label 的样本不受影响。
4. `Test同源` 与新增用例全绿；`gate` 在 v10 冻结时能正常比对（退 0/1，不是「测不成」）。

## 5. 本文边界（不做的）

- **不**动 `questions.py` / `branches.py`（决策树补节点是 G-2 的活，另行立项）。
- **不**改 `score_d5` 的打分逻辑本身（只改「放行 → undetermined」那一处判定 +
  P-3 的「对照金标 label」读入口）。
- **不**让 `score_d5` **自己**判定「该落哪个节点」——那需要语义判定力，
  超出代码评分器边界；P-3 的「对照金标」是**照出人工/黄金集已给的正确节点**，
  不是机器自己发明正确节点。两者不可混。
- **不**让 P-3 的对照越权到校准回路（不写分诊档、不产分歧卡，那些仍是
  `agreement` 口径 C 的职责）。
