## 1. 根因证据链（提取层视角，已确认事实）

### 1.1 百度真实搜索结果的 href 形态：100% 是 `/link?url=<密文>` 包裹

百度自然结果（`div.result h3 a`）的链接**不是直链**，而是：
`http://www.baidu.com/link?url=<密文>`。密文不可解（不是 URL 编码，是服务端签名参数）。

存档证据（`TPIN01__9c38dc2e.json`）：

- `links_total = 113`，落盘（`OBS_LINK_LIMIT=50`）的 50 条里 `/link?` 形态 **0 条**——
  真实结果全部排在 index ≥ 50，运行时可见、落盘不可见（与 04 文档 §1.1「真实候选 index≥50」一致）；
- 含「功夫」的全部是 `www.baidu.com/s?wd=` 相关搜索词（如 `功夫在线观看高清`），
  真实结果标题链接同属含片名的 26 条，但**不落盘**；
- `candidate_filter`：`engine_self=91`、`excluded_host:baidu.com=17`——113 条里 108 条被结构性剔除，活 5 条。

### 1.2 剔除逻辑剔错了对象：`engine_self` 把「引擎中转结果」当「引擎自身页」吃了

`exclusion_reason`（`search.py` L196–227）判定顺序：

```
non_http_scheme → unparseable → no_host → engine_self → excluded_host → …
→ path_noise → redirect_wrapper（只认 url= 值为明文 http 的包裹）
```

百度真实结果 `http://www.baidu.com/link?url=<密文>`：
host = `www.baidu.com` **在走到 `redirect_wrapper` 之前就被 `engine_self` 命中**，
返回 `"engine_self"` → 剔除。`redirect_wrapper` 分支（L223–226）形同虚设：
它只处理「`url=` 值是明文 http 的包裹」，而百度给的是**密文**；
更致命的是它在 `engine_self` 之后——就算是明文包裹，host 是 `www.baidu.com` 也先被杀。

结果：**真实搜索结果（text 含片名的 26 条）全军覆没**；幸存 5 个候选是
百度「视频聚合卡片」的直链（`vfm=2008_aldbd` 参数），text 无片名。

### 1.3 标题回写（title_for）不是本轮的瓶颈——真实结果的 text 就是标题

04 文档 §2.4-1 担心「候选 text 不含片名 → 钉窗失败」，现场确认了实际形态：
**被 `engine_self` 吞掉的那些链接，links 里的 `text` 本身就是结果标题（含片名）**——
TPIN01 现场「全量 113 条中 text 含「功夫」的 26 条」即证据（其中相关搜索仅 5–6 条，
其余为真实结果标题链接）。`title_for` 是为了 bing 的面包屑 text 而存在；
百度真实结果的 `link.text` **不需要写回**就已经是片名。

（`title_for` 对百度包裹形态确实双键都 miss——T001 实测——但那是 bing 场景的
历史问题，且不阻塞本轮：见 §6。）

### 1.4 完整链条：剔错对象 → 候选 text 无片名 → 钉窗白钉 → kept=0 → D-2 不可判定

```
百度结果页 113 条
  ├─ 真实结果 ~20 条（text=标题，含片名）→ host=www.baidu.com → engine_self 剔除 ✗ 错杀
  ├─ 相关搜索/热搜（baidu.com 站内页）→ engine_self 剔除 ✓ 该剔
  ├─ 聚合卡片裸链 5 条（text 无片名）→ 活下来 → 成为候选 ✗ 不该当候选
  └─ 导航/功能页 → excluded_host 等剔除 ✓
→ 候选 = 5 条无片名裸链
→ pin_candidates_first 把它们钉进 links 前 5（04 已落地，物理生效）
→ 但感知层 _ordered_links 按「text 含片名」分桶：26 条含片名链接占满 hit 区（前 20）
→ 5 个候选 text 无片名 → 落 miss 区被挤出窗口（TPIN01 存档 warning「5/5 不在窗口内」）
→ 模型看不见候选 → kept=0 → 全 unresolved → D-2 100% 不可判定
```

**04 方案修复后「候选 ⊆ 窗口」由构造保证的前提是「候选 text 含片名」——
而这个前提在上游提取层就被拆掉了。本轮修的就是这一环。**

## 2. 修复设计

### 2.1 核心原则变化：引擎「中转路由」≠ 引擎「自身页」

`engine_self` 的本意（存档注释 L203–214、L44–55）：剔除搜索引擎**自己的功能页**
（导航、帮助、搜索框相关）。百度结果页里 `www.baidu.com` 链接分两类，**必须分叉**：

| 形态 | 例子 | 结构判定（path + query，纯事实） | 现行 | 应该 |
|---|---|---|---|---|
| **引擎自身功能页** | `/s?wd=`、`/gaoji/`、`/more/`、`/` | 不是中转路由 | `engine_self` 剔除 | 剔除（不变） |
| **引擎中转结果** | `/link?url=<密文>` | path=`/link` 且 query 含 `url` 键 | `engine_self` 误杀 | **放行**——它是真实结果的承载者 |

判定用**路由形态**（path + query 键存在性），不猜密文内容：
「这是不是百度自己的功能页」看结构（path），「这个中转指向哪」是密文、解不开——
**目标未知是透明度问题，不是剔除理由**（fail-closed 管「结论」不「采集」）。
「放行后到底是不是内容站」仍由判断点 ①（语义层）裁决，代码不越权。

### 2.2 主方案：`exclusion_reason` 前置「中转路由」判定，密文包裹放行

在 `exclusion_reason` 的 `engine_self` 判定**之前**插入：

```python
#: 每个引擎的「结果中转路由」形态：path 前缀 + query 键。
#: 命中 = 引擎把真实结果包在中转链接里（百度 /link?url=<密文>）。
#: 这是结构性事实（路由 + 参数键存在），不是语义判断。
RESULT_REDIRECT_ROUTES: dict[str, tuple[str, ...]] = {
    "baidu": ("/link",),          # http://www.baidu.com/link?url=...
    # bing 的 /ck/a?…&u= 走明文 base64（u= 值以 a1aHR0 即 base64("http") 开头），
    # 不属于本轮范围，见 §6；不举例以免误导。
}

def _is_result_redirect(parsed, engine: str) -> bool:
    """parsed 是否是引擎的结果中转路由（纯结构判断，不解密）。"""
    route = RESULT_REDIRECT_ROUTES.get(engine)
    if route is None:
        return False
    path = parsed.path or ""
    return any(path == r or path.startswith(r + "/") for r in route) and "url" in parse_qs(parsed.query or "")
```

`exclusion_reason` 改为（顺序关键，`redirect` 判定必须在 host 类判定**之前**）：

```python
if _is_result_redirect(parsed, engine):
    target = parse_qs(parsed.query or "").get("url")
    if target and target[0].startswith(_BROWSABLE_SCHEMES):
        return "redirect_wrapper"        # 明文包裹：仍剔（现状口径不变）
    return ""                            # 密文包裹：放行——真实结果的承载者
```

动机（两句话）：

1. **透明切换**：明文的 `url=` 值可解，解出后目标 host 语义完整，`extract_candidates`
   会重新判定（`_unwrap_redirect` 后走全流程），所以明文包裹返回 `redirect_wrapper`
   与现状一致，**不扩大行为面**；
2. **密文只能放行**：解不开 → 无法判定目标 → 按 fail-closed 原则，代码**不给结论**
   （不断言它是/不是内容站），放行为候选，由语义层（判断点 ①/②）落地判定。

### 2.3 去重降级：解包失败 → 不按 host 去重

`extract_candidates`（L363–378）现状按 `host` 去重。密文包裹的 host 是 `www.baidu.com`——
若放行后仍按 host 去重，**26 条真实结果会互相撞车只剩 1 条**，等于白修。

把「是否密文包裹」在 `exclusion_reason` 之外单独提出来（`_is_undecodable_redirect`，
复用 §2.2 的路由判定），供 `extract_candidates` 复用，去重键改为：

```python
# 去重键：解包成功 → host；解包失败（密文中转）→ 该条链接本身（不去重，仅 rank 去重）
dedup_key = (urlparse(raw).hostname or "").lower()
if _is_undecodable_redirect(raw, engine):     # 密文包裹
    dedup_key = ""                              # host 未知 → 不进入 seen_hosts 去重
```

即：**密文包裹按原始链接各自保留**（同站多条真实结果可能重复入候选，见 §5 风险 R3），
明文/裸链维持 host 去重不变。候选上限仍由 `limit`（20）截断，`over_limit` 照常记账。
遍历仍是 `for link in obs.links`（`extract_candidates` L365），**页面原始顺序不重排**——
去重只剔除「已见过的宿主」，不改变剩余候选的相对次序（M7 口径与现状一致）。

### 2.4 候选 text：直接吃 link.text（真实结果的 text 就是标题）

`extract_candidates` L381 `title_for(titles, link.href) or link.text` **保持不动**：
放行的密文包裹其 `link.text` 就是结果标题（§1.3 已证实含片名），`title_for` miss 时
回落 `link.text` 恰好命中目标。**不需要改**——这正是「text 是面包屑」的 bing 场景
才依赖 `title_for`，百度场景卸下这个依赖。

### 2.5 `Candidate.host` 与下游

- `Candidate.host`（L175–181）对密文候选返回 `www.baidu.com`——**失真**，
  会污染存档（orchestrator L227 `{"host": c.host}`）与 `cli review` 展示（L422）。
  → 本轮把 `Candidate.host` 对「密文中转 URL 形态」返回空串 `""`（未知），
  不伪装成百度自家站。改动面：`Candidate.host` property + 一个 `_is_undecodable_redirect` 判定。
- `_drop_site_homepages`（orchestrator L397）：`_is_site_homepage` 只判 `urlsplit(url).path`
  （L390–394）。密文候选 `url` 的 path = `/link` → 不是 `""`/`"/"` → **不会误判首页**，无需改；
- `_apply_selection`（orchestrator L299）：匹配键 `candidate.source_href or candidate.url`——
  密文候选的 `source_href` 与窗口内链接 `href` 一致（同一份观察），**天然匹配**，无需改；
- `pin_candidates_first` / `candidates_outside_window`（04 方案落地品）：候选 text 现在含片名 →
  hit 区 → 在窗口内；钉窗校验从「必然报警」变成「不再报警」，**无需改**。

### 2.6 备选方案与取舍

| 方案 | 做法 | 结论 | 否决理由 |
|---|---|---|---|
| **A（主）** | 引擎中转路由前置判定；密文包裹放行 + 去重降级 | ✅ **推荐** | 一处判定 + 一处去重，改动最小；「目标未知」由语义层兜底，不越权 |
| B | 解密百度的 `url=` 密文（逆向签名算法） | ❌ 否决 | 服务端签名参数无法本地解；依赖逆向属于黑盒行为，且随时失效 |
| C | 真实运行里对每条密文链接 `goto` 一次拿到落地 URL 再回填候选 | ❌ 否决 | 把「遍历」提前到「提取」，每批多 N 次导航，成本爆炸；落地判定本就是判断点 ② 的职责 |
| D | 把真实结果（含 baidu host）放行但**保留在 links 里由感知层直接选**，不再进候选 | ❌ 否决 | 候选与窗口来源不同步（候选=无，窗口全站内页），`_apply_selection` 匹配失效，重回 kept=0 |
| E | 提高 `OBS_LINK_LIMIT` / `max_candidates` 让候选数超 20 | ❌ 否决 | 治标不治本：候选集合构成不变；且窗口 `LLM_LINKS=20` 装不下 → 04 方案 §2.4-3 预警的超窗场景 |

## 5. 风险与回退

- **R1（可接受）**：放行密文包裹 → 候选 url 是 `www.baidu.com/link?url=`，
  遍历时 `goto` 该链接由 obscura 跟随 302 到真实目标；极少数可能落到百度错误页/验证页 →
  由判断点 ②（IS_REACHABLE / landing 检测，visit.py L93–96 已处理 `redirected`）判为不可达，
  进既有失败分支，**不会静默**。这是「放行」的必然代价，也是「目标未知」的兜底位。
- **R2（低）**：同站多条真实结果（如爱奇艺首页 + 剧集页两条密文）因不去重而重复入候选，
  遍历时该站被访问两次。缓解：limit=20 截断 + 总访问量有限；若实测噪声大，后续可加
  「同名 host 去重」在**落地 URL** 上做（落地是遍历期已知的，见 §6）。
- **R3（低）**：百度改版换路由形态（`/link?` 变其他 path）→ `RESULT_REDIRECT_ROUTES`
  失效 → 回退为现状（候选 5 条裸链）。缓解：`probe` 取证脚本 + 存档 `candidate_filter`
  分布即是报警器（`engine_self` 回升、候选骤减肉眼可见）。**选择器失效是可见降级，不是静默错**。
- **回退**：改动集中在 `search.py` 三个函数（判定 + 去重 + host），删掉新增分支与
  `Candidate.host` 特例即回退；无 schema 迁移、无存档回填、无模型行为变化。

---

## 6. 本轮不做（明确边界）

1. **bing 明文包裹（`/ck/a?…&u=<base64>`）**：u= 值是 base64 编码的明文 URL，
   理论上可解（与百度密文本质不同），但 bing 当前不是默认引擎、且改动会扩大行为面。
   列为后续独立一轮（如需启用 bing）。
2. **`title_for` 双键形态错位**（T001 实测）：对百度不再关键（§2.4）；若后续启用 bing，
   需在 `browser_extract` 的 `urls[]` 与 `links[].href` 的形态映射上单独设计。
3. **落地 URL 级去重**：密文候选的目标 host 在**遍历期**才可知（`landed_url`），
   本轮不动 visit 层；若 R2 噪声被实测证实，再在落地后记账时合并。
4. **反爬规避**（第二批 2 条被百度拦截）：与本方案正交，另行处理。

## 7. 与 04 文档的衔接

- 04 方案解决「候选 ⊆ 窗口」；本文档解决「候选集合构成正确」。
  两者**叠加**后完整链条才成立：真实结果（text 含片名）→ 进候选 → 钉进窗口 → 模型可见 → kept>0。
- 04 §5 风险 R1（候选 text 无片名）在本方案下**从「概率低」变为「结构性解决」**
  （百度场景候选 text 即标题；bing 场景仍受 R1 约束，见 §6-2）。
- 实施完成后回写 04 §7 / `docs/05-现状与验收.md` 为「已落地」。

**一句话总结**：百度真实结果 100% 是 `/link?url=<密文>` 包裹，`exclusion_reason` 的
`engine_self` 按 host 把它们全吞成 `engine_self`，候选只剩无片名的聚合卡片裸链——
把「引擎中转路由」从「引擎自身页」判定中拆出来、密文包裹放行、去重降级为
「host 未知不去重」，真实结果（text 即标题）重回候选，钉窗与 kept>0 由构造恢复；
目标未知的兜底位在判断点 ②（落地检测），代码不给语义结论，fail-closed 不变。
